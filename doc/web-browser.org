Much everyday work happens in web apps, so the environment needs a real browser.
=SuperL-b= opens a web page in a tab of the environment. The engine is the host's
own Google Chrome, started headless inside a container whose root is the host's
distribution, driven over the DevTools protocol, and drawn by our Lisp.

*Status: built* (kernel tag #26 or later; the camera needs #32). Pickers for
=<select>=, colour and date ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]]), video calls with camera, microphone and a shared
screen ([[#video-calls-google-meet][Video calls: Google Meet, with screen sharing]]). Tested against Chrome 148.

* 1. The decision: Chrome, headless, over the DevTools protocol

The architecture comes before the engine: *headless + our own blit*. The engine
renders into memory and shows nothing; our Lisp puts its pixels on the screen as one
more pane. The Lisp stays the only process on =/dev/fb0=, which
[[file:processes.org::#invariant-exactly-process-writes][processes.org, The invariant: exactly one process writes to /dev/fb0]] requires. No GPU driver, no compositor.

Chrome fills that shape with no C code of ours. It has a headless mode
(=--headless=new=) that is the real browser with no window, and a control protocol
that already covers frames, input, tabs, downloads and dialogs. It's usually
installed already (=/usr/bin/google-chrome=).

** 1.1 Chrome or WPE: the comparison that decided it

|-------------------------------------------+------------------------------------------------------------------------------------+-------------------------------------------------------------------------------------------------------------|

| How input reaches it                      | =Input.dispatchKeyEvent= / =dispatchMouseEvent= / =insertText= ([[#input][Input]])              | an embedder API in C                                                                                        |

| Code we wrote                             | Lisp only, *no C* (=web-cdp.lisp= 527 lines, =web.lisp= 2,882, with page scripts)  | a C shim plus Lisp; not estimated                                                                           |
| Memory, one simple page                   | 240–280 MB PSS on the host ([[#numbers][Numbers]]), 436 MB in the guest                             | ~570 MB RSS for one heavy site (RSS, an upper bound)                                                        |

| Licence                                   | proprietary binary, used as installed                                              | LGPL                                                                                                        |

The licence row is the honest cost. We don't ship Chrome: the image *calls* the copy
installed on the host's disk. That's the stance [[file:previews.org][previews.org]] takes for
=libstbi.so=, one step further — a host program used at runtime, because writing our
own isn't realistic (=loc.sh= counts only what we wrote).

Nothing in [[#user-sees][What the user sees]]–[[#running-guest][Running it in the guest]] is Chrome-specific except the protocol. Replacing the engine would
replace =web-cdp.lisp= and keep the pane.

** 1.2 Alternatives considered
:PROPERTIES:
:CUSTOM_ID: alternatives-considered
:END:

A browser is mostly its *engine* (HTML/CSS layout, JavaScript VM, painting). Writing
one is out of scope, so the question is which engine, and how much desktop it drags in.

| Option                     | Engine / JavaScript                              | How it draws                   | Verdict                                       |
|----------------------------+--------------------------------------------------+--------------------------------+-----------------------------------------------|
| Links2 =-g=, w3m           | own; HTML 4, basic CSS; no JS                    | framebuffer / terminal         | tiny, but the modern web is out of reach      |
| NetSurf (framebuffer)      | own; CSS 2.1, partial CSS 3; minimal JS          | =libnsfb=                      | best of the small ones; single-page apps break |
| WPE WebKit                 | full WebKit + JavaScriptCore                     | DRM/KMS, or headless           | the real web without a desktop; the runner-up |
| WebKitGTK / Nyxt 3         | full WebKit                                      | GTK → X or Wayland             | needs a whole desktop                         |
| Electron / Nyxt 4          | Chromium                                         | its own stack                  | heavier than Chrome itself                    |
| Remote (VNC into the host) | any                                              | a Lisp RFB client in the guest | a thin client, not a browser                  |
| Closure (CL, McCLIM)       | pure Lisp, HTML 4 / CSS 1 era                    | McCLIM                         | a historical toy                              |

- *DRM/KMS* is the kernel's modern display API (=/dev/dri/card0=), what a GPU driver
  such as =i915= exposes. The image doesn't have it: only the firmware framebuffer
  =efifb= ([[file:framebuffer.org][framebuffer.org]]). So only *headless* fits.
- *Why not Nyxt.* It's a Lisp shell around someone else's engine. Nyxt 3 renders
  through WebKitGTK; =ldd= on the host gives 166 shared libraries (~187 MB) for
  =libwebkit2gtk-4.1=, against 143 (~137 MB) for =libWPEWebKit-2.0=. The totals are
  close; the difference is that GTK needs a display server and wants the main thread.

*WPE dead ends* (on a Debian host with =libwpewebkit-2.0-1=, kept so nobody repeats
them):

- *=cog= under X fails.* =libwpe [FATAL]: could not load the impl library ...
  libWPEBackend-default.so=. Debian builds cog with only the =drm=, =headless= and
  =wl= platforms; =-P x11= falls through to a backend that doesn't exist.
- *=cog -P wl= under =cage= with =LIBGL_ALWAYS_SOFTWARE=1= crash-loops.* The web
  process dies on an assertion in =dmabuf_feedback_check_main_device= inside
  WPEBackend-fdo, the legacy backend. =WEBKIT_DISABLE_DMABUF_RENDERER=,
  =WEBKIT_DISABLE_COMPOSITING_MODE= and =WEBKIT_SKIA_ENABLE_CPU_RENDERING= don't
  help; =GALLIUM_DRIVER=softpipe= avoids it but is unusably slow. WebKit's own
  =MiniBrowser= doesn't crash (it uses the newer built-in platform layer) unless given
  =--use-legacy-api=.
- *DRM on a bare VT needs the VT's owner.* Run from an X session,
  =WPE_DISPLAY=drm MiniBrowser= fails with =Failed to become DRM master=: logind
  hands the display only to the user owning that VT.
- *Web Inspector needs the sandbox off.* =WEBKIT_INSPECTOR_HTTP_SERVER= works only
  with =WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1=; =WEBKIT_SHOW_FPS=1= printed
  nothing on 2.54.

WPE in software rendering under =cage= worked. Benchmarks
(Speedometer/JetStream/MotionMark) and PSS measurements were never taken, since
Chrome was chosen first.

* 2. What the user sees
:PROPERTIES:
:CUSTOM_ID: user-sees
:END:

=SuperL-b= ("browse") opens a new tab with the address prompt in the minibuffer.
Type an address or some words and press Enter. The Spotter (=SuperL-Space=) offers
web rows too: "open URL" when the query looks like an address, "search the web" for
any other text, the open web tabs whose title or URL match, and pages from your
history ([[#address-prompt-knows-paths][The address prompt knows paths and your history]]).

A web tab is an ordinary tab: its label is the page's title, and =SuperL-1…9=,
=SuperL-Tab= and =SuperL-w= work on it. A toolbar shows back =<=, forward =>=,
reload (stop while loading) and the address; clicking the address edits it.

| Key                                              | Does                                                                                                                  |
|--------------------------------------------------+-----------------------------------------------------------------------------------------------------------------------|
| =C-l=                                            | the address prompt: an address, a path, or words to search for; the panel above it lists files or your history ([[#address-prompt-knows-paths][The address prompt knows paths and your history]]) |
| =SuperL-Left= / =SuperL-Right=                   | back / forward in the page's history                                                                                  |
| =C-r=                                            | reload                                                                                                                |
| =Esc= while loading                              | stop (otherwise =Esc= goes to the page)                                                                               |
| =C-f=                                            | find in the page as you type; Enter finds the next                                                                    |
| =C-c= / =C-x= / =C-v=                            | copy / cut / paste through *our* clipboard ([[#copy-paste-go-through][Copy and paste go through our clipboard]])                                                                     |
| =C-Insert= / =S-Insert=                          | copy / paste, X style                                                                                                 |
| =C-+= / =C--= / =C-0=                            | zoom in, out, back to 100% ([[#page-zoom-fills-pane][Page zoom fills the pane: upscale, then sharpen]])                                                                                     |
| =Shift-F10=, the Menu key, right click           | the environment's menu for the page                                                                                   |
| =SuperL-click= on a link                         | open it in a new tab (Ctrl-click opens it behind)                                                                     |
| a click (or Space, Alt-Down, F4) on a =<select>= | our list of its options ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]])                                                                                        |
| a click on a colour input, Alt-Down on a date    | the minibuffer asks for the value ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]])                                                                              |
| anything else                                    | the page's                                                                                                            |

Every =SuperL= key stays the environment's. Every other key belongs to the page —
=Tab=, =Esc=, =C-g=, =C-c= included — because that's what you're typing into. The
exceptions in the table are the chords a desktop browser also keeps for itself.

*Alt-Left isn't "back".* The console keymap gives Alt-Left/Right to switching
virtual terminals: in =./linux/drivers/tty/vt/defkeymap.c_shipped=, =alt_map[105]=
and =alt_map[106]= (=KEY_LEFT=, =KEY_RIGHT=) are =0xf210= / =0xf211=,
=K_DECRCONSOLE= / =K_INCRCONSOLE= in =include/uapi/linux/keyboard.h=. The kernel acts
on them before any program sees a byte, so a test pressing Alt-Left ended up on
another VT. Back/forward are =SuperL-Left/Right= instead. The environment now rebinds
Alt-Left/Right to plain cursor keys (for Org), so =M-Left/Right= arrive as
=ESC [ 1 ; 3 D= / =C= and no longer switch VTs ([[file:input.org::#tty-enough][input.org, Why the tty is not enough]], "Alt with the
arrows").

* 3. How it works

** 3.1 The DevTools protocol

Chrome's developer tools (the F12 panel) control the browser through the *Chrome
DevTools Protocol*, CDP. It's plain JSON. We send a *command*:

#+begin_src js
{"id": 7, "method": "Page.navigate", "params": {"url": "https://example.com"}}
#+end_src

Chrome answers with a *response* carrying the same id, ={"id":7,"result":{...}}= or
={"id":7,"error":{...}}=, and sends *events* whenever it likes, with no id:
={"method":"Page.frameNavigated","params":{...}}=. That's the whole grammar.

The vocabulary is a few hundred methods in domains (=Page=, =Input=, =Target=,
=Runtime=, =Emulation=, =Browser=), documented at
https://chromedevtools.github.io/devtools-protocol/. Puppeteer and Playwright are
built on it; =web-cdp.lisp= is our much smaller equivalent, with a JSON reader and
writer limited to what this traffic uses.

** 3.2 The pipe, not a socket
:PROPERTIES:
:CUSTOM_ID: pipe-socket
:END:

Started with =--remote-debugging-pipe=, Chrome speaks CDP on two inherited *file
descriptors* instead of a WebSocket port. (A file descriptor is a small integer
naming an open file or pipe: 0 is stdin, 1 stdout, 2 stderr.) Chrome reads commands
from fd 3 and writes replies and events to fd 4. Each message ends with a NUL byte,
which can't occur inside JSON text.

No HTTP, no WebSocket framing, no port another program could connect to. The one
difficulty: =sb-ext:run-program= gives a child fresh pipes on stdin and stdout only.
So a shell moves them before it becomes Chrome
([[file:../initramfs/web-cdp.lisp::defun pipe-wrapper][=pipe-wrapper=]]):

#+begin_src sh
exec 3<&0 4>&1 >>/tmp/lol-chrome-1.log 2>&1 </dev/null; exec google-chrome --headless=new --remote-debugging-pipe ...
#+end_src

=3<&0= makes fd 3 a copy of stdin (our command pipe), =4>&1= fd 4 a copy of stdout
(our reply pipe). Chrome's own messages go to a log file, so they never interleave
with the protocol.

*Both ends are non-blocking.* The reply pipe is read for whatever is there. The
command pipe matters because the writer is the environment's thread: a Chrome that
stops reading fills its 64 KB, and a blocking write would freeze the screen.

- *A wait without progress.* [[file:../initramfs/web-cdp.lisp::defun cdp-write-octets][=cdp-write-octets=]] gives up after
  =+cdp-write-seconds+= (5) with /no progress/; every octet Chrome takes restarts the
  wait. A deadline for the whole message is wrong: a Chrome busy in a call reads a
  multi-megabyte message slower than that while reading steadily ([[#video-calls-google-meet][Video calls: Google Meet, with screen sharing]]).
- *Giving up kills Chrome.* It closes the pipe (half a message has corrupted the
  stream anyway) and sends Chrome =SIGTERM=. Closing alone isn't enough: Chrome runs
  on without its command pipe and answers nothing. After =SIGTERM= the reader sees
  EOF, the pane reports "Chrome exited", and =r= restarts it.

=poc/web-test.lisp= asserts both: a child that never reads its stdin is given up on;
one that reads slowly but steadily (64 KB every 0.2 s, 1 MB against a 1 s wait) is
not.

** 3.3 Tabs, sessions, and frames
:PROPERTIES:
:CUSTOM_ID: tabs-sessions-frames
:END:

One Chrome process holds many tabs; in CDP a tab is a *target*.
=Target.createTarget= makes one, and =Target.attachToTarget= with =flatten: true=
returns a *session id*. A command for that tab carries ="sessionId"= beside
="method"=, and so does every event from it. One pipe, many tabs.

*Frames come by screencasting.* =Page.startScreencast= makes Chrome send a
=Page.screencastFrame= event whenever the page repaints: a JPEG, base64-encoded (JSON
strings can't carry raw bytes; base64 spells every 3 bytes as 4 letters).

- *Flow control.* We answer each frame with =Page.screencastFrameAck=, and Chrome
  doesn't send the next until it gets it. A slow reader gets fewer frames, not a
  backlog. An unchanged page sends nothing, so an idle tab costs no CPU.
- *Decoding.* Base64, then the JPEG through stb_image ([[file:previews.org][previews.org]]), into the
  canvas's =#x00RRGGBB= pixels. Only the newest frame is decoded; one replaced before
  we drew it is dropped.
- *The pane's size is the page's.* =Emulation.setDeviceMetricsOverride= lays the page
  out as if the window were exactly the pane, and the screencast restarts at that
  size. When the pane changes size (font, screen), the next turn resends both.
- *Zoom* is the =deviceScaleFactor= of that same call: =C-+= re-lays-out and
  re-rasterises the text larger. The screencast ignores the factor, which needs a
  step of its own ([[#page-zoom-fills-pane][Page zoom fills the pane: upscale, then sharpen]]).
- *Only the tab on screen streams.* Switching tabs sends =Page.stopScreencast= to
  the one you left.

*The tab on screen is also Chrome's foreground page.* Headless Chrome still keeps one
page "in front" (the newest, unless told otherwise), and only that one runs its
compositor. A page behind it takes clicks and keys, but a =mouseWheel= sent to it
never completes, so it never scrolls, and its frames arrive seconds late. So a tab
that starts streaming is first made the front page with =Target.activateTarget=
([[file:../initramfs/web.lisp::defun web-activate][=web-activate=]]). Measured in the guest: input-to-frame latency fell from 2.4–43 s
to 20–96 ms.

** 3.4 Input
:PROPERTIES:
:CUSTOM_ID: input
:END:

- *Clicks.* =Input.dispatchMouseEvent=: =mousePressed=, then =mouseReleased= when the
  button comes up, the point converted to the page's CSS pixels. A drag sends
  =mouseMoved= with the button held (text selection, sliders). Bare moves are sent
  too, for hover menus. A touchpad tap has no release of its own, so it goes as press
  and release together.
- *The wheel.* A =mouseWheel= of 100 CSS pixels per notch (Chrome's own step on
  Linux) at the pointer, so the page scrolls whatever is under it.
- *Keys.* =Input.dispatchKeyEvent=, a =keyDown= and a =keyUp=, filled in as a page's
  =KeyboardEvent= expects: =key= is the meaning (="a"=, ="Enter"=), =code= the
  physical key (="KeyA"=), =windowsVirtualKeyCode= the old numeric code many sites
  still read. =text= is present only when the key inserts something; a keyDown
  without it (=C-a=, an arrow) is a command. Shift, Ctrl and Alt map to CDP's bits 8,
  2 and 1.
- *Paste.* =Input.insertText= inserts a whole string, the way an input method commits
  text.

* 4. The pane in the shell

** 4.1 A tab is a trail

=SUBJ-WEB= is a subject like a folder or a definition. =present= gives a view of kind
=:web= whose data is the =WEB-TAB=, so the tab strip, the right-button menu (from
=commands-for=), the halo and the Spotter's recents work without knowing what a web
page is.

- *Each web tab is its own trail.* Closing one needs no hook in the shell: every
  turn, =WEB-COLLECT-TABS= closes the Chrome page of any web tab no trail holds.
- *New windows become trails.* A link that opens one (=target=_blank=,
  =window.open=, Ctrl-click) arrives as =Target.targetCreated= with an /opener/. The
  opener test matters: Chrome also reports pages that already exist, its startup
  =about:blank= among them, and those mustn't become tabs.
- *Two sources for the title.* =Target.targetInfoChanged=, and =document.title=
  whenever a load finishes — for a =file://= page Chrome 148 keeps reporting the file
  name as the title.
- *The home page is the project's guide.* A tab opened without a URL loads
  =doc/guide/index.html= ([[file:../initramfs/web.lisp::defun web-home-url][=web-home-url=]]). The build freezes the repo's path into
  the image, as [[file:../initramfs/sbcl-source.lisp][=sbcl-source.lisp=]] does for =./sbcl=; on real hardware the repo is
  at the same path under the mounted =/home=, which Chrome's container sees too. A
  diskless boot has no =/home=, so it gets =about:blank=. Setting =*web-home*= to a
  URL overrides both. The address prompt opens empty on the home page.

** 4.2 Copy and paste go through our clipboard
:PROPERTIES:
:CUSTOM_ID: copy-paste-go-through
:END:

Headless Chrome keeps its clipboard inside its own process, where nothing else can
paste from it.

- *=C-c=* asks the page for its selection (inside a focused text field, which
  =getSelection()= alone misses, else the document's) and puts it in
  =lol.clipboard='s history ([[file:clipboard.org][clipboard.org]]). The key is also sent on, so a site's
  own copy handler still sees it.
- *=C-v=* types our newest clipboard entry.
- *A drag selection* goes to PRIMARY when the button comes up, as everywhere in the
  environment, so a middle click pastes it into the Workspace.
- *The address prompt* (=C-l=) is our minibuffer: =C-y=, =C-v= or Shift-Insert insert
  the newest entry with newlines and tabs made spaces (=minibuffer-paste-text=, so a
  URL copied with its line break pastes clean). =C-u=, or the =✕ clear= button at
  the prompt's right, empties it.

** 4.3 Downloads, dialogs, find

- *Downloads* go to =~/Downloads= under their own names
  (=Browser.setDownloadBehavior=); the status line reports progress and the result.
  =/home= is the host's own, so a download is a real file on the disk.
- *alert(), confirm(), prompt()* freeze the page until answered. They're answered in
  the minibuffer at once: Enter is OK (with the typed text, for a prompt), =C-g= is
  Cancel.
- *Find* is the page's own =window.find=, re-run as you type.

** 4.4 Pickers: the popups the screencast cannot see
:PROPERTIES:
:CUSTOM_ID: pickers-popups-screencast-cannot
:END:

*The problem.* Click a =<select>= and, without help, no list appears. A select's list
isn't drawn by the page: a desktop browser shows it in a borderless *popup widget*,
so it can hang past the page's edge. In Chrome that widget has its own *compositor
frame* (one finished picture of one surface; the compositor stacks them into what a
window shows). =Page.startScreencast= sends only the *page's* frames ([[#tabs-sessions-frames][Tabs, sessions, and frames]]), and
headless has no window to stack the popup onto. The popup opens, takes the keyboard,
and is never in any frame we receive.

/Verified/ in the guest (Chrome 148, tag #27, no pickers): after a real QMP click,
=select.matches(':open')= was =true=; the newest screencast frame held *0* pixels of
the popup's highlight blue, while a =Page.captureScreenshot= at the same moment held
*2809* (that command composites popups). Down and Enter still changed the value,
blind.

| Control                                                        | Headless Chrome 148                                                                         | What we do                                                                                     |
|----------------------------------------------------------------+---------------------------------------------------------------------------------------------+------------------------------------------------------------------------------------------------|
| =<select>= (single, size ≤ 1)                                  | an invisible popup that takes the keys                                                      | our chooser (below)                                                                            |
| =<input type=color>=                                           | an invisible colour chooser, opened on /click/; it took every following key                 | the minibuffer asks for =#rrggbb=                                                              |
| =<input type=date>=, =time=, =datetime-local=, =month=, =week= | no picker at all: the calendar icon does nothing                                            | the minibuffer asks (=yyyy-mm-dd= …); typing digits into the field also works, and is visible  |
| =<input list=…>= with a =<datalist>=                           | no visible suggestions; once open, they swallowed the arrow keys (=Esc= closed them)       | our chooser, on Down / Alt-Down / a click on the field's arrow                                 |

*How we draw them.* Three pieces, all in [[file:../initramfs/web.lisp::defparameter +web-picker-js+][=web.lisp='s "pickers" section]]:

1. *A page script* (=+WEB-PICKER-JS+=) is installed into every document the tab will
   load (=Page.addScriptToEvaluateOnNewDocument=) and once into the current one. It
   listens on =window= in the *capture phase*: DOM events travel from the window down
   to the target (capture), then back up (bubble), so a capture listener on =window=
   runs before the page's handlers and the browser's default action.
   - On a =mousedown= on a select (or Space, Enter, Alt-Down, F4 on a focused one) it
     calls =preventDefault()=, so Chrome never opens its popup, and reports the
     control: an id (a counter in a =WeakMap=, so elements aren't marked), its box in
     CSS pixels, and its options (label, value, disabled, =<optgroup>= label,
     selected).
   - A colour input also has its =click= cancelled, since that's when its chooser
     opens.
   - A datalist input loses its =list= attribute while focused (restored on blur):
     Chrome offers suggestions only to a focused input with one, so its invisible
     list never opens.
2. *A binding carries the report.* =Runtime.addBinding= puts a function on the page's
   =window=; each call becomes a =Runtime.bindingCalled= event on our pipe, with one
   string (here JSON) and the *execution context* it came from (each frame has its own
   JavaScript world). Events come only while the Runtime domain is enabled — forget
   =Runtime.enable= and the script cancels the click while its report goes nowhere.
3. *Our chooser.* The event is queued and, after the pipe has been read, shown by
   =WEB-PICK=. A list goes to the right-button menu's card,
   [[file:../poc/overlays.lisp::defun run-chooser][=RUN-CHOOSER=]], with a kind of its own, =:select=:
   - placed under the control (CSS pixels times =*web-zoom*= plus the page's origin on
     screen, the mapping =WEB-PAGE-POINT= inverts), at least as wide as it, opening on
     the current option, optgroups as section headers, disabled options dim and never
     landed on;
   - Up/Down, Home/End, PageUp/PageDown move; typing jumps to the next option starting
     with what was typed (letters within a second accumulate); Enter, Space or a click
     picks; Esc, =C-g= or a click outside leaves it unchanged;
   - the answer goes back with =Runtime.evaluate= *in the reporting frame's context*:
     =__lolPickerApply= sets =selectedIndex= (checked against the option's value, in
     case the list changed) and fires =input= and =change= with =bubbles: true=, as a
     real choice does.

   Colour and date go to the minibuffer instead, pre-filled with the current value;
   the page refuses a malformed one, and the status line says so.

- *Why queue.* The chooser waits for an answer. =WEB-EVENT= runs inside =CDP-PUMP='s
  loop over a batch of messages just read, so waiting there would leave the rest of
  the batch undelivered. While the chooser is up the pipe isn't read at all, which is
  harmless: Chrome sends the next frame only after the last is acked ([[#tabs-sessions-frames][Tabs, sessions, and frames]]).
- *The press is released first.* =WEB-FINISH-PRESS= releases the opening press to the
  page before the chooser comes up, since the chooser will eat the real release.

*Not covered:*

- *Cross-site iframes.* Chrome runs such a frame in its own process, a target we
  never attach to, so our script isn't in it and its popup stays invisible.
  Same-site iframes work (the box is shifted by each enclosing frame).
- *List boxes.* =<select multiple>= and =size= > 1 are drawn by the page itself and
  left alone.
- *=input.list=* reads =null= to the page's own JavaScript while a datalist input
  has focus.
- *=<input type=file>=* is a different mechanism (a file chooser dialog, [[#limits-next][Limits, and what is next]]).

** 4.5 Saying we are Chrome: the user agent and its client hints
:PROPERTIES:
:CUSTOM_ID: saying-chrome-user-agent
:END:

Some sites refuse or degrade a browser that looks automated. Google's sign-in says
"This browser or app may not be secure", and its search answers with captchas. Four
things give a headless, pipe-driven Chrome away:

- *=HeadlessChrome= in the user agent.* =web-chrome-ready= removes the "Headless" and
  sends the result with =Emulation.setUserAgentOverride=.
- *Empty client hints.* A modern Chrome describes itself twice: the =User-Agent=
  string and the /User-Agent Client Hints/ (the =Sec-CH-UA*= headers,
  =navigator.userAgentData= for scripts). Overriding the string alone leaves the hints
  empty, a known sign of automation. [[file:../initramfs/web.lisp::defun web-ua-metadata][=web-ua-metadata=]] builds the matching
  =userAgentMetadata=: the brands =Chromium=, =Google Chrome= and the "GREASE" brand
  =Not/A)Brand= (a deliberately odd name that keeps servers from hard-coding the
  list); the full version from =Browser.getVersion='s =product= into
  =*web-chrome-version*=; Linux, x86, 64-bit, not mobile. Every new tab gets string
  and hints together.
- *=navigator.webdriver= is true.* That W3C flag marks a browser driven by automation,
  and =--remote-debugging-pipe= sets it. =--disable-blink-features=AutomationControlled=
  in [[file:../initramfs/web.lisp::defun web-chrome-argv][=web-chrome-argv=]] clears it.
- *An impossible screen.* Headless reports an 800 x 600 screen whatever the window,
  and its window (=--window-size=) was smaller than the page inside it.
  =Emulation.setDeviceMetricsOverride= now also sends =screenWidth= / =screenHeight=,
  the world's size from [[file:../initramfs/web.lisp::defun web-screen-size][=web-screen-size=]] (divided by the zoom, as Chrome's own zoom
  does), and Chrome's window starts at that size.

Measured against Chrome 148 inside the environment:

| What the page reads                        | Before        | Now                |
|--------------------------------------------+---------------+--------------------|
| =navigator.webdriver= (page and iframes)   | *=true=*      | =false=            |
| =screen.width= x =screen.height=           | *800 x 600*   | the world's size   |
| =outerWidth= x =outerHeight=               | *1024 x 700*  | the world's size   |
| =innerWidth= x =innerHeight=               | 1256 x 701    | 1256 x 701         |
| UA string, client hints, in a Worker too   | Chrome, full  | Chrome, full       |

Already right: =window.chrome=, five plugins, the languages. *Known limit:* WebGL is
absent (=--disable-gpu=, no GPU), and a site that insists on it will see that. Google
also remembers a network that sent "unusual traffic" for a while. =web-test= checks
the first two rows.

** 4.6 The address prompt knows paths and your history
:PROPERTIES:
:CUSTOM_ID: address-prompt-knows-paths
:END:

=C-l= opens the one-line minibuffer with a *candidate panel* on top of it, over the
bottom of the screen. What the panel lists depends on the first characters typed:

| You type                            | The panel lists                                                                                                                       | Enter on the line           |
|-------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------+-----------------------------|
| =/=, =~/=, =./=, =../= or =file://= | the folder you're in, like a small file manager: folders first, then files with size and date; what you typed of the name lights up | opens it as a =file://= URL |
| anything else                       | your history: pages whose address or title contain every word typed                                                                   | an address, or a search     |
| nothing (a new tab)                 | the most recent pages                                                                                                                 | the home page               |

Nothing is chosen until you move into the list, so Enter opens what you typed.

| Key                 | Does                                                                                                                    |
|---------------------+-------------------------------------------------------------------------------------------------------------------------|
| =Down= / =C-n=      | choose a row (the first, from the line)                                                                                 |
| =Up= / =C-p=        | the row above; above the first, back to the typed text                                                                  |
| =Enter=             | open the chosen row, else the typed text                                                                                |
| =Tab=               | the chosen row into the line, to keep typing; with no row, complete like a shell (common prefix, a folder gets its =/=) |
| =M-Backspace=       | delete the last word, i.e. go up one folder                                                                             |
| =Shift-Delete=      | forget the chosen page (history rows only)                                                                              |
| a click / the wheel | open a row / move the choice                                                                                            |

So a folder is browsed with Tab: =~/= lists your home, =Doc= =Tab= gives
=~/Documents/= and lists inside it, =Down= =Tab= enters the chosen sub-folder,
=Enter= on a file opens it. =Enter= on a folder opens Chrome's own listing. A typed
path is always a file, never a web search.

*The panel is generic.* [[file:../poc/shell.lisp::defun minibuffer-read][=minibuffer-read=]] takes =:candidates=, a function from the
text to a list of plists (label, detail, the text the row stands for, a section, a
"forget" function), and a title. The panel is a morph of the desk,
[[file:../poc/morphic.lisp::defclass minibuffer-panel][=minibuffer-panel=]], not of the shell, so the panes under it keep their size: a page
isn't resized because you typed into its address bar. =desk-sync= adds, sizes and
removes it. It isn't an overlay, because the keys stay the minibuffer's. The web
pane's candidates come from [[file:../initramfs/web.lisp::defun web-address-candidates][=web-address-candidates=]].

*The history is ours, not Chrome's.* Chrome's is an SQLite file in the profile, which
would need an SQLite reader. [[file:../initramfs/web.lisp::defun web-history-note][=web-history-note=]] keeps one plist per URL
(=:url :title :visits :last=, newest first, at most 2000) in
=~/.lol/web/history.lisp=, mode 0600.

- *What counts as a visit.* =Page.frameNavigated= for the main frame, and
  =Page.navigatedWithinDocument= (a single-page app's =pushState=). The title is
  filled in when the page says it. =about:=, =data:=, =chrome:=, =javascript:= URLs
  and the home page aren't kept.
- *Writes.* Atomic and fsync'd, at most every 10 s and at power-off. A crash loses at
  most the last few seconds. A diskless boot keeps it in memory.
- *Ranking* ([[file:../initramfs/web.lisp::defun web-history-matches][=web-history-matches=]]). Every word must occur in the URL or title,
  ignoring case. Then a blend of recency and frequency ("frecency"): each visit
  counts as a day more recent, up to a month's worth, and a page whose address
  /starts/ with the first word (=git= for =github.com=) comes first. The Spotter uses
  the same function, adding up to five history pages no open tab shows.

*Where a file is depends on who looks.* The panel lists files as the environment sees
them, but Chrome opens them inside its container ([[file:containers.org][containers.org]]), whose root is the
host's distribution. The two agree only under the folders =lol-ct.c= binds in:
=/home=, =/tmp=, =/dev=, =/sys=. So in the guest an absolute path outside those is
listed from =/mnt/host=, our mount of the host's root
([[file:../initramfs/web.lisp::defun web-chrome-root][=web-chrome-root=]]); the rows still read =/usr/share/=, as Chrome names them. The
container's overlays can add files =/mnt/host= doesn't show — close enough for a
listing. On the host both run in the same root and nothing is mapped.

Tests: [[file:../poc/url-prompt-test.lisp][poc/url-prompt-test.lisp]] (host, no Chrome, 44 checks: URL rules, the
history's file, ranking and 0600 mode, the panel by keys, click and Shift-Delete, the
=/mnt/host= mapping, and after every step the incrementally repaired screen equal to
a fresh paint; =LOL_SHOTS=DIR= keeps two screenshots). =check-web.lisp= drives it in
the guest with real keys ([[#asserted][What is asserted]]).

** 4.7 Page zoom fills the pane: upscale, then sharpen
:PROPERTIES:
:CUSTOM_ID: page-zoom-fills-pane
:END:

=C-+= zooms the way Chrome's own =Ctrl-+= does ([[#tabs-sessions-frames][Tabs, sessions, and frames]]): the page is laid out in fewer
CSS pixels drawn at 1.5 device pixels each, so =window.innerWidth= shrinks and a
narrow layout can kick in. But a /screencast/ frame comes at CSS-pixel size —
Chrome ignores the scale factor there. Blitted 1:1, a zoomed page fills only part of
the pane, and clicks land off. Measured against Chrome 148 with a 1256 x 677 pane:

| Page zoom | Chrome's CSS viewport | Screencast frame | Screenshot   |
|-----------+-----------------------+------------------+--------------|
| 100%      | 1256 x 677            | 1256 x 677       |              |
| 125%      | 1004 x 541            | *1004 x 541*     |              |
| 150%      | 837 x 451             | *837 x 451*      | 1256 x 677   |

A /screenshot/ (=Page.captureScreenshot=) does come at device size, but takes
46–55 ms — too slow for every frame while you scroll. So each zoomed frame is scaled
up at once and replaced once the page is still
([[file:../initramfs/web.lisp::defun web-sharpen][=web-sharpen=]]):

1. *Upscale.* [[file:../initramfs/web.lisp::defun web-upscale][=web-upscale=]] stretches a CSS-sized frame to the pane, bilinear (each
   output pixel a weighted mix of the four source pixels around it, in 16.16 fixed
   point). 13 ms for 837 x 451 -> 1256 x 677 on the host. Full at once, slightly soft.
2. *Sharpen.* When no frame has come for 150 ms, one screenshot replaces it, crisp.
   It's dropped if a newer frame arrived meanwhile. The poll loop's timeout
   ([[file:../initramfs/web.lisp::defun web-timeout][=web-timeout=]]) wakes us when one is due, so nothing spins.

Chrome renders =floor(1256 / 1.5)= = 837 CSS pixels, so a 150% screenshot is
1255 x 676, one pixel short each way. [[file:../initramfs/web.lisp::defun web-pad][=web-pad=]] repeats the last column and row
rather than resampling, which would blur the crisp picture.

*Ruled out:* =setDeviceMetricsOverride='s =scale= parameter changes nothing in the
frames. CSS =zoom= on the root element gives full, crisp frames for free, but the page
still sees the full-width viewport, so a narrow layout never kicks in. The
environment's own scale (=SuperL-==) was never the issue: the frame follows it.

Tests: =poc/web-test.lisp= (=C-+ C-+= gives =devicePixelRatio= 1.5 and a narrower
viewport; the pane full at once and soft, then full and sharp; =C-0= back; the
upscaler's edges exact).

** 4.8 Video calls: Google Meet, with screen sharing
:PROPERTIES:
:CUSTOM_ID: video-calls-google-meet
:END:

*Status: built and host-tested* (=poc/web-test.lisp=, 18 "calls:" checks, Chrome 148).
Camera, microphone and a shared screen have worked in a Meet test meeting on real
hardware; a call with another person is still to be tried (see "Still open").

*** What a call needs, against what our Chrome had

A call is a web page plus four things a desktop gives a browser for free: speakers, a
microphone, a camera, and a screen to share. Our Chrome runs headless in a container
([[#running-guest][Running it in the guest]]), so each has to be handed to it on purpose.

| Need          | What the page calls     | What headless Chrome lacks                                                  | Provided by                  |
|---------------+-------------------------+-----------------------------------------------------------------------------+------------------------------|
| Hear the call | an =<audio>= element    | a sound device: ALSA's =default= is the host's PipeWire, not running here   | =--alsa-*-device= (M1)       |
| Speak         | =getUserMedia({audio})= | the same, plus a permission nobody can click (no bubble without a window)   | M1 + our prompt (M2)         |
| Be seen       | =getUserMedia({video})= | =/dev/video0=: no V4L2 in the kernel before tag #32                         | tag #32 + our prompt (M4)    |
| Share         | =getDisplayMedia()=     | anything to capture: no display, and the picker is never shown              | our canvas (M5)              |
| Sign in       | Google's login          | nothing since [[#saying-chrome-user-agent][Saying we are Chrome: the user agent and its client hints]]                                                          | —                            |

*** M1. Sound and the microphone — measured, then two switches

Measured with Chrome 148 on a Realtek ALC289 (Dell XPS 13 9300):

- *No switch.* A played tone leaves the card's playback =closed=
  (=/proc/asound/card0/pcm0p/sub0/status=), and =getUserMedia= fails with
  =NotReadableError: Could not start audio source=. Chrome's log: =PcmOpen:
  default,Host is down=. Debian's Chrome tries PulseAudio, finds no server, falls back
  to ALSA, and ALSA's =default= is PipeWire's plugin with no PipeWire behind it.
- *=--alsa-output-device=plughw:0,0 --alsa-input-device=plughw:0,0=.* Playback is
  =RUNNING= on the card and the microphone streams (capture =RUNNING=, peak level
  0.097 from the room). =enumerateDevices= lists the card's ALSA devices by name.

So [[file:../initramfs/web.lisp::defun web-chrome-argv][=web-chrome-argv=]] passes both switches, with the device from
[[file:../initramfs/web.lisp::defun web-audio-device][=web-audio-device=]]: =plughw:0,0= (the card itself, as the recorder uses it), unless a
sound server is running (a socket at =$XDG_RUNTIME_DIR/pipewire-0= or =pulse/native=,
as on a host desktop where PipeWire holds the card).

*** M2. Permissions — our prompt, Chrome's grant

Without a window Chrome can't ask "allow microphone?": an unanswered =getUserMedia= is
refused at once with =NotAllowedError=. What works is =Browser.grantPermissions= for
the page's origin, after which =navigator.permissions= says =granted=.

*The script asks us first.* [[file:../initramfs/web.lisp::defparameter +web-media-js+][=+web-media-js+=]], installed into every document like
the pickers' script ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]]), wraps =MediaDevices.prototype.getUserMedia= (and the old
=navigator.webkitGetUserMedia=): it asks through a binding and calls Chrome's own
function only after the answer. Wrapping the prototype, not the one
=navigator.mediaDevices= object, catches pages that call the prototype's function.

*The question.* [[file:../initramfs/web.lisp::defun web-ask-media][=web-ask-media=]] asks in the minibuffer: "meet.google.com wants your
microphone and camera: y allow · a always · n no".

- *=y=* grants the origin until Chrome exits.
- *=a=* also writes it to =~/.lol/web/permissions.lisp= (0600), granted again at every
  start of Chrome.
- *=n= or =C-g=* refuses with =NotAllowedError=, as a refusing user would.
- *No origin, no question.* A =file:= page's origin is ="null"=; granting it would
  grant every origin, so it's refused without asking.

*Grant facts.* A grant lasts only as long as Chrome, and it /replaces/ an origin's
set, so [[file:../initramfs/web.lisp::defun web-grant][=web-grant=]] always sends the union of what the origin has.

*Pan-tilt-zoom.* A page may ask =navigator.permissions.query({name: 'camera',
panTiltZoom: true})=; with =videoCapture= alone granted, that reads =denied= while the
plain camera reads =granted=, and Meet waits in its "allow camera" dialog. So a
camera grant carries =cameraPanTiltZoom= too. The name matters: the protocol's older
=videoCapturePanTiltZoom= is refused by Chrome 148 ("Unknown permission type"), and
one unknown name makes Chrome refuse the /whole/ grant.

*A block stored in the profile.* Chrome's content settings =media_stream_camera= and
=media_stream_mic= can hold 2 (block) for an origin — likely from a request that
reached Chrome's own prompt, which headless can't show. The page then never calls
=getUserMedia=; it calls =permissions.query=, reads =denied=, and waits.
=Browser.grantPermissions= overrides the block: the page reads =granted= and its
=PermissionStatus= fires =change= (what a page like Meet waits on). So the script's
=permissions.query= wrapper asks us at the first =denied= of a document, once, for
camera and microphone together ("... has your microphone and camera blocked: y allow ·
a always · n keep blocked"). The stored block stays in the profile, overridden each
time.

*The question is sticky.* An open minibuffer prompt normally ends on any press ("a
click is a change of subject"), so clicking the page's own "Allow" button dismissed
ours. A page's question is now /sticky/ (=*minibuffer-sticky*=, set by
=minibuffer-read='s =:sticky=): only =y=, =a=, =n=, Esc or =C-g= end it. The same goes
for a page's =alert= / =confirm= / =prompt=. While a page waits, the strip over its
foot says "the page is waiting for your answer in the line below ↓" (=web-asking=).
The flag is a variable beside =*minibuffer*= rather than a slot of the =mb= struct, so
a running image can take it from a patch.

*Logging.* Every question, answer and refused grant goes to =session.log= ("web:
..."). Pages that touch the media also report each =getUserMedia= (constraints and
result) and each camera/microphone =permissions.query= ("web: page ..."). A call made
from a cross-site iframe (a target we don't attach to) gets neither script nor binding.

*Ruled out:*

- *"Bind context provider failed"* in Chrome's log appears on every camera start,
  working or not: noise (no GPU context), not a fault.
- *Chrome's =<permission>= element* (an in-page button asking through Chrome's own
  prompt) doesn't exist in Chrome 148 (=HTMLPermissionElement= is undefined).

*** M3. Sharing a tab — ruled out, replaced by M5

Headless Chrome /can/ capture a tab: with
=--auto-select-tab-capture-source-by-title=Example=,
=getDisplayMedia({preferCurrentTab: true})= gave a live 800 x 600 stream
(=displaySurface: browser=). But the tab is picked by a title fixed on the command
line at start. Anything else (no switch, or =--auto-select-desktop-capture-source=)
leaves the promise waiting for a picker that's never drawn, and
=--use-fake-ui-for-media-stream= picks the desktop and fails (=NotReadableError=: no
display). A background tab also doesn't render ([[#tabs-sessions-frames][Tabs, sessions, and frames]]). M5 shares what's on our
screen instead, which includes any web tab on it.

*** M4. The camera — kernel tag #32

A typical laptop webcam is USB Video Class (e.g. =0bda:58fe= "Integrated_Webcam_HD").
Tag #32 adds V4L2 and the UVC driver ([[file:kernel-config.org::#webcam-v4l2-usb-video][kernel-config.org, The webcam — V4L2 + USB Video Class, NEW in tag #32]]), and preinit's
=give_devices= hands =/dev/video*= to the user as it does =/dev/snd=. The container
bind-mounts our =/dev=, and Chrome speaks V4L2 itself. The permission is M2's prompt
("wants your camera").

*** M5. Sharing the screen — our canvas as a screen

Chrome can't capture what it can't see, so the page gets a picture of our screen as
if it were one:

1. *The script replaces =getDisplayMedia=.* After "y share the whole screen", it makes
   a canvas the screen's size and returns =canvas.captureStream()=; the track says
   =displaySurface: monitor=, and stopping it tells us. Meet's /Present now/ sends
   that canvas.
2. *We paint the canvas through the pipe we hold*, with =Runtime.evaluate= calling the
   page's =__lolShare.put=. Only what changed goes:
   [[file:../initramfs/web.lisp::defun web-share-note][=web-share-note=]] is one of =*frame-taps*= (fb-browser.lisp, the recorder's hook),
   told the rects of every repair; a full frame, or more than 32 rects, sends the
   whole screen. The page draws the pointer over a copy, since ours is never in the
   canvas.
3. *Base64 without carrying.* Three bytes of colour are exactly four base64
   characters, so [[file:../initramfs/web.lisp::defun web-share-message][=web-share-message=]] turns each pixel into four octets, building
   the message as octets (=cdp-send-built=, web-cdp.lisp) instead of through
   =json-string=.
4. *Rate and flow control.* At most =+web-share-fps+= (10) updates a second, and the
   next waits for the page's answer to the last: the screencast's flow control, run
   the other way.
5. *Bounded updates.* [[file:../initramfs/web.lisp::defun web-share-take][=web-share-take=]] sends at most =+web-share-max-pixels+=
   (512 x 512, 1 MB of base64) per update; a rect too big is cut into bands of whole
   rows, the rest kept for the next. A whole screen is nine updates, about a second.
   The environment's thread never writes more than 1 MB at a time — one 8.8 MB write
   used to hold it long enough to freeze the call, and tripped the old whole-message
   deadline of [[#pipe-socket][The pipe, not a socket]].

Measured (Chrome 148, =poc/web-test.lisp=): a whole 1920 x 1200 screen is 8.8 MB,
32 ms of the environment's thread to encode and write, and the page answers about
190 ms later (its decode; =Uint8Array.fromBase64= took that from 208 to 184 ms); 8.8 MB
in 9 updates arrives in 1.1 s. A repaired rect is a few kilobytes. While sharing, the
tray shows =SHARING meet.google.com= in red; the web tab's menu has "Stop sharing the
screen", and Meet's "Stop presenting" works too (the track's =ended= fires).

*Ruled out:* a WebSocket from the page to PID 1 (an HTTP server and SHA-1 in Lisp, for
no gain over the pipe); =v4l2loopback= as a fake camera (out of tree, and the kernel
has =CONFIG_MODULES= unset); =--use-file-for-fake-video-capture= (plays a file, not a
live feed).

*** A call in the background

You present while looking at another pane, so the call's tab isn't Chrome's
foreground page ([[#tabs-sessions-frames][Tabs, sessions, and frames]]). Measured with two tabs and a canvas over a loopback
=RTCPeerConnection=: from the background tab every frame still arrived (50 of 50),
but timers ran at about 1 Hz (5 ticks of a 100 ms =setInterval= in 5 s; 52 in the
foreground). Meet runs on timers. With =Emulation.setFocusEmulationEnabled= the timers
came back (52 in 5 s), so a tab given the microphone, camera or screen is kept focused
([[file:../initramfs/web.lisp::defun web-in-call][=web-in-call=]]). The test asserts 19 ticks in about 2 s with another tab on screen.

*** Still open

- *A call with another person.* Sign-in, camera, microphone and presenting across
  pane switches work in a test meeting; hearing and being heard is untried.
- *CPU.* No GPU: Meet's video decode, WebRTC's encoding of camera and screen, the
  screencast's JPEGs and our decode all run in software. Unmeasured.
- *One device, one stream.* =plughw:0,0= is the hardware itself: one capture and one
  playback stream. Meet opens the microphone a second time, raw (no echo
  cancellation), and that open fails with =NotReadableError=; the call goes on with
  the first. Two sounds at once (a chime) can fail the same way, and recording a call
  (=SuperL-r=) while Chrome holds the mic fails for whichever opens second. ALSA's
  =dsnoop= / =dmix= share one device among several streams; not tried.
- *The whole screen only.* A window or a single pane could be shared by cutting its
  rect; not offered.
- *The guest check.* =check-web.lisp= has no calls section; the guest's QEMU sound
  card and the container's =/dev/snd= are what it would prove.

** 4.9 A loading page shows it: the strip under the toolbar
:PROPERTIES:
:CUSTOM_ID: loading-page-shows-strip
:END:

Headless Chrome draws no tab spinner or progress bar, so a link to a slow server
used to leave the old page on screen with no sign except =reload= turning into
=stop=. =Page.frameStartedLoading= arrives about 12 ms after the click and
=frameStoppedLoading= when the page has loaded, so the tab already knows
(=web-tab-loading=).

- *The strip.* A few pixels between toolbar and page
  ([[file:../initramfs/web.lisp::defun draw-web-progress][=draw-web-progress=]]): still while the page is, and while it loads a bar a third
  of its width slides across once every 1.2 s, in the accent colour.
- *Clock-driven.* The bar's place comes from the clock, so the whole pane and the
  strip drawn alone show the same picture.
- *Cheap.* While a page loads, =web-timeout= wakes the loop every 50 ms, and
  [[file:../initramfs/web.lisp::defun web-loop-service][=web-loop-service=]] paints only the strip, as a frame is painted ([[#event-loop-services][The event loop: services]]).

*Not covered:* a page's background requests (=fetch=, =XMLHttpRequest=), such as a
sign-in's "Next". They send no =Page= event; seeing them would need the =Network=
domain, an event per request, hundreds on big pages. Those pages draw their own
spinner.

=web-test= drives a real slow server: the strip still when loaded, lit within 200 ms
of the click, moving while the server hasn't answered, still again once loaded.

** 4.10 The pointer's shape follows the page
:PROPERTIES:
:CUSTOM_ID: pointer-s-shape-follows
:END:

A page says how the pointer should look over each of its parts with CSS =cursor=
(=pointer= over a link, =text= over text). Headless Chrome works it out but has no
pointer to draw, and the protocol has nothing that reports it: Chrome 148's
=/json/protocol= (56 domains) has no command or event whose definition mentions a
cursor. So the page reports it.

- *The script.* [[file:../initramfs/web.lisp::defparameter +web-cursor-js+][=+web-cursor-js+=]], installed like the pickers' ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]]), listens to
  =mousemove= in the capture phase. The moves are ours: [[file:../initramfs/web.lisp::defun web-hover][=web-hover=]] sends an
  =Input.dispatchMouseEvent= for every pointer move over the page. Each time the
  script reads =getComputedStyle(el).cursor= under the pointer and, when it differs
  from the last, calls the =__lolCursor= binding.
- *Resolving =auto=* (most of a page) as Chrome does: the I-beam over an editable
  field or over a text's characters (=caretRangeFromPoint=, and the point must lie on
  that text's boxes, since the caret lands in the nearest text even from blank space),
  the arrow elsewhere.
- *Our three shapes.* [[file:../initramfs/web.lisp::defun web-cursor][=web-cursor=]] maps =pointer= to the hand, =text= and
  =vertical-text= to the I-beam, everything else (=move=, =wait=, resize arrows) to
  the arrow, and draws it at once ([[file:framebuffer.org][framebuffer.org]], the pointer's shapes).
- *Off the page* (toolbar, another pane) =web-hover= gives the arrow back; during a
  press (a drag selecting text) nothing changes. Over a cross-site frame (no script of
  ours) the shape stays as it was.
- *Lost reports recover.* The page reports only /changes/, so a lost report would
  leave a wrong shape until the next change. When the pointer enters a page,
  =web-hover= first tells it to forget its last report (=__lolCursorReset=). A report
  from a page the pointer isn't over is ignored.

*Pitfall: live redefinition.* Chrome's event handler is the /symbol/ =web-event=,
looked up on every call, not the function object =#'web-event=. A function object
captured when Chrome starts would keep calling the old definition after =C-c C-c= or a
patch redefines it.

=web-test= checks: the hand over a link, the I-beam over a text field and over a
heading's characters, the arrow over the blank end of that heading's line and on the
toolbar, and a lost report recovered by leaving the page and coming back.

* 5. The event loop: services
:PROPERTIES:
:CUSTOM_ID: event-loop-services
:END:

The browser's loop ([[file:../initramfs/fb-browser.lisp][fb-browser.lisp]]) wakes for input, a running stage or a clock
deadline. A web page adds another reason: Chrome writes to a pipe whenever the page
changes, and the loop must wake for that without polling on a timer. =*FB-SERVICES*=
is the general mechanism; a service registers functions the loop calls by key:

| Key        | Called                                        | Web pane's                                                                             |
|------------+-----------------------------------------------+----------------------------------------------------------------------------------------|
| =:fd=      | before each poll; an fd to watch              | Chrome's reply pipe                                                                    |
| =:timeout= | before each poll; ms until it must run anyway | 10 ms while a resize is being sent, 100 ms while waiting for a first frame, else never |
| =:run=     | every turn, after input                       | pump the pipe, sync the screencast, decode the newest frame                            |
| =:motion=  | on a bare pointer move                        | hover: =mouseMoved= into the page                                                      |

When only the page's pixels changed, =:run= copies the new frame into the canvas and
sends just the page rectangle to the screen — the same economy as the pointer and
the systray clock. A scrolling page costs one JPEG decode and one rectangle, not a
full repaint. The input poll (=poll-input-once=) gives the services' fds the slots its
devices leave free.

- *The first frame is nudged.* Starting a screencast usually makes the page repaint.
  In about one run in twenty it didn't, and the pane stayed white, so a tab still
  without a frame 700 ms after its stream started gets one =Page.captureScreenshot=.
- *Nothing blocks.* Chrome takes about a second to start on the host and five in the
  guest. Every exchange is a chain of callbacks run as replies arrive; the pane says
  "starting Chrome ..." until then. Only =WEB-JS= (tests, the REPL) waits for an
  answer. From another thread (the net REPL) it sends with a callback and waits for
  the browser's loop to deliver the reply, because two threads reading one pipe would
  race.

* 6. Running it in the guest
:PROPERTIES:
:CUSTOM_ID: running-guest
:END:

** 6.1 Why a container

Chrome isn't one file. It needs a whole userland: 81 shared libraries
(=ldd /opt/google/chrome/chrome=), fonts and fontconfig, =/proc/self/exe= (it
re-executes itself for child processes), =/dev/shm=, and a writable =/tmp=. Our root
is a small initramfs with none of that. =lol-ct= runs a command with the host's
distribution (at =/mnt/host=) as its root, as the user, with our =/home=, =/tmp=,
=/dev= and network ([[file:containers.org][containers.org]]). =web.lisp= asks for that through
=container-command-line=, in a container of its own named =web=, so Chrome's writes
never mix with a project's container. Chrome's state lives in =/home= anyway ([[#profile-ours-default-yours][The profile: ours by default, yours if you choose]]).

The =/bin/sh= that moves the pipes ([[#pipe-socket][The pipe, not a socket]]) is therefore the host's, inside the
container. Our root has no shell, and that absence is how =web.lisp= tells it runs in
the image (=WEB-IN-GUEST-P=). On the host, Chrome starts directly.

** 6.2 Lifecycle

- *Lazily.* Chrome starts with the first web tab, not at boot.
- *If it dies*, every tab says so. =r= or a click restarts Chrome and reloads each tab
  at its last address.
- *At power-off*, =POWER-OFF= calls =WEB-SHUTDOWN= first. It sends =Browser.close=, so
  Chrome writes its profile while =/home= is still writable, and waits for it to exit
  before =RELEASE-DISK= remounts =/home= read-only.
- *Reaping.* A dead child stays a *zombie* (a process-table entry holding its exit
  status) until its parent waits for it, and orphans are handed to PID 1.
  =sb-ext:run-program= waits only for processes it started. Inside the container
  lol-ct's init is PID 1 of the pid namespace and reaps there. As a safety net,
  =WEB-REAP-ORPHANS= looks at every waitable child *without* reaping it (=waitid= with
  =WNOWAIT=) and reaps only the ones SBCL doesn't know, so =run-program='s exit codes
  are never stolen. check-web.lisp asserts no zombie is left after =WEB-SHUTDOWN=.

** 6.3 Memory

Measured in the guest (tag #26, QEMU, =-m 2048=, one simple page): Chrome's processes
total *436 MB PSS*, and =MemAvailable= went from 1890 MB to 1573 MB. PSS
("proportional set size") divides each shared page among the processes sharing it, so
per-process PSS adds up honestly; RSS would count the shared libraries again for every
process. 2 GB was enough for the checks. Heavy single-page apps use several times
this, as in any browser.

** 6.4 Chrome's sandbox works inside the container
:PROPERTIES:
:CUSTOM_ID: chrome-s-sandbox-works
:END:

Chrome confines its renderers (the processes running web pages' code) in a sandbox.
One layer is namespaces (a renderer sees no other process and has no network of its
own); the other is seccomp-BPF, a kernel filter on which system calls a process may
make. Both work unprivileged on a kernel with =USER_NS= and =SECCOMP_FILTER=, on since
tag #26.

Inside lol-ct, Chrome runs as PID 2 of its own pid namespace with =NO_NEW_PRIVS= and
no capabilities. =NO_NEW_PRIVS= is a prerequisite of seccomp, not an obstacle, and a
user namespace may create nested ones. So the sandbox stays: =*WEB-SANDBOX*= is
=:auto=, which passes no =--no-sandbox=. check-web.lisp opens =chrome://sandbox=,
Chrome's own report, and asserts its all-clear. In the guest: "Layer 1 Sandbox:
Namespace · PID namespaces: Yes · Network namespaces: Yes · Seccomp-BPF sandbox: Yes ·
Seccomp-BPF sandbox supports TSYNC: Yes · *You are adequately sandboxed.*"

=(setf *web-sandbox* nil)= passes =--no-sandbox=, for a kernel without those options.
Then a page that exploits a renderer bug runs with all of the user's rights.

* 7. Settings

All are =defvar=​s in =web.lisp=, set from the Workspace or an init file.

** 7.1 The engine and the window

- =*web-chrome-binary*= — ="/usr/bin/google-chrome"=, as seen *inside* the container
  (the host's root is its =/=). That's the alternatives link to
  =/opt/google/chrome/google-chrome=, a bash script that execs the real binary beside
  it.
- =*web-extra-args*= — more switches, e.g. ="--force-dark-mode"=.
- =*web-quality*= — the screencast's JPEG quality, 80.
- =*web-zoom*= — the page zoom, also set by =C-+=/=C--=/=C-0=.

** 7.2 Search

=*web-search*= is a =FORMAT= string, Google by default
(="https://www.google.com/search?q=~a"=). =WEB-URL-FOR= decides what you typed:

- *A URL.* Anything with =://= or a known scheme is used as it is.
- *A host.* Something shaped like one (=github.com/x=, =localhost:3000=,
  =10.0.2.2:8000/a=) gets a scheme: =http= for =localhost= and bare IPv4 addresses
  (where development servers live), =https= otherwise.
- *Words.* Anything else is percent-encoded and searched for.

** 7.3 The profile: ours by default, yours if you choose
:PROPERTIES:
:CUSTOM_ID: profile-ours-default-yours
:END:

A Chrome *profile* is the directory holding cookies (your logins), history, saved
passwords and cache. =*web-profile*= is =NIL= by default, meaning
=~/.lol/web/chrome/= (part of the [[file:session-persistence.org][=~/.lol/= tree]]): *our own* profile, separate from
the desktop Chrome's =~/.config/google-chrome=. Two reasons:

- *A profile is locked by the Chrome using it.* If the desktop Chrome is running, a
  second Chrome can't open its profile. In the image the desktop isn't running, so
  this bites only when both run at once (QEMU on a host desktop).
- *Its secrets may not decrypt here.* On Linux, Chrome encrypts cookie values and
  saved passwords with a key kept in the desktop keyring (the Secret Service, e.g.
  =gnome-keyring-daemon=). The image has no keyring, so we pass
  =--password-store=basic=, which keeps the key in the profile. A profile encrypted
  with the *keyring* key would open, but its logins would be unreadable: logged out
  everywhere. /Not tested/ against a real desktop profile's cookie database.

To try your own profile, with the desktop Chrome closed, evaluate
=(setf *web-profile* "/home/<you>/.config/google-chrome")= before the first web tab.
The lasting answer is to log in once in our profile; it persists in =/home= like any
other file.

** 8.1 What is asserted
:PROPERTIES:
:CUSTOM_ID: asserted
:END:

[[file:../poc/web-test.lisp][poc/web-test.lisp]] (host, =sbcl --script poc/web-test.lisp=) drives the host's Chrome
through the shell's own entry points (a press through the world to the page's pane,
=browser-key=, =browser-scroll=) and reads every answer back from the page with
=Runtime.evaluate=, never from pixels.

- *Basics.* Start and first page, a decoded frame, the title in the tab strip, the
  viewport equal to the pane, a link click, back, typing and Backspace.
- *Clipboard, find, download.* =C-a C-c= into =lol.clipboard=, =C-v= from it, =C-f=, a
  download into =~/Downloads= with its status line.
- *Tabs and addresses.* The wheel, a =target=_blank= link becoming a new tab with its
  own title and frame, closing that tab closing its Chrome page, =C-l= and typed
  addresses, =WEB-URL-FOR='s rules.
- *Everything in [[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]]–[[#pointer-s-shape-follows][The pointer's shape follows the page]].* Pickers (18 checks, with =*CHOOSER*= bound to a function
  that records what it was offered and answers, since the host has no modal loop),
  the user agent, zoom, calls, the loading strip, the pointer's shape; plus [[#pipe-socket][The pipe, not a socket]]'s
  write guard.
- *Output.* PPMs of three states in =poc/out/=.
- *Ruled out:* a =file://= page's =download= attribute is ignored by Chrome (a file
  URL is an opaque origin, so Chrome navigates to the file), which is why the test's
  download link is a =data:= URL.

[[file:../check-web.lisp][check-web.lisp]] (guest: =LOL_GUEST_HOSTROOT=1 LOL_PORT=4015 sbcl --script
check-web.lisp=) boots the image with the host's root shared in, serves two pages from
the host on =LOL_PORT=+1000 (QEMU's user network shows the host as =10.0.2.2=), and
drives everything with real QMP input:

- *Browsing.* =SuperL-b= held down, an address typed key by key, a click by relative
  pointer motion, =SuperL-Left=, typing into a field, wheel notches. It refocuses the
  test page's tab after checking that a tab with no URL shows the guide.
- *The real web.* =https://example.com= (DNS and TLS are Chrome's own, in the
  container) and =chrome://sandbox=.
- *A =<select>=* (optgroups, a disabled option, an =onchange= that writes the title):
  our chooser opens on the current option (read from =*CHOOSER-STATE*=; the
  screendump changes), Down skips the disabled one, Enter changes the value and runs
  =onchange=, Esc changes nothing, Space opens it from the keyboard. Whether Chrome's
  own popup stayed shut is asked only on the host: the net REPL's =WEB-JS= waits for
  the browser's loop, which is inside the modal chooser.
- *The address panel* ([[#address-prompt-knows-paths][The address prompt knows paths and your history]]): =/usr/sh= lists =/usr/share/= from the host's root,
  =Down= =Tab= takes it, =doc/= =Enter= opens Chrome's listing of =/usr/share/doc/=,
  and =C-n= =Enter= on "lol test" loads the test page from the history.
- *A torn-off window* ([[file:morphic.org::#tests][morphic.org, Tests]]): load, scroll, click, type, move the window;
  the frame and the input follow it.
- *Shutdown.* =WEB-SHUTDOWN= leaves no Chrome process and no zombie.

It needs a host with =/dev/kvm=; it can't run inside the environment's own container,
where QEMU's =fat:= drive puts a temporary file in =/var/tmp= (ignoring =TMPDIR=) and
the overlay answers EOVERFLOW. =LOL_QEMU_MEM= raises the guest's RAM; not needed.

* 9. Limits, and what is next
:PROPERTIES:
:CUSTOM_ID: limits-next
:END:

- *A page's sound* plays once Chrome is told the ALSA device ([[#video-calls-google-meet][Video calls: Google Meet, with screen sharing]], M1). Measured on
  real hardware, not yet in the guest. A page's video comes through the screencast
  like any other pixels, unsynchronised; a video file plays properly with the host's
  MPlayer (=play-video=, [[file:screencast.org][screencast.org]]).
- *Pickers* are ours for =<select>=, colour, date/time and =<datalist>= ([[#pickers-popups-screencast-cannot][Pickers: the popups the screencast cannot see]]), but not
  inside a cross-site iframe, where our page script never runs.
- *No file upload dialog.* =<input type=file>= opens nothing yet. The next step is
  =Page.setInterceptFileChooserDialog= plus a file-manager prompt.
- *No per-link right-click menu.* The right button shows the page's commands, not the
  link under the pointer. "Open in new tab" is =SuperL-click=.
- *Frame rate* is bounded by one decode and one blit per frame in Lisp; heavy pages
  don't scroll at 60 fps in the guest.
- *Hover* is sent on every bare pointer move, unthrottled. Chrome copes.
- *Non-ASCII typing* works: =fb-read-key= decodes the console's UTF-8, and a second
  layout is typed with Right Alt or Caps Lock ([[file:input.org::#tty-enough][input.org, Why the tty is not enough]], "Two layouts").
