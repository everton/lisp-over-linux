* 1. The decision: Chrome, headless, over the DevTools protocol

The appendix chose an architecture before it chose an engine: *headless + our own
blit*. The engine renders into memory and shows nothing. Our Lisp puts its pixels
on the screen, as one more pane. The Lisp stays the only process on =/dev/fb0=,
which [[file:processes.org][processes.org]] §1 requires. No GPU driver is needed and
no compositor.

It picked WPE WebKit to fill that shape. We use the same shape with a different
engine: *Google Chrome*, which is already installed on the laptop, at
=/usr/bin/google-chrome=, and which is the browser the user's web work is done in.
Chrome has a headless mode (=--headless=new=) that is the real browser with no
window. It also has a control protocol that already does everything the shape
needs. WPE would have needed C code against an API nobody here has read yet
(§A6, last paragraph).

The licence row is the honest cost. Chrome is not free software. We do not ship
it: the image *calls* the copy the user installed, from the host's own disk. That is
the same stance [[file:previews.org][previews.org]] takes for =libstbi.so=, one step
further: a host program, used at runtime, because writing our own is not
realistic (see =loc.sh=, which counts only what we wrote).

The appendix's checklists T1–T7 are still the right way to judge WPE, if that is
ever wanted. Nothing in §2–§6 below is Chrome-specific except the protocol, so
replacing the engine would replace =web-cdp.lisp= and keep the pane.

* 2. What the user sees

=SuperL-b= ("browse") opens a new tab with the address prompt in the minibuffer.
Type an address or some words and press Enter. The Spotter (=SuperL-Space=) offers
web rows too: "open URL" when the query looks like an address, "search the web" for
any other text, the open web tabs whose title or URL match, and pages from your
history (§4.6).

A web tab is an ordinary tab of the environment. Its label is the page's title, and
=SuperL-1…9=, =SuperL-Tab= and =SuperL-w= work on it like on any other. Inside it,
a toolbar shows back =<=, forward =>=, reload (or stop while loading) and the
address; clicking the address edits it. Below is the page.

Every =SuperL= key stays the environment's. Every other key belongs to the page,
=Tab=, =Esc=, =C-g=, =C-c= included, because the page is what you are typing into.
The exceptions in the table are the chords a desktop browser also keeps for itself.

*Alt-Left is not "back".* Every desktop browser uses it, so it was the first choice.
In the guest, check-web.lisp's back check failed and every check after it failed too.
The reason: the console keymap gives Alt-Left and Alt-Right to switching virtual
terminals. /Verified/ in =./linux/drivers/tty/vt/defkeymap.c_shipped=: =alt_map[105]=
and =alt_map[106]= (=KEY_LEFT=, =KEY_RIGHT=) are =0xf210= and =0xf211=, which are
=K_DECRCONSOLE= and =K_INCRCONSOLE= in =include/uapi/linux/keyboard.h=. The kernel
acts on them before any program sees a byte. So the guest had switched to another
VT, and the later keys went there. =SuperL-Left/Right= are back and forward instead;
=M-Left/Right= still work wherever they arrive. Since 2026-10-18 that includes the
guest: the environment rebinds Alt-Left/Right to the plain cursor keys for Org's
promote / demote, so they arrive as =ESC [ 1 ; 3 D= / =C= and no longer switch VTs
([[file:input.org][input.org]] §1, "Alt with the arrows").

* 3. How it works

** 3.1 The DevTools protocol

Chrome's developer tools (the panel you open with F12) control the browser through
a protocol of their own: the *Chrome DevTools Protocol*, CDP. It is plain JSON. We
send a *command*:

#+begin_src js
{"id": 7, "method": "Page.navigate", "params": {"url": "https://example.com"}}
#+end_src

Chrome answers with a *response* carrying the same id, ={"id":7,"result":{...}}= or
={"id":7,"error":{...}}=. It also sends *events* whenever it likes, with no id:
={"method":"Page.frameNavigated","params":{...}}=. That is the whole grammar. The
vocabulary is a few hundred methods grouped into domains (=Page=, =Input=,
=Target=, =Runtime=, =Emulation=, =Browser=), documented at
https://chromedevtools.github.io/devtools-protocol/. Puppeteer and Playwright, the
usual browser-automation libraries, are built on it. =web-cdp.lisp= is our much
smaller equivalent, with a JSON reader and writer limited to what this traffic uses.

** 3.2 The pipe, not a socket

Chrome usually serves CDP on a TCP port, over a WebSocket. Started with
=--remote-debugging-pipe=, it uses two inherited *file descriptors* instead. A file
descriptor is a small integer naming an open file or pipe in a process: 0 is
stdin, 1 is stdout, 2 is stderr. Chrome reads commands from fd 3 and writes replies
and events to fd 4. Each message ends with a NUL byte, which can never occur inside
JSON text, so it marks message boundaries unambiguously.

This needs no HTTP, no WebSocket framing, and opens no port another program could
connect to. The one difficulty is getting the pipes onto fds 3 and 4.
=sb-ext:run-program= gives a child fresh pipes on its stdin and stdout only. So we
start a shell that moves them before it becomes Chrome
([[file:../initramfs/web-cdp.lisp::defun pipe-wrapper][=pipe-wrapper=]]):

#+begin_src sh
exec 3<&0 4>&1 >>/tmp/lol-chrome-1.log 2>&1 </dev/null; exec google-chrome --headless=new --remote-debugging-pipe ...
#+end_src

=3<&0= makes fd 3 a copy of stdin, our command pipe. =4>&1= makes fd 4 a copy of
stdout, our reply pipe. Chrome's own messages then go to a log file, so they can
never interleave with the protocol. Our end of the reply pipe is non-blocking:
=web-cdp.lisp= reads whatever is there and never waits on it.

Since 2026-10-17 the *command* pipe is non-blocking too. A Chrome that stops
reading (hung, or stopped) fills its 64 KB, and the writer is the environment's
thread, so a blocking write froze the screen. [[file:../initramfs/web-cdp.lisp::defun cdp-write-octets][=cdp-write-octets=]] now waits at most
=+cdp-write-seconds+= (5) for room. After that it closes the pipe: half a message has
corrupted the stream anyway. Chrome exits when its command pipe closes, so the pane
reports "Chrome exited" and =r= restarts it. =poc/web-test.lisp= asserts it with a
child process that never reads its stdin.

** 3.3 Tabs, sessions, and frames

One Chrome process holds many tabs. In CDP a tab is a *target*. =Target.createTarget=
makes one, and =Target.attachToTarget= with =flatten: true= returns a *session id*.
After that, a command meant for that tab carries ="sessionId"= beside ="method"=, and
every event from that tab carries it too. One pipe, many tabs, told apart by one
string.

Pixels come from *screencasting*. =Page.startScreencast= asks Chrome to send a
=Page.screencastFrame= event whenever the page repaints. The event holds the frame
as a JPEG, base64-encoded (JSON strings cannot carry raw bytes; base64 spells every
3 bytes as 4 letters). We answer each frame with =Page.screencastFrameAck=, and
Chrome does not send the next frame until it gets that ack. This is the protocol's
*flow control*: a slow reader (us, under QEMU) gets fewer frames, not a growing
backlog. A page that does not change sends nothing, so an idle tab costs no CPU.

Each frame is decoded the way an image preview is: base64, then the JPEG through
stb_image ([[file:previews.org][previews.org]]), into the canvas's own =#x00RRGGBB=
pixels. Only the newest frame is decoded. A frame replaced before we drew it is
dropped undecoded.

The pane's size becomes the page's: =Emulation.setDeviceMetricsOverride= lays the
page out as if the window were exactly the pane, and the screencast is restarted at
that size. When the pane changes size (another font, a different screen), the next
draw records the new size and the next turn resends both. Zoom is the
=deviceScaleFactor= of the same call, so =C-+= re-lays-out and re-rasterises the
text larger. It does not enlarge a picture. The screencast does not follow that
factor, though, which needs a step of its own (§4.7).

Only the tab on screen streams. When you switch to another tab, =Page.stopScreencast=
stops the one you left.

*The tab on screen is also Chrome's foreground page* (2026-10-16). With no window,
headless Chrome still keeps one page "in front", the newest unless told otherwise,
and only that one runs its compositor. A page behind it takes clicks and keys,
because the main thread handles those, but a =mouseWheel= sent to it never
completes, so the page never scrolls. Its frames also come back seconds late. So a
tab that starts streaming is first made the front page with =Target.activateTarget=
([[file:../initramfs/web.lisp::defun web-activate][=web-activate=]]). Found by =check-web.lisp=. Since 2026-10-13 it opened a second
tab, the guide, and left it in front. Reproduced against the host's Chrome 148 with
a pipe-driven script: after a second =createTarget=, the wheel on the first page
hung; after =activateTarget=, it scrolled 100 px. In the guest the latency from
input to the next frame fell from 2.4–43 s to 20–96 ms.

** 3.4 Input

A click becomes =Input.dispatchMouseEvent=: a =mousePressed=, then a =mouseReleased=
when the button comes up, with the point converted to the page's CSS pixels. A drag
sends =mouseMoved= with the button held, so text selection and sliders work. A bare
pointer move is sent too, for hover menus. A touchpad tap has no release of its own,
so it is sent as press and release together. The wheel becomes a =mouseWheel= of
100 CSS pixels per notch, Chrome's own step on Linux, at the pointer's position, so
the page scrolls whatever is under it.

A key becomes =Input.dispatchKeyEvent=, a =keyDown= and a =keyUp=, filled in the way
the page's =KeyboardEvent= expects. =key= is what the key means (="a"=, ="Enter"=).
=code= is which physical key it is (="KeyA"=). =windowsVirtualKeyCode= is the old
numeric code many sites still read. =text= is present only when the key inserts
something: a keyDown with text types a character; one without (=C-a=, an arrow) is a
command. The modifiers map Shift, Ctrl and Alt to CDP's bits 8, 2 and 1.

Paste uses =Input.insertText=, which inserts a whole string the way an input method
commits text.

* 4. The pane in the shell

** 4.1 A tab is a trail

=SUBJ-WEB= is a subject like a folder or a definition. =present= gives a view of kind
=:web= whose data is the =WEB-TAB=, so the tab strip, the right-button menu (from
=commands-for=), the halo and the Spotter's recents all work without knowing what a
web page is.

Each web tab is its own trail, so it gets its own tab in the strip. Closing it needs
no hook in the shell. On every turn, =WEB-COLLECT-TABS= closes the Chrome page of any
web tab that no trail holds any more. A link that opens a new window
(=target=_blank=, =window.open=, Ctrl-click) arrives as a =Target.targetCreated= event
with an /opener/, and becomes a new trail. The opener test matters: Chrome also
reports pages that already exist, its own startup =about:blank= among them, and those
must not become tabs.

The page title comes from =Target.targetInfoChanged=, and also directly from
=document.title= whenever a load finishes. The second source exists because for a
=file://= page Chrome 148 kept reporting the file name as the title (found by
poc/web-test.lisp).

*The home page is the project's guide* (2026-10-13). A tab opened without a URL
loads =doc/guide/index.html= ([[file:../initramfs/web.lisp::defun web-home-url][=web-home-url=]]). The build freezes the guide's path into the
image the way [[file:../initramfs/sbcl-source.lisp][=sbcl-source.lisp=]] freezes =./sbcl='s: =web.lisp= is loaded from
=<repo>/initramfs/=. On the laptop the repo is at the same path under the mounted
=/home=, and Chrome's container sees that =/home= too. A diskless boot has no
=/home=, so the file is missing there and the tab gets =about:blank=. Setting
=*web-home*= to a URL overrides both. The address prompt opens empty on the home
page, as on =about:blank=. Before this fix it was pre-filled with the guide's URL,
so a typed address was appended to it — which is how =check-web.lisp= caught it.

** 4.2 Copy and paste go through our clipboard

Headless Chrome keeps its clipboard inside its own process, where nothing else can
paste from it. So =C-c= asks the page for its selection (the selection inside a
focused text field, which =getSelection()= alone does not see, else the document's)
and puts it in =lol.clipboard='s history ([[file:clipboard.org][clipboard.org]]). The
key is also sent on to the page, so a site with its own copy handler still sees it.
=C-v= types our newest clipboard entry. Selecting text with a drag puts it in
PRIMARY when the button comes up, as everywhere else in the environment, so a middle
click can paste it into the Workspace.

The address prompt (=C-l=) is our minibuffer, not the page, so it pastes from our
clipboard too: =C-y=, =C-v= or Shift-Insert insert the newest entry with newlines and
tabs made spaces (=minibuffer-paste-text=, so a URL copied with its line break pastes
clean). =C-u=, or the =✕ clear= button drawn at the prompt's right while it holds
text, empties it.

** 4.3 Downloads, dialogs, find

- *Downloads* go to =~/Downloads= under their own names
  (=Browser.setDownloadBehavior=), and the status line reports progress and the
  result. =/home= is the laptop's own, so a download is a real file on the disk.
- *alert(), confirm(), prompt()* freeze the page until they are answered. They are
  answered in the minibuffer at once: Enter is OK (with the typed text, for a
  prompt), =C-g= is Cancel.
- *Find* is the page's own =window.find=, re-run as you type.

** 4.4 Pickers: the popups the screencast cannot see

*The symptom* (on the laptop, 2026-10-13): click a =<select>= in a web page and no
list of options appears. The page does not seem to react at all.

*Why.* A =<select>='s list is not drawn by the page. On a desktop the browser shows
it in a little borderless window of its own, a *popup widget*, so that it can hang
below the bottom of the page or past the window's edge. Inside Chrome a popup widget
is a separate renderer widget with its own *compositor frame*. (A compositor frame is
one finished picture of one surface; Chrome's compositor stacks them to make what a
window shows.) =Page.startScreencast= sends us the *page's* compositor frames only
(§3.3). Headless, nothing stacks the popup's frame on top, because there is no
window. So the popup opens, takes the keyboard, and is never in any frame we
receive.

/Verified/ in the guest (Chrome 148.0.7778.215, tag #27, before the fix): after a
real QMP click on a select, =select.matches(':open')= was =true=; the newest
screencast frame held *0* pixels of the popup's highlight blue; a
=Page.captureScreenshot= taken at the same moment held *2809*, because that command
does composite popups. Arrow keys then still worked, but blind: Down and Enter
changed the value through a list nobody could see. The host's Chrome behaves the
same.

The same probe looked at the other controls that use browser UI:

| Control                                                        | Headless Chrome 148                                                                                | What we do                                                                                                                                    |
|----------------------------------------------------------------+----------------------------------------------------------------------------------------------------+-----------------------------------------------------------------------------------------------------------------------------------------------|
| =<select>= (single, size ≤ 1)                                  | an invisible popup that takes the keys                                                             | our chooser (below)                                                                                                                           |
| =<input type=color>=                                           | an invisible colour chooser, opened on /click/; it took every following key                        | the minibuffer asks for =#rrggbb=                                                                                                             |
| =<input type=date>=, =time=, =datetime-local=, =month=, =week= | no picker at all: the calendar icon does nothing                                                   | the minibuffer asks for the value (=yyyy-mm-dd= …); typing digits into the field also works, and is visible, because the field itself is page |
| =<input list=…>= with a =<datalist>=                           | no visible suggestions; once typing opened them, they swallowed the arrow keys (=Esc= closed them) | our chooser, on Down / Alt-Down / a click on the field's arrow                                                                                |

*How we draw them.* Three pieces, all in [[file:../initramfs/web.lisp::defparameter +web-picker-js+][=web.lisp='s "pickers" section]]:

1. *A page script* (=+WEB-PICKER-JS+=) is installed into every document the tab
   will load (=Page.addScriptToEvaluateOnNewDocument=) and, once, into the one it
   already has. It listens on =window= in the *capture phase*. DOM events travel
   from the window down to the target (capture), then back up (bubble); a capture
   listener on =window= runs before any of the page's own handlers and before the
   browser's default action. On a =mousedown= on a select (or Space, Enter, Alt-Down
   or F4 on a focused one) it calls =preventDefault()=, so Chrome never opens its
   popup, and reports the control: an id (a counter kept in a =WeakMap=, so the
   page's elements are not marked), its box in CSS pixels, and its options (label,
   value, disabled, the =<optgroup>= label, which one is selected). A colour input
   also has its =click= cancelled, because that is when its chooser opens. A
   datalist input loses its =list= attribute while it has focus (it is put back on
   blur): Chrome offers suggestions only to a focused input that has one, so its
   invisible list can never open.
2. *A binding* carries the report. =Runtime.addBinding= puts a function on the
   page's =window=; each call of it becomes a =Runtime.bindingCalled= event on our
   pipe, with one string (here, JSON) and the *execution context* it came from
   (each frame of a page has its own JavaScript world, its own context). The event
   is sent only while the Runtime domain is enabled. The first host run forgot
   =Runtime.enable=: the script cancelled the click and its report went nowhere.
3. *Our chooser.* The event is queued and, after the pipe has been read, shown by
   =WEB-PICK=. A list goes to the *right-button menu's card*, the same
   =RUN-CHOOSER= ([[file:../poc/overlays.lisp::defun run-chooser][poc/overlays.lisp]]; =RUN-CHOOSER-FB= until Morphic step 4)
   with a kind of its own, =:select=: placed under the control (CSS pixels times
   =*web-zoom*= plus the page's origin on screen, the mapping =WEB-PAGE-POINT=
   inverts), at least as wide as it, opening on the current option, the optgroups as
   section headers, disabled options dim and never landed on. Up/Down, Home/End,
   PageUp/PageDown move; typing jumps to the next option starting with what was typed
   (letters typed within a second accumulate); Enter, Space or a click picks; Esc,
   =C-g= or a click outside leaves it unchanged. The answer goes back with
   =Runtime.evaluate= *in the reporting frame's context*: the script's
   =__lolPickerApply= sets =selectedIndex= (checked against the option's value, in
   case the list changed meanwhile) and fires =input= and =change= with
   =bubbles: true=, which is what a real choice fires. Colour and date go to the
   minibuffer instead, pre-filled with the current value, and the page refuses a
   malformed one (we say so in the status line).

Why queue rather than open the chooser inside =WEB-EVENT=: the chooser is *modal*.
It runs its own input loop until you choose. =WEB-EVENT= is called from inside
=CDP-PUMP='s loop over the messages just read, so a modal loop there would leave
the rest of that batch undelivered until you chose. While the chooser is up the
pipe is not read at all. That is harmless: Chrome sends the next frame only after
the last one is acked (§3.3).

The press that opened the select is released to the page (=WEB-FINISH-PRESS=)
before the chooser comes up, because the chooser's own loop will eat the real
release.

*What is still not covered:*

- A =<select>= inside a *cross-site iframe*. Chrome runs such a frame in a process of
  its own, as a separate target we never attach to, so our script is not in it and its
  popup is still invisible. Same-site iframes work: the box is shifted by each
  enclosing frame's position.
- =<select multiple>= and =size= > 1 are drawn by the page itself as a list box,
  so they need nothing and are left alone.
- The page's own JavaScript sees =input.list= as =null= while a datalist input has
  focus.
- =<input type=file>= is a different mechanism (a file chooser dialog, §9).

** 4.5 Saying we are Chrome: the user agent and its client hints

Headless Chrome's user agent contains =HeadlessChrome=, and some sites refuse or
degrade a browser that says so. Since the first version, =web-chrome-ready= removes
the "Headless" and sends the result with =Emulation.setUserAgentOverride=.

That was half the job. Google's sign-in still refused us with "This browser or app
may not be secure". A modern Chrome describes itself twice: the =User-Agent= string,
and the /User-Agent Client Hints/ (the =Sec-CH-UA*= request headers, and
=navigator.userAgentData= for scripts). Overriding the string *alone* leaves the
hints empty: no brands and no =Sec-CH-UA= header. A Chrome with no client hints is a
known sign of an automated browser. This was found in a session run inside the
environment, against Chrome 148.

So [[file:../initramfs/web.lisp::defun web-ua-metadata][=web-ua-metadata=]] builds the =userAgentMetadata= that goes with the string,
as a desktop Chrome on Linux sends it:
- the brands =Chromium=, =Google Chrome= and the "GREASE" brand =Not/A)Brand= (a
  deliberately odd name that keeps servers from hard-coding the list);
- the full version, taken from =Browser.getVersion='s =product=
  (="HeadlessChrome/148.0.7778.215"=) into =*web-chrome-version*=;
- the platform: Linux, x86, 64-bit, not mobile.

Every new tab gets the string and its hints together.

That was still not enough. /Reported 2026-10-20: Google search kept asking for a

** 4.6 The address prompt knows paths and your history

/Asked for 2026-10-20: "if I start typing / or ~/ it can infer I'm looking for a file
and allow me to use TAB to complete, and/or open a file-manager experience at the
bottom of the window. A similar approach for navigation history."/

=C-l= opens the same one-line minibuffer as before, and a *candidate panel* now sits
on top of it, over the bottom of the screen. What the panel lists depends on the
first characters typed:

| You type                              | The panel lists                                                              | Enter on the line          |
|---------------------------------------+------------------------------------------------------------------------------+----------------------------|
| =/=, =~/=, =./=, =../= or =file://=   | the folder you are in, like a small file manager: folders first, then files with size and date; what you typed of the name lights up | opens it as a =file://= URL |
| anything else                         | your history: pages whose address or title contain every word typed           | an address, or a search    |
| nothing (a new tab)                   | the most recent pages                                                         | the home page              |

Nothing is chosen until you move into the list, so Enter keeps doing what it did:
it opens what you typed. The keys:

| Key                        | Does                                                                         |
|----------------------------+------------------------------------------------------------------------------|
| =Down= / =C-n=             | choose a row (the first, from the line)                                       |
| =Up= / =C-p=               | the row above; above the first, back to the typed text                        |
| =Enter=                    | open the chosen row, else the typed text                                      |
| =Tab=                      | the chosen row into the line, to keep typing; with no row, complete like a shell (common prefix, a folder gets its =/=) |
| =M-Backspace=              | delete the last word, i.e. go back up one folder                              |
| =Shift-Delete=             | forget the chosen page (history rows only)                                    |
| a click / the wheel        | open a row / move the choice                                                  |

So a folder is browsed with Tab: =~/= lists your home, =Doc= =Tab= gives
=~/Documents/= and the panel lists inside it, =Down= =Tab= enters the chosen
sub-folder, and =Enter= on a file opens it. =Enter= on a folder opens Chrome's own
listing of it. A typed path is now always a file: before this, =/etc/hosts=
became a web search.

*The panel is generic.* Any prompt can have one: [[file:../poc/shell.lisp::defun minibuffer-read][=minibuffer-read=]] takes
=:candidates=, a function from the text to a list of plists (label, detail, the text
the row stands for, a section, a "forget" function) and a title. The panel is a
morph of the desk, [[file:../poc/morphic.lisp::defclass minibuffer-panel][=minibuffer-panel=]], and not of the shell. That way the panes under
it keep their size: a web page is not resized because you typed into its address
bar. =desk-sync= adds it, sizes it and removes it with the list. It is not an
overlay, because the keys stay the minibuffer's. The web pane's candidates come
from [[file:../initramfs/web.lisp::defun web-address-candidates][=web-address-candidates=]].

*The history is ours, not Chrome's.* Chrome keeps one in an SQLite file inside the
profile, and reading it would need an SQLite reader. [[file:../initramfs/web.lisp::defun web-history-note][=web-history-note=]] keeps
one plist per URL (=:url :title :visits :last=, newest first, at most 2000) in
=~/.lol/web/history.lisp=, mode 0600. A visit is counted on Chrome's
=Page.frameNavigated= for the main frame and on =Page.navigatedWithinDocument= (a
single-page app's =pushState=, e.g. the next YouTube video); the title is filled in
when the page says it. =about:=, =data:=, =chrome:= and =javascript:= URLs and the
home page are not kept. The file is written atomically and fsync'd, at most every
10 s and when Chrome is shut down at power-off. A crash can lose the last few seconds
of history and nothing else. A diskless boot keeps it in memory.

How matches are ranked, in [[file:../initramfs/web.lisp::defun web-history-matches][=web-history-matches=]]: every word must occur in the URL or
the title, ignoring case. Then a blend of recency and frequency (Firefox calls this
"frecency"): each visit counts as a day more recent, up to a month's worth, and a
page whose address /starts/ with the first word (=git= for =github.com=) comes before
the rest. The Spotter uses the same function: its web rows now include up to five
history pages that no open tab shows.

*Where a file is, depends on who looks.* The panel lists files as the environment
sees them, but Chrome opens them inside its container ([[file:containers.org][containers.org]]), whose root
is the host's Debian. The two agree only under the folders =lol-ct.c= binds in:
=/home=, =/tmp=, =/dev=, =/sys=. Without care, =/usr/= would list the initramfs's
few files while Chrome opened the host's. So in the guest, an absolute path outside
those folders is listed from =/mnt/host=, our mount of the host's root
([[file:../initramfs/web.lisp::defun web-chrome-root][=web-chrome-root=]]). The rows still read =/usr/share/=, as Chrome names them. The
container's overlays can add files that =/mnt/host= does not show; for a listing that
is close enough. On the host, both run in the same root and nothing is mapped.

** 4.7 Page zoom fills the pane: upscale, then sharpen

/Reported 2026-10-20: "when I zoom, the web browser reduces the visible area of the
page and leaves a lot of white space around it."/ The environment's own scale
(=SuperL-==) was never the cause: a bigger font only shortens the page by the toolbar's
growth, and the frame follows. The page zoom was. Measured against the host's
Chrome 148, with a 1256 x 677 pane:

| Page zoom | Chrome's CSS viewport | Screencast frame | Screenshot   |
|-----------+-----------------------+------------------+--------------|
| 100%      | 1256 x 677            | 1256 x 677       |              |
| 125%      | 1004 x 541            | *1004 x 541*     |              |
| 150%      | 837 x 451             | *837 x 451*      | 1256 x 677   |

=C-+= zooms the way Chrome's own =Ctrl-+= does (§3.3): the page is laid out in fewer
CSS pixels and drawn at 1.5 device pixels each, so =window.innerWidth= shrinks and a
narrow layout can kick in. But a /screencast/ frame comes at CSS-pixel size, because
Chrome ignores the scale factor there, and the frame was blitted 1:1. So the page
filled two thirds of the pane, and the rest was the blit's white. Clicks were
off too: input was mapped through the zoom, the picture was not. A /screenshot/
(=Page.captureScreenshot=) does come at device size, but took 46–55 ms per frame on
the dev laptop. Too slow to take for every frame while you scroll.

So each zoomed frame is scaled up at once, and replaced once the page is still
([[file:../initramfs/web.lisp::defun web-sharpen][=web-sharpen=]]):

1. *Upscale.* [[file:../initramfs/web.lisp::defun web-upscale][=web-upscale=]] stretches a CSS-sized frame to the pane, bilinear: each
   output pixel is a weighted mix of the four source pixels around where it falls,
   in 16.16 fixed point. 13 ms for 837 x 451 -> 1256 x 677 on the host. The pane is
   full at once, slightly soft.
2. *Sharpen.* When no frame has come for 150 ms, one screenshot replaces it, crisp.
   It is dropped if a newer frame arrived while it was being taken: a page that moved
   on keeps its newer frame and is sharpened when it stops again. The poll loop's
   timeout ([[file:../initramfs/web.lisp::defun web-timeout][=web-timeout=]]) wakes us when one is due, so nothing spins.

Chrome renders =floor(1256 / 1.5)= = 837 CSS pixels, so a 150% screenshot is
1255 x 676, one pixel short each way. [[file:../initramfs/web.lisp::defun web-pad][=web-pad=]] repeats the last column and row
rather than resampling, which would blur the crisp picture the screenshot was taken
for.

/Ruled out, measured the same day:/ =setDeviceMetricsOverride='s =scale= parameter
changes nothing in the frames. CSS =zoom= on the page's root element gives full,
crisp frames at no cost, but it is not Chrome's zoom: the page still sees the
full-width viewport, so a narrow layout never kicks in. It was declined for that.
Tests: =poc/web-test.lisp= (=C-+ C-+= gives =devicePixelRatio= 1.5 and a narrower
viewport; the pane is full at once and soft, then full and sharp; =C-0= back; the
upscaler's edges exact).

*** What a call needs, against what our Chrome had

| Share         | =getDisplayMedia()=      | anything to capture: headless has no display, and the picker is never shown     | our canvas (M5)              |

*** M1. Sound and the microphone — measured, then two switches

Measured with a page on =https://example.com= and Chrome's switches varied

- With no switch, a played tone leaves the card's playback =closed=
  (=/proc/asound/card0/pcm0p/sub0/status=), and =getUserMedia= fails with
  =NotReadableError: Could not start audio source=. Chrome's log says why:
  =PcmOpen: default,Host is down=. Debian's Chrome tries PulseAudio, finds no
  server, falls back to ALSA as expected, and ALSA's =default= is PipeWire's plugin,

- With =--alsa-output-device=plughw:0,0 --alsa-input-device=plughw:0,0= the tone's

So [[file:../initramfs/web.lisp::defun web-chrome-argv][=web-chrome-argv=]] passes both switches, with the device from
[[file:../initramfs/web.lisp::defun web-audio-device][=web-audio-device=]]: =plughw:0,0= (the card itself, as the recorder uses it), unless a
sound server is running (a socket at =$XDG_RUNTIME_DIR/pipewire-0= or =pulse/native=:

*** M2. Permissions — our prompt, Chrome's grant

Without a window Chrome cannot ask "allow microphone?". Measured: a =getUserMedia=
nobody answers is refused at once with =NotAllowedError= (it does not wait). What
works is =Browser.grantPermissions= for the page's origin, after which
=navigator.permissions= says =granted= and the call goes through.

So a page script ([[file:../initramfs/web.lisp::defparameter +web-media-js+][=+web-media-js+=]], installed into every document as the pickers'
script is, §4.4) wraps =navigator.mediaDevices.getUserMedia=: it asks us first,
through a binding, and calls Chrome's own function only after the answer.
[[file:../initramfs/web.lisp::defun web-ask-media][=web-ask-media=]] asks you in the minibuffer: "meet.google.com wants your microphone and
camera: y allow · a always · n no". =y= grants the origin until Chrome exits; =a=
also writes it to =~/.lol/web/permissions.lisp= (0600), granted again at every start
of Chrome; =n= or =C-g= refuses with =NotAllowedError=, as a refusing user would. A
page with no origin (a =file:= page's is ="null"=) is refused without asking: a grant
there would be a grant to every origin. Two facts about the grant: it lasts only as
long as Chrome, and it /replaces/ an origin's set, so [[file:../initramfs/web.lisp::defun web-grant][=web-grant=]] always sends the
union of what the origin has.

*** M5. Sharing the screen — our canvas as a screen

Chrome cannot capture what it cannot see, so the page is handed a picture of our
screen as if it were one:

1. The same page script replaces =getDisplayMedia=. After you answer "y share the
   whole screen", it makes a canvas the screen's size and returns
   =canvas.captureStream()=; the track says =displaySurface: monitor= to pages that
   look, and stopping it tells us. Meet's /Present now/ sends that canvas.
2. We paint the canvas through the DevTools pipe we already hold, with
   =Runtime.evaluate= calling the page's =__lolShare.put=. What goes is only what
   changed: [[file:../initramfs/web.lisp::defun web-share-note][=web-share-note=]] is one of =*frame-taps*= (fb-browser.lisp, the
   recorder's hook made a list), told the rects of every repair; a full frame, or
   more than 32 rects, sends the whole screen. The pointer is drawn by the page over
   a copy, since our pointer is never in the canvas (fb-browser.lisp draws it
   straight to the screen).
3. Three bytes of colour are exactly four base64 characters, so
   [[file:../initramfs/web.lisp::defun web-share-message][=web-share-message=]] turns each pixel into four octets of the message with no
   carrying between pixels, building the whole message as octets
   (=cdp-send-built=, web-cdp.lisp) instead of through =json-string=.
4. At most =+web-share-fps+= (10) updates a second, and the next waits for the
   page's answer to the last: the screencast's flow control, run the other way.

Measured on the laptop (Chrome 148, =poc/web-test.lisp=): a whole 1920 x 1200 screen
is 8.8 MB, 32 ms of the environment's thread to encode and write, and the page
answers about 190 ms later (its decode; =Uint8Array.fromBase64= took that from 208 to

=SHARING meet.google.com=, in red; the web tab's menu has "Stop sharing the screen",
and Meet's own "Stop presenting" works too (the track's =ended= event fires).

* 5. The event loop: services

The browser's loop ([[file:../initramfs/fb-browser.lisp][fb-browser.lisp]]) used to wake
only for input, a running stage, or a clock deadline. A web page adds another
reason: Chrome writes to a pipe whenever the page changes, and the loop has to wake
for that without polling on a timer. =*FB-SERVICES*= is the general mechanism. A
service registers functions the loop calls by name:

| Key        | Called                                        | Web pane's                                                                             |
|------------+-----------------------------------------------+----------------------------------------------------------------------------------------|
| =:fd=      | before each poll; an fd to watch              | Chrome's reply pipe                                                                    |
| =:timeout= | before each poll; ms until it must run anyway | 10 ms while a resize is being sent, 100 ms while waiting for a first frame, else never |
| =:run=     | every turn, after input                       | pump the pipe, sync the screencast, decode the newest frame                            |
| =:motion=  | on a bare pointer move                        | hover: =mouseMoved= into the page                                                      |

When only the page's pixels changed, =:run= copies the new frame into the canvas
and sends just the page rectangle to the screen. This is the same economy the
pointer and the systray clock already use, so a scrolling page costs one JPEG decode
and one rectangle, not a full repaint. The input track's poll
(=poll-input-once=) gives the services' fds the slots its devices leave free.

Two smaller things in this layer:

- *The first frame is nudged.* Starting a screencast usually makes the page repaint,
  which sends the first frame. In about one run in twenty of poc/web-test.lisp it did
  not, and the pane stayed white. So a tab still without a frame 700 ms after its
  stream started gets one =Page.captureScreenshot= to show in the meantime.
- *Nothing blocks.* Starting Chrome takes about a second on the host and five in the
  guest. So every exchange is a chain of callbacks, run as the replies arrive, and
  the pane says "starting Chrome ..." until then. Only =WEB-JS=, for tests and the
  REPL, waits for an answer. When called from another thread (the net REPL), it sends
  with a callback and waits for the browser's loop to deliver the reply, because two
  threads reading one pipe would race.

* 6. Running it in the guest

** 6.1 Why a container

Chrome is not one file. It needs the host's whole userland: 81 shared libraries
(=ldd /opt/google/chrome/chrome= on the dev host), fonts and fontconfig, =/proc/self/exe= (it re-executes itself for its
child processes), =/dev/shm= for shared memory, and a writable =/tmp=. Our root is a
small initramfs with none of that. The containers track built exactly what is
needed: =lol-ct= runs a command with the host's Debian (at =/mnt/host=) as its root,
as the user, with our =/home=, =/tmp=, =/dev= and network
([[file:containers.org][containers.org]]). =web.lisp= asks for that through
=container-command-line=, in a container of its own named =web=, so that Chrome's
writes never mix with a project's container. Chrome's state lives in =/home= anyway
(§7.3).

The =/bin/sh= that moves the pipes (§3.2) is therefore the host's, inside the
container. Our root has no shell of its own, and that absence is also how =web.lisp=
tells that it runs in the image (=WEB-IN-GUEST-P=). On the host, Chrome starts
directly.

** 6.2 Lifecycle

- *Lazily.* Chrome starts with the first web tab, not at boot.
- *If it dies*, every tab says so. =r= or a click restarts Chrome and reloads each tab
  at its last address.
- *At power-off*, =POWER-OFF= calls =WEB-SHUTDOWN= first. That sends =Browser.close=,
  which lets Chrome write its profile while =/home= is still writable, and then
  waits for it to exit before =RELEASE-DISK= remounts =/home= read-only.
- *Reaping.* When a process dies, its children are handed to PID 1. A dead child
  stays a *zombie* (a process-table entry holding its exit status) until its parent
  waits for it. =sb-ext:run-program= waits only for processes it started. Inside the
  container this is not our problem: lol-ct's init is PID 1 of the container's pid
  namespace and reaps there. As a safety net for a Chrome started any other way,
  =WEB-REAP-ORPHANS= looks at every waitable child *without* reaping it
  (=waitid= with =WNOWAIT=) and reaps only the ones SBCL does not know. That way
  =run-program='s exit codes are never taken from it. check-web.lisp asserts that
  no zombie is left after =WEB-SHUTDOWN=.

** 6.3 Memory

Measured in the guest (tag #26, QEMU, =-m 2048=, with one simple page): Chrome's
processes total *436 MB PSS*, and =MemAvailable= went from 1890 MB to 1573 MB. PSS
("proportional set size") divides each shared page among the processes sharing it,
so per-process PSS adds up honestly; RSS would count the shared libraries again for
every process. 2 GB was enough for the checks, and =-m 4096= was not needed. The
laptop has far more. Heavy single-page apps will use several times this; that is
the norm for any browser.

** 6.4 Chrome's sandbox works inside the container

Chrome confines its renderers, the processes that run web pages' code, in a sandbox
of their own. One layer is namespaces (a renderer sees no other process and no
network of its own); the other is seccomp-BPF, a kernel filter on which system calls
a process may make. Both work without privileges on a kernel with =USER_NS= and
=SECCOMP_FILTER=, both of which are on since tag #26.

Inside lol-ct, Chrome runs as PID 2 of its own pid namespace with =NO_NEW_PRIVS= and
no capabilities. =NO_NEW_PRIVS= is a prerequisite of seccomp, not an obstacle. A
user namespace may create further, nested user namespaces. So we keep the sandbox:
=*WEB-SANDBOX*= is =:auto=, which passes no =--no-sandbox=. check-web.lisp opens
=chrome://sandbox=, Chrome's own report, and asserts the line it prints when all is
well. In the guest it reads: "Layer 1 Sandbox: Namespace · PID namespaces: Yes ·
Network namespaces: Yes · Seccomp-BPF sandbox: Yes · Seccomp-BPF sandbox supports
TSYNC: Yes · *You are adequately sandboxed.*" =--no-sandbox= remains available
(=(setf *web-sandbox* nil)=) for a kernel without those options. It means that a

=*web-search*= is a =FORMAT= string. The default is Google

** 7.3 The profile: ours by default, yours if you choose

A Chrome *profile* is the directory that holds cookies (your logins), history,
saved passwords and cache. =*web-profile*= is =NIL= by default, which means
=~/.lol/web/chrome/= (=~/.config/lol/chrome/= until 2026-10-17, moved at boot with the
rest of the [[file:session-persistence.org][=~/.lol/= tree]]): *our own* profile, separate from the one the desktop
Chrome uses (=~/.config/google-chrome=). Two reasons it is not the default:

- *A profile is locked by the Chrome using it.* The desktop Chrome is usually
  running when the laptop is in its desktop session. Then it holds the lock and a
  second Chrome cannot open that profile. (In the image the desktop is not running,
  so this only bites when both run at once, as under QEMU on the dev host.)
- *Its secrets may not decrypt here.* On Linux, Chrome encrypts cookie values and
  saved passwords with a key it keeps in the desktop keyring (the Secret Service,
  provided here by =gnome-keyring-daemon=). The dev host runs one (/verified/:
  =gnome-keyring-daemon --components=pkcs11,secrets= is running). The image has no
  keyring. That is why we pass =--password-store=basic=, which keeps the key in the
  profile itself. A profile whose cookies were encrypted with the *keyring* key
  would open, but its logins would be unreadable, so you would be logged out
  everywhere. /Not tested here/: we did not read the user's cookie database to
  confirm which key it uses.

To try your own profile, with the desktop Chrome closed, evaluate
=(setf *web-profile* "/home/<you>/.config/google-chrome")= before the first web tab.
The lasting answer is to log in once in our profile: it persists in =/home= like
any other file.

* Appendix: the WPE exploration (2026-10-02)

This was the whole document before the browser was built, kept as it was written.
Section numbers inside it are its own (A1–A6). Its "what it would take in the image"
table (§A6) is now mostly answered by the container and the network rather than by
copying libraries in.

** A1. The short answer

A web browser is mostly its *engine*: the HTML/CSS layout, the JavaScript VM and the
painting. Writing one is out of scope for this project, so the real question is
/which engine, and how much of a desktop does it drag in with it/.

- *Nyxt* is a Lisp shell around someone else's engine: WebKitGTK in Nyxt 3, Electron
  (that is, Chromium) in Nyxt 4. The Lisp part would be easy; it is everything
  under it that costs (§A2).
- *WPE WebKit* is the same WebKit with *no GTK and no display server*. It is the
  engine we would pick (§A3).
- Before anything goes into the image, the engine can be tested on the host, with the
  same Debian packages we would copy from (§A4–§A5).

** A2. Why not Nyxt (yet)

Nyxt 3 renders through WebKitGTK. Measured on the host by following every shared
library it pulls in (=ldd=, the dynamic linker's "who do you need" listing):

| Library                  | Shared libs it pulls in | Their size | Its own size                     |
|--------------------------+-------------------------+------------+----------------------------------|
| =libwebkit2gtk-4.1.so.0= |                     166 | ~187 MB    | 96 MB, plus JavaScriptCore 33 MB |
| =libWPEWebKit-2.0.so.1=  |                     143 | ~137 MB    | 130 MB (JavaScriptCore included) |

The totals are close. *What* gets pulled in is where they differ. WebKitGTK needs GTK, and GTK
needs a display server: an X server or a Wayland compositor (a "compositor"
is the program that owns the screen and combines every window's pixels into one
picture). Our image has neither, and its only screen is =/dev/fb0=. On top of that,
GTK wants to own the main thread, and Nyxt compiles Lisp at runtime, which the guest
currently cannot do safely (the generic-arithmetic fault in =AGENTS.md=). Nyxt
would be the /last/ step, not the first.

** A3. The options, and why WPE

| Option                     | Engine / JavaScript                              | How it draws                   | Weight              | Verdict                                  |
|----------------------------+--------------------------------------------------+--------------------------------+---------------------+------------------------------------------|
| Links2 =-g=                | own; HTML 4 + basic CSS; no JS                   | its own framebuffer driver     | tiny, can be static | fast, but the modern web is out of reach |
| w3m                        | text; no JS                                      | the terminal                   | tiny                | docs and Hacker News, little more        |
| NetSurf (framebuffer)      | own; HTML 4 / CSS 2.1, partial CSS 3; minimal JS | =libnsfb=, a Linux fb surface  | a few MB            | the best of the small ones; SPAs break   |
| *WPE WebKit*               | *full WebKit + JavaScriptCore*                   | DRM/KMS directly, or headless  | ~270 MB of libs     | *the real web, without a desktop*        |
| WebKitGTK / Nyxt 3         | full WebKit                                      | GTK → X or Wayland             | §A2                 | needs a whole desktop                    |
| Electron / Nyxt 4          | Chromium                                         | its own stack                  | larger still        | no                                       |
| Remote (VNC into the host) | any                                              | a Lisp RFB client in the guest | no native deps      | a thin client, not a browser             |
| Closure (CL, McCLIM)       | pure Lisp, HTML 4 / CSS 1 era                    | McCLIM                         | Lisp only           | a historical toy                         |

Two terms the WPE row leans on:

- *DRM/KMS* is the kernel's modern display API (=/dev/dri/card0=). It is what a GPU
  driver such as =i915= exposes, and it is what our image *lacks*: it only has the
  old firmware framebuffer =efifb= (see [[file:framebuffer.org][framebuffer.org]]).
- *Headless* means WebKit renders into memory buffers and shows them nowhere. Some
  other program has to put the pixels on screen. For us that program would be our
  Lisp, blitting into =/dev/fb0=, which is the "process that sends pixels" case
  [[file:processes.org][processes.org]] declined for its own components and
  which a web engine would justify.

So WPE in *software rendering + headless* mode needs no GPU driver and no
compositor at all. That is the combination worth testing.

*** A4.2 Two dead ends, recorded so nobody repeats them

- *=cog= under X fails* with

  Debian builds cog with only the =drm=, =headless= and =wl= platforms (see
  =/usr/lib/x86_64-linux-gnu/cog/modules/=); there is no =x11= platform, so
  =-P x11= falls through to a backend that does not exist.
- *=cog -P wl= under cage with =LIBGL_ALWAYS_SOFTWARE=1= crashes in a loop*: the
  window stays black and cog prints
  =Crash!: The renderer process crashed= over and over. The web process dies on
  =wayland-egldisplay.c:525: dmabuf_feedback_check_main_device: Assertion `dev->size == sizeof(dev_t)' failed=,
  inside *WPEBackend-fdo*, the legacy backend cog uses. None of
  =WEBKIT_DISABLE_DMABUF_RENDERER=, =WEBKIT_DISABLE_COMPOSITING_MODE= or
  =WEBKIT_SKIA_ENABLE_CPU_RENDERING= helps. =GALLIUM_DRIVER=softpipe= avoids it, but
  softpipe is far too slow to measure anything with. *MiniBrowser does not crash*,
  because it uses WebKit's newer built-in platform layer instead of libwpe/fdo. So
  never pass it =--use-legacy-api=, which selects the crashing path again. For the
  product this means: build on WebKit's new platform API, not on cog.

#+begin_src html

    if (now - last >= 1000) { out.textContent = frames + ' fps'; frames = 0; last = now; }

*** T3 — Straight onto the display, on a bare VT (the product's architecture)

This is the closest the host gets to the image: no X, no compositor; WebKit itself
drives the screen through DRM/KMS.

1. Press =Ctrl-Alt-F3= and log in on the text console. Logging in matters: WebKit
   asks logind for the display device, and logind only hands it to the user /owning
   that VT/. Run from your X session instead, it fails with
   =Failed to take control of session ... EBUSY= and
   =Failed to become DRM master= (verified).
2. Run it under =timeout=. Once WebKit owns the screen, the keyboard goes to the
   browser rather than to the shell, so =Ctrl-C= may never arrive:

   #+end_src
3. When it exits, the console comes back. =Ctrl-Alt-F7= (or F1/F2, whichever holds
   your X) returns you to the desktop.
4. Repeat with software rendering:
   #+begin_src sh
   WPE_DISPLAY=drm LIBGL_ALWAYS_SOFTWARE=1 timeout 60 $MB https://en.wikipedia.org/wiki/Lisp_machine
   #+end_src

   whether llvmpipe can hand its buffers to KMS at all, which decides between "DRM +
   software" and "headless + our own blit" for the image.

- *Watch*: the mouse pointer and the scroll wheel. Here WebKit reads input itself
  through libinput, the same evdev devices our own [[file:input.org][input.org]] code reads.
- *Record*: started / refused (with the error), fps from =file:///tmp/fps.html=,
  and whether the pointer and the wheel behaved.
- *If the screen is stuck*: wait for =timeout=. If even that fails, switch to another

*** T5 — CPU and memory

*CPU while working.* Start a browser (T2's software setup is the interesting one),
then in another terminal:

#+begin_src sh
top -b -d 2 -n 15 -p "$(pgrep -d, -f 'MiniBrowser|WPEWebProcess|WPENetworkProcess|cage')" \
  | grep -E 'MiniBrowser|WPE|cage'
#+end_src

That prints 15 samples, 2 s apart. Scroll a long page while it runs, then repeat
while the page sits idle. =%CPU= above 100 means more than one core is busy.
Rendering in software spreads across llvmpipe's threads.

*Memory.* The obvious number, RSS ("resident set size": the pages a process has
in RAM), *double-counts* the pages several processes share, and WebKit's processes
share many libraries. *PSS* ("proportional set size") divides each shared page
among the processes sharing it, so PSS values add up honestly:

#+begin_src sh
for p in $(pgrep -f 'MiniBrowser|WPEWebProcess|WPENetworkProcess'); do
  printf '%-22s %8s kB PSS\n' "$(cat /proc/$p/comm)" \
    "$(awk '/^Pss:/{print $2}' /proc/$p/smaps_rollup)"
done
#+end_src

Measure three states: a blank page, one heavy site, and three heavy sites opened one
after another. Each MiniBrowser run is a single page, so "three sites" means
navigating via links within one run.

/Measured so far/: with donorbox.org loaded in software mode, the web process held
*~570 MB RSS* and the network process ~100 MB. That is RSS, so it is an upper bound.
Redo it as PSS.

| =about:blank=     |                   |                       |                  |       |

*** T7 — When a site breaks: finding out why

1. *Read the terminal.* A web-process crash prints its assertion or signal there;
   that is how §A4.2's fdo bug was found.
2. *Open Web Inspector* (the same devtools Safari has) in your normal browser:
   #+begin_src sh
   WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1 \
   WEBKIT_INSPECTOR_HTTP_SERVER=127.0.0.1:5999 \
     cage -- $MB https://the-broken-site/
   #+end_src
   Then open =http://127.0.0.1:5999= in Firefox. It lists the page under
   /Inspectable targets/ with an *Inspect* button: console errors, network
   failures, DOM. Without the sandbox line, the web process cannot reach the inspector
   server and logs =org.freedesktop.portal.Error.NotAllowed: This call is not
   available inside the sandbox= (verified). The sandbox exists to contain hostile
   pages, so only disable it while debugging.
3. *Compare with Firefox*: if the site is broken in Firefox too, it is not a WebKit
   problem.
4. *Core dumps*: =coredumpctl list WPEWebProcess= shows web-process crashes if
   systemd-coredump is installed. Without it, the terminal message is all there is.

** A6. What it would take in the image

This is not a plan yet, just the shopping list the tests feed into.

| Need             | Today (#24)                               | For WPE                                                                                 |
|------------------+-------------------------------------------+-----------------------------------------------------------------------------------------|
| storage          | tmpfs only                                | a real filesystem: ~270 MB of libraries (§A2), plus a profile dir for cookies and cache |
| shared libraries | ld.so + libc + libm, copied from the host | the =ldd= closure of =libWPEWebKit-2.0.so.1=, copied the same way                       |
| DNS + TLS        | sockets + DHCP, no resolver               | =/etc/resolv.conf=, =nsswitch.conf=, a CA bundle, =glib-networking=                     |
| fonts            | our own bitmap fonts                      | TTF fonts + fontconfig and its cache                                                    |
| display          | =efifb= only, =DRM= off                   | /headless/ + our Lisp blitting (no kernel change), or =DRM= + a GPU driver (T3 decides) |
| input            | our own evdev reader                      | headless: we forward events into WebKit; DRM: WebKit reads them itself via libinput     |
| child processes  | the supervisor spawns workers             | web, network (and GPU) processes; PID 1 must reap them                                  |
| sandbox          | no =USER_NS=, no =SECCOMP=                | run without it, or enable both (bubblewrap)                                             |

The headless route is the one that keeps the system ours: Lisp stays the only
process on =/dev/fb0= and treats a web page as one more thing it draws. How WebKit's
new platform API hands headless buffers to an embedder has *not* been looked at yet.
That is the next question once the tests above say the engine is worth it.
