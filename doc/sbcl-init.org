* The challenge in one sentence

Our previous inits (glibc/musl "hello") were a few KB and self-contained.
SBCL is a whole *language runtime*: a ~2 MB C runtime PLUS a ~34 MB Lisp heap
image ("core"), and it is *dynamically linked* against glibc. So "make it init"
becomes a lesson in shipping a dynamic program + its shared libraries inside an
initramfs — the exact thing static linking let us avoid before.

* Findings from the actual ./sbcl tree (grounded, measured)

SBCL here is a *built source tree*, version 2.6.8 (reached via the gitignored
=./sbcl= symlink -> =sources/sbcl-2.6.8=):
  - runtime:  ./sbcl/src/runtime/sbcl        (2.2 MB, ELF, dynamically linked)
  - core:     ./sbcl/output/sbcl.core        (~35 MB Lisp heap image)
  - contribs: ./sbcl/contrib/...             (NOT needed for a minimal init)

Runtime shared-library dependencies (from =ldd=) — the ONLY external pieces:
  - /lib64/ld-linux-x86-64.so.2   the glibc dynamic loader  (~225 KB)
  - libc.so.6                     glibc                      (~2.0 MB)
  - libm.so.6                     glibc math                 (~1.0 MB)
  - linux-vdso.so.1               provided by the kernel, NOT a file to ship
(modern glibc folded libpthread/libdl into libc.so.6, so there are no separate
pthread/dl libraries to copy. No libzstd => this core is uncompressed.)

Crucial runtime behaviour:
  - A standalone =:executable= image finds its embedded core by reading
    */proc/self/exe* — that is [[file:../sbcl/src/runtime/linux-os.c::os_get_runtime_executable_path][=os_get_runtime_executable_path=]] in
    [[file:../sbcl/src/runtime/linux-os.c][=sbcl/src/runtime/linux-os.c=]], which literally =readlink=s that path; the
    core is then located and mapped by [[file:../sbcl/src/runtime/coreparse.c][=coreparse.c=]].
    => /proc MUST be mounted before SBCL starts, or it can't find its core.
  - SBCL uses threads (futex), mmaps a large dynamic space (~1 GB reserved,
    lazily committed) => give the VM/host enough RAM (>= ~1-2 GB).

* The approach we followed

1. *Standalone image.* =save-lisp-and-die :executable t= bakes the core INTO a
   single executable (/sbin/lisp) — ~40 MB at tag #24, and it grows with the
   Lisp world since it *is* the heap (see "What 'a frozen heap' actually means"
   below). No separate .core file to manage.
2. *Ship glibc.* Copy the 3 glibc pieces (loader + libc + libm) into the
   initramfs at the exact paths the binary expects.
3. *C preinit.* A tiny musl-static C =/init= mounts /proc /sys /dev /tmp and then
   =execv=s /sbin/lisp (so /proc exists before SBCL looks for its core; PID 1 is
   replaced in place, staying PID 1).
4. *Separate initrd.* The kernel embeds NO initramfs (=CONFIG_INITRAMFS_SOURCE=""=);
   the ~43 MB cpio is a SECOND file the EFISTUB loads via =initrd== on the
   built-in cmdline. Keeps the kernel small and lets us iterate on the Lisp world
   without ever rebuilding the kernel.

* Build & run it — build.sh

=~/lisp-over-linux/build.sh= is the one-step rebuild. The fast path rebuilds only the
userland (the whole point of the separate initrd — no kernel rebuild):

  - =./build.sh=                 preinit + lol-ct + lisp-init + initramfs.cpio   (seconds)
  - =./build.sh --kernel=        ALSO rebuild the kernel + BOOTX64.EFI  (minutes)
  - =./build.sh --run=           build, then boot HEADLESS in QEMU and screenshot it
  - =./build.sh --interactive=   build, then boot in a QEMU WINDOW you can type into
  - =./build.sh --kernel --run=  the full cycle
  - =./build.sh --install-host=  build, then copy kernel + cpio to the host's
    =/boot/lisp= for a GRUB entry (sudo) — see
    [[file:micro-distro.org::Booting from the host's GRUB][micro-distro.org → Booting from the host's GRUB]]
  (flags combine; env =QEMU_WAIT=<seconds>= tunes the pre-screenshot boot wait,
  =QEMU_DISPLAY=<gtk|sdl>= picks the =--interactive= window backend)

=--run= boots iso_root/ under OVMF headless, waits, grabs the framebuffer via the
QMP socket to =screen.png=, and prints the serial boot markers. Everyday loop:
edit =supervisor.lisp= -> =./build.sh --run= -> open =screen.png=.

=--interactive= is what you want to actually *use* the REPL. It boots the same
image in a foreground QEMU window with =-display gtk= and =-serial mon:stdio=.
Because the kernel cmdline ends with =console=tty0=, /dev/console (PID 1's
stdin/stdout) is the *framebuffer VT* — so you type the menu/REPL in the QEMU
window, while the terminal you launched from mirrors the serial + kernel log and
gives you the QEMU monitor (=Ctrl-A C=). =-no-reboot= means the menu's
=s) shut down= (which calls =reboot(RB_POWER_OFF)=) cleanly quits QEMU and
returns your shell. This is the right mode for exercising the line editor (the
arrows / Ctrl-A E K U W / history added in [[file:line-editing.org][line-editing.org]]).

Both modes (and every other QEMU launch in the repo) pass
=-machine q35,accel=kvm:tcg=: hardware virtualisation when =/dev/kvm= is usable,
software emulation otherwise. Before that flag the image always ran emulated, and
the browser was an order of magnitude slower than it needed to be — see the note
under "OVMF firmware on this box" in [[file:micro-distro.org][micro-distro.org]].

Ordering constraints, so you know which moves are safe: =line-editor= must precede
=repl= and =fb-browser= (both expand its =with-raw-mode= macro, which must exist when
they are compiled) and, by convention, =shell= (it only *calls* =token-start= /
=longest-common-prefix= and reads =*completer*= at run time — a softer need; the
derived graph in [[file:guide/modules.html][the guide's module map]] lists every such edge); =canvas=
precedes =textview=/=fb=/=shell=; =model= precedes =present=; =json= and
=agent-wire= precede =agent=, which precedes =agent-ui=, which follows =shell=
(it defines methods on the shell's subjects and calls its pane functions);
=agent-tools= and =agent-store= follow =agent-ui= (an =:around= method on its Activity
subject; the store hangs on =agent='s =*turn-end-hooks*=); =net= precedes
=dhcp=, which precedes =dns= / =sntp= / =wifi= (they hang on its =*lease-hooks*= and
=*netd-hooks*=); =tls= precedes =http=; =net-views= comes after =shell= and =wifi=; =logcount-fix= goes first so the image is repaired before anything else
lands (nothing at build time needs it — the build host has POPCNT — but first is
where a reader looks for a patch to SBCL itself); and =supervisor= is last because
it is the entry point. Everything else
is grouped for readability rather than forced.

Note that the =poc/= toolkit is not a copy — =build.sh= loads those files
*straight out of =poc/=*, the same sources =sbcl --script poc/run-host.lisp= runs
on the dev host. One implementation, two backends ([[file:../poc/README.org][poc/README.org]]).

The network REPL is *off at boot* unless QEMU's =fw_cfg= (or =lol.netrepl=1=) asks
for it (tag #26), and can be toggled from the menu (=t=).
It serves the full line editor over the socket; a host-side raw-forwarding client
lives in =host-client/= (NOT in the image). See [[file:networking.org][networking.org]] §6a.

The =net.lisp= TCP REPL is built on the *=sb-bsd-sockets= contrib baked into the
image*: =build.sh= does =(require :sb-bsd-sockets)= at build time (with =SBCL_HOME=
pointed at the SBCL tree's =obj/sbcl-home=) before =save-lisp-and-die=, so sockets
are frozen into =/sbin/lisp= and need no fasl at runtime. See [[file:networking.org][networking.org]].

One executable, several roles chosen by argv: no args => the SUPERVISOR (PID 1);
"worker <id>" => a short-lived WORKER; "job NAME" => compute one view and print it
(worker.lisp); "serve NAME" => stay up and serve a LIVE view (worker-live.lisp);
"try" => Accept one definition in a throwaway heap (sandbox.lisp); "repl" => a REPL
on its own terminal. Toplevel =init-toplevel= dispatches; key functions
=supervisor-main=, =run-repl=, =power-off=, =worker-main=, =spawn-worker=.

*Boot goes straight into the environment.* After its diagnostics (input devices,
DHCP, the network REPL, interfaces) =supervisor-main= calls =run-browser-fb=, which
opens on the Workspace alone — the environment is what the machine is for, so it
should not wait behind a menu. The menu is the *fallback*: you reach it by leaving
the environment (=SuperL-q=, which first asks: this console, or power off straight
away; a bare =q= is only /back/ — it once left too, and so killed the environment
from an image viewer), and you land on it if the
environment dies, because =run-browser-fb= catches any =serious-condition=, prints
it and returns. The screen is cleared /before/ the environment opens, not after, so
a dying environment's last words stay above the menu. With no framebuffer at all
the environment fails at once and the menu is simply first.

The supervisor menu is read from the console ([[file:../initramfs/supervisor.lisp::defun print-menu][supervisor.lisp →
print-menu]] prints it, and the =cond= right below it dispatches):
  r) run a Lisp REPL              -> read-eval-print loop; :quit (or EOF) returns
  b) the environment              -> reopen the tabbed pixel browser on /dev/fb0,
                                     the one the image booted into, on the
                                     Workspace; SuperL-m adds the MODULE INDEX
                                     (every definition by the file it came from,
                                     the only view of the whole system, lol.*
                                     toolkit included). =run-browser-fb= with no
                                     root; [[file:code-browser.org][code-browser.org]] §4⅔
  p) Lisp workspace               -> a scratch buffer: Do it / Print it / Inspect it
  c) change set                   -> definitions edited live this session
  l) all definitions (CL-USER)    -> the flat package view — the former default
                                     root, kept because "one alphabetical list of
                                     everything in CL-USER" is still sometimes what
                                     you want. Any other package: the Spotter.
  w) spawn a worker process       -> fork+exec another /sbin/lisp as a worker
  a) draw the Land-of-Lisp alien  -> blit a sprite to /dev/fb0 (see framebuffer.org §8)
  m) show memory usage            -> =report-memory= ([[file:../initramfs/meminfo.lisp][meminfo.lisp]])
  t) network REPL on TCP :4005    -> toggle the listener ([[file:networking.org][networking.org]] §6a)
  s) shut down (power off)        -> sync + reboot(2)

How each piece works:
  - *Reading the console.* The menu reads =*standard-input*= (= fd 0 = /dev/console
    = the fb console). The kernel N_TTY line discipline gives canonical input, so
    you type a choice and press Enter; backspace works.
  - *REPL.* =run-repl= is a guarded read/eval/print loop. EVERY read and eval is
    wrapped in =handler-case= for =serious-condition=, so a bad form or error
    just prints and re-prompts — it can never kill PID 1. =:quit= leaves the REPL.
  - *Shutdown.* =power-off= calls libc via sb-alien FFI: =sync()= then
    =reboot(#x4321fedc)= (=RB_POWER_OFF=). No new dependency — the symbols live in
    the libc we already ship. If power-off is refused it returns to the menu.
  - *Workers.* spawned with =sb-ext:run-program= (forks+execs /sbin/lisp, reaps
    its own children). The menu loop catches =serious-condition= too, so nothing
    in a menu action can crash init.
  - *Alien (framebuffer graphics).* =draw-alien= reads the fb geometry from
    sysfs (=read-fb-geometry=) and blits a 256x150 RGBA sprite (=/alien.rgba=)
    into the top-right of =/dev/fb0= via seek + read-modify-write, honouring the
    alpha channel for a transparent cutout. The menu clears the screen and calls
    =draw-alien= *after* printing, every cycle, so the alien persists in the
    corner (silent on redraws; =a)= passes =:announce t= for the status line).
    Pure userland, no kernel change. Full write-up:
    [[file:framebuffer.org][framebuffer.org]] §8 (and §5 for /dev/fb0).

Key bits learned while writing it:
  - =sb-posix:getpid= is a CONTRIB and is NOT loaded by default. This entry used
    to add "and =(require :sb-posix)= fails against this source tree"; that was
    true when written and is *no longer* — it failed for want of =SBCL_HOME=,
    which the build has set since the =sb-bsd-sockets= work, and the contrib
    loads and freezes in fine. We still do not ship it, but for a different and
    much more interesting reason, measured on *2026-09-20*: several sb-posix
    entry points (=tcgetattr= among them) are =declaim inline= and expand into
    its groveled alien structs, and *that alien type information does not survive
    =save-lisp-and-die= into the guest*. Code calling them runs, but can never be
    RECOMPILED inside the running image — which breaks =C-c C-c= on any
    definition that uses one, and self-editing is the whole point here. The audit
    is [[file:processes.org][processes.org]] §6. =(sb-unix:unix-getpid)= remains the right call: no
    contrib, no constraint.
  - PID 1 must reap children or they become zombies. =run-program= reaps the
    children IT launched. A fuller init would also reap *reparented* orphans with
    a waitpid(-1, WNOHANG) loop on SIGCHLD — noted, not implemented.
  - PID 1 must never return — every menu action loops or powers off.

** Two findings while testing in QEMU
  - *"segfault" spam on the console is NORMAL SBCL.* Its generational GC uses
    write-protected pages + a SIGSEGV handler as a write barrier (fault code 7 =
    user write to a write-protected page); SBCL handles each and resumes. The
    kernel logs every one as "lisp[1]: segfault ..." onto the console. The preinit
    silences it: write "0" to =/proc/sys/debug/exception-trace= after mounting /proc.
  - *ACPI power-off — FIXED (kernel #19).* It used to halt instead of powering off:
    the DSDT wouldn't load ("ACPI: Unable to load the System Description Tables",
    AE_BAD_PARAMETER during Region init) so there was no \_S5. ROOT CAUSE: the
    kernel had =# CONFIG_PCI is not set=. A DSDT declares operation regions in PCI
    *config space*; with PCI off the ACPI PCI-config region handler isn't
    registered, so region init fails and the whole DSDT is rejected. Enabling
    =CONFIG_PCI=y= fixed it — now "reboot: Power down" and QEMU exits cleanly.
    (Same root cause as the real-hardware keyboard bug below — see
    [[file:micro-distro.org][micro-distro.org]] "Real-hardware input (PCI/USB/HID)".)
  - *Real-hardware keyboard — FIXED (kernel #19).* The supervisor booted on the
    laptop but the keyboard was dead, while QEMU worked. QEMU emulates a legacy
    PS/2 keyboard (i8042, which we had); a real laptop keyboard is USB or I2C-HID,
    both PCI-bus devices — and PCI was off. Enabling PCI + the USB stack + USB_HID
    + I2C-HID made it work; verified in QEMU with =-device qemu-xhci -device usb-kbd=
    (the QEMU USB Keyboard enumerated and drove the menu). The supervisor now also
    prints =/proc/bus/input/devices= names at startup (=show-input-devices=) as a
    keyboard-detection diagnostic.

    *Why the startup =(sleep 2)= exists.* UEFI had a working keyboard in its own
    menus, but that does NOT carry over: the firmware's keyboard driver is a Boot
    Services driver, destroyed at =ExitBootServices()=, so the kernel must bind its
    OWN keyboard. On a real laptop that means walking PCI -> USB -> xHCI -> USB-HID
    -> input device, and that binding is *asynchronous* — it finishes a short moment
    AFTER PID 1 starts, not before. So =supervisor-main= sleeps ~2 s "give USB a
    moment to enumerate" before reading input, and =show-input-devices= is the
    direct check that the re-binding actually completed. (Background — why firmware
    drivers die at the handoff and the kernel re-enumerates everything except the
    framebuffer: [[file:background/background.org][background.org]] §5, with the handoff itself in §3.)

** Building the SBCL image (what build.sh stage 2 runs)

=build.sh= does not keep this script on disk — it *generates* one into a temp file
(=mktemp=, removed by a =trap=), emitting one =(load-recording …)= line per entry
of =LISP_SOURCES=, then feeds it to the SBCL in =./sbcl=. The shape of what it
generates:

*One compilation unit around the modules* (2026-10-17). A call to a function
defined in a later file, or further down the same file, used to draw an "undefined
function" STYLE-WARNING the moment its caller compiled. That came to about 350
warning lines per build, all of them resolved by the end, and they buried the real
ones. Inside =with-compilation-unit= SBCL holds such warnings until the unit ends
and reports only names that are *still* undefined then. A clean build now ends with
no "Undefined function" summary, so if one appears, it names something missing from
the image. Checked when the change was made: every one of the 181 names the old
build flagged was defined in the booted image (=fboundp= / =boundp= / =find-class=
over the net REPL). The handful of warnings left are style-only and known: struct
accessors called before their =defstruct= (=mb-*= in =shell.lisp=, =lease-iface=
from =agent.lisp='s preflight) cost an inline expansion, not correctness, and three
lambda lists mix =&optional= with =&key=. Six variables used before their =defvar=
(full WARNINGs: a =setf= of an unknown variable) had their =defvar= moved up. None
was a bug, because no =let= bound one before its =defvar=, which would have made the
binding lexical.

Both =require= calls matter and both must come *before* the modules: =net.lisp=
names the =sb-bsd-sockets= package at load time, and =registry.lisp='s =senders=
wrapper names =sb-introspect='s. =SBCL_HOME= is what lets =require= find the
contrib fasls in the built tree ([[file:../sbcl/obj/sbcl-home][=sbcl/obj/sbcl-home=]]); after
=save-lisp-and-die= they are frozen into the heap and neither the fasls nor
=SBCL_HOME= exist at runtime.

** What "a frozen heap" actually means

The phrase turns up all over these docs as if it were a known term. It is worth
one paragraph, because it is the single fact that most shapes how this project is
built.

A running Lisp is a *heap*: one graph of live objects — every package, symbol,
function object, class, and global — reachable from a set of roots.
[[file:../sbcl/src/code/save.lisp::defun save-lisp-and-die][=save-lisp-and-die=]] ([[file:../sbcl/src/code/save.lisp][=sbcl/src/code/save.lisp=]]) does the obvious brutal
thing: it runs a full GC, then writes *that entire graph, verbatim*, out to a
file, and exits. Reading it back is [[file:../sbcl/src/runtime/coreparse.c][=coreparse.c=]] on the C side. Starting the resulting
image is not "loading a program"; it is *mapping the graph back into memory and
resuming*. There is no initialisation phase, no =main=, no re-loading of
anything — the world simply picks up where it was frozen, with =:toplevel= as the
one function it calls on the way in.

Three consequences that explain many decisions here:

- *Anything you want must be present before you save.* =require=, Quicklisp, and
  =load= all need machinery (and files) that will not exist in the initramfs, so
  every dependency is baked in at build time — hence both =require= lines above,
  hence [[file:networking.org][networking.org]]'s insistence on pulling =sb-bsd-sockets= in early.
- *But the image is not read-only.* This is the part that surprises people:
  "frozen" describes the *file*, not the *running system*. =eval= and =compile=
  are still there, because they were part of the graph too. That is precisely why
  the code browser can compile an edited definition straight into the live image
  ([[file:code-browser.org][code-browser.org]]) — it needs no fasl, no compiler on disk, no source tree.
- *It is why the binary is ~40 MB.* You are shipping a heap, not a program.
  Equally, it is why startup is effectively instant: nothing is being loaded.

The rest of that graph is also why [[file:../initramfs/registry.lisp][=registry.lisp=]]'s trick works at all —
=load-recording= stuffs each definition's *source text* into the heap on the way
past, so the frozen world carries its own source and can show it back to you with
no files present.

* The C preinit

[[file:../initramfs/preinit.c][=initramfs/preinit.c=]] began as ~40 lines and still has that core: mount
=/proc=, =/sys=, =/dev=, =/tmp=, then =execv= the Lisp (the process stays PID 1).
Since tag #25 (storage) it has grown to ~540 lines at #26, 713 on 2026-10-16, because it also does every *privileged*
setup step, once, before the Lisp exists:

1. read =/etc/lol.conf= (written by =build.sh=: the user and the disk UUID) and
   any =lol.user== / =lol.disk== on the kernel command line;
2. find the disk by reading ext4 superblocks itself (no udev/blkid), mount it at
   =/mnt/host=, bind-mount only its =/home= onto ours, make =/mnt/host= read-only;
3. look the user up in the host's =/etc/passwd= / =/etc/group=, chown the device
   nodes the Lisp opens, fork =lol-rootd= (the one process that stays root: device
   hotplug + read-only remount at power-off, and three one-signal requests since —
   the clock, the NetworkManager profiles, and since 2026-10-20 installing a new
   build into the host's =/boot/lisp=, section "Updating from inside");
4. drop to the user, keeping five capabilities through =execve= via the *ambient*
   set, and =execve= the Lisp with =HOME=, =USER=, =LOL_ROOTD_PID= (and
   =LOL_NETREPL=1= when QEMU asked for the net REPL — read here because the
   fw_cfg files are root-only).

Tag #26 added three things around those steps: a =devpts= mount at =/dev/pts= (ptys:
the terminal pane, container shells) and a tmpfs at =/dev/shm= (=shm_open=: Chrome,
PostgreSQL); fw_cfg blobs =opt/lol/user= and =opt/lol/disk= that override
=lol.conf= the way the cmdline does (QEMU cannot give an OVMF-booted EFISTUB kernel a
cmdline); and =disk=9p:<tag>=, which mounts the *build host's real* =/= over virtio-9p
read-only at =/mnt/host= with =/home= as an overlay on a tmpfs — the QEMU-only path
that lets tests run the host's programs ([[file:storage.org][storage.org]] §8).

Since 2026-10-12 preinit also writes =0 2147483647= to
=/proc/sys/net/ipv4/ping_group_range=, the value Debian's systemd writes. An
unprivileged =ping= uses an ICMP "datagram" socket, which the kernel allows only for
groups inside that range, and the default range =1 0= is empty. So =ping= failed in
every container (no =CAP_NET_RAW= there) even when the network worked.
=check-containers.lisp= pings SLIRP's gateway to prove it.

Since 2026-10-16 ([[file:diagnostics.org][diagnostics.org]]) it also writes =10= to =/proc/sys/kernel/panic=, so a
dead PID 1 reboots after ten seconds instead of leaving the last frame on screen;
appends the host's =/etc/hosts= to ours once the disk is mounted
([[file:../initramfs/preinit.c::static void merge_host_hosts][=merge_host_hosts=]], [[file:networking.org][networking.org]] §2c); and starts the Lisp with
=--dynamic-space-size 4GB= (SBCL's default heap ceiling is 1 GiB; the runtime strips
that option from =*posix-argv*=, so the role dispatch still sees no argument).

Since tag #29 (2026-10-17) =give_devices= hands =/dev/snd/*= to the user too — the
mixer (=controlC0=), playback and capture (=pcmC0D0p= / =pcmC0D0c=) — so =mixer.lisp= and
the host's ffmpeg and mplayer in a container can open the sound card
([[file:screencast.org][screencast.org]] §3.1).

Every step is non-fatal; with no disk it is exactly the old shim and the Lisp runs
as root. The full story — why each mount flag, why capabilities, why in C and not
in Lisp, what was ruled out — is [[file:storage.org][storage.org]]. The skeleton (only =argv= has grown):
#+begin_src c
  int main(void) {
      mount("proc",     "/proc", "proc",     0, NULL);
      mount("sysfs",    "/sys",  "sysfs",    0, NULL);
      mount("devtmpfs", "/dev",  "devtmpfs", 0, NULL);
      mount("tmpfs",    "/tmp",  "tmpfs",    0, "size=64m,mode=1777");

=capset= structs are copied into the file from the kernel's

* lol-ct — the second C program (containers)

[[file:../initramfs/lol-ct.c][=initramfs/lol-ct.c=]] (~620 lines, 71,312 bytes static, 2026-10-12) runs one
command inside the host's own Debian: user + mount + pid + uts namespaces, the
host root at =/mnt/host= with per-directory overlays on top, our =/home=, =/tmp=,
=/dev= bound in, =pivot_root=, and the command executed as the user with no
capabilities. The design and every finding are in [[file:containers.org][containers.org]]; what matters
here is how it fits the build:

- =build.sh= compiles it right after preinit, with the same command:
  =musl-gcc -static -O2 -s -o initramfs/lol-ct initramfs/lol-ct.c=.
- the cpio carries it as =/sbin/lol-ct= (mode 0755, owned by root — it needs no
  setuid bit: an ordinary user may create a user namespace, and everything else
  happens inside one).
- the Lisp starts it with =sb-ext:run-program=
  ([[file:../initramfs/containers.lisp::defun container-command-line][=containers.lisp=, =container-command-line=]]). It has to be a separate
  process, and not the Lisp itself: =unshare(CLONE_NEWUSER)= refuses a
  multithreaded caller, and PID 1 has threads (the net REPL, a run pane's reader).

Its output reaches the screen through =runs.lisp= (a pty, a reader thread, a
snapshot copied into a read-only pane on the poll loop's tick) and the SGR
reader at the end of =ansi.lisp= — both in =LISP_SOURCES=, after the file manager.

* The web pane — a third process tree, and no new file in the image

[[file:../initramfs/web-cdp.lisp][=web-cdp.lisp=]] and [[file:../initramfs/web.lisp][=web.lisp=]] come last in =LISP_SOURCES= before the
network modules, after =fb-browser.lisp=, because =web.lisp= registers itself with
the browser loop's =*FB-SERVICES*= when it is loaded (Chrome's pipe joins the poll;
each turn runs =WEB-LOOP-SERVICE=). Nothing is added to the cpio: Chrome is the
*host's* =/usr/bin/google-chrome=, started on first use through
=container-command-line= in a container named =web=, so the image grows by the two
Lisp files only. Three things touch PID 1's duties:

- *Reaping.* lol-ct's init reaps inside the container; =WEB-REAP-ORPHANS= is a
  safety net that reaps only children SBCL did not start (=waitid= with =WNOWAIT=
  first, so =run-program='s exit codes are never stolen).
- *Power-off.* =POWER-OFF= ([[file:../initramfs/process.lisp::defun power-off][process.lisp]]) calls =WEB-SHUTDOWN= before
  =RELEASE-DISK=, so Chrome writes its profile while =/home= is still writable.
- *Threads.* The net REPL may ask a page a question (=WEB-JS=) while the
  browser's loop reads the pipe; sends are serialised by a mutex and replies are
  delivered by the loop. Details: [[file:web-browser.org][web-browser.org]] §5–§6.
- *Modal choosers from a service* (2026-10-13). A page's =<select>= is answered
  with the chooser (kind =:select=; =RUN-CHOOSER-FB= then, the =RUN-CHOOSER= overlay
  since Morphic step 4, which waits by turning the environment's loop). =WEB-SERVICE=
  opens it only after the pipe's batch has been dispatched, never from inside
  =WEB-EVENT=; while it is up nobody reads Chrome's pipe, which Chrome's frame acks
  make harmless — since step 4 because a service inside its own =:run= sits the
  inner turns out, fd and all (=*services-running*=, fb-browser.lisp).
  [[file:web-browser.org][web-browser.org]] §4.4.

** Reading those =nod= lines — what a device node is

The three =nod= lines are the least self-explanatory thing in the file, so:

#+begin_src text
  nod  /dev/console 0600 0 0 c 5 1
       └─ path      └─ mode
                         └─ uid, gid
                                └─ type: 'c' = character, 'b' = block
                                    └─ major   └─ minor
#+end_src

A *device node* is a file that is not storage — it is a *name for a driver*.
Opening it connects you to kernel code rather than to bytes on a disk. The two
numbers are how the kernel decides *which* code:

- the *major* number selects the *driver* — 5 is what =devices.txt= calls
  "Alternate TTY devices", 1 is the "Memory devices" driver that owns
  =/dev/null=, =/dev/zero= and friends;
- the *minor* number selects *which thing that driver manages* — major 5 minor 1
  is the system console; minor 0 is =/dev/tty=, "the terminal my process happens
  to be attached to"; and major 1 minor 3 is =/dev/null=.

So =c 5 1= reads as *"a character device, handled by driver 5, unit 1"* —
i.e. =/dev/console=. The numbers are not ours to invent: they are fixed by Linux
and listed in [[file:../linux/Documentation/admin-guide/devices.txt][=Documentation/admin-guide/devices.txt=]]. Get one wrong and you do
not get an error, you get a file that talks to the wrong driver.

*Character vs block* is the other letter. A character device is a *stream* — you
read and write bytes in order, as with a terminal. A block device is *randomly
addressable* in fixed-size blocks and sits behind the kernel's buffer cache, as a
disk does. =/dev/fb0= is a character device even though it behaves like an array
of memory — see [[file:framebuffer.org][framebuffer.org]] §5½ for why that is the right classification.

** Why both static nodes *and* devtmpfs

It looks redundant: we hand-write three nodes here, and then [[file:../initramfs/preinit.c][=preinit.c=]] mounts
=devtmpfs= on =/dev=, which populates it with *every* device the kernel knows —
including a =console=, a =null= and a =tty=. Why do both?

*Because of ordering.* The static nodes exist in the cpio the instant the kernel
unpacks it, which is *before any of our code runs*. The kernel opens =/dev/console=
as PID 1's stdin/stdout/stderr at exec time; =preinit= then wants =perror= to go
somewhere real if a mount fails. Both of those happen *before* the =devtmpfs=
mount that would have created those nodes. Without the static three, the earliest
failures would be invisible — the classic silent boot.

After the mount, devtmpfs's own nodes shadow ours and everything else in =/dev=
(=/dev/fb0=, =/dev/input/event*=, =/dev/tty0=) appears without us listing a
thing. The static set is a *bootstrap*, deliberately minimal: exactly the three
nodes needed to survive the window before =/dev= is real.

* Updating from inside — build, install, restart

/Since 2026-10-20 (tag #31)./ The laptop boots the image through the host's GRUB
from =/boot/lisp= ([[file:micro-distro.org::Booting from the host's GRUB][micro-distro.org → Booting from the host's GRUB]]). The environment's
terminal can *build* a new image: its container is the host's own Debian, with the
same compilers, the checkout in =/home= and room to write (measured 2026-10-20 on the
laptop: =./build.sh= 11 s, the kernel's =make -j8 bzImage= 19.5 s incremental). It
could not *install* one. =/boot/lisp= is root's, on the host's root filesystem, which
the image only ever sees read-only, and a container has no =sudo= (setuid is off
there by design, [[file:containers.org][containers.org]] §3.4). So every update meant: boot Debian,
=sudo cp=, boot back. Now it is one step:

1. In the terminal (=SuperL-Return=): =./build.sh= (with =--kernel= if the kernel
   changed).
2. =SuperL-q= -> *Install the new build and restart* (key 5; it names the build).
   From the supervisor's console menu, the same is =u=.

The desk is saved on the way out, as by "Save and shut down", so the restart comes
back to the same tabs and Workspace text.

What happens, piece by piece:

- *=build.sh=* writes =iso_root/build-info= last, after both files are final: one
  READable plist, =(:stamp "rev date" :bzimage N :initramfs N)= — the same stamp it
  bakes into =*build-stamp*=. It is removed when packing starts, so a half-done build
  never has one vouching for it. It also bakes =*build-root*=, the checkout's path, so
  the image knows where to look for its successor. =--install-host= copies
  =build-info= into =/boot/lisp= too. Inside a container it only says to use the menu
  (=LOL_CONTAINER= is set there).
- *[[file:../initramfs/update.lisp::defun pending-build][=pending-build=]]* is a finished checkout build (its two files the
  sizes =build-info= says) whose stamp differs from =/boot/lisp/build-info='s. Only
  then does the leave menu offer the entry.
- *[[file:../initramfs/update.lisp::defun install-pending-build][=install-pending-build=]]* runs while the environment is still on screen,
  so a refusal shows in the status line and nothing has been left. It copies the
  three files into =~/.lol/stage/=, checks the copy is still that build, and sends
  =lol-rootd= signal 42. Then it waits (60 s at most) for the one-line answer in
  =/tmp/lol-install.status=.
- *lol-rootd* ([[file:../initramfs/preinit.c::static void do_install][=do_install=]]) takes no argument: the source is always
  =<home>/.lol/stage/=, the destination always =/boot/lisp/=. It opens the stage *as
  the user* (=setfsuid=, =O_NOFOLLOW=), so a planted symlink to a root-only file is
  refused rather than copied. It checks each file's magic number (=MZ= and =HdrS= at
  =0x202= for the bzImage, the x86 boot protocol; =070701= for a newc cpio) and size.
  It makes the =/mnt/host= view writable for the copy (a bind remount), writes every
  file to =.NAME.new= with an fsync, and only then renames: the old file to
  =NAME.prev=, the new one into place. Then the view is read-only again, before it
  answers =ok=.
- *[[file:../initramfs/process.lisp::defun restart-machine][=restart-machine=]]* loads =/boot/lisp='s pair with =kexec_file_load(2)= and
  reboots into it (=LINUX_REBOOT_CMD_KEXEC=). A kernel without kexec answers
  =ENOSYS=, and then it restarts through the firmware, whose GRUB boots our entry
  first. =(save-setting :restart-via :firmware)= skips kexec. Both share
  =stop-for-reboot= with =power-off=: Chrome closed, the session log's last line
  (=shutdown: restart (kexec)=, so the next boot reads a clean end), sync, the disk
  read-only.

*Rollback*: the previous pair stays as =bzImage.prev= / =initramfs.cpio.prev=. If a
new build does not come up, boot Debian (GRUB's next entry) and move them back.

*The first update from #30* goes through the firmware: a #30 kernel has no kexec.
From #31 on, restarts are kexecs.

*What this widens*: whoever may install an image may run any code as root at the next
boot. That is the request's purpose, not a side effect. It is still a fixed request
with no arguments, like the other three, and [[file:storage.org][storage.org]] §6 records it.

* /tmp — what it took

Two ingredients:
  1. The directory must EXIST. One gen_init_cpio line creates it with the
     conventional sticky, world-writable mode:
        dir /tmp 1777 0 0
  2. (optional but done here) A dedicated *tmpfs* mounted on it, for a real,
     size-capped scratch fs separate from the root. Requires =CONFIG_TMPFS=y=
     (we enabled it; =CONFIG_SHMEM=y= is its prerequisite). The preinit mounts it:
        mount("tmpfs", "/tmp", "tmpfs", 0, "size=64m,mode=1777");
Because the initramfs root is ALREADY a writable RAM filesystem, step 1 alone
makes /tmp usable; step 2 just gives it isolation + a size limit.

* Gotchas / lessons (the interesting part)

  - *PID 1 must never exit.* The Lisp =:toplevel= loops forever; if it returns,
    the kernel panics ("Attempted to kill init!"). Same rule as the C init.
  - */proc before the core.* The =:executable= image finds its embedded core via
    /proc/self/exe — mount /proc FIRST (the C preinit does). Without it SBCL may
    fail to locate its core. This is the whole reason for the preinit shim.
  - *Dynamic linking is the real tax.* We must ship the loader + libc + libm at
    the exact paths and keep them version-matched to the host that built SBCL.
    Mismatched glibc => loader errors at boot.
  - *No ld.so.cache.* The loader can't consult /etc/ld.so.cache; rely on default
    search paths (place libs in /usr/lib/x86_64-linux-gnu).
  - *RAM.* SBCL wants real memory; don't test with -m 256.
  - *Skip personal config* when building images: --no-userinit --no-sysinit.
  - Secure Boot, framebuffer console, BOOTX64.EFI placement: all unchanged from
    micro-distro.org — only the initramfs contents (and initrd= cmdline) differ.

* rlwrap (rich line editing) — dependency notes  [NOT IMPLEMENTED]

Reference notes so we don't re-derive this. The framebuffer console already gives
*canonical-mode* line editing for free (backspace, Ctrl-U, Ctrl-W, line-at-a-time
via the kernel N_TTY line discipline). What it does NOT give is *rich* editing —
command history (up-arrow), in-line cursor movement (left/right, Ctrl-A/E), tab
completion. Those need a readline layer. =rlwrap= is one way to add it.

Cost: ~1 MB of files + a terminfo entry + a devpts mount. NO kernel rebuild
(CONFIG_UNIX98_PTYS is already =y=). Measured against this host:

** 1. Binary + 4 NEW shared libraries (beyond libc/libm/loader we already ship)
   | soname (what the loader asks for) | real file on host  | size   |
   |-----------------------------------+--------------------+--------|
   | libreadline.so.8                  | libreadline.so.8.3 | 379 KB |
   | libtinfo.so.6                     | libtinfo.so.6.6    | 220 KB |
   | libptytty.so.0                    | libptytty.so.0     | 117 KB |
   | libgcc_s.so.1                     | libgcc_s.so.1      | 183 KB |
   | (rlwrap itself)                   | /usr/bin/rlwrap    | 104 KB |
   Subtlety: ship the REAL file at the SONAME path (gen_init_cpio lets dest != src):
     file /usr/lib/x86_64-linux-gnu/libreadline.so.8 /usr/lib/x86_64-linux-gnu/libreadline.so.8.3 0755 0 0
     file /usr/lib/x86_64-linux-gnu/libtinfo.so.6    /usr/lib/x86_64-linux-gnu/libtinfo.so.6.6     0755 0 0
     file /usr/lib/x86_64-linux-gnu/libptytty.so.0   /usr/lib/x86_64-linux-gnu/libptytty.so.0      0755 0 0
     file /usr/lib/x86_64-linux-gnu/libgcc_s.so.1    /usr/lib/x86_64-linux-gnu/libgcc_s.so.1       0755 0 0
     file /usr/bin/rlwrap                            /usr/bin/rlwrap                                0755 0 0

** 2. terminfo data file (easy to forget)
   readline/libtinfo look up $TERM in the terminfo DB to know key sequences. The
   fb console is TERM=linux => need /usr/share/terminfo/l/linux (1740 bytes):
     dir  /usr/share/terminfo            0755 0 0
     dir  /usr/share/terminfo/l          0755 0 0
     file /usr/share/terminfo/l/linux  /usr/share/terminfo/l/linux  0644 0 0
   AND set TERM=linux in the launch env (preinit: switch execv -> execve with
   {"TERM=linux", NULL}). Without it, arrow keys won't decode.

** 3. pty subsystem (the architectural one)
   rlwrap runs the wrapped program inside a PSEUDO-TERMINAL (child on the slave
   side; rlwrap shuttles bytes + does the editing in the middle). Needs:
     - CONFIG_UNIX98_PTYS=y   -> already enabled, no rebuild
     - /dev/ptmx              -> appears automatically once devtmpfs is mounted
     - devpts mounted at /dev/pts  -> NOT done yet; add:
         (list)    dir /dev/pts 0755 0 0
         (preinit) mount("devpts","/dev/pts","devpts",0,"mode=0620,gid=5,ptmxmode=0666");

** The catch (why we did NOT do it here)
   rlwrap changes the process model: /init -> execv -> rlwrap (PID 1) -> forks ->
   SBCL (child, in a pty). So rlwrap becomes PID 1, not SBCL, and rlwrap exits when
   its child exits (PID 1 exiting = panic; fine only while the child loops forever).
   rlwrap is built to wrap ONE interactive REPL, so it composes badly with our
   supervisor-spawns-workers design. Good fit: a SIMPLE "SBCL REPL as init" image.
   For an interactive REPL into the SUPERVISOR, prefer Swank/SLynk (next steps) —
   no pty/terminfo/readline files at all, richer REPL from your editor.

   PURE-LISP alternative (no rlwrap, no native readline): do the line editing in
   Lisp itself — raw-mode termios via sb-alien FFI to the libc we already ship,
   plus ANSI escapes the fbcon understands. See [[file:line-editing.org][line-editing.org]] for the full
   write-up, the linedit feature list, and why linedit's deps (osicat native shim
   + terminfo DB) make a hand-rolled editor the better fit here.

* Next steps / ideas

  - On-demand by a real trigger: have the supervisor spawn a worker in response
    to input (a console line, a socket message) rather than a timer/top-up loop.
  - Reap reparented orphans too: a SIGCHLD handler doing waitpid(-1, ..., WNOHANG).
  - Mount /proc,/sys from within Lisp via sb-alien (FFI to mount(2)) and drop the
    C preinit entirely — a more "pure Lisp" init (but keep /proc for core lookup;
    chicken-and-egg makes the shim safer).
  - Give SBCL a real console REPL; add a getty-like read loop.
  - Build SBCL static (musl) to eliminate the shipped glibc libs entirely.
  - Swank/SLynk over a serial or network socket => remote Lisp REPL into PID 1.
  - *A debugger that can't kill PID 1.* Today =run-repl= catches =serious-condition=
    around every eval and just prints the error (=repl.lisp=) — so an error never
    reaches =invoke-debugger=, and you lose the interactive debugger you'd get from
    a normal SBCL. Two ways to get the debugger back without endangering init:
    (a) instead of swallowing the condition, rebind =*debugger-hook*= to a small,
    guarded mini-debugger (print the backtrace, offer a restart that returns to the
    REPL/menu) so a debug session can always unwind back to a safe loop; or
    (b) run the REPL in a *subprocess* (a worker, like =spawn-worker=) rather than
    in PID 1 itself — then the child can drop into the real SBCL debugger, and even
    if it dies it only kills the child, never init. (b) is the cleaner separation
    of concerns: PID 1 stays a dumb, unkillable supervisor; the REPL/debugger lives
    where a crash is survivable. Relates to the Swank/SLynk idea above, which also
    moves the rich REPL off the PID-1 console.
* Toolchain currency (both external trees)

Both halves of the toolchain are *current and verified*. The image is built
against SBCL =2.6.8= (the newest release, August 2026) on the Linux =7.2.5=
kernel (the current stable line) — each baked in at build time by whatever the gitignored
=./sbcl= / =./linux= symlinks point at (=deps.sh=), so moving either version is
independent of the other. Nothing in the userland pins a version (the banner just
reports =lisp-implementation-version=), which is why the SBCL jump from the old
=2.5.7= tree moved forward cleanly, and so did the =2.6.6= -> =2.6.8= one: a full
=make.sh= rebuild, then =./build.sh=, then a headless QEMU boot, all green — no new
=sb-alien=/=sb-int= style-warnings from the internals the line editor and REPL lean
on, and the three PRIVATE internals the browser reaches for still exist
(=sb-di::debug-fun-debug-vars= for frame locals, =sb-kernel::restart-function= and
=sb-kernel::restart-interactive-function= for the debugger — those are the ones a
release could quietly move, so they are checked by name on every bump). The kernel
jump from =6.18.3= was likewise clean (=make olddefconfig= took the new symbols at safe defaults; the
one deliberate fix was pinning =PREEMPT_LAZY= so =TINY_RCU= survives on our
uniprocessor image — see [[file:kernel-config.org][kernel-config.org]] tag =#24=). Both recipes are the same
shape: re-point the symlink, rebuild, boot-test — so any future bump is routine.
