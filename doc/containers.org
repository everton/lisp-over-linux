#+TITLE: Containers — running a full distribution's programs inside the environment
#+STARTUP: showall

The environment's own userland is one frozen SBCL heap on an initramfs. A
container lets you run programs that need a whole Linux distribution — a
compiler toolchain, a language runtime with native libraries, a database
server — without baking any of it into the image.

The container's root is the host's own distribution, already mounted read-only
at =/mnt/host= ([[file:storage.org][storage.org]] §4). Writable overlays sit on top, and everything
runs in a user namespace, so PID 1 needs no new capability.

Code: [[file:../initramfs/lol-ct.c][=lol-ct.c=]] (the namespace helper, =/sbin/lol-ct=),
[[file:../initramfs/containers.lisp][=containers.lisp=]] (the Lisp side and public API),
[[file:../initramfs/runs.lisp][=runs.lisp=]] (a command's output streamed into a pane). Needs kernel tag #26 or
later. Related: [[file:storage.org][storage.org]] (the disk and why PID 1 runs as the user),
[[file:processes.org][processes.org]] (second processes), [[file:terminal.org][terminal.org]] (the terminal pane).

* 1. What it gives you

- *The host's toolchain, unchanged.* Inside, =/usr=, =/etc=, =/var= and =/opt= are
  the host's. A program finds the same libraries, certificates and paths it finds
  when you boot the host normally.
- *A shared workspace.* =/home= is the same directory the environment's editor and
  file manager use, so you edit in Lisp and build or run inside the container.
- *Your own identity.* You're your normal uid inside, with no capabilities.
- *Shared networking.* No network namespace, so a server started inside is
  reachable from Lisp sockets, and outbound connections work as they do outside.
- *Persistent changes, per container.* Writes to =/etc= or =/usr= land in a
  per-container overlay under =~/.lol/ct/<name>/=. Delete that directory and the
  container is fresh again.

The rule behind it: *the image doesn't grow to serve a project.* A toolchain
belongs to the project, not to the machine.

* 2. The kernel features it's built from

** 2.1 Namespaces

A *namespace* gives a process tree its own private copy of one kind of global
kernel state. Everything else stays shared. The container takes four:

- *Mount namespace.* Its own list of mounts. The container can mount overlays and
  switch root without PID 1 seeing any of it.
- *User namespace.* Its own uid table, mapped onto real uids. Inside, a process
  holds full capabilities — but only over objects its namespace owns. That's how
  an ordinary user may create mounts without =CAP_SYS_ADMIN= in the real world.
  Overlayfs, =proc=, =devpts= and =tmpfs= all declare =FS_USERNS_MOUNT=, so a user
  namespace may mount them.
- *PID namespace.* Its own process numbering. The first process in it is PID 1 /of
  the container/, and a fresh =/proc= shows only the container's processes.
- *UTS namespace.* Its own hostname (=lol-<name>=), so a shell prompt says where
  you are.

No *network namespace*: that's what keeps networking shared. It also means a
fresh sysfs can't be mounted, so =/sys= is bound in read-only instead.

** 2.2 Identity: the uid map

A new user namespace starts with an empty uid map. The creator writes one line
to =/proc/PID/uid_map=, and an unprivileged creator may map only /its own/ uid:

| Map                       | Inside you are | Consequence                                            |
|---------------------------+----------------+--------------------------------------------------------|
| =0 1000 1= (=unshare -r=) | root           | tools that refuse to run as root (=initdb=) refuse     |
| =1000 1000 1= (identity)  | yourself       | *used*: the same identity as on the host               |

The identity map needs one ordering trick. The helper does its mounts while it
still holds the namespace's capabilities, then =execve=​s the command as the
user. A non-root uid loses its capabilities across =execve=, so the command
starts with none (=CapEff= reads =0000000000000000=).

** 2.3 Overlayfs

*Overlayfs* stacks directories. A read-only *lower* layer (the host's =/usr=) is
shown merged with a writable *upper* layer. The first write to a lower file
/copies it up/ into the upper layer; the lower is never touched. A /work/
directory on the upper's filesystem is overlayfs' scratch space.

Two kernel rules shape the layout:

- *An upper can't sit inside its lower.* Overlayfs refuses that with =ELOOP=
  ("overlapping", =fs/overlayfs/super.c=). The uppers live under =/home=, which
  may be on the same ext4 as =/mnt/host/usr=, but outside it — that's allowed.
- *An overlay can't be another overlay's upper.* This matters only in testing
  (§9).

The root is built *one directory at a time* rather than as one overlay over the
whole host root. That keeps the host's =/boot=, =/root= and =lost+found= out of
the container, and lets =/home= be our own bind rather than the host's copy.

** 2.4 =pivot_root=

=pivot_root= swaps the process's root for a new tree and parks the old root on a
subdirectory, which is then unmounted. Unlike =chroot=, nothing can climb back
out.

It works from an initramfs on kernel 7.2: rootfs now sits on an immutable
=nullfs=, which is what makes moving it legal (see the comment above
=pivot_root= in =linux/fs/namespace.c=). Older kernels refused. =lol-ct= keeps
=MS_MOVE= + =chroot= as a fallback and logs which one it used.

* 3. The container's layout

#+begin_example
new root = a fresh tmpfs
  /usr /etc /var /opt   overlay(lower=/mnt/host/<d>, upper=~/.lol/ct/<name>/<d>/upper)
  /bin /lib /lib64 …    symlinks into usr/   (the host is merged-/usr)
  /home                 recursive bind of our /home   (read-write, shared)
  /tmp                  bind of our /tmp              (shared, see below)
  /dev                  recursive bind of our /dev, plus a fresh devpts on /dev/pts
  /proc                 fresh proc for the PID namespace
  /sys                  read-only bind
  /run                  fresh tmpfs
then pivot_root into it, and detach the old root
#+end_example

- *=/tmp= is shared.* One run's database socket must be reachable from the next
  run, and the web browser ([[file:web-browser.org][web-browser.org]]), which runs in a container, shares
  =/tmp= with the Lisp.
- *Name resolution follows the environment.* Our =/etc/resolv.conf= and
  =/etc/hosts= are bound over the host's. When the host's =resolv.conf= is a
  symlink (systemd's =../run/systemd/resolve/…=), =lol-ct= follows it inside the
  new root and binds over the target. Our =/etc/hosts= includes the host's own
  entries, appended by preinit at boot.
- *Overlay fallbacks.* If the upper can't be mounted, =lol-ct= tries, in order: the
  state upper, the same with =userxattr=, a tmpfs upper (changes vanish when the
  run ends), a read-only bind. The first that mounts wins. Each run writes the
  outcome and any reasons to =~/.lol/ct/<name>/layout=.

* 4. What you can and can't change

The user namespace maps exactly one uid. Every host file owned by anyone else
shows up inside as =nobody= (65534), and overlayfs checks permissions against
that:

| Path inside      | Owner seen | Write                                    |
|------------------+------------+------------------------------------------|
| =/etc= (its own upper) | you        | yes                                      |
| =/etc/apt=       | 65534      | /Permission denied/                      |
| =/var/lib/dpkg=  | 65534      | so =apt-get install= fails on its lock   |

*So the container runs the host's distribution but can't administer it.*

- *Install dependencies under =/home=.* Most language ecosystems already work this
  way: version managers (rbenv, nvm, pyenv), per-project package paths, a
  per-project database cluster in the project tree.
- *Install system packages from the host.* Boot the host distribution and use its
  package manager; the containers see the result.

=sudo= can't work inside, for four independent reasons:
1. =lol-ct= sets =PR_SET_NO_NEW_PRIVS= before the exec, so the kernel ignores
   setuid bits.
2. =/mnt/host=, and the =/home= bound from it, are =nosuid=
   ([[file:../initramfs/preinit.c::static int mount_storage][=mount_storage=]]), a flag locked inside a user namespace.
3. uid 0 isn't in the map, so =setuid(0)= fails, and a setuid file owned by an
   unmapped uid never grants anything.
4. =sudo= refuses an =/etc/sudoers= not owned by uid 0, and here it's owned by
   =nobody=.

And PID 1 isn't root either, so there's nothing to hand down. The one
administrative job the environment needs — installing its own next build — goes
through a fixed =lol-rootd= request instead
([[file:sbcl-init.org::Updating from inside — build, install, restart][sbcl-init.org → Updating from inside]]).

* 5. =lol-ct=, the helper

** 5.1 Why it's C

=unshare(CLONE_NEWUSER)= silently adds =CLONE_THREAD=, and =check_unshare_flags=
then refuses any caller with other threads (=linux/kernel/fork.c=). PID 1 is
multithreaded — the net REPL alone is an =sb-thread= — so the namespace work
needs a fresh, single-threaded process. A small static C program (musl, like
preinit) is the simplest one.

** 5.2 Command line and exit codes

#+begin_example
lol-ct [-n NAME] [-s STATEDIR] [-r HOSTROOT] [-C DIR] [-e VAR=VALUE]... [-N] [-v]
       [--] PROGRAM [ARG...]
lol-ct --probe-root [-r HOSTROOT]
#+end_example

=-N= makes stdin =/dev/null=. =--probe-root= tests whether an overlay with the
whole host root as its lower layer mounts here (§9).

|          Exit | Means                                                       |
|---------------+-------------------------------------------------------------|
| the program's | it ran; 128+N if signal N killed it                         |
|           125 | =lol-ct= couldn't build the container (reason on stderr)    |
|           127 | the program couldn't be executed                            |

** 5.3 The process tree

#+begin_example
the Lisp ── lol-ct (OUTER)   unshare user+mount+uts, write the id maps,
              │              unshare pid, fork; forward signals; relay the status
              └─ lol-ct (INIT, PID 1 inside)   build the root, pivot_root, fork;
                   │                           reap orphans; forward signals
                   └─ PROGRAM (PID 2)          execve'd as you, no capabilities
#+end_example

- *Why an outer process.* =unshare(CLONE_NEWPID)= moves only the caller's
  /children/ into the new namespace, so the container's PID 1 must be forked.
- *Why the init isn't the program.* The kernel drops any signal sent to a PID
  namespace's init that has no handler for it (=pid_namespaces(7)=). A program
  that never installs a SIGTERM handler — =sleep=, most shells — couldn't be
  stopped politely. The init catches the polite signals, forwards them to PID 2,
  and reaps orphans a daemonising program leaves behind.
- *One command, one lifetime.* When PID 2 exits, the init exits and the kernel
  kills everything left in the namespace. Run a long-lived server as its own run,
  in the foreground; the shared =/tmp= and network let later runs reach it.
- *If the outer process dies*, =PR_SET_PDEATHSIG= takes the init, and the whole
  namespace, down with it.
- *The init can't use =getppid()= to watch its parent.* It returns 0 in a PID
  namespace's init, because the parent lives in the ancestor namespace.

* 6. Using it

** 6.1 From the environment

- *Spotter* (=SuperL-Space=), type =containers=: the list of containers, plus "run
  a command in default…" and "new container…". Each container is also a Spotter
  row (=container default=), and =runs= lists this session's commands, live ones
  first.
- *On a container:*
  - *x* asks for a command line and runs it. It starts in the folder the focused
    pane shows when that's under =/home= (so *x* from the file manager runs
    there), otherwise in =$HOME=.
  - *s* opens a login shell in a terminal pane ([[file:terminal.org][terminal.org]]).
    =SuperL-Return= does the same for =default= from anywhere.
  - *D* deletes it after you type =yes=. *g* refreshes.
- *The container's view* shows its runs, its state directory (drill in for the
  file manager), and the last =layout= file, with any fallback tinted as a
  warning.

** 6.2 Run panes

A *run pane* is a read-only text pane that fills while the command runs.

- *Title and status.* =running 4 s=, then =exit 0 after 1.2 s= or =killed by
  signal 9=; a last line in green or red says the same.
- *Keys.* *k* stops it (SIGTERM, then SIGKILL after 3 s). *r* runs it again. *G*
  or *End* jumps to the end. *M-w* copies.
- *Following.* New output follows the end only while you're /at/ the end, so
  scrolling up to read stops the chase. The last 20,000 lines are kept.
- *A pty for output, =/dev/null= for input.* Behind a pipe, programs turn colour
  off and buffer whole blocks. Behind a pty for input, a login script asking for a
  passphrase would wait forever. So the program writes to a pty and reads
  =/dev/null= (=-N=).

Commands run through a *login* bash (=bash -lc=,
[[file:../initramfs/containers.lisp::(defparameter *container-run-shell*][=*container-run-shell*=]]), because =~/.profile= is
where version managers put themselves on the =PATH=. The price: whatever your
login dotfiles print heads every run pane. Set the variable to ='("bash" "-c")=
to skip them.

** 6.3 From Lisp

#+begin_src lisp
  (container-command-line '("git" "status") :name "default" :cwd "/home/me/app")
  ;; => ("/sbin/lol-ct" "-n" "default" "-C" "/home/me/app" "--" "git" "status")
  ;;    :env '("APP_ENV=test")  adds -e pairs;  :no-input t  adds -N

  (run-in-container '("bash" "-l") :pty t)        ; => an SB-EXT:PROCESS (lol-ct's)
  (container-run-output "id -u; hostname")        ; => lines and exit code, waited for
  (run-shell-in-container "make test" :cwd "/home/me/app")  ; a run pane
#+end_src

- *[[file:../initramfs/containers.lisp::defun container-command-line][=container-command-line=]] is the contract.* The
  terminal pane runs its shell through it, and the web browser runs Chrome
  through it.
- *Stopping.* Signal the process =run-in-container= returns; =lol-ct= forwards it
  inside.
- *State directories.* =create-container=, =list-containers= and
  =delete-container= are =mkdir=, a listing and a recursive delete (which first
  makes overlayfs' mode-000 =work/work= listable). Deleting is refused while any
  =lol-ct= for that container runs, found through =/proc/*/cmdline=: removing a
  mount point from another namespace would detach the running container's
  mounts.

** 6.4 Building the image inside a container

=./build.sh= works in the =default= container, kernel included: the host's
=gcc=, =musl-gcc= and firmware are all visible through the overlays.

One wrinkle: =build.sh= bakes in the UUID of the disk holding =$HOME=, and
=findmnt= can't find it inside — there's no udev and no =/dev/disk/by-uuid=, and
the block device is root's. So =build.sh= falls back to the host's =/etc/fstab=,
taking the =UUID== of the longest mount point holding =$HOME=. Installing the
result goes through the environment, not the container
([[file:sbcl-init.org::Updating from inside — build, install, restart][sbcl-init.org → Updating from inside]]).

* 7. Kernel and boot requirements

| Piece                                      | Provided by                                               |
|--------------------------------------------+-----------------------------------------------------------|
| =NAMESPACES=, =PID_NS=, =UTS_NS=, =NET_NS= | the kernel config                                         |
| =USER_NS=, =OVERLAY_FS=                    | the kernel config since tag #26 (=OVERLAY_FS= selects =FS_STACK=, =EXPORTFS=) |
| =UNIX98_PTYS= + =devpts= on =/dev/pts=     | the kernel config + preinit (which also mounts =/dev/shm=) |
| =/sbin/lol-ct=                             | the initramfs                                             |

- *No sysctl switch needed.* =unprivileged_userns_clone= is a Debian kernel patch;
  a vanilla kernel only limits =user.max_user_namespaces= (=kernel/ucount.c=).
- *No memory cap.* =CGROUPS=/=MEMCG= are off. =USER_NS='s help text recommends
  =MEMCG= to contain hostile users, which a single-user machine doesn't have.

* 8. Alternatives

| Option                                                           | Why not the default                                                   |
|------------------------------------------------------------------+-----------------------------------------------------------------------|
| Run =/mnt/host/usr/bin/…= directly through the host's loader     | Programs hard-code absolute paths (stdlib dirs, =/etc/ssl=, =#!= lines); only a mount namespace makes =/mnt/host= look like =/=. Fine for a single self-contained binary — Wi-Fi does this ([[file:networking.org][networking.org]] §7). |
| A separate root filesystem per project (=debootstrap= into =~=)  | Every file is the user's, so the =0 uid 1= map lets =apt= write it. The route for a different release, or for system packages without rebooting. Packages that =chown= to a second system user still fail. |
| A full uid range written by =lol-rootd= (like =newuidmap=)      | Needs =CAP_SETUID= in the parent namespace; widens the root helper. Not built. |
| A VM (KVM + the host's =qemu= run inside a container)           | For projects needing systemd or Docker. Needs =VIRTUALIZATION= + =KVM_*= (off) and =/dev/kvm= for the user. |
| A remote machine over SSH                                       | The host's =ssh= binary runs inside a container, so this builds on containers anyway. |

* 9. Tests and known pitfalls

=check-containers.lisp= boots the image in two modes, because no single QEMU
setup matches real hardware:

- *=LOL_GUEST_HOSTROOT=1=* mounts the build host's root read-only over virtio-9p.
  It checks: uid and hostname inside, the command as PID 2, no capabilities,
  =/etc= writable and =/etc/apt= not, a language runtime loading OpenSSL, a private
  Postgres started and queried, =git= under =/home=, outbound HTTPS, SIGTERM
  stopping a run, a run pane driven over QMP filling live with colour, and our
  =/etc/hosts= including the host's names.
- *=LOL_GUEST_DISK=test-disk.img=* uses an ext4 stand-in disk with no distribution
  on it. =lol-ct= builds the container and the exec fails with 127, as it should;
  the check asserts =/etc='s upper is under =~/.lol/ct/default/= and that the root
  was entered with =pivot_root=.

Together they cover real hardware: the toolchain runs (9p) and the uppers persist
(ext4).

Pitfalls worth knowing:

- *In 9p mode the uppers fall back to tmpfs.* There =/home= is itself an overlay
  (so tests can't write to the host), and an overlay can't be another's upper.
  The =layout= file says so: =upper in tmpfs (changes VANISH)=. A test artifact,
  not a design problem.
- *Whole-root overlays depend on the setup.* An overlay with =lowerdir=/mnt/host=
  mounts in the guest (9p and ext4, with and without =userxattr=). On a Debian
  7.1 host kernel, the same overlay over =/= failed with =EINVAL= at
  =FSCONFIG_CMD_CREATE=. Ruled out as the cause: the upper's filesystem (tmpfs
  fails too), =userxattr=, recursive binds, and stacking depth (=/= was plain
  ext4). Unexplored: Debian's kernel patches, and the lower being the mount
  namespace's root rather than a mount below it. The per-directory layout
  sidesteps the question; =lol-ct --probe-root= re-asks it.
- *Inbound connections are unverified.* A server inside the container reached from
  the Lisp side follows from leaving out =CLONE_NEWNET= but has no test yet.
