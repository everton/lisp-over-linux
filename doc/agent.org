#+TITLE: The Agent — an LLM client native to the Lisp machine
#+STARTUP: showall

The agent is an LLM client written in Lisp that lives in the image. It speaks the
Messages API over HTTPS, reasons about the running system through the
introspection layer the code browser already uses, and is reached from the REPL,
from any pane of the environment, and from inside the debugger.

Status: *built and in use.* The client, the tool surface, the three doorways, the
gate, failure reporting and saved conversations are in the image, tested end to end
against a mock Messages API (§13) and used against the real one. What's still owed
is in §15.

Related: [[file:networking.org][networking.org]] (the TCP, DNS and HTTPS it stands on) ·
[[file:code-browser.org][code-browser.org]] (the environment it plugs into) ·
[[file:sbcl-init.org][sbcl-init.org]] (the Lisp userland) ·
[[file:session-persistence.org][session-persistence.org]] (the =~/.lol/= tree).

* 1. What it is

An LLM client is four layers on a socket: a *transport* (HTTP/1.1 over TLS), a *wire
format* (JSON in, JSON or Server-Sent Events out), a *protocol* (the Messages API and
its tool-use loop) and a *tool surface* (what the model may do). The first three are
the same work anybody does. The fourth is the only one specific to this machine, and
here it's almost free: =registry.lisp=, =model.lisp= and =present.lisp= already
implement every capability an agent wants, as ordinary functions.

* 2. Why a native client

** 2.1 The alternatives

- *The =claude= CLI in the guest.* It's a single Bun-compiled ELF (about 290 MB) that
  needs only the glibc family and a kernel we mostly already had. Making it /useful/,
  though, means importing a POSIX userland — a shell, coreutils, git — into a system
  whose premise is that Lisp is the userland, so it can reason about the machine by
  reading files that don't exist there. It now runs in a container's terminal pane
  ([[file:terminal.org][terminal.org]]) as an ordinary program, at arm's length from the image.
- *A host-side TLS broker.* A small host program holding the key and doing the
  handshake, with the guest speaking plain HTTP to it. Never built: HTTPS arrived first
  through the host's own libssl (§4.1). It would also have had to be addressed as
  SLIRP's =10.0.2.2=, which exists under QEMU and nowhere else.
- *TLS 1.3 in Lisp.* Removes the host dependency; scoped but not built (§12).

The client itself — HTTP, JSON, SSE, the protocol, the tool loop — is ordinary,
dependency-free Lisp, written for the same reason as the DHCP client and the line
editor: to understand it from the inside.

** 2.2 It queries the machine it reasons about

A conventional coding agent works at arm's length: it reads text files, runs
processes, parses their output. Here there's no arm's length:

- *=(source-of 'draw-alien)=* returns the definition the image is running.
- *=(senders 'read-fb-geometry)=* returns the callers from SBCL's own xref database —
  not a text search, so a macro-generated call is found even when the name never
  appears at the call site.
- *=accept-source=* compiles a definition into the running image and records it in
  the change set. The agent's edits land where yours do: no file to write, no build,
  no reload, which is what makes the loop fast enough to be conversational.
- *After an accept*, =lisp-source= returns the new text, because the registry holds
  it. The agent's view of the system updates the instant the system does.

** 2.3 An answer should be an object, not a paragraph

If a reply is a string, everything downstream is string handling. Make it a CLOS object
that takes part in =present= / =commands-for= and a message is drillable like a class
or a method: a tool call becomes a row that opens what it asked about, a proposed
definition sits in a buffer where =C-c C-c= accepts it. The same argument makes JSON
objects a class (§5).

* 4. Transport, key and settings

** 4.1 HTTPS through =http-request=

The agent calls the networking track's =http-request= (=(transport)= in =agent.lisp=;
a test redirects it through =*agent-transport*=). That client does HTTP/1.1, chunked
bodies and streaming callbacks, and does TLS by loading the *host's* OpenSSL from
=/mnt/host= at runtime — never at build time, so the image doesn't depend on it
([[file:networking.org][networking.org]] §2e).

Depending on a finished network layer — a default route, a Lisp DNS resolver, SNTP for a
clock that makes certificate dates checkable — is what lets the same image work under
QEMU and on real hardware. The cost: a diskless boot has no =/mnt/host=, so no HTTPS.

** 4.2 The key

- *Where.* =~/.lol/agent/anthropic-api-key=: one line, the key, mode =0600=. A key
  left at the older =~/.config/lol/anthropic-api-key= is moved there at boot by
  [[file:../initramfs/lol-home.lisp::defun migrate-lol-home][=migrate-lol-home=]], never overwriting one already there.
- *Read at runtime.* =save-lisp-and-die= freezes the heap, so a key present at build
  time would ship in the image forever. It lives in one special variable, is never
  printed or logged, and is sent *only* when the endpoint is =https://api.anthropic.com=
  — not over http, not to any other host (tested both ways). A mock server gets no key.
- *No home.* A diskless boot has no =/home=; the agent says it has no key and where it
  would look, and the environment starts as usual.
- *Unreadable.* A key file with the wrong owner or mode is its own failure (§9),
  quoting strerror's words and never the contents.

** 4.3 Settings

Everything about a request is a special variable, and =~/.lol/agent/settings.lisp= may
set them: =:model :max-tokens :effort :thinking-display :endpoint :fallbacks :wrap
:max-rounds :initiative :authority=.

- *Read, never loaded.* The file is one plist, =READ= with =*read-eval*= off — a
  settings file must not be able to run code, and =#.= would. Unknown keys and
  ill-typed values are reported and skipped.
- *Written atomically.* [[file:../initramfs/agent.lisp::defun save-agent-setting][=save-agent-setting=]] rewrites the whole plist through a
  temporary file and a rename, so a crash leaves the old file or the new one.

* 5. JSON, and one decision that earns its keep

| JSON    | Lisp                                              | Why                                         |
|---------+---------------------------------------------------+---------------------------------------------|
| object  | a =json-object= *instance* (ordered alist inside) | so =present= can dispatch on it             |
| array   | =simple-vector=                                   | distinguishable from a list at a glance     |
| string  | =string=                                          |                                             |
| number  | =integer= / =double-float=                        |                                             |
| =true=  | =t=                                               |                                             |
| =false= | =:false=                                          | never =nil= — =nil= is ambiguous three ways |
| =null=  | =:null=                                           | ditto                                       |

- *Objects are a class.* It costs an accessor instead of =gethash= and buys
  =(present response)=: every content block, usage object and error body is a
  navigable tree in the same UI as everything else.
- *Order is kept.* Request bodies must serialise byte for byte the same, or prompt
  caching silently stops working; =poc/agent-test.lisp= checks two serialisations are
  equal.
- *The writer refuses =nil=*, so an ambiguous value never reaches the wire.
- *Surrogate pairs* are glued back together; a lone half reads as U+FFFD.
- *Names are qualified.* =agent.lisp= writes =lol.json:jget= in full rather than
  =use-package=, because another module defines its own =JOBJ= in =CL-USER= (§14).

* 6. The conversation and the protocol

** 6.1 The conversation as a live object

#+begin_src lisp
  (defclass conversation ()
    ((messages …)     ; newest last; each content block exactly as the API knows it
     (turns …) (calls …)  ; what the pane draws: questions, notes, tool calls
     (authority …)    ; NIL: follow *agent-authority*; else this conversation's own
     (tools …)        ; the tools array as first sent (§7.4)
     (usage …) (cost …)
     (lock …) (revision …) (thread …) (jobs …)))  ; shared with the UI thread (§6.4)
#+end_src

- *The turn loop is a method on it*, so the same conversation is driven from the REPL,
  a tab or the debugger without any of them owning it.
- *=present= methods* on the conversation and its parts give the browser its view
  (§8.3).
- *Several coexist.* The debugger's ASK gets its own, seeded with the backtrace, and
  leaves the one in your tab alone.
- *It's inspectable* with the very tools it's using.

The protocol rule people get wrong: on a =stop_reason= of =tool_use=, append the
assistant's *entire* content — thinking blocks unmodified — then send one user message
with one =tool_result= per =tool_use=, keyed by =tool_use_id=. Dropping or editing a
block breaks the turn.

** 6.2 The request

- *Model.* =claude-opus-5-5= by default (=*agent-model*=).
- *Thinking.* Adaptive, =display: "summarized"=; a summary costs one dim
  =;; (thinking: …)= line. Thinking blocks go back unchanged, signature included.
- *Prompt caching.* The system prompt carries a cache breakpoint, so does the last
  tool, and the request carries the top-level automatic one, which caches the history.
  The body is serialised field by field in a fixed order (§5).
- *Tool input streams eagerly* (=eager_input_streaming=), so a long =lisp-accept=
  source arrives as it's written. The API then no longer validates it, so the client
  checks every input against its schema (=check-tool-input=) and answers unparseable
  JSON with an =INVALID_JSON= error result instead of running anything.
- *Refusals.* =fallbacks: "default"= with the =server-side-fallback-2026-07-01= beta
  header, on models that have server-side fallback. A =refusal= or =max_tokens= stop
  never runs the tool calls in it; the next question first answers them with "not run"
  results, because an unanswered =tool_use= makes the next request invalid.

** 6.3 Retries, cancellation, cost

- *Retried.* 408, 409, 429, 5xx and 529; the =overloaded_error=, =api_error= and
  =rate_limit_error= events that can arrive mid-stream; dropped connections; a TLS read
  that timed out or broke mid-stream. Exponential backoff or the server's
  =retry-after=, up to =*agent-retries*= (6) attempts, each a visible note in the
  transcript. A partial reply is never kept in the history.
- *Not retried.* 400, 401, 403, 404; a certificate that doesn't verify; OpenSSL
  missing; a name that doesn't exist; whatever the preflight refuses (§9).
  [[file:../initramfs/agent.lisp::defun retryable-p][=retryable-p=]] decides.
- *Cancellation.* =C-g= sets a flag the stream checks between chunks *and* interrupts
  the turn's thread with a =throw=, because a turn can be blocked in a read with no chunk
  coming. The conversation carries on afterwards.
- *Cost.* Every response's =usage= (input, cache read, cache write, output) is priced
  per model (=+agent-prices+=; a cache write at 1.25× input), per turn, per conversation
  and per session.

** 6.4 Two threads, one owner of the UI

=http-request= is a blocking call with a callback, so a turn runs on a thread of its own.
*Tools run on the environment's thread*: the turn posts a job and waits, and the frame
tick runs it. So the image's UI state is still touched by one thread, and an approval
has a screen to ask on.

- *What's shared.* Only the conversation object, under its mutex, with a revision
  counter the tick polls.
- *Redraws* are budgeted at ~15 Hz while a turn runs and stop entirely when none does.
- *Exceptions.* Off-main tools (§7.5), =await-subagents= (§7.6), and the debugger's
  conversation (§8.8) run their work on the turn's thread.

* 7. The tool surface

** 7.1 What the model is told

Not the image's source — far too large, and it would waste the semantic index. The
system prompt, =*agent-system-prompt*=, says what the machine is (SBCL as PID 1, no
shell, the registry owns the source) and the model navigates: =lisp-apropos=, then
=lisp-source=, then =lisp-senders= — the glob/read/grep motion, except every step is
exact.

- *The prompt is a definition in the registry*, so it's browsable, editable and
  Accept-able like everything else.
- *No package of its own.* The agent lives in =CL-USER= like the other modules;
  =lisp-apropos= skips it by *file* (the registry knows where every definition came
  from), which needs no package.
- *Findings are marked.* The prompt asks the model to begin a finding with =◆= and a
  finished piece of work with =✔ Done:=; the pane colours those lines.

Every tool is a =define-agent-tool= and goes through =execute-tool-call=: input checked
against its schema, a gated one through the approval condition (§8.4), any error an
=is_error= result.

- *Name lookup never interns.* Names go through =find-symbol=, never =read=, so a typo
  doesn't litter the image with symbols.
- *The key never leaves in a result.* CL's =describe= prints a variable's value, so
  =lisp-describe= of =*agent-api-key*= once printed the key. Every result now passes
  [[file:../initramfs/agent.lisp::defun redact-api-key][=redact-api-key=]], and =lisp-inspect= shows it as =[the API key — never shown]=.
- *=lisp-backtrace= reads a copy.* An sb-di frame is a pointer into the debugger
  thread's stack, but the debugger's conversation runs its tools on another thread
  (§8.8). So the ASK restart first copies every frame's name, definition and locals as
  strings, on the debugger's own thread (=note-debugger-context=). The debugger is
  modal, so the stack can't change meanwhile. Elsewhere the tool says there's no
  condition and lists the image's threads.
- *=web-fetch= is gated like a write* though it changes nothing here: a GET carries its
  URL out, and a URL can carry anything the conversation has read. So it asks under
  =:ask= and isn't offered under =:read-only= — which also means a subagent can't fetch.
- *=lisp-eval= exists* though it subsumes every other tool. The gate carries the weight.

** 7.3 Gating writes

The gated tools can change the world or send data out. The *authority* dial (§8.9)
decides what happens to them:

| Authority    | Behaviour                                                       |
|--------------+-----------------------------------------------------------------|
| =:read-only= | gated tools aren't offered                                      |
| =:ask=       | each call raises an approval request (§8.4) — the default       |
| =:allow=     | run it                                                          |

- *A denial isn't an error.* It goes back as a =tool_result= saying the user declined,
  and the model adapts. That's why =:ask= as the default doesn't make the loop useless.
- *Allow all writes.* [[file:../initramfs/agent.lisp::defun allow-all-writes][=allow-all-writes=]] sets authority to =:allow= for the
  session, and for the conversation if it has its own setting (which would otherwise
  win). =:save t= also writes =:authority :allow= to the settings file.
  [[file:../initramfs/agent.lisp::defun ask-before-writes][=ask-before-writes=]] undoes it. The agent's commands offer "Allow all writes
  (stop asking, this session)", "… always (save …)" and "Ask before writes again"; at
  the REPL's approval prompt, =a= allows this call and every later one.
- *The dial is checked when a call runs*, not only when the request is built (§7.4):
  =gated-run= declines a write under =:read-only=.

** 7.4 A conversation's tools never change

A thinking block's signature covers the request that produced it, and the tools array
is part of that request. Change one byte of it mid-conversation and the API refuses
every earlier thinking block with a 400 ("Invalid =signature= in =thinking= block … The
=tools= list differs …"), and the conversation is dead.

The array used to be rebuilt per request, so it moved whenever authority entered or
left =:read-only=, a tool's =AVAILABLE-P= changed, or =C-c C-c= on a =define-agent-tool=
moved it to the end of =*agent-tools*=. Now:

- *Frozen at the first request.* [[file:../initramfs/agent.lisp::defun conversation-tools][=conversation-tools=]] computes the array once and
  sends the same bytes for the rest of the conversation (and saves them, §10).
- *Enforced at call time.* =gated-run= declines a write under =:read-only=;
  =execute-tool-call= answers a tool whose =AVAILABLE-P= has turned false with an error
  result.
- *New tools wait.* A new or redefined tool reaches the model in the next conversation.
  A conversation that already hit the 400 can't be repaired; start a new one.

** 7.5 Tools that can't freeze the environment

Tools run on the environment's thread (§6.4), and =C-g= is read by that same thread. A
=lisp-eval= that never returns, or a =container-run= whose program never exits, used to
stop the screen for good ([[file:diagnostics.org][diagnostics.org]] §9). Three limits:

- *Off-main tools.* A tool defined with =:off-main t= ([[file:../initramfs/agent.lisp::defun post-job-and-wait][=post-job-and-wait=]]) sends only
  its *approval* to the environment's thread; the work runs on the turn's thread, where
  =C-g= reaches it. =container-run= and =web-fetch= are off-main: neither touches Lisp
  state, and either can wait minutes. =cancel-conversation= interrupts the thread, and
  =container-run='s cleanup ([[file:../initramfs/agent.lisp::defun stop-tool-process][=stop-tool-process=]]) sends TERM, then KILL, then reaps,
  =without-interrupts= so a second =C-g= can't cut it short.
- *Time limits.* =lisp-eval= is stopped after =*lisp-eval-seconds*= (60) with
  =sb-ext:with-timeout=, unwinding the form as C-c would; the model gets an error naming
  the limit, plus whatever the form printed. =container-run= stops its program after
  300 s, or sooner if the model passes ="timeout"=.
- *Output capped as it's written.* Both print into a =capped-output= Gray stream that
  keeps =*tool-output-cap*= (200000) characters and only counts the rest. Capping
  afterwards was too late: =(loop (print 1))= fills a string until the heap is gone,
  long before any timeout.

=lisp-eval= stays on the environment's thread, because the image is changed by one thread
at a time. A looping form is now stopped, but the screen still waits up to 60 s.

** 7.6 Plans and subagents

- *=update-plan=* takes the whole task list each time, one task per line with a mark:
  =[x]= done, =[>]= active, =[ ]= pending, =[!]= failed ([[file:../initramfs/agent.lisp::defun parse-plan][=parse-plan=]]).
- *=spawn-subagent=* starts a *read-only* conversation on a goal, on its own thread, and
  returns at once. At most =*subagent-max*= (4) run at a time; a subagent can't start
  its own.
- *=await-subagents=* waits up to a timeout and returns each one's final answer. It's
  the one tool that runs on the turn's own thread (=*in-thread-tools*=): the subagents'
  tool calls run on the environment's thread, so waiting there would deadlock them.

The tools find their conversation through =*tool-conversation*=, bound by
=execute-tool-call=. A conversation's plan and subagents live in a weak side table
(=*conversation-activities*=) rather than a new slot, so a running image could take the
change without redefining the =conversation= class under live instances. Both show in
the Activity panel (§8.3).

* 8. How you talk to it

** 8.0 The constraint: no fifth idiom

Everything you can already do in the environment is one of four moves:

1. *evaluate a form* — the REPL, =C-x C-e= /Do it/, =C-c C-p= /Print it/
2. *drill into a subject* — =Enter=, =Super-Space= (Spotter), =M-.=, =present=
3. *choose from what's offered* — the debugger's restarts, a command menu
4. *accept a change* — =C-c C-c=, landing in the change set

The agent expresses itself entirely in those four moves. A chat pane with a text box, a
modal approval dialog, an "agent mode" you enter and leave — each would be a fifth idiom
and a foreign body, however familiar from other tools. §8.10 lists what this rejects;
§8.9 refines it: ambient *state* isn't modal capture. The reward is that almost none of
the interaction had to be written — it already existed.

** 8.1 "Ask it" — the sixth verb

The environment's verbs are Smalltalk's — Accept (=C-c C-c=), Do it, Print it, Inspect it
(=C-c C-i=), Debug it (=C-c C-d=). The agent adds one:

#+begin_src
  C-c C-a   Ask it     — ask about the selection
  C-c ?     Ask it     — the same, everywhere
#+end_src

- *Where.* =C-c C-a= in every editor pane and on lists — except a function's inspector,
  where =C-c C-a= already means /Apply it/. =C-c ?= is Ask everywhere.
- *What gets asked.* Prose selected: that prose is the question. A form or nothing
  selected: the minibuffer asks for a question, and Enter alone asks "what is this".
- *You're always already somewhere.* Standing in =draw-alien= and asking means "about
  =draw-alien=" without typing its name, because =present= already models where you are
  as a subject. A terminal agent can't have that.
- *Every subject* gains an /Ask the agent about this/ command (one =:around= method on
  =commands-for=), so it's in the right-button menu and the halo.

** 8.2 The REPL: one character

#+begin_src
  lisp> ?why does draw-alien flip the rows?      ; prose — no quotes, no parens
  lisp> ?                                        ; prose mode until a blank line, prompt ?>
  lisp> (ask "…")  (ask :new "…")                ; the function, for composing
#+end_src

- *The =?= test* happens before =read=, so it costs one character comparison.
- *=(ask …)= returns the conversation*, so the REPL's history variables hold it:
  =(present *)= opens it, =(show-inspect *)= inspects it. =(ask :new "…")= starts a
  fresh one.
- *Writes ask right there*: the same restarts as the environment's chooser, numbered.
- *It works over the network REPL* unchanged, so the agent is reachable from a host
  terminal (tested).
- *Not built:* the prompt's agent mark (§15).

** 8.3 A conversation is a Workspace, not a chat pane

A conversation is literally a =:workspace= view. In a chat pane a code suggestion is
text in a bubble you copy somewhere; here the model's proposed definition is already in
an editable buffer where =C-c C-c= compiles it into the image and records it in the
change set. Conversations are Spotter entries, so =Super-Space= finds the one you had.

- *Prose as comments.* The model's prose is written as =;;= comments and only its
  =```lisp= blocks as raw code. The Workspace verbs find "the form before point" by
  reading from the top, so prose with a stray comma or unbalanced quote would make every
  form below it unreachable. As comments, the conversation reads as a Lisp file, and
  =C-x C-e= / =C-c C-c= work on a proposal where it landed. Markdown is cleaned into
  plain lines.
- *Asking.* The next question is what you type after the last =;; --- your turn= line;
  asking takes it out of the buffer and the turn writes it back as =;; ?= lines. A rule
  between turns names the authority in force.
- *Read-only while streaming.* Motion still works; edits above are never overwritten.
- *Steps folded.* Under =*agent-steps-detail*= =:concise= (the default) each run of tool
  calls is one dim line, such as =⋯ 6 steps · read 4 · ran 2 ✓=, and thinking is hidden.
  =:verbose= shows every =;; #N= line and the thinking; the conversation's menu
  switches. A call waiting for approval is always shown in full.
- *The Activity panel.* A conversation pane at least 900 px wide gets a list view on its
  right, about a third of the width: [[file:../initramfs/agent-ui.lisp::defstruct (subj-agent-activity][=subj-agent-activity=]]. Its groups are the
  plan, calls waiting for approval, subagents, the last twelve changes (definitions
  accepted, files written) and what =browse= showed you. Rows drill; =SuperL-o= moves
  focus between transcript and panel; the menu hides or shows it. The layout follows
  the static mock =doc/design/agent-workbench.html= (layout A).

** 8.4 Approval is a condition, not a dialog

#+begin_src lisp
  (restart-case (signal 'tool-approval-request :call call)
    (allow () …) (deny (&optional reason) …) (edit (new-text) …))
#+end_src

Whoever is around decides, with machinery that already exists:

| Where you are      | What you see                                                       |
|--------------------+--------------------------------------------------------------------|
| the environment    | the chooser card the right-button menu uses; keys 1–4, Esc denies  |
| the REPL           | the same restarts, numbered                                        |
| a script or a test | =handler-bind= chooses — policy with no extra API; nobody = denied  |

- *The chooser, not the debugger's rail.* The rail belongs to a modal debugger standing
  on a stack; the chooser is the environment's existing "choose from what's offered".
- *Esc denies*, because the turn's thread is waiting on an answer.
- *Only asked while you look at the conversation.* Elsewhere the status line says the
  agent waits, the tab's dot turns amber, and =SuperL-a= takes you there (§8.5's "never
  steal focus").
- *You see what you approve.* A write's full input — the form, the source, the file
  body — is in the transcript above the card.

** 8.5 It can show you things

The =browse= tool asks the shell to =present= a subject, so the answer to /where is this
used?/ is the senders view, live and drillable, not a list of names in prose. It isn't a
web browser; fetching a URL is =web-fetch=.

- *Beside, never steal focus.* A browsed subject becomes a row in the Activity panel's
  "shown to you" group, one Enter away — a =present :around= on the Activity subject in
  =agent-tools.lisp=. With no panel on screen, it opens in a tab behind the current one.
- *Main thread only.* It touches the screen only from the environment's thread.

** 8.6 "How do you know that?" is one keystroke

Every claim the agent makes about this system came from a tool call, and every tool call
has a subject. Under =:verbose= each call is a =;; #N name argument -> summary= line;
=C-c C-o= on it opens the subject it was about — the same view you'd have reached by
hand (the last column of §7.2). Verifying the oracle is the same motion as browsing.

** 8.7 Ask and keep working

Asking never blocks: the turn runs on its own thread (§6.4), you keep browsing, and the
conversation's tab fills in behind you, its dot pulsing while it works. =C-g= in a
conversation that's answering stops the turn, because =C-g= already means "get me out of
this" everywhere else. Deltas arrive faster than the framebuffer should redraw, so the
tick redraws on a ~15 Hz budget.

** 8.8 The debugger — where it converges

=run-debugger-fb= establishes one more restart around the rail:

#+begin_example
  ASK   — explain this, and propose a fix
#+end_example

It's not a chat window that opens on an error; it's one more restart, chosen like any
other, and listed *last* so Enter still means the condition's own first restart.

- *Seeded.* Choosing it starts a conversation with the condition's report, the
  restarts, the backtrace, and the source and locals of the innermost frame there's
  source for — the source exists because the image owns it.
- *A viewer over the standing stack.* The answer streams in there; =C-c C-c= accepts the
  form before the caret; Esc returns to the rail, where retrying is the condition's own
  resuming restart. Retry is only offered when the condition has one — =abort= and
  =continue= aren't the same thing.
- *Read-only, its tools on its own thread.* The debugger is modal and runs no frame tick
  to hand tools to, and it's the highest-stakes place to let a model write. The one
  write here is your =C-c C-c=. =lisp-backtrace= reads a copy of the stack (§7.2).

** 8.9 Modes — because there are two actors now

*Modal capture* — a mode that changes what your keys mean — is what §8.0 rejects.
*Ambient state* — something that changes what the environment may do without being asked
— is a different thing, and Lisp is full of it: =*package*=, =*print-base*=, a
read-only buffer.

The test: if it changes what your keys do, reject it. If it changes what the environment
may do unasked, it must exist *and be visible*. This environment hides its chrome on
purpose, but with a second actor you must always see whether it can act and what it may
touch.

*** Two dials, not one

Initiative and authority are orthogonal; one on/off switch conflates "proactive but
powerless" with "reactive but dangerous".

- *Initiative* — =:off= · =:reacting= · =:interacting= (=*agent-initiative*=)
- *Authority* — =:read-only= · =:ask= · =:allow= (=*agent-authority*=, §7.3)

|                | =:read-only=                          | =:ask=                                       | =:allow=           |
|----------------+---------------------------------------+----------------------------------------------+--------------------|
| =:reacting=    | an oracle — the safest useful default | the normal working mode                      | "just do it"       |
| =:interacting= | an observer that may offer opinions   | *pairing* — it notices, proposes, you accept | delegated autonomy |

=:off= makes asking inert: no sockets, no tokens. =:interacting= exists and shows (a
filled dot), but nothing acts unasked yet (§15).

*** Local modes are dynamic bindings

A local mode isn't a per-pane field; it's a special variable with dynamic extent.

#+begin_src lisp
  (let ((*agent-initiative* :interacting)
        (*agent-authority* :read-only))
    …)
#+end_src

Scope is well defined, it nests, and a script binds both for its extent the way it binds
=*package*=. A conversation can also carry its own authority, which wins over the global
one.

*** The indicators

| Scope    | Indicator                                                                                                                  |
|----------+----------------------------------------------------------------------------------------------------------------------------|
| global   | the tray item: an orange creature (=draw-agent-icon=, dimmed when =:off=), the authority and the session's cost, e.g. =ask $0.01=; =...= while working, =?= while waiting |
| per tab  | a dot over the =·= of a conversation's tab: hollow =:reacting=, filled =:interacting=, pulsing while working, solid amber while waiting |
| the REPL | the prompt — not built (§15)                                                                                              |

- *No new palette entries.* Colour is authority, mapped onto meanings the shell already
  carries: teal =*ui-accent*= = safe (read-only), amber =*ui-amber*= = "something wants
  you" (ask), red = "look here" (allow); dim for off. Deliberately not the green of
  =:method= — the agent isn't a kind of definition.
- *The tab's stripe keeps meaning kind.* One channel, one meaning.
- *In the terminal* only the 16 ANSI colours exist (fbcon ignores =38;5;n=), so a prompt
  mark would use SGR 90 / 96 / 93 / 91 for the same meanings.
- *The cost is on screen.* An environment that can spend money while you read owes you a
  visible meter, and =:interacting= would spend tokens with no keystroke of yours.

The design mock: [[file:../media/agent-indicator-design.html][media/agent-indicator-design.html]] (open locally).

*** Changing modes needs no new idiom

The agent is a subject — Spotter "agent" — whose rows are settable with =C-c C-c= and
whose commands set the dials. From the REPL they're variables, so you set them. There's
no preferences screen.

** 8.10 What it deliberately doesn't have

| Not this                                   | Because                                                 |
|--------------------------------------------+---------------------------------------------------------|
| a chat tab with an input box at the bottom | a fifth idiom (§8.0); the Workspace already is one      |
| a modal approval dialog                    | a condition and the chooser do it (§8.4)                |
| a mode that captures input                 | ambient state yes, modal capture no (§8.9)              |
| a permanent sidebar / assistant panel      | the indicators are the chrome budget; the Activity panel is a drilled-into view, not furniture |
| suggestions while =:reacting=              | in that mode, pull never push — and the mode is visible |
| a preferences screen                       | modes are variables and a subject (§8.9)                |
| a second completion mechanism              | =Tab= completion belongs to the editor, not the oracle  |

* 9. Failure reporting

Every failure says what went wrong and what to do, in the pane, at once. A question
asked with no network used to produce *nothing* in the pane; three causes were found:

- *A silent path.* =start-turn-async= caught an error escaping =run-turn= only to set a
  status the transcript draws while a turn is in progress — so the pane stayed as it
  was and the thread ended quietly.
- *The explanation came late.* Failures that couldn't change ("no DNS server") were
  retried like a 503, five attempts and 30 s of backoff, then shown in the same style as
  retry notes.
- *A connect could take minutes.* The one 300 s timeout was =SO_SNDTIMEO=, which on
  Linux also bounds =connect()=, so a connect to an address that never answers ran the
  kernel's whole SYN-retry budget (=TCP_SYN_RETRIES= 6: about two minutes) per attempt.

** The preflight

=agent-preflight= runs once per turn before any request and sends nothing:

- *A literal endpoint address*: is there a route covering it (=/proc/net/route=;
  loopback always)?
- *A name*: is there a default route (v4 or v6), a DNS server, and a route to it?
- *=api.anthropic.com=*: is there a key, and can it be read?
- *https*: does the host's OpenSSL load?

It signals =agent-not-ready= with /every/ reason found — the first as the headline, the
rest as "Also: …", so fixing the network doesn't merely uncover the missing key one
attempt later. Never retried.

** A short connect

=http-request= takes =:connect-timeout=; the agent uses 15 s (=*agent-connect-timeout*=)
and keeps 300 s between reads.

** One description per failure

Every failure becomes the turn's =failure=, a plist =(:headline :details :advice)= written
by one function, =describe-agent-failure=:

- *The preflight's reasons.*
- *HTTP statuses.* 400 (the API's own message), 401 (the key file named, never the key —
  and the cached key is dropped so the next try re-reads the file), 403, 404 (model and
  endpoint named), 413, 429, 529/overloaded, other 5xx.
- *The stream.* An error event mid-stream; a stream cut short.
- *The network.* DNS (NXDOMAIN vs no answer), TLS (no OpenSSL on this boot vs a
  certificate, with the clock as the usual suspect), connect refused or timed out.
- *The key file* unreadable: =key_unreadable=, with strerror's words.
- *Anything else*, named by type as /a bug in the agent's code/ — not the network or the
  key.

=run-turn= does all its work inside its handler, and =start-turn-async='s outer handler
calls =fail-turn= too, which makes a turn for the question if none was in progress — so
even a failure before the turn began has a place in the transcript.

** How it shows

- *The error block.* =;; !! FAILED: <headline>=, the details indented under it, then
  =What to do:=. Text that streamed before the failure stays above it, marked =(the
  answer broke off here)=, and is never sent back. Still Lisp comments, so the buffer
  still evaluates. A failed turn that spent nothing shows no meter line.
- *Red, decided by the text.* The textview's =tint= slot is a function =(line) → colour or
  NIL= that draws a whole line in one colour over the syntax. =present= on a conversation
  passes =conversation-tint=, which colours every line starting =;; !!= in
  =(concept-color :condition)=, the red a condition has everywhere. Because it reads the
  line, it holds after any edit; the debugger's ASK viewer uses it too.
- *The status line*, once per failure, set by the frame tick (never from the turn's
  thread): =agent: <headline> — C-c C-a with nothing typed asks again=, or =— SuperL-a
  shows why= when the conversation isn't on screen.
- *The REPL* prints the same failure in red, its advice adapted (asking again there is
  another =?= line).

** Asking again

=C-c C-a= with nothing typed after a failure starts a turn marked =(asked again)= (=run-turn=
=:again=). When the history already ends in the user's unanswered message, it's sent as
is — =add-user-text= folds new text into a trailing user message, so re-adding the question
would say it twice. A /new/ question typed instead is folded into the unanswered one, and
the model sees both.

* 10. Persistence

A conversation is written to =~/.lol/agent/conversations/<UTC stamp>-<id>.json= at the
end of every turn, however the turn ended (=*turn-end-hooks*=, called in =run-turn='s
cleanup). The file holds what it takes to *continue* the conversation, not only to read
it:

- *Every message*, each content block as the API knows it, thinking signatures byte for
  byte.
- *The tools array as first sent.* A thinking signature is bound to its request, tools
  included (§7.4), so a reopened conversation must send the same tools, not today's.
- *The turns* (question, notes, failure, cost), the tool calls (input, result, summary)
  and the plan.

It's JSON because the messages and tools already are: they go back out as they came in,
with no second mapping to get wrong.

- *Same promises as =settings.lisp=.* Nothing written without a real home (a diskless
  boot's =HOME= is =/=); atomic writes (=write-file-atomically=); nothing signals (a
  failure goes to the session log).
- *The user's alone.* =0600= in a =0700= folder, because a conversation quotes whatever
  its tools read.
- *Never the key.* It travels in a header, never in a message; every tool result has it
  taken out; a file whose text would still contain it isn't written at all.
- *Not saved.* The endpoint (a setting); each call's live subject (the common ones are
  found again from the call's input, so =C-c C-o= still works on a reopened
  =lisp-source=); subagents (their reports are already in the parent's transcript).

*Reopening.* The Spotter lists "saved conversations" and, for each one not open, "saved
conversation: TITLE"; its preview reads the file and loads nothing. Drilling it makes it
a live conversation again, made current, and the next question continues it into the same
file. Its earlier spend is kept apart, so the tray's cost stays this session's; the file's
=cost= is the total.

* 11. Security

- *Never bake the key* (§4.2). It's read at runtime from =/home= and lives in one special
  variable.
- *Prompt injection is real here.* The model reads =source-of= output, content from the
  image. If it can also =accept-source=, anything that can write a definition can steer the
  agent; that's why =:ask= is the default. The same goes for files, web pages and
  container output it reads.
- *Data out.* =web-fetch= is gated because a URL can carry anything the conversation has
  read (§7.2).
- *The clock.* Certificate dates depend on SNTP, which is unauthenticated: bootstrapping a
  trust decision from an unauthenticated time source is a known chicken-and-egg,
  universally accepted, and still a reason to want an RTC.
- *No backpressure into the framebuffer.* If redraw can't keep up, drop frames, never
  deltas.
- *Token cost is invisible unless shown* — hence the tray meter (§8.9).

* 12. TLS 1.3 in Lisp — not built

The sub-project that would drop the host's libssl. Nothing above changes when it lands:
=http.lisp= gets an encrypted stream from Lisp instead of from OpenSSL. Scoped as one
client talking to one endpoint, which removes most of the standard — no server side, no
resumption, no 0-RTT, no renegotiation, no TLS 1.2:

| Piece                       | Choice                            | Why                                             |
|-----------------------------+-----------------------------------+-------------------------------------------------|
| Version                     | TLS 1.3 only                      | one handshake, and the simpler one              |
| AEAD                        | =TLS_CHACHA20_POLY1305_SHA256=    | pure integer math; AES-GCM wants carryless mult |
| Key exchange                | X25519                            | one curve, well specified, RFC test vectors     |
| Hash / KDF                  | SHA-256, HMAC, HKDF               | ~150 lines together                             |
| Cert signature verification | RSA PKCS#1 v1.5 *and* ECDSA P-256 | we don't choose the server's certificate        |

Estimated piece by piece: SHA-256 (~100 lines), HMAC+HKDF (~60), ChaCha20 (~80), Poly1305
(~80), X25519 (~150), record layer + handshake (~400–600), ASN.1/DER + X.509 (~300),
signatures (~100) — about 1500 lines, each primitive checkable against published test
vectors. RSA verification is nearly free (SBCL has bignums: =(mod (expt s 65537) n)=);
ECDSA P-256 needs real field arithmetic.

Trust would come in three stages, each stated out loud:

1. *Encrypted, unauthenticated.* Proves the record layer and key schedule. Lab only.
2. *Pinned.* The SHA-256 of the endpoint's intermediate SPKI, required to match. Real
   security, no X.509; fails closed and loudly when the certificate rotates.
3. *Chain verification.* DER, signatures up to a shipped root bundle, name matching,
   validity dates — which need a trustworthy clock.

* 14. Pitfalls and ruled out

- *Name collisions in =CL-USER=.* Every module shares it. =web-cdp.lisp= defines its own
  =JOBJ= / =JGET= / =WRITE-JSON=, so =(use-package :lol.json)= followed by loading it would
  have silently redefined =LOL.JSON:JOBJ= — hence qualified names. =http.lisp= has
  =PARSE-URL= and =HEADER-VALUE=, so the agent's are =agent-parse-url= /
  =agent-header-value=. =session-log.lisp= has =UTC-STAMP=, so the store's is
  =STORE-STAMP=.
- *"The conversation hangs after a cancel"* — the mock, not the client. It served one
  connection at a time (the cancelled slow reply held it) and steered by every text block
  of the last user message, which after a cancel still said "slow". Fixed in the mock.
- *"A non-ASCII probe kills the net REPL"* — the harness's stream is Latin-1 on the host,
  the guest reads UTF-8, so a literal é broke the pipe. A property of the test channel;
  the check spells it =(code-char 233)=.
- *A stale last frame* (real, fixed): the turn's final touch could land just after the
  tick that saw the conversation go idle, and the loop slept until a key. The poll deadline
  now also wakes for a revision not yet drawn.
- *"The mock's 401 is a dropped connection"* — the mock's =~@[retry-after: ~a~a~]=
  consumes two arguments when true and skips one when =NIL=, so every error without a
  =retry-after= shifted the later arguments and never ended the header block. The client
  was right to call that a dropped connection. Fixed in the mock.
- *Stale guest checks, not bugs:* the tray no longer says "agent" (the creature replaced
  the word), and a tool call's =;; #0= line is folded under =:concise=. Section 3's
  occasional "no stopped note" was the harness typing into a pane still read-only while a
  turn streamed; it now waits (=ready-to-type=).
- *Interrupted is not timed out.* Many apparent TLS "timeouts" were an interrupted read,
  fixed in =tls.lisp= ([[file:networking.org][networking.org]] §2e).
- *Not reproduced, kept so it's recognised:* once, after the failure-reporting changes, an
  approved =lisp-eval= ran but the pane never showed the model's follow-up, the next =C-c
  C-a= took the half-rendered turn's lines as its draft, and the chooser it raised blocked
  every later check. Five later runs passed. Suspect: timing between the approval
  chooser's loop and the tick's refresh of a turn.
