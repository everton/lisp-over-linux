The point: the project is about to be shown to other people, and a two-minute video

screenshot. That video should be made *from inside the environment, on the laptop*:
start recording with a key, talk, pause, resume, stop, watch the encode, play the
result back in a pane, and only then hand the file to the world.

Sound is *required* (the user's decision, 2026-10-17). That makes this a kernel tag
as well as userland work: tag #28 had no sound at all (=# CONFIG_SOUND is not set=); tag #29 adds it
([[file:kernel-config.org][kernel-config.org]] §9, snapshot [[file:../kernel/config-7.2.5][kernel/config-7.2.5]]).

* 0. The shape, in one picture

#+begin_example
   PID 1 (the environment's thread)            container "default" (the host's Debian)
   ───────────────────────────────            ─────────────────────────────────────────
   world-repair ─► present-repair ──► /dev/fb0
                        │
                        └─ tap: "the canvas changed"
                                │
   sampler (30 fps, only a copy │                ┌──────────────── ffmpeg ─────────────────┐
   of the canvas + the pointer) ▼                │ in 0: rawvideo bgra on stdin            │
   bounded queue ─► writer thread ─── pipe ────► │ in 1: -f alsa plughw:0,0  (the mic)     │
                                                 │ out : seg-NNN.mp4 (H.264 + AAC)         │
   recorder pane / tray ◄── fd 3: mic levels ─── │ out : 8 kHz mono s16 PCM (the meter)    │
                        ◄── -progress lines ──── │                                         │
                                                 └─────────────────────────────────────────┘
   stop ─► ffmpeg -f concat -c copy ─► NAME.mp4 ─► ffprobe -of json ─► the result view
   play ─► *screen-lent* ─► the host's mplayer -vo fbdev2 -slave (keys ─► its stdin) ─► hand back
#+end_example

Two ideas carry it. The pixels are *already in Lisp memory* — the environment draws
into a canvas and copies rects of it to the framebuffer — so recording is "copy the
canvas sometimes", not "read the screen back". And the encoder, the decoder and the
ALSA library are the *host's* (ffmpeg and libasound in the default container), the
same rule as OpenSSL and Chrome (AGENTS.md: host programs are used at runtime, from
=/mnt/host=, never baked in). The image grows by a few hundred lines of Lisp and a
handful of kernel options.

* 2. The laptop's sound, checked on its Debian

Checked 2026-10-17 on the build host, which *is* the laptop (=/sys/class/dmi/id=:
Dell XPS 13 9300, i7-1065G7):

- *Controller:* =00:1f.3 Intel Ice Lake-LP Smart Sound Technology Audio Controller
  [8086:34c8]=. Three drivers can bind it (=snd_soc_avs=, =snd_sof_pci_intel_icl=,
  =snd_hda_intel=) and Debian's kernel chose *=snd_hda_intel=*
  (=snd_intel_dspcfg.dsp_driver= is 0, "decide by the hardware").
- *Codecs:* =Realtek ALC289= (codec 0) and =Intel Icelake HDMI= (codec 2).
- *The microphone is analogue, on the codec.* Node 0x12 is =[Fixed] Mic at Oth
  Mobile-In= with the control "Internal Mic Boost Volume"; nodes 0x19 / 0x1b are the
  headset jack's mics.
- *PCMs:* =00-00: ALC289 Analog : playback 1 : capture 1=, plus four HDMI playbacks.
- PipeWire on the host records =s32le 2ch 48000Hz= from that source.

*Why this matters.* On many Intel laptops the built-in mics are /digital/ (DMIC) and
wired to the DSP, and then only SOF works — which needs the DSP's firmware and a
topology file copied from the host, as the Wi-Fi firmware is ([[file:networking.org][networking.org]] §7).
Here the mic goes through the Realtek codec, which plain HD-Audio drives without any
firmware. So the plan is the *legacy HDA path*, and SOF is ruled out on purpose (it is
not even built, so =snd_intel_dspcfg= cannot pick it).

*A trap ruled out early:* the container's libasound reads the host's ALSA config, and
the host has =/etc/alsa/conf.d/99-pipewire-default.conf=, which points ALSA's
=default= device at PipeWire. There is no PipeWire in the guest, so every command
line here names the card directly: =plughw:0,0= (=plug= converts the format/rate the
hardware offers into what ffmpeg asks for; bare =hw:= would refuse a mismatch).

** 2.1 The headset: wired, through the jack (the user's, 2026-10-17)

The user narrates through a *wired headset on the 3.5 mm jack*, so that is the mic the
recorder is built for; the built-in one is the fallback. It is the *same codec and the
same driver*: the jack is the ALC289's, and node 0x19 is its headset mic ("Headset Mic
Boost Volume"; node 0x1b is the "Headphone Mic"). Nothing is added to tag #29 for it.

What the jack adds is *choosing the mic*. The XPS's jack is a combo jack (one 4-pole
plug carries both earphones and mic), and the kernel's HDA code handles it:
=alc269.c= has the Dell chain =ALC269_FIXUP_DELL4_MIC_NO_PRESENCE= → =ALC269_FIXUP_HEADSET_MODE=,
which declares 0x19 the headset mic "without its own jack detect" and lets the
codec's headset mode tell a headset from plain earphones. The fixup, the
auto-mic switch (capture follows the plug) and the jack's state are all *inside the
kernel*, so whatever works under Debian's kernel works under ours — on Debian,
PipeWire only reads that state and moves its default source. In the guest the
recorder reads it itself:

- the card's *jack controls* (the HDA driver exposes each jack as a boolean control,
  "… Jack") through the same =controlC0= ioctls as the mixer (§3.1), so the pane says
  *which* mic it is recording — =Mic  headset (jack)= or =Mic  built-in= — and the
  preflight warns "recording the built-in mic: is the headset plugged in?";
- the jack controls send events on =controlC0= (=SNDRV_CTL_IOCTL_SUBSCRIBE_EVENTS=), one
  more service fd: plugging or unplugging during a take is noted in the result.

/To prove on the laptop (step 0):/ the control names, that our kernel picks the same
fixup as Debian's (=dmesg='s =autoconfig for ALC289= lines, read with root on the host
and in =kernel.log= in the guest), that auto-mic switches capture to 0x19 on plugging
in, and that a 3-pole earphone is not mistaken for a headset. If auto-mic does not
switch, the recorder selects the input itself through the capture source control.

*Measured on the host's Debian (2026-10-17, read-only through =mixer.lisp=):* the jack
controls are =Headphone Mic Jack= (the combo jack's sense: =1= with a plug in) and three
/phantom/ jacks, =Internal Mic Phantom Jack=, =Headset Mic Phantom Jack= and
=Speaker Phantom Jack= (always =1=: they stand for fixed devices, so that a mixer can
show them). The input is chosen by =Capture Source= (enumerated). The full control
list is in §8.5.

*Ruled out (2026-10-17): Bluetooth headsets.* The laptop has paired Bluetooth earbuds,
which is why the question came up. A Bluetooth mic would need the kernel's Bluetooth
stack and the AX201's Bluetooth firmware, the host's =bluetoothd= with a D-Bus system
bus, and *PipeWire* in the guest, because the mic only exists in the hands-free profile
(HFP), which BlueZ alone does not implement. HFP audio is also phone quality (8 kHz, or
16 kHz with mSBC). That is a project of its own, and the wrong mic to narrate with.
USB headsets are not planned either; if one is ever wanted, it is a single kernel
option (=SND_USB_AUDIO=, no firmware) and a card picker in the preflight.

** 2.2 The speakers

/To prove on the laptop (step 0):/ that the internal speakers play under our kernel.
=alc269.c= has a Dell fixup for this family (=ALC289_FIXUP_DELL_SPK1=), applied by the
codec's PCI subsystem id (Dell 096d), so it should — but speaker amps are where laptops
surprise. The headset's earphones (§2.1) are the usual output for playback anyway,
and the mic does not depend on the speakers.

- *The mixer.* On Debian, WirePlumber and =alsactl= set the codec's switches and gains

* 4. Recording: the frames

** 4.1 The tap

=present-repair= and =present-frame= call one function, =note-frame-changed=, when a
recording is running (a special being =nil= otherwise: one test per repair). It sets a
flag; it does not copy. Copying at the rate of repairs would be wrong in both
directions — an idle screen makes no repairs (the video would have holes) and a busy
one makes more than 30 a second.

** 4.2 The sampler: a constant frame rate

Video files want a constant rate. A sampler deadline (one more entry in =fb-cycle='s
=earliest-timeout=, like the tray's tick) fires every 1/30 s while recording. On each:

- if the canvas changed or the pointer moved since the last sample, copy the canvas
  (=replace= on the pixel vector: ~1–2 ms for 9.2 MB), draw the pointer onto the copy,
  and queue it;
- else queue *the same* buffer again (no copy). ffmpeg sees a frame either way.

Buffers come from a small pool (4 × 9.2 MB) so the GC sees no garbage.

** 4.3 Never stall the environment

A recorder that blocks the environment's thread freezes the screen — and the
watchdog's STALL report ([[file:diagnostics.org][diagnostics.org]]) would say so. So the sampler only
*queues*; a writer thread (named, with =with-main-activity=-style labels so a stall
report names it) writes to ffmpeg's stdin. When the queue is full the *newest frame is
dropped* and counted — never waited for. The count is shown live and in the result
(§6): a recording with drops says so instead of looking fine and stuttering.

** 4.4 What appears in the frame

Everything on screen, including the pointer (§4.2) and the tray's REC indicator. The
recorder's own pane is visible if it is open — the usual move is to start with
=SuperL-r= from wherever you are and never open the pane until you stop.

* 5. Recording: two ways to the file

** 5.1 Live encoding (proposed default)

One ffmpeg per segment (§5.3), started in the default container:

#+begin_example
ffmpeg -hide_banner -nostats -progress pipe:2 \
  -thread_queue_size 64 -use_wallclock_as_timestamps 1 \
    -f rawvideo -pix_fmt bgra -s 1920x1200 -r 30 -i pipe:0 \
  -thread_queue_size 1024 -f alsa -ac 2 -ar 48000 -i plughw:0,0 \
  -map 0:v -map 1:a \
    -c:v libx264 -preset ultrafast -crf 23 -pix_fmt yuv420p \
    -c:a aac -b:a 160k -af aresample=async=1 \
    -movflags +faststart  seg-001.mp4 \
  -map 1:a -ac 1 -ar 8000 -f s16le pipe:3
#+end_example

The last output is the *mic meter*: 16 000 bytes a second of mono samples, whose peak
per 50 ms the recorder draws as a level bar. "Was the mic on?" is the classic way a
screencast is lost, and this answers it before you have talked for ten minutes.

*Measured on the laptop's own Debian (2026-10-17)*, 10 s of 1920×1200 at 30 fps of
=testsrc2= (a noisy picture, worse than a UI) piped as raw =bgra= into =libx264
ultrafast=: *4.1× real time, ~0.95 CPU-seconds per recorded second* (including the
process generating the frames) — about one of the eight hardware threads. =ultrafast=
alone on the same picture runs 12×; =veryfast= 4.2×. File size for that noisy test:
20 MB for 10 s; a UI that mostly sits still compresses far better (/to measure/ on a
real recording, step 2).

*Proved on the host (step 1, 2026-10-18), and it was the fallback that won.* A loopback
probe: a Lisp generator wrote frames into ffmpeg's stdin at 30 fps and, *at the same
instant*, a 100 ms tone into =pacat=; every 2 s the frame went white while the tone
sounded. ffmpeg recorded the frames (constant 30 fps, *no* wall-clock stamps) and the
sound card's output — a PipeWire null sink's monitor, standing in for the mic, so
nothing came out of the speakers — and the analysis found each flash and each beep's
onset in the file. Over 12 s the sound sat a constant 32.0 ms behind the picture; over
*3 minutes, all 89 beeps 26.7 ms behind, the first and the last alike: no drift at
all*. That offset is one frame, inside what nobody notices (sound up to ~45 ms late), and
part of it is the probe's own playback buffer (=pacat --latency-msec=10= and
PipeWire's). So the recorder stamps nothing: the frame COUNT is the video's clock
(§4.2), and the sound keeps its own. Learned on the way, and used by the recorder: a
live audio input never ends, so ffmpeg does not stop at the video's EOF — it waited
until the probe sent SIGINT (§13).

** 5.2 The damage log (the option)

The other way records *nothing but what changed*, and encodes after stop:

- =seg-NNN.dmg=: a header (width, height, the start time on =CLOCK_MONOTONIC=), one full
  frame, then records =(time-ns x y w h pixels)= — exactly the rects =world-repair=
  returned, plus a small record for each pointer move (position only; the arrow is
  drawn at encode time). Pixels compressed with =lol.deflate=, the writer the log
  archives already use ([[file:../poc/deflate.lisp][poc/deflate.lisp]]).
- =seg-NNN.flac=: the mic, from an audio-only ffmpeg (=-f alsa -i plughw:0,0 -c:a flac=),
  its start time written next to it on the same clock.
- *Encode* (at stop): a background thread replays the log into a canvas, samples it at
  30 fps the way §4.2 does live, and pipes those frames with the FLAC into ffmpeg.

|                                          | Live (§5.1)          | Damage log (§5.2)                                                                                                            |
|------------------------------------------+----------------------+------------------------------------------------------------------------------------------------------------------------------|
| CPU while recording                      | ~1 thread            | the copies of changed rects + deflate; near zero when idle                                                                   |
| Wait after stop                          | seconds (a concat)   | the whole encode (≈ duration / 4)                                                                                            |
| Frames dropped under load                | possible, counted    | none: every repair is in the log                                                                                             |
| Re-encode later (other fps, size, codec) | lossy from the MP4   | exact, from the log                                                                                                          |
| Disk while recording                     | the MP4              | the log (/to measure/: typing repairs one text line at a time, so it should be small; a playing web video is the worst case) |
| New code                                 | the sampler + writer | that plus the log format, its replayer, an encode job                                                                        |

The log is the better recording and the worse experience; live is the reverse. Both
share the sampler, the meter, the segments and the result view, so the log is a
second writer, not a second recorder.

** 5.3 Pause and resume: segments

ffmpeg cannot pause an ALSA input, and a paused recording should not contain the
pause. So *a pause ends a segment* (=SIGINT= to ffmpeg: it finishes the file cleanly)
and *resume starts the next* (=seg-002=, …). Stop ends the last one and joins them:

#+begin_example
ffmpeg -f concat -safe 0 -i segments.txt -c copy -movflags +faststart NAME.mp4
#+end_example

=-c copy= re-encodes nothing — the segments share every parameter, so the join takes
seconds. A paused recorder keeps the mic meter running (so you can check the level
before resuming) and shows =❚❚ 01:23= in the tray.

** 5.4 Files

A recording is a folder =~/.lol/rec/2026-10-17-1530/= (via =lol-path=, mode 0700)
holding the segments, =segments.txt=, =ffmpeg.log= (stderr, for when it fails) and
the finished =NAME.mp4= (0600 — chmod it to share). See §12 for the
question whether the finished file belongs in =~/Videos= instead.

Before recording, =statvfs= the home: refuse with less than 1 GB free, warn on the
pane below 5 minutes' worth at the measured rate.

* 6. Encoding progress and the result

ffmpeg's =-progress pipe:2= writes =key=value= blocks; checked on the host, the keys
include =frame=, =fps=, =out_time_us=, =dup_frames=, =drop_frames=, =speed= and a
final =progress=end=. The recorder reads them as one more service fd.

- *While recording live:* =out_time_us= is the recorded length; =speed= below 1.0 means
  the encoder is falling behind — the pane says so in red before frames start dropping.
- *While encoding (concat; the damage log's encode):* the total is known (the sum of
  the segments), so the tray and the pane show =⟳ encoding 42% · 3.9× · 0:21 left=.
- *The result:* =ffprobe -v error -of json -show_format -show_streams NAME.mp4=, read
  with =lol.json=, becomes the *result view* — duration, size, resolution, frame rate,
  video and audio codecs, the number of segments, frames dropped, the mic's peak level
  over the whole take (a take that never rose above -40 dB gets a warning: you
  probably recorded silence), and commands: *Play*, *Show in files* (=SuperL-f= at the
  folder), *Rename*, *Delete*, and (damage log) *Re-encode*.

The output is MP4 with H.264 (=yuv420p=, which every player and browser takes) and AAC
at 48 kHz, =+faststart= so a web page can play it before it has all of it — the file
you can attach to an issue, a README or a message as it is.

** 7.3 Preflight: every failure says why

Like the agent's preflight ([[file:agent.org][agent.org]] §14.8), checked before anything starts,
each failure a red block in the pane with its cause and what to do:

1. a sound card (=/proc/asound/cards= non-empty) — else "this kernel has no sound:
   tag #29 or later";
2. =/dev/snd/pcmC0D0c= openable by us — else "lol-rootd has not given /dev/snd yet";
3. a home on disk (=lol-path=) and free space;
4. the default container and its =ffmpeg= with =libx264= and =aac=;
5. which mic (§2.1): the headset's when its jack says plugged in — else a warning, not
   a refusal: "recording the built-in mic: is the headset plugged in?";
6. one second of mic: peak above the noise floor — else "the mic is silent: check
   the gain row, or the headset's own mute switch", with the gain row right there.

* 8. Playback, without leaving the environment: the host's player

*Decided (the user, 2026-10-17): we do not build a player; we use one from the host.*
Decoding, A/V sync, seeking and the audio output are a player's whole job, and the
host already has players that do it well. Our part is to lend it the screen and pass
it the keys.

** 8.2 The proposal: MPlayer on the framebuffer, the screen lent

Only one process may write =/dev/fb0= /at a time/ ([[file:processes.org][processes.org]]): two writers
overwrite each other's pixels and nobody owns the result. So playing is a *hand-off*,
the way leaving to the console already is:

1. *Lend the screen.* A special =*screen-lent*= makes the presenting functions do
   nothing. That is enough to stop *every* write of ours, because all of them are
   =present-frame=, =present-repair=, =move-cursor= and =put-cursor= in
   [[file:../initramfs/fb-browser.lisp::defun present-repair][fb-browser.lisp]] (§1). The world keeps running: the tray's clock, a
   streaming agent reply, a terminal's output all still repair the canvas; they just
   reach the screen after the hand-back.
2. *Run the host's player* in the default container (our =/dev= is bind-mounted, so
   =/dev/fb0= and =/dev/snd= are there, owned by the user):

   #+begin_example
   mplayer -slave -quiet -idle -nolirc -nomouseinput -noconsolecontrols \
     -vo fbdev2:/dev/fb0 -ao alsa:device=plughw=0.0 \
     -ss T  NAME.mp4
   #+end_example

   A recording is at the screen's own size (1920×1200, §5.1), so it fills the screen
   with no scaling; a file of another size gets =-vf scale= to fit (MPlayer's software
   scaler — fbdev2 has none of its own).
3. *Keys stay ours.* The environment keeps reading the keyboard (evdev and the tty,
   as always) and turns each key into a slave command on MPlayer's stdin; MPlayer's
   own key handling is off (=-noconsolecontrols=), so nothing reaches it any other way.
4. *Progress* is MPlayer's own on-screen display (=osd_show_progression=: a bar with
   the time, drawn into its frames), shown on every seek and pause. The environment
   asks =get_time_pos= / =get_time_length= too, to remember where you stopped.
5. *Hand back.* On =q= or end of file (=-idle= keeps MPlayer alive at the end, so the
   last frame stays until you press =q=), MPlayer is quit, =*screen-lent*= cleared,
   and the whole frame presented once (=present-frame=) — everything that happened
   meanwhile appears at once.

Controls (slave commands, checked in =mplayer -input cmdlist=):

| Key                      | Command                                      |
|--------------------------+----------------------------------------------|
| =SPC=                    | =pause= (a toggle)                           |
| =←= / =→=, =S-←= / =S-→= | =seek -5= / =seek 5=, =seek -30= / =seek 30= |
| =0=–=9=                  | =seek N0 1= (percent)                        |
| =-= / =+=                | =volume -5= / =volume 5=                     |
| =o=                      | =osd_show_progression=                       |
| =q=, =Esc=               | =quit=, then the hand-back                   |

Pause and seek are MPlayer's: nothing is restarted, and A/V sync is MPlayer's problem
(it has solved it for twenty years). An ALSA underrun on resuming from a pause is
MPlayer's to recover from, as it does on any desktop.

What we write: the hand-off and the key table, about 150 lines; no decoder, no pane.

** 8.3 What the hand-off costs

- *Full screen only.* The video does not sit in a pane or a window; you see it the
  way you would in a player's full-screen mode, then you are back exactly where you
  were. For "watch the take before sharing it", that is the right view anyway.
- *No pointer, no overlays* while it plays: nothing of ours is drawn.
- *A safety net:* if MPlayer dies or hangs, the hand-back still happens — a dead child
  is noticed in the poll (its stdout closes); =SuperL-Esc= always kills it and takes the
  screen back. A player must never be able to leave the screen without an owner.

*Proved in QEMU (2026-10-17, tag #28, OVMF + efifb at 1280×800, the host's MPlayer
run from a terminal pane in the default container — the recipe of §8.5):* both
=fbdev2= (full screen) and =fbdev= with =-geometry= (a window) draw on efifb's fixed
32-bpp mode as it is, with correct colours; the environment keeps running under it
and our =KD_GRAPHICS= tty is left alone; =q= typed into the pane quits it. Three
facts learned, each now in §8.5: =fbdev2= /centres/ the picture without scaling it
(=-vf scale= to the screen's size fills it); =fbdev= *does not clip* — a window whose
right edge passes the screen's wraps onto the left of the next line; and the
=do_connect: could not connect to socket= MPlayer prints is LIRC (the infrared-remote
client), silenced by =-nolirc=.

/Still to prove on the laptop:/ the frame rate at 1920×1200, and (tag #29) that
=-ao alsa= reaches the headset.

** 8.4 Ruled out, and why

- *Our own decoder into a pane* (the first version of this section: ffmpeg decoding
  to =bgra= over a pipe into a =video-body=, ~400 lines). It would have let the video
  sit in a window, but it meant writing pause, seeking and A/V sync ourselves — a
  player. The user's call: use the host's. If an in-pane player is ever wanted, the
  way that still uses a host player is libvlc's =vmem= (VLC decodes into our memory,
  plays its own sound) through a small C helper, since =libvlc-dev= is not installed
  and libvlc calls back from its own threads, which PID 1 should not host.
- *Not ruled out — later, as step 4b: MPlayer in a window's rect* (=-vo fbdev
  -geometry X:Y -vf scale=W:H=; per =man mplayer=, =-geometry= is honoured by =fbdev=
  but not =fbdev2=). It works (§8.5), but it is two writers on one screen again, so
  as a built mode it needs rules: our presents leave the rect out (a hole in the screen
  we own); anything that covers it (an overlay, a window raised above, the halo)
  pauses MPlayer; the pointer is hidden over it; a moved or resized window restarts
  MPlayer at =-ss= in its new place (a fraction of a second's hiccup); and a paused
  frame is read back from =/dev/fb0= into the window's own store, so our repairs keep
  it. About half a day on top of the full-screen hand-off.
- *VLC's =fb= output:* it works the same way, but by default it takes the tty
  (=--fb-tty=); MPlayer's fbdev2 does less, and its slave protocol is plain text. VLC
  stays the second choice if fbdev2 misbehaves on efifb.
- *ffplay* and *mpv:* §8.1 — no framebuffer output (ffplay) or not installed (mpv).
- *Chrome's =<video>= in the web pane:* the screencast it is drawn from is JPEG at
  Chrome's chosen rate (blurrier and choppier than the file — the thing you want to
  judge), and headless Chrome's audio output in the container is untried. It stays a
  useful last check: "does it play in a browser?"

*** 3. Play it from a Workspace

Use your Workspace, or keep the test apart in a *new* one: =SuperL-S-e= opens
another Workspace tab (the desk keeps its text across reboots, like the first).
Paste this, put the caret after its *last* parenthesis and press =C-x C-e= (/Do it/).
The status line must then end in ~=> PLAY~ — the function's name, which is what a
=defun= returns. If it does not, the =defun= was not evaluated, and a =(play …)=
will only report "undefined function: PLAY" (in the status line since 2026-10-17; on
the first laptop try that warning went to the console and froze the environment —
[[file:diagnostics.org][diagnostics.org]] §1, the stopped console):

#+begin_src lisp
(defun play (file &key window)
  "Play FILE (in your home) with the host's mplayer, in a new tab that takes its keys:
   full screen, or with :WINDOW T a window 640 wide against the right edge."
  ;; PROBE-FILE resolves "~/..." (SBCL reads it as :HOME) and a name relative to your
  ;; home to the real absolute path; NAMESTRING would keep the "~" and mplayer, with no
  ;; shell in between, would not find it. -really-quiet says NOTHING about a missing
  ;; file and exits 0, so the check is ours.
  (let* ((found (probe-file (merge-pathnames file (user-homedir-pathname))))
         (path (if found (sb-ext:native-namestring found) (error "no such file: ~a" file))))
    (open-terminal
     (container-command-line
      (append (list "mplayer" "-really-quiet" "-nolirc" "-ao" "alsa:device=plughw=0.0")
              (if window
                  (list "-vo" "fbdev" "-geometry" "100%:50%" "-vf" "scale=640:-3")   ; -3: keep the aspect
                  (list "-vo" "fbdev2" "-vf" (format nil "scale=~d:~d" *fb-xres* *fb-yres*)))
              (list path)))
     :title "mplayer")))
#+end_src

Then, each with =C-x C-e= after it:

#+begin_src lisp
(play "lol-test.mp4" :window t)   ; a window, flush right, centred vertically
(play "lol-test.mp4")             ; the whole screen
#+end_src

The file can be a name in your home (=lol-test.mp4=), a =~/= path
(=(play "~/screencasts/screencast_00000.mp4" :window t)=; how it resolves was checked on the laptop
2026-10-18) or an absolute one; a file that is not there is an error in the status line.

What it does: =container-command-line= ([[file:../initramfs/containers.lisp][containers.lisp]]) wraps the argv to run
in the default container, where the host's =mplayer= is; =open-terminal= runs that
on a pty in a *new tab* ([[file:terminal.org][terminal.org]]), so while that tab has the focus your keys
go to MPlayer. =*fb-xres*= / =*fb-yres*= are the screen's size, so the same text
fills 1920×1200 on the laptop and 1280×800 in QEMU. =C-x C-e=, not =C-c C-c=: Accept
would journal =play= and compile it back in on every boot
([[file:session-persistence.org][session-persistence.org]]) — fine if you want to keep it, but a test helper needn't.

*** 4. The keys, and getting back

MPlayer's own: =SPC= pause, =←= / =→= 10 s, =↑= / =↓= a minute, =9= / =0= its
volume, =o= its on-screen clock, =q= quit. After =q= the tab says
=exited with code 0=; =Return= closes it and you are back where you were.

Two things you will see, both what §8.2's hand-off is for:

- *The environment still paints.* In QEMU the tray's clock appeared over the
  full-screen video every second (its strip is repainted by itself), and a pane
  that changes repaints over a window. The video is not damaged, only covered.
- *The last frame stays after =q=*: nothing of ours knows it is there.
  =SuperL-Tab= twice repaints almost everything; thin strips in the gutters stay
  until something redraws them.

*** 5. The same from the terminal

#+begin_example
mplayer -really-quiet -nolirc -ao alsa:device=plughw=0.0 -vo fbdev \
        -geometry 100%:50% -vf scale=640:400 ~/lol-test.mp4
mplayer -really-quiet -nolirc -ao alsa:device=plughw=0.0 -vo fbdev2 \
        -vf scale=1920:1200 ~/lol-test.mp4
#+end_example

=-geometry X:Y= is the window's top-left corner, in pixels or as a percentage of the
room left over. *Keep it inside the screen*: fbdev does not clip, and a window past
the right edge wraps onto the left (seen in QEMU with =1000:150= on a 1280-wide
screen). Without =-vf scale=, fbdev2 shows the clip at its own size, centred.
=-ao alsa:device=plughw=0.0= is MPlayer's spelling of =plughw:0,0=: not ALSA's
=default=, which the host's ALSA configuration points at PipeWire (§2).

*** 6. If it plays without sound

- Is the tray at =VOL mute= or a low level? The volume keys fix both.
- Headset: plugging it in moves the sound from the speakers to it — the kernel's
  own auto-mute (the =Auto-Mute Mode= control). The jack's state is a control too:
  in a Workspace, =C-c C-p= on =(getf (find-control "Headphone Mic Jack") :values)=
  prints =(1)= when something is plugged in.
- All the controls and their values: =C-c C-p= on =(mixer-controls)=. On the host's
  Debian (read through the same code, 2026-10-17) the ALC289 has =Master=,
  =Headphone= and =Speaker= playback volumes and switches (0–87), =Capture=
  volume (0–63) and switch, =Capture Source=, =Auto-Mute Mode=, the three mic boosts
  (0–3), and the jacks =Headphone Mic Jack= (the combo jack's sense) and the
  /phantom/ jacks of the built-in mic and speaker. =restore-audio= switched every
  playback and capture switch on at boot.
- *Why not =pactl=, as on the host?* =pactl= is a client of a sound *server* — on
  Debian, PipeWire answering the PulseAudio protocol — which then writes these same
  ALSA controls. =alsa-utils= (=amixer=) was not replaced by it: it is the layer
  below, and is simply not installed on the host. The image runs no sound server,
  so =pactl= in the container would find nobody to talk to; =mixer.lisp= writes the
  controls directly, which is what both tools end in. (The StumpWM bindings step by
  =1000= — raw PulseAudio units of 65536, so about 1.5 %, not the 10 % their comment
  says. Ours step 5 %, =*volume-step*=.)

*Worth noting back from the laptop:* sound in the headset (and in the speakers,
§2.2); smooth motion at 1920×1200 (drop =-really-quiet= to see MPlayer's =A-V= and
dropped-frame counts); tearing; colours; the volume keys; and whether the
=VOL= level you set is there after a reboot.

* 11. Costs and risks

- *CPU:* ~1 thread live; the damage log much less while recording, then an encode.
  The laptop has eight threads; the environment uses one.
- *Battery and heat* on a long take: say so in the pane, nothing more.
- *MPlayer's fbdev2 on efifb* (§8.3) is unproven; VLC's =fb= output is the second
  choice, and the hand-back is guarded so a failing player cannot keep the screen.
- *The combo jack* (§2.1): if headset mode misdetects the plug, the mic is silent or
  the built-in one is used; the preflight's mic and level checks catch both before
  you talk.
- *The speakers* (§2.2) may need a fixup we do not get; the headset always works.
- *Mixer defaults* (§3.1) unknown until step 0.
- *A slow disk or a full one*: the writer drops and counts, ffmpeg's error goes to
  =ffmpeg.log= and the pane; the environment never waits.
- *Kernel size:* the HDA core plus the Realtek driver; measure at tag #29 and record
  it in =kernel-config.org=.

* 13. What was built (2026-10-18)

Steps 1–4 of §10, in [[file:../initramfs/recorder.lisp][recorder.lisp]] and [[file:../initramfs/player.lisp][player.lisp]], with the two hooks they
need in [[file:../initramfs/fb-browser.lisp::Every write of ours to /dev/fb0][fb-browser.lisp]]. Proved in QEMU by =check-recorder.lisp= (25 checks); a
take on the laptop — the real mic, real speech, the CPU at 1920×1200 — is owed.

** 13.1 What shipped

- *The tap and the lent screen.* =*frame-tap*= is called by =present-frame= and
  =present-repair=; =*screen-lent*= turns off all five functions that write
  =/dev/fb0= (=put-cursor=, =present-frame=, =present-repair=, =move-cursor=,
  =hide-cursor=), and while it is set the loop gives input events to the player
  instead of the world. The volume keys still work during playback: they are read
  before events reach anyone (=mixer.lisp=).
- *The sampler* is a service (=:timeout= / =:run=, like the web pane): every slot that
  is due gets a frame, so a late wake-up still writes the right number — the count
  is the video's clock (§5.1). A slot copies the canvas only when it was presented
  or the pointer moved since the last copy, and draws the arrow onto the copy (it is
  never in the canvas); otherwise it queues the last frame again.
- *The writer* is a thread: the environment's thread never writes to ffmpeg. Its
  queue holds =(buffer . copies)=, so a repeated frame costs a counter, not a copy.
  When no pooled buffer is free (4 per recording), the sampler repeats the last
  frame — the timing kept, the picture a frame or two stale — and counts it; the
  result says how many (*stale*).
- *ffmpeg* in the container, as §5.1 proved: rawvideo =bgr0= on stdin at a constant
  30 fps, ALSA =plughw:0,0= stereo, H.264 =ultrafast= + AAC 160k into =seg-NNN.mp4=,
  and a second output, the mic as 8 kHz mono into a FIFO in the shared =/tmp=, read
  by a meter thread (opened non-blocking, so a FIFO nobody writes yet cannot hang it)
  for the level in the tray and the pane.
- *Pause and stop* end a segment on a thread (§13.2), the state =:finishing= meanwhile;
  stop then joins with the concat demuxer and =-c copy=, reading its =-progress= file
  for =SAVING n%=, renames a single segment instead, and asks =ffprobe= (JSON, read
  with =lol.json=) what came out. =result.lisp= beside the video keeps that: duration,
  size, size in pixels, codecs, frames written and stale, segments, the take's
  loudest moment.
- *The preflight*: a sound card, =/dev/snd/pcmC0D0c= openable, a home on a disk with
  1 GB free, containers, the host's ffmpeg. Each failure is the status line's
  message and the recorder pane's first row.
- *The recorder pane* (Spotter "record" / "recordings"): state, time, the mic as a
  bar with its dB, the frames, the segment; then every recording, newest first, a
  "(silent!)" on any whose loudest moment stayed under -50 dB. A recording drills to
  its result; =p= plays it full screen, =w= in a window, =f= opens its folder with
  the video selected, =D= deletes it (refused while recording).
- *The tray*: =REC 01:23 ###...= (the mic's level as a bar), =PAUSED 01:23=,
  =SAVING 42%=, in red and amber.
- *The player*: =(play-video FILE)= lends the screen to =mplayer -slave -vo fbdev2=
  scaled to the screen; =SPC= pauses, the arrows seek 5 s (with Shift 30 s), =0=–=9=
  jump to 0–90 %, =o= shows its clock, =q= or Esc ends it; a player still there 3 s
  after =q= is killed; when it is gone the whole canvas is presented once.
  =:window t= is still §8.5's interim way, a terminal tab drawing over a corner.

** 13.2 What changed against the design, and why

- *A segment does not end by itself.* §5.1 planned "close stdin, and =-shortest=
  ends the file". It ends the main output, but the meter's output is the live mic
  alone, which never ends — the first build waited the full 30 s and then counted
  ffmpeg's exit as a failure. Now stdin is closed, ffmpeg gets a second to read the
  last frames, then SIGINT, its graceful stop (flush the encoder, write the index);
  its exit code 255 counts as success *when ffprobe finds a video in the file*.
- *Ending a segment must not happen on the environment's thread.* The first build
  did, and in QEMU pause froze the screen for the whole 30 s. Pause and stop now
  stop sampling at once on the environment's thread (=rec-close-segment=, which also
  counts the time) and do the rest on a thread (=rec-in-background=).
- *The meter's level is not yet proved.* QEMU's capture is silence, which proves the
  silent-take warning but not that the bar moves with a voice: that is the laptop's.
- *The file manager does not yet open videos with the player*, as §8.1 planned; the
  recordings do (=p=, =w=).
- *The tray's indicator is visible in the video*, as §12 decided.

** 13.3 Measured

- *Sync* (host, §5.1): sound 26.7 ms behind the picture, constant over 3 minutes.
- *A take in QEMU* (1280×800, the Workspace with some typing, TCG emulation): 11.1 s
  in two segments → 1.4 MB, 334 frames for 11.12 s (30 per second to the frame), 8
  stale — the emulated machine's encoder briefly behind.
- *The picture is the screen*: the last frame decoded from the file against the
  canvas, as mean colour per channel: red 30 vs 32, blue 40 vs 42 (the H.264 colour
  conversion's rounding). A wrong pixel format would have swapped the two.
- *The hand-back*: 48 points of the screen equal the canvas before playing, none
  while the clip plays, all 48 again after =q=.

** 13.4 Traps found while testing (so nobody falls in again)

- *=key-event= builds a QMP event; =qmp-events= sends it.* The first check called
  =key-event= alone for =SuperL-S-r=, so nothing was pressed and "stop does not work"
  was the test, not the recorder.
- *A binary PPM's header is P6, width, height, maxval.* The check's first reader took
  the third field as the width, read the wrong pixel, and made a correct hand-back
  look like a wrong one.
- *QEMU's home under =LOL_GUEST_HOSTROOT=1= is a tmpfs in the guest's RAM*: 0.3 GB free,
  so the 1 GB rule refuses there (as it should). The check lowers =*rec-min-free*=.
- *=sb-unix= has no =unix-chmod=, =unix-rmdir= or =o_nonblock=*: =files.lisp='s
  =%chmod= / =%rmdir=, and =O_NONBLOCK= = =#o4000= from =asm-generic/fcntl.h=.
