#+TITLE: The systray — battery from sysfs, time from the CMOS clock
#+STARTUP: showall

Sibling docs: [[file:kernel-config.org::#platform-power][kernel-config.org, Platform & power]] (the options that make the battery
visible) · [[file:code-browser.org][code-browser.org]] (the browser whose tab strip carries the tray) ·
[[file:input.org][input.org]] (the same "the kernel already exposes it as a file" lesson, for
the mouse).

The browser fills the whole screen, so the battery and the time live in a small
tray at the right end of the tab strip. This doc covers the *data* behind it,
[[file:../initramfs/sysinfo.lisp][=initramfs/sysinfo.lisp=]]; the drawing is the shell's.

* The one-sentence essence

The battery is a handful of one-line text files the kernel keeps under
=/sys/class/power_supply/=, and the time is =get-universal-time= plus one fixed
number — the UTC offset — because the image has no time-zone database.

* 1. The fields
:PROPERTIES:
:CUSTOM_ID: fields
:END:

The tray follows a StumpWM mode line (=*screen-mode-line-format*=): right-aligned
fields separated by =" | "=.

| # | Field         | StumpWM source                                     | Here                                |
|---+---------------+----------------------------------------------------+-------------------------------------|
| 1 | battery       | a script parsing =acpi -b=                         | =battery-string=                    |
| 2 | Wi-Fi SSID    | =iwgetid -r=, else =Not connected!=                | =network-tray-item=                 |
| 3 | date and time | =%d= with =*time-modeline-string*= = ="%F %T"=     | =clock-string=                      |
| 4 | tray icons    | =%T= — the stumptray module's placeholder          | the shell's icons (clipboard first) |

The clock reads =2026-10-02 09:01:52= — ISO date, 24-hour time, seconds. The
battery reads:

| State                          | Text                        | Tone        | Colour |
|--------------------------------+-----------------------------+-------------+--------|
| discharging, ≥ 50 %            | =BAT -72% 3:05=             | =:ok=       | green  |
| discharging, 20–49 %           | =BAT -45% 1:20=             | =:warn=     | yellow |
| discharging, < 20 %            | =BAT -12% 0:18=             | =:low=      | red    |
| charging / full / not charging | =BAT +37% 3:13=, =BAT 100%= | =:charging= | green  |

=+= is charging, =-= discharging, and =H:MM= is time to full or to empty. A status
of =Unknown= is coloured as if discharging.

** The network field

[[file:../initramfs/wifi.lisp::defun network-tray-item][=network-tray-item=]] in =wifi.lisp=, which =tray-items= calls by name (it loads
later). It reads only =*wifi-state*=, refreshed every 5 s by the =netd= thread
from the supplicant's =STATUS= and =SIGNAL_POLL=. The tray repaints every second,
so it must never wait on a socket.

| State                                 | Text             | Tone                                      |
|---------------------------------------+------------------+-------------------------------------------|
| Wi-Fi associated                      | =Home 72%=       | =:ok= ≥ 55 %, =:warn= ≥ 30 %, else =:low= |
| a radio, not associated               | =Not connected!= | =:low= (red)                              |
| no radio, a wired lease (QEMU's eth0) | =eth0 10.0.2.15= | =:ok=                                     |
| no radio, no lease                    | (no item)        |                                           |

The percentage is NetworkManager's rough mapping, =2 × (dBm + 100)= clamped to
0–100. Details: [[file:networking.org::#environment][networking.org, In the environment]].

*Known limit:* a machine with two batteries shows the first one, as =acpi -b='s
first line does.

* 2. Battery: the power_supply class in sysfs

*sysfs* is a filesystem the kernel synthesises in memory and mounts at =/sys=
(our [[file:../initramfs/preinit.c][=preinit.c=]] mounts it). Every file is a window onto one kernel variable:
reading it makes the kernel format the value as text on the spot. Nothing is
stored on disk; =cat= is the whole API.

The *power_supply class* is the kernel's one vocabulary for anything that powers
the machine. Each supply registers a directory under =/sys/class/power_supply/=
(a symlink into the device tree), one attribute per file. A typical laptop:

#+begin_example
/sys/class/power_supply/AC/type       Mains
/sys/class/power_supply/AC/online     1
/sys/class/power_supply/BAT0/type     Battery
/sys/class/power_supply/BAT0/status   Full
/sys/class/power_supply/BAT0/capacity 100
/sys/class/power_supply/BAT0/charge_now  2306000    (µAh)
/sys/class/power_supply/BAT0/charge_full 2306000
/sys/class/power_supply/BAT0/current_now 1000       (µA — a trickle, while full)
#+end_example

On a laptop, ACPI fills them in. =CONFIG_ACPI_BATTERY= ([[file:../linux/drivers/acpi/battery.c][=drivers/acpi/battery.c=]])
evaluates the firmware's =_BIF=/=_BST= methods and registers the battery;
=CONFIG_ACPI_AC= ([[file:../linux/drivers/acpi/ac.c][=drivers/acpi/ac.c=]]) does the adapter. Both are =default y= in
[[file:../linux/drivers/acpi/Kconfig][=drivers/acpi/Kconfig=]] and both =select POWER_SUPPLY=, so they've been in our
kernel since =CONFIG_ACPI= went on at tag #19. The tray needed no kernel change
(checked at tag #24; the =grep= is in [[file:kernel-config.org::#platform-power][kernel-config.org, Platform & power]]).

Four details the code honours, each taken from the kernel source:

- *Go by =type=, not name.* The adapter is =AC= on some firmware, =ADP1= or
  =ACAD= on others. [[file:../initramfs/sysinfo.lisp::defun supply-type][=supply-type=]] reads the file.
- *Two unit families.* The firmware's =_BIF= declares a power unit, and
  =battery.c= exposes either =charge_now=/=charge_full=/=current_now= (µAh, µA)
  or =energy_now=/=energy_full=/=power_now= (µWh, µW) — never both. Time left is
  =now/rate= hours in either family, so [[file:../initramfs/sysinfo.lisp::defun battery-amounts][=battery-amounts=]] never converts; it
  only refuses to mix.
- *Not every battery is the battery.* A wireless mouse's battery is also
  =type=Battery=, with =scope=Device=; an empty bay says =present=0=.
  [[file:../initramfs/sysinfo.lisp::defun system-battery-p][=system-battery-p=]] skips both.
- *Closed status vocabulary.* Exactly =Unknown=, =Charging=, =Discharging=,
  =Not charging=, =Full= (=POWER_SUPPLY_STATUS_TEXT= in
  [[file:../linux/drivers/power/supply/power_supply_sysfs.c][=power_supply_sysfs.c=]]).

Reading the battery runs a firmware method each time, so =battery-status= caches
its answer for =*battery-cache-seconds*= (5) while the clock beside it ticks every
second.

*QEMU can't show any of this.* It emulates no ACPI battery or adapter (QEMU 11.1's
=-device help= lists neither), so under =build.sh --run= the directory is empty and
the tray shows only the clock — also the right answer on a desktop. The battery
path is tested on the host against fake sysfs trees:
=sbcl --script poc/sysinfo-test.lisp= ([[file:../poc/sysinfo-test.lisp][source]]).

* 3. Time: the CMOS clock, UTC, and a fixed offset

** Who sets the clock at boot

A PC keeps time while off in the *RTC*: the battery-backed "CMOS clock", a
MC146818-compatible chip at I/O ports =0x70/0x71=. Usually =hwclock= or an RTC
driver copies it into the kernel's clock at boot. We have neither:
=# CONFIG_RTC_CLASS is not set=, so there's no =/dev/rtc= and no =rtc-cmos=
driver. The clock is right anyway, because x86 reads the chip *itself*, very
early:

1. =timekeeping_init()= ([[file:../linux/kernel/time/timekeeping.c][=kernel/time/timekeeping.c=]]) calls
   =read_persistent_wall_and_boot_offset()=, which calls =read_persistent_clock64()=;
2. on x86 that is [[file:../linux/arch/x86/kernel/rtc.c][=arch/x86/kernel/rtc.c=]], which calls =x86_platform.get_wallclock=;
3. which defaults to =mach_get_cmos_time= ([[file:../linux/arch/x86/kernel/x86_init.c][=x86_init.c=]]), reading the chip
   through =mc146818_get_time()= — library code that =config X86= =select=s
   (=RTC_MC146818_LIB=y= in our =.config=, independent of =RTC_CLASS=).

Without =RTC_CLASS= the kernel can't *write* the time back or let userspace read
the chip. That's fine for a machine that only displays the time. (Setting the
system clock from the network is SNTP's job: [[file:networking.org::#userland-half-reaching-network][networking.org, Userland half — reaching the network from SBCL]].)

** UTC or local?

The chip stores a date and time with no zone, and =mach_get_cmos_time= converts it
with =rtc_tm_to_time64()= — *as UTC*. The kernel treats it as local time only if
userspace says so (=timekeeping_warp_clock()=, triggered by the first
=settimeofday= with a zone — what =hwclock --systz= does in local mode). We never
do that, so the image needs an RTC kept in UTC.

To check a Linux install on the same machine: =timedatectl= prints
=RTC in local TZ: no=, and the last line of =/etc/adjtime= is =UTC=. A dual-boot
with Windows breaks this (Windows keeps the RTC in local time), and the tray then
reads off by the zone's offset.

** From UTC to local, with no zoneinfo

A time zone is normally a file in =/usr/share/zoneinfo= holding the zone's whole
history of offsets and DST switches. The image has none, so *a time zone here is
one integer*: =*utc-offset*=, seconds east of UTC, with the sign =date +%z= uses
(=-0300= → =-10800=).

- *Passed explicitly.* [[file:../initramfs/sysinfo.lisp::defun clock-string][=clock-string=]] passes it to =decode-universal-time= as
  CL's =time-zone= argument, which counts *hours west* (the opposite sign) and may
  be a ratio for zones like =+0530=. Passing it also keeps SBCL from asking libc
  for the local zone, which has nothing to find in the image.
- *Baked at build.* =build.sh= appends =(set-utc-offset "<date +%z>")= from the
  build host, on the assumption that you build where you boot. Change it live
  with =(set-utc-offset "+0100")=.

*The DST caveat.* A fixed offset can't follow daylight saving. In a zone without
DST (=America/Sao_Paulo= since 2019, for one) it costs nothing. In a DST zone, an
image built in winter is an hour off all summer, until rebuilt or
=set-utc-offset= is called. The fix, if it's ever needed, is to bake the one
zone's rules — a POSIX =TZ= string such as =CET-1CEST,M3.5.0,M10.5.0/3= is a
single line — rather than the whole database.

* 4. The API

All in =CL-USER=, all safe to call every frame — none of them signals:

| Function                      | Returns                                                                              |
|-------------------------------+--------------------------------------------------------------------------------------|
| =(battery-status &key fresh)= | =(:percent 87 :status :discharging :ac nil :minutes-left 192 :name "BAT0")= or =NIL= |
| =(battery-string b)=          | ="BAT -87% 3:12"=                                                                    |
| =(battery-tone b)=            | =:ok= / =:warn= / =:low= / =:charging=                                               |
| =(clock-string &optional ut)= | ="2026-10-02 09:01:52"= (no seconds when =*clock-seconds*= is =NIL=)                 |
| =(tray-items)=                | a list of plists left to right, each with =:kind= (=:battery=, =:clock=) and =:text= |
| =(set-utc-offset "-0300")=    | sets =*utc-offset*= (accepts an integer of seconds too)                              |

=*power-supply-root*= (default ="/sys/class/power_supply/"=) is what the host test
repoints at a scratch directory.

Other modules add their own items, each called by name so the tray works without
them:

- *Network.* =network-tray-item= (=wifi.lisp=), [[#fields][The fields]] above.
- *Agent cost.* From =agent-ui.lisp=.
- *Volume.* =VOL 50%= or =VOL mute= (=sound-tray-item= in [[file:../initramfs/mixer.lisp][mixer.lisp]], tag #29;
  nothing without a card, the card read at most every 2 s).
- *Recording.* =REC 01:23 ###...= (the mic's level as a bar), =PAUSED 01:23= or
  =SAVING 42%= (=recorder-tray-item=, [[file:../initramfs/recorder.lisp][recorder.lisp]], [[file:screencast.org::#recorder-pane-tray][screencast.org, The recorder pane and the tray]]).

* 5. Drawing it: one strip, repainted by itself
:PROPERTIES:
:CUSTOM_ID: drawing-strip-repainted-itself
:END:

[[file:../poc/shell.lisp::defun draw-tray][=draw-tray=]] draws the tray at the right end of the tab strip: the clipboard
icon (lit while the history holds something; a click opens the manager,
[[file:clipboard.org::#manager][clipboard.org, The manager]]), then each item of =tray-items=, battery coloured by its
tone. The tabs stop short of it ([[file:../poc/shell.lisp::defun tray-width][=tray-width=]]).

The clock changes every second with nobody touching anything. Redrawing the frame
for it would be cheap — 3 ms under KVM, 5 ms on real hardware
([[file:framebuffer.org::#done-blit-single-copy][framebuffer.org, DONE: the blit is a single copy]]) — but it isn't needed:

- *Wake on the second.* The browser's loop wakes at the next wall-clock second
  ([[file:../initramfs/fb-browser.lisp::defun tray-timeout][=tray-timeout=]], from =sb-ext:get-time-of-day=); with =*clock-seconds*= nil,
  once a minute.
- *Repaint the tray alone.* The tray is a morph of its own ([[file:morphic.org::#tree][morphic.org, The tree]]);
  [[file:../poc/morphic.lisp::defun tick-tray][=tick-tray=]] repaints it into the canvas and sends only that rectangle — the
  same economy as the pointer ([[file:framebuffer.org::#pointer-part-frame][framebuffer.org, The pointer is not part of the frame]]).
- *Pointer on top.* If the pointer is parked over the tray, it's put back on top.
