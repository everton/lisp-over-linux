* The one-sentence essence

On a desktop the clipboard is a /protocol/ between programs; in this image every
editor lives in one Lisp process, so the clipboard is just *a list of strings and
a few rules about it* — and the whole design is choosing the rules.

* 1. Why there is no protocol here

On X11, "copy" does not copy anything. The program you copied from merely
announces to the X server that it now /owns/ a named selection (=CLIPBOARD=). When
another program pastes, it asks the server, the server asks the owner, and the
owner converts its text and sends it over — the ICCCM selection dance. If the
owner exits, the text is gone. That is why clipboard /managers/ such as Parcellite
exist at all: a small daemon that watches ownership change, grabs a copy of the
text each time, and so outlives the programs and remembers a history.

None of that machinery has anything to do here. There is no X server (the browser
draws on =/dev/fb0=, see [[file:framebuffer.org][framebuffer.org]]), and every text view that can copy
or paste — the source panes, the Workspace, the side editor — is an object in the
*same Lisp heap*. Copying in one and pasting in another needs no ownership, no
conversion and no daemon: both read the same variable,
[[file:../poc/clipboard.lisp::defvar *clipboard*][=*clipboard*=]]. What is left of "a clipboard manager" is
the part that was always the interesting part: the /history/ and its manners.

That is also why the file has no dependency on any other file of the project. It
knows nothing about pixels, keys or text views — the editor decides /when/ to copy
(which key was pressed, whether this kill continues the last one); this file
decides /what that does/ to the stored text. Being pure, it is tested on the host
by a plain =sbcl --script=, no QEMU.

* 2. Parcellite — what we copy and what we don't

Parcellite's options are a good catalogue of what a clipboard history can do. The
names below are the keys in its config file (=~/.config/parcellite/parcelliterc=),
read off the host this was written on.

| Parcellite option                          | what it does                                                  | here                                        |
|--------------------------------------------+---------------------------------------------------------------+---------------------------------------------|
| =history_limit= (host value: 25)           | keep at most N entries                                        | *yes* — =board-limit=, default 50           |
| =ignore_whiteonly=                         | "ignore any clipboard additions that contain only whitespace" | *yes, always on* (see below)                |
| re-copying an entry                        | moves it to the top instead of listing it twice               | *yes* — de-duplication                      |
| =data_size=                                | a cap on entry size                                           | *yes* — =board-max-length=, 1 000 000 chars |
| =single_line= + =item_length= (50)         | show each entry as one ellipsised row                         | *yes* — [[file:../poc/clipboard.lisp::defun clip-label][=clip-label=]]                        |
| =type_search= / =case_search=              | type to filter the menu                                       | *yes* — [[file:../poc/clipboard.lisp::defun clip-filter][=clip-filter=]], case-insensitive     |
| =history_key= (host: =Ctrl-Alt-H=)         | a key that pops the history up                                | *yes* — =SuperL-h= (§7)                     |
| =use_copy= / =use_primary= / =synchronize= | track CLIPBOARD, PRIMARY, or keep both equal                  | *partly* — §3: a mouse selection sets both  |
| =trim_wspace_begend= / =trim_newline=      | rewrite the text on the way in                                | *no* — a copy should paste back exactly     |
| =save_history= / =persistent_history=      | survive a restart                                             | *no* — §8, the rootfs is tmpfs              |
| =hyperlinks_only=, actions (=actions_key=) | URL filtering, run a command on an entry                      | *no* — no browser, no shell to run it in    |

*Blank refusal* is the rule that gave this file its first test. A copy that is
all whitespace is almost always a mis-click — a double-click in a margin, a drag
that caught only the indentation — and recording it would push a real entry off
the bounded end of the history in exchange for a row you cannot even see. So
[[file:../poc/clipboard.lisp::defun clip-copy][=clip-copy=]] returns =NIL= with a second value =:BLANK= (or =:TOO-LONG=), so the caller
can say "nothing copied" rather than silently doing nothing. Note what it does
/not/ do: the text is still deleted from the buffer by a kill — refusing to
/record/ is not refusing to /edit/. (Honest aside: on the host this was written
on, Parcellite's own =ignore_whiteonly= is currently =false=; here the rule is
always on, because a 50-slot list has no room for invisible entries.)

*De-duplication* differs from Emacs, which by default happily keeps the same text
twice (=kill-do-not-save-duplicates= is =nil=, and even when set it only compares
against the newest entry). We follow Parcellite: re-copying anything already in
the list moves it to the front. In a browsable list, duplicates are pure noise.

* 3. Two selections: CLIPBOARD and PRIMARY

X has two everyday selections, and they are independent:

- *CLIPBOARD* — set by an explicit Copy (=Ctrl-C=, =M-w=, =Ctrl-Insert=), pasted
  by an explicit Paste.
- *PRIMARY* — set just by /selecting/ text, with no key at all; pasted by the
  *middle mouse button*. Select a word in one terminal, middle-click in another,
  done.

We model them as two different things: the *history* (§2, whose newest entry is
the CLIPBOARD) and [[file:../poc/clipboard.lisp::defun set-primary][=set-primary=]] / =primary=, a single string with no history,
exactly as X has.

*Does a mouse selection also enter the history?* The request was "any mouse
selection automatically copies to the clipboard", so *yes*: [[file:../poc/clipboard.lisp::defun clip-select][=clip-select=]] sets
PRIMARY /and/ calls =clip-copy= — Parcellite's =synchronize= behaviour. (Emacs's
equivalent knob, =mouse-drag-copy-region=, is =nil= by default — Emacs puts a
mouse selection in PRIMARY only. We deliberately go further.)

The trap is the drag. While the button is held, the selection grows on every
motion event — =f=, =fo=, =foo= — and committing each would fill the history with
prefixes that de-duplication cannot catch, since they are all different strings.
So the contract is: *call =clip-select= once, on button RELEASE*, with the final
selection. Only the release means "this is what I selected".

PRIMARY accepts a blank selection (X does too); only the history refuses it,
because only the history has slots to protect. Clearing the history leaves
PRIMARY alone.

* 4. The Emacs kill ring — the same list

Emacs never had a "clipboard"; it has the *kill ring*: every kill (=C-k=, =C-w=,
=M-d=, ...) and every copy (=M-w=) pushes a string, newest first, bounded
(=kill-ring-max=, 120 in Emacs 30.2), and =C-y= yanks the newest. That is
Parcellite's history under another name, so here it is *one list*. Two Emacs verbs
need more than a list, and both are in =LOL.CLIPBOARD=:

** Consecutive kills accumulate

=C-k C-k C-k= in Emacs does not make three entries: kills issued back-to-back are
/appended/ into one, so the three lines come back with a single =C-y=. Backward
kills (=M-DEL=) /prepend/ instead, so the text stays in buffer order. The caller —
which knows whether the previous command was also a kill — passes
=:append :after= (or =t=) or =:append :before=.

One subtlety cost a real bug, caught by the host test. =C-k= at the end of a line
kills only the newline. Alone, that is blank and refused. But as the second half
of "kill =foo=, then the newline", it is exactly what the user wants. So the
sequence accumulates in its own slot (=kill-tail=) whether or not each fragment
was storable, and the blank rule is applied to the /accumulated/ text. The entry
the sequence owns is compared by =EQ=, so if the user promoted something else in
between, a continued kill becomes a new entry instead of silently overwriting an
unrelated one. The bug: a fresh, refused kill left the /previous/ sequence's
entry marked as owned, and the next append replaced it; =clip-copy= now clears the
ownership whenever a sequence starts.

=C-k= itself is [[file:../poc/clipboard.lisp::defun kill-line-span][=kill-line-span=]], following Emacs's docstring to the letter:
"kill the rest of the current line; if no nonblanks there, kill thru newline". A
blank rest-of-line therefore takes the newline with it.

** Yank-pop walks a pointer, not the ring

=M-y= right after a =C-y= replaces the text just yanked with the next older
entry; again, and the one before that, wrapping round. Emacs does this by moving
a /pointer/ (=kill-ring-yank-pointer=), not by rotating the list — so a later
=C-y= yanks whatever you popped to, and the next new kill puts the pointer back
on the newest. [[file:../poc/clipboard.lisp::defun clip-yank-pop][=clip-yank-pop=]] is that pointer (=:n -1= goes the other way,
like =M-- M-y=). The /caller/ has to remember where the yanked text sits in its
buffer, because only it can replace it — [[file:../poc/clipboard.lisp::defun insert-text][=insert-text=]] returns the end position
for exactly that.

* 5. Rectangles

A *rectangle*, in Emacs, is the block of text between two corners taken
/column-wise/: every line from the top corner's line to the bottom one, and on
each of those, the columns from the left corner's column to the right one —
whichever corner was point and whichever was the mark. Its use is editing
/columns/: removing a column of a table, indenting a block by inserting spaces
down a column, prefixing every line with =;; =.

The difficulty is that lines are *ragged*. Take this buffer and the rectangle
from line 0, column 2 to line 3, column 5:

#+begin_example
          col 0123456789
   line 0     ab[cde]fgh
   line 1     ab               <- ends AT the left edge
   line 2     ab[cd ]          <- ends INSIDE the block
   line 3     ab[cde]fghij
#+end_example

Every command has to decide what a short line means. We follow
=lisp/rect.el= of Emacs 30.2 (default behaviour, no prefix argument), checked
line by line, and the host test pins each case on exactly this buffer:

| Emacs key   | command                  | ours           | on a ragged line                                             |
|-------------+--------------------------+----------------+--------------------------------------------------------------|
| =C-x r M-w= | =copy-rectangle-as-kill= | [[file:../poc/clipboard.lisp::defun rect-extract][=rect-extract=]] | padded with spaces — a rectangle is always a true block      |
| =C-x r k=   | =kill-rectangle=         | [[file:../poc/clipboard.lisp::defun rect-kill][=rect-kill=]]    | delete + extract                                             |
| =C-x r d=   | =delete-rectangle=       | [[file:../poc/clipboard.lisp::defun rect-delete][=rect-delete=]]  | a line ending before the block is left alone                 |
| =C-x r y=   | =yank-rectangle=         | [[file:../poc/clipboard.lisp::defun rect-yank][=rect-yank=]]    | short lines padded out to the column; lines added at the end |
| =C-x r o=   | =open-rectangle=         | [[file:../poc/clipboard.lisp::defun rect-open][=rect-open=]]    | blanks only where there is text to push right                |
| =C-x r c=   | =clear-rectangle=        | [[file:../poc/clipboard.lisp::defun rect-clear][=rect-clear=]]   | a line ending inside the block is cut, not space-filled      |
| =C-x r t=   | =string-rectangle=       | [[file:../poc/clipboard.lisp::defun rect-string][=rect-string=]]  | short lines padded to the left edge, then the string         |

Two properties hold for all of them. Each *returns a new lines vector and never
mutates its input* — so undo can be "keep the old vector", the same choice
=textview.lisp= already makes for every edit. And the corners may come in *any
order*, each axis sorted on its own — unlike a /region/, where only the pair of
positions is ordered (=order-positions= vs. =rect-bounds= in the code; mixing the
two up is the rectangle version of the classic selection bug).

A zero-width rectangle (both corners in one column) is useful, not degenerate:
=rect-string= on it /inserts/ the string down a column — that is how =C-x r t ;; RET=
comments out a block.

*The rectangle register.* Emacs keeps the last killed rectangle in its own
variable, =killed-rectangle=, not in the kill ring: a rectangle is a 2-D shape,
and pasting it as running text would lose the shape. So =C-y= and =C-x r y= never
compete for a slot. We do the same — [[file:../poc/clipboard.lisp::defun clip-set-rectangle][=clip-set-rectangle=]] / =clip-rectangle= — and a
rectangle does /not/ appear in the history or the manager.

Tabs: a column here is a character index. Emacs counts display columns, so a tab
spans several; we do not, which is honest only because the text view inserts
spaces for =Tab=. Pasted text containing tabs would rectangle-cut by characters.

Where each key comes from, since the console delivers them unevenly:

- *=Insert=* arrives as =ESC [ 2 ~=, now decoded as =:insert=; its Shift or Ctrl is
  folded in from the keyboard's evdev, because the console sends the same bytes
  either way ([[file:input.org][input.org]], "A bare modifier needs the keyboard's own evdev").
- *=M-Backspace=* is =ESC DEL=, decoded as =:backspace= with Meta.
- *Consecutive kills* are recognised by =*last-edit*=, which every editing key
  clears and the kill commands set; =M-y= reads the span the last paste recorded
  there, and refuses after anything else (Emacs's "Previous command was not a
  yank").
- *A selection made by the mouse* goes to PRIMARY and into the history; one made
  with Shift-arrows does not (the request named only the mouse — Emacs would, with
  =select-active-regions=). Drag-selecting works in *read-only* text too: copying is
  reading.
- *Middle click already meant something* — the *halo* ([[file:code-browser.org][code-browser.org]]). The
  resolution in [[file:../poc/shell.lisp::defun pane-middle-click][=pane-middle-click=]] is by place: in /editable/ text with a
  PRIMARY to paste, the button pastes; anywhere else, or with =SuperL= held, it
  opens the halo. Read-only text cannot receive a paste, so there the button is
  free.
- *A touchpad has no middle button.* A two-finger press is one, and so is
  Alt-click ([[file:input.org][input.org]], "Three buttons on a pad with one").

* 5½. Drag and drop is not the clipboard

A row dragged onto a text you can edit inserts text too — but nothing passes through
the clipboard: neither the history nor PRIMARY changes, and =M-y= does not see it.
What travels is not text but a *subject*, carried by the hand
([[file:morphic.org][morphic.org]] §13.3); the text view asks it for a *readable reference*
([[file:../poc/shell.lisp::defun drop-reference][=drop-reference=]]: ='name=, =#'f=, =(find-class 'c)=, a path as a string) and inserts
that where it lands, as one undoable edit ([[file:../poc/shell.lisp::defun drop-reference-at][=drop-reference-at=]]). Two reasons it
stays apart:

- *A drop is about a thing, the clipboard about text.* The same drag dropped on the
  tab strip opens the thing, and on an inspector field stores its /value/; only a text
  turns it into characters. Copying would make the text the primary reading.
- *X keeps them apart too.* X's drag-and-drop (XDND) is a protocol of its own beside
  the selections, not a use of CLIPBOARD or PRIMARY — from the literature, not checked
  here against an X server.

* 6½. Undo — the other history beside the kill ring

The kill ring remembers what you /took out/; undo remembers what the buffer /was/.
Both are Emacs's, and the second is wired the Emacs way too: =C-_=, =C-/= or
=C-x u= ([[file:../poc/shell.lisp::defun editor-undo][=editor-undo=]] over [[file:../poc/textview.lisp::defun tv-undo][=tv-undo=]]).

*Why it costs almost nothing here.* The text view's buffer is /persistent/: no
edit ever writes into a lines vector. Every one — a typed character
(=replace-line= copies), a newline, the clipboard's =region-delete= and
=insert-text=, a rectangle kill, the Workspace weaving a printed value in — builds
a /new/ vector and installs it (§1 already relied on this: the clipboard
functions return new vectors). So the state before an edit is just the old
vector, kept. An undo record is =(LINES LINE COL)=: one list and two numbers,
whatever the buffer's size, and "did this command change the text?" is an =EQ=
test. Nothing is diffed and nothing is copied. (Checked: the only =setf aref= on a
lines vector in =textview.lisp= and =clipboard.lisp= writes into a fresh copy.)

*The protocol is Emacs's, exactly*, because it is what makes undo unable to lose
anything:

| step              | what happens                                                                             |
|-------------------+------------------------------------------------------------------------------------------|
| an edit           | the state it replaced is pushed on the buffer's undo list                                |
| =C-_=             | restore the next older state — and push the one it leaves, since an undo is a change too |
| =C-_= again       | keep walking back (the run's own steps are not revisited)                                |
| any other command | the run ends; motion counts, as in Emacs                                                 |
| =C-_= after that  | walks back over the /undos/ first — Emacs's redo; there is no redo stack to fall off     |

Typing amalgamates: up to 20 consecutive self-inserted characters are one record
(Emacs's =amalgamating-undo-limit=), so =C-_= takes back a word or so rather than a
letter. A newline, a kill, a paste each make their own. A key that only starts a
chord (=C-x=, =C-c=) does not end a run, so =C-_ C-x u= is two undos, as in Emacs.
The list keeps the last 1000 records per buffer. Every path that edits goes
through one macro, [[file:../poc/shell.lisp::defmacro with-undo][=with-undo=]]: the editing keys, the right-button menu's
Cut / Paste / Paste the selection (which also gains an Undo entry), and the middle
click's paste.

*Where the keys come from on the console* ([[file:../linux/drivers/tty/vt/defkeymap.c_shipped][defkeymap.c_shipped]], the default
keymap): Ctrl-minus is byte 31, decoded as =C-_=; but Ctrl-/ is byte 127, /the
same/ as plain Backspace (=ctrl_map[53]= is =0xf07f=). Only the keyboard's evdev,
which says Ctrl is held, tells them apart (as with every bare modifier —
[[file:input.org][input.org]]). Ctrl-Backspace sends byte 8, so =fb-read-key= now gives byte 8 the
Ctrl bit and a DEL read /with/ Ctrl held is =C-/=. Under X both arrive as
keysyms, so neither trick is needed there.

Host test: [[file:../poc/undo-test.lisp][poc/undo-test.lisp]] (=sbcl --script poc/undo-test.lisp=, 18
assertions); in the guest, section K of [[file:../check-clipboard.lisp][check-clipboard.lisp]].

* 6¾. Search — =C-s= / =C-r=, and the mark it leaves

The third history an Emacs hand expects beside the kill ring and undo is the one of
/where you were looking/. =C-s= searches forward, =C-r= backward, in any text view —
the Workspace, a source, a file, and read-only text too (searching is reading).
(Built 2026-10-17; this doc holds it because §6 is where the editor's Emacs keys
already live, and its yank keys, =C-w= / =C-y=, are the kill ring's.)

*Incremental, and a mode rather than a prompt.* Every key you type moves to the next
match /at once/, and the search lasts until a key that is not a search key — and
then /that key still acts/: =C-s foo C-a= stops on "foo" and goes to the start of
its line. That is why it is not the shell's minibuffer, though it is drawn where the
minibuffer is: the minibuffer takes every key until Enter. The state lives on the
text view ([[file:../poc/textview.lisp::defstruct (isearch][=isearch=]], the view's =isearch= slot), and
[[file:../poc/textview.lisp::defun tv-isearch-key][=tv-isearch-key=]] says what became of each key — /taken/, /done/ (Enter),
/cancelled/ (=C-g=), or /exit/: the search is over and the key was not taken, so
[[file:../poc/shell.lisp::defun browser-key][=browser-key=]] goes on and handles it as if no search had run
([[file:../poc/shell.lisp::defun isearch-key][=isearch-key=]] is the joint).

*The semantics are =isearch.el='s, checked key for key against Emacs 30 =-Q=* in
batch — =execute-kbd-macro= on a temp buffer, then =point= and =(mark t)=; each case
is a check in the host test, with Emacs's answer written in:

| keys                              | what happens                                                                                    |
|-----------------------------------+-------------------------------------------------------------------------------------------------|
| a character                       | the string grows; the search goes again from the /start/ of the current match, so it can stay   |
| =C-s= / =C-r= again               | the next match; at the end "Failing", and the repeat after that wraps round the buffer          |
| after a wrap                      | "Wrapped", then "Overwrapped" once past where the search began — at once if it began at the top |
| =C-r= after =C-s=                 | turns round on the same match first (point to its other end), then goes back                    |
| =C-s= on an empty string          | the last string searched for again ("No previous search string" if there is none)               |
| =DEL=                             | back one /step/ — after a =C-s=, to the previous match, not off the string's last letter        |
| =C-g=                             | while it matches: cancel, point back where it began; while failing: drop the failing steps      |
| Enter, or any other key           | stop at the match; the mark is left at the start ("Mark saved where search started")            |
| =C-w= / =C-y= (or =Shift-Insert=) | add the next word at the match / the clipboard's newest entry                                   |
| a capital in the string           | the search becomes exact; all lower case ignores case (=search-upper-case=)                     |
| a space                           | matches any run of spaces and tabs (=isearch-lax-whitespace=, on by default in Emacs)           |

A yanked word is lower-cased first unless the string already has a capital, so
=C-w= on "Bar" does not turn a case-blind search exact — the =not-yanks= value of
=search-upper-case=, which Emacs's =isearch-yank-string= applies that way.

*The steps are a stack.* Each key that changes the search pushes its whole state —
string, direction, success, wrapped, the current match and point — and =DEL= pops
one (Emacs's =isearch-cmds=). That is the whole of "undo a step", and of =C-g='s
"strip what fails": pop until a state that matched.

*The mark, and =C-x C-x=.* A finished search leaves Emacs's mark where it began, so
=C-x C-x= ([[file:../poc/textview.lisp::defun tv-exchange-point-and-mark][=tv-exchange-point-and-mark=]]) goes back there with the region between
shown. The view had no mark apart from its selection anchor, so it gained one, the
=mark= slot: set by a search's end and by =C-SPC=. With =C-SPC= already set, a
search /grows the region/ to the match instead, as in Emacs (=C-SPC C-s baz RET=
selects up to "baz"). Unlike Emacs's mark the slot is not a marker — an edit above
it does not move it — and it is clamped when used.

*What you see.* The match point stands on is a dim amber band under its text, the
other matches in view a quieter olive one (Emacs's =isearch= and =lazy-highlight=
faces); neither is the accent, which a function name already wears. The bands are
part of what a row shows ([[file:../poc/textview.lisp::defun tv-row-keys][=tv-row-keys=]]), so the world repairs exactly the rows a
key changed ([[file:morphic.org][morphic.org]] §13). The status line shows Emacs's prompt —
"Failing wrapped I-search backward: " and the like — with the part of the string
that matches nothing in red ([[file:../poc/shell.lisp::defun draw-isearch-prompt][=draw-isearch-prompt=]]). A match off to the right
scrolls the view sideways even in a read-only pane, which has no caret to follow.

*How the keys arrive.* On the console =C-s= is byte 19, which a terminal's line
discipline takes as XOFF while =IXON= is on — it used to stop the console
([[file:diagnostics.org][diagnostics.org]] §1); raw mode clears =IXON=, so it is a key like any other.
=C-x C-s= is still save: the chord is decided before =C-s= is looked at.

*Where it differs from Emacs, deliberately:*

- *A match never crosses a line.* The buffer is a vector of lines and the string has
  no newline in it (Emacs's =C-j= / =C-q C-j= are not bound).
- *=C-w= adds a Lisp token* — what =M-f= moves over here — where Emacs's word stops
  at a hyphen.
- *No =M-c= / =M-r= / =M-e=* (toggle case, regexp, edit the string), no search ring
  beyond the last string, and =C-y= adds only the first line of what it yanks.
- *Enter on an empty string just ends the search*; Emacs starts a non-incremental one.
- *A click ends a search* where it stands, then places the caret; so does a key
  that moves focus to another pane.
- *Lists are not searched.* =C-s= is for text; a list has its own filter (=/= in a
  folder, the Spotter everywhere).

assertions; 42 cases were run in Emacs first); the repaired screen equals a fresh

* 7. The manager — a sketch

Parcellite's history is a pop-up menu. Ours should be the shape the environment
already has for "pick one from many": a *modal card like the Spotter*
(=SuperL-Space=, [[file:code-browser.org][code-browser.org]] §4¾), drawn with the same list widget.

#+begin_example
 ┌ Clipboard · 7 entries ────────────────────────────── SuperL-h ┐
 │ filter: def█                                                  │
 │ ▶ 0  (defun clip-copy (string &key append ...)\n  "Record...   │
 │   3  (defparameter *x* 3)                                     │
 │   5  (defun f ()\n  1)                                        │
 │ ───────────────────────────────────────────────────────────── │
 │ PRIMARY: foo-bar                                              │
 │ ↑↓ move · ↵ make current & paste · Del drop · Esc close       │
 └───────────────────────────────────────────────────────────────┘
#+end_example

| key                      | does                                                                     |
|--------------------------+--------------------------------------------------------------------------|
| =SuperL-h=               | open the card (so does the clipboard icon in the systray)                |
| typing                   | filter (=clip-filter=, case-insensitive substring); =Backspace= edits it |
| =↑= / =↓=, =C-p= / =C-n= | move the selection                                                       |
| =↵=                      | =clip-promote= the entry, close, and paste it at the caret               |
| =Delete=                 | =clip-delete= the entry (the list stays open)                            |
| =Esc= / =C-g=            | close without changing anything                                          |

Rows come from =clip-filter=, which returns =(index . string)= pairs, so a
filtered list still promotes and deletes by the real history index. Each row's
text is =clip-label=: one line, newlines shown as the two characters =\n= (plain
ASCII, so the bitmap font is sure to have it), runs of blanks collapsed, cut with
=...=. As built, the newest entry is marked =current=, the others by their place
(=#1=, =#2= …), and the PRIMARY line in the sketch was left out: PRIMARY is not part
of the history, and a middle click is the way to use it. =↵= pastes into whichever
editor had focus; with none, it only makes the entry current. Drawing:
[[file:../poc/shell.lisp::defun draw-clipboard-card][=draw-clipboard-card=]]; input: [[file:../poc/overlays.lisp::defun run-clipboard-manager][=run-clipboard-manager=]] (an overlay that waits for
the pick; [[file:../poc/shell.lisp::defun open-clipboard-manager][=open-clipboard-manager=]] pastes it).

* 8. Limits

- *Not shared with the host.* There is no X server inside the image and no
  channel to the host's selections; text copied on the laptop's desktop cannot be
  pasted in the guest, or back. (Under QEMU the net REPL on :4005 is the way to
  move text in.)
- *Not persisted.* The root filesystem is the unpacked initramfs, living in RAM
  ([[file:sbcl-init.org][sbcl-init.org]]), so the history
  dies with the power-off — the same storage-target question that defers the
  change set's file-out.
- *One process.* A second process (the =job= worker of [[file:processes.org][processes.org]]) has its
  own heap and so its own, empty clipboard. Nothing it does today copies text.
- *Columns are characters* (see §5's note on tabs).
