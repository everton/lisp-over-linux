#+TITLE: Input devices — evdev, the mouse, the wheel, and the modifiers the tty hides
#+STARTUP: showall

Sibling docs: [[file:line-editing.org][line-editing.org]] (the *other* half of input — raw-mode termios and
the cooked tty) · [[file:framebuffer.org][framebuffer.org]] (the output half — =/dev/fb0=) ·
[[file:kernel-config.org][kernel-config.org]] (the options that create these device nodes) ·
[[file:code-browser.org][code-browser.org]] §6.3 (what the browser does with them).

Question that prompted this: /how does the machine know the mouse moved, or that
the wheel turned?/ There is no X server, no libinput, no udev, and no mouse
daemon. The answer is one character device, one 24-byte struct, and =poll(2)=.

* The one-sentence essence

The kernel turns every input device into a file at =/dev/input/eventN= that emits
*fixed 24-byte records* saying "this type of thing, this code, this value" — and
our entire mouse driver is a loop that reads 24 bytes at a time and adds the
numbers up.

* 1. Why the tty is not enough

We already read the keyboard, and we read it through the *terminal*: fd 0, put
into raw mode with termios, one byte per keystroke ([[file:line-editing.org][line-editing.org]]). That path
is excellent for *text* and useless for two things:

1. *The mouse.* The tty carries characters. A pointer has no character.
2. *A bare modifier.* Hold Ctrl on its own and the tty delivers *nothing at all* —
   there is no byte for "Ctrl is currently down". The tty only ever tells you
   about a modifier once it has already been *combined* with a key: =C-g= arrives
   as byte 7, and the Ctrl-ness is gone by the time you see it.

The browser needs both — a pointer to click with, and =Ctrl-click= /
=SuperL-click= as distinct gestures ([[file:code-browser.org][code-browser.org]] §4¾). So it opens a second
and third door onto the hardware, underneath the terminal: the raw input devices.

*Three kinds of fd, three jobs*, and they are deliberately not interchangeable:

| fd                            | carries                                      | why not one of the others                                                            |
|-------------------------------+----------------------------------------------+--------------------------------------------------------------------------------------|
| =0= (the console tty)         | typed *text*, escape sequences               | the only one that has been through the keymap — evdev gives key /codes/, not letters |
| every pointer's =eventN=      | motion, buttons, the wheel                   | the tty has no notion of a pointer                                                   |
| every keyboard's own =eventN= | *only* Ctrl / Shift / Super / Alt held state | the tty cannot report a bare modifier                                                |

"Every": a laptop with an external mouse and keyboard has two of each kind, and
all of them are open at once — §4¾ is how, and why it used to be one of each.

That third one is worth restating because it looks redundant: we read the
keyboard *twice*, through two different doors, on purpose. Text comes from the
cooked-ish tty because that is where the keymap lives (evdev would hand us
"keycode 30", not =a=). The modifier *state* comes from evdev because that is the
only place it exists. The main loop then =logior=s the evdev modifier bits into
the state word before dispatching the tty's key — see [[file:../initramfs/fb-browser.lisp][=fb-browser.lisp=]]'s
=run-browser-fb=.

* 2. What evdev is

=CONFIG_INPUT_EVDEV=y= builds [[file:../linux/drivers/input/evdev.c][=drivers/input/evdev.c=]], a *generic* handler that
attaches to every input device the kernel has and exposes each as a character
device =/dev/input/eventN=.

It is generic in the strong sense: it does not know what a mouse is. It publishes
the input subsystem's internal event stream verbatim, and userland decides that a
device emitting relative-X and relative-Y is a pointer. The keyboard, the mouse,
the touchpad and the ACPI power button all arrive through the identical
interface, distinguished only by *which kinds of event they are capable of*.

** The record

Reading the device gives back a whole number of =struct input_event= records
([[file:../linux/include/uapi/linux/input.h::struct input_event][=include/uapi/linux/input.h=]]). On 64-bit x86 one record is *24 bytes*:

| offset | size | field     | meaning                                            |
|--------+------+-----------+----------------------------------------------------|
|      0 |    8 | =tv_sec=  | timestamp, seconds — read by the tap gesture (§4½) |
|      8 |    8 | =tv_usec= | timestamp, microseconds — likewise                 |
|     16 |    2 | =type=    | *what kind* of event (a key? motion?)              |
|     18 |    2 | =code=    | *which* one (which key, which axis)                |
|     20 |    4 | =value=   | signed 32-bit: how much / pressed?                 |

The 16-byte =struct timeval= at the front is why the record is 24 and not 8, and
it is the single most common source of "my offsets are wrong" — on a 32-bit
machine that timeval is 8 bytes and the record is 16.

There is no framing, no length prefix, and no escaping: records simply abut. The
driver enforces this — [[file:../linux/drivers/input/evdev.c][=evdev.c=]] returns =-EINVAL= rather than a partial record
if you hand it a buffer smaller than one event, and otherwise fills as many whole
records as fit. So "read 24 bytes, decode, repeat" is not a convention we adopted;
it is the contract.

** Reading it in Lisp

No new dependency: the same =sb-alien= FFI style as [[file:../initramfs/net.lisp][net.lisp]], on the =libc= we
already ship. Open the node non-blocking ([[file:../initramfs/fb-browser.lisp::defun open-evdev][=open-evdev=]]) and drain it
([[file:../initramfs/fb-browser.lisp::defun read-mouse][=read-mouse=]]):

#+begin_src lisp
  (let ((n (%fbb-read fd buf 24)))
    (when (< n 24) (return))                    ; queue empty — O_NONBLOCK
    (let* ((type (logior (deref e 16) (ash (deref e 17) 8)))            ; u16 LE
           (code (logior (deref e 18) (ash (deref e 19) 8)))            ; u16 LE
           (v    (logior (deref e 20) (ash (deref e 21) 8)
                         (ash (deref e 22) 16) (ash (deref e 23) 24)))
           (val  (if (>= v #x80000000) (- v #x100000000) v)))           ; s32
      …))
#+end_src

Two details that matter:

- *Little-endian reassembly by hand.* We read bytes and shift, rather than casting
  a struct, because that is honest about the wire format and costs nothing.
- *Sign extension.* =value= is =__s32=. Moving the mouse left gives =-1=, which
  arrives as =#xFFFFFFFF=; the last line turns it back into =-1=. Skip it and the
  cursor teleports right by four billion pixels on the first leftward twitch —
  a very memorable bug.

*The non-blocking read is the loop's terminator.* With =O_NONBLOCK= a read on an
empty queue returns =-1= (=EAGAIN=) rather than waiting, so =(< n 24)= means
"nothing more right now" and we stop. Draining in a loop rather than one record
per frame is what makes a fast mouse flick feel smooth: several records collapse
into one cursor move and one redraw.

* 3. The events we actually decode

Of the ~30 event types, the browser needs four. Constants from
[[file:../linux/include/uapi/linux/input-event-codes.h::#define REL_WHEEL][=input-event-codes.h=]]:

| =type=       | =code=                                                | =value=                               | what we do                                                                        |
|--------------+-------------------------------------------------------+---------------------------------------+-----------------------------------------------------------------------------------|
| =2= =EV_REL= | =0= =REL_X=                                           | delta, signed                         | =(incf *cursor-x* val)=, clamped                                                  |
| =2= =EV_REL= | =1= =REL_Y=                                           | delta, signed                         | =(incf *cursor-y* val)=, clamped                                                  |
| =2= =EV_REL= | =8= =REL_WHEEL=                                       | notches, ±1                           | sum into =wheel= (see §6)                                                         |
| =3= =EV_ABS= | =0= / =1= =ABS_X/Y=                                   | absolute, in the *device's own* range | scale onto the screen, or difference it (§4½)                                     |
| =1= =EV_KEY= | =#x110= =BTN_LEFT=                                    | =1= press / =0= release               | on press: a =:down= event, to the morph under the pointer (a pane's =pane-click=) |
| =1= =EV_KEY= | =#x14a= =BTN_TOUCH=, =#x145/#x14d/#x14e= =BTN_TOOL_*= | =1= down / =0= up                     | a contact changed: forget the last pad position, and open or close a *tap* (§4½)  |
| =1= =EV_KEY= | =29=/=97= Ctrl, =42=/=54= Shift, =125=/=126= Meta     | =1= down =2= repeat =0= up            | set =*ctrl-down*= / =*shift-down*= / =*super-down*=                               |
| =1= =EV_KEY= | =115= / =114= =KEY_VOLUMEUP= / =DOWN=, =113= =KEY_MUTE=, =248= =KEY_MICMUTE= | =1= press, =2= repeat (volume only) | =mixer.lisp='s =audio-key= (tag #29): no tty byte exists for these keys |
| =0= =EV_SYN= | =0= =SYN_REPORT=                                      | —                                     | end of packet: apply the gathered position                                        |

Relative *and* absolute are both handled because the three ways we run differ:
QEMU's default PS/2 mouse is relative; =-device usb-tablet= is absolute and maps
onto the screen (which is what makes a scripted click land predictably, and so
matters for the QMP screenshot harness — [[file:code-browser.org][code-browser.org]] §8); and a real
laptop has a *touchpad*, which is absolute but is emphatically not a screen.
That third case is §4½, and it is the one that took a rewrite.

Note that =EV_SYN= earns a row now. A packet is several records — =ABS_X=, then
=ABS_Y=, then perhaps =BTN_TOUCH= — and =SYN_REPORT= is the kernel saying "that
was one coherent report". Acting record by record moves an absolute pointer in an
L instead of a straight line, so we gather and act at the =SYN=.

Note =EV_KEY= covers *both* buttons and keys — a mouse button is just a key whose
code happens to be =0x110=. That is the input subsystem's view, not a quirk.

* 4. Finding the device without udev

This is the part that surprised us, and it is the reason [[file:../initramfs/fb-browser.lisp::defun scan-input-device][=scan-input-device=]]
exists at all.

Two non-obvious facts:

1. *=eventN= is not stable.* The number depends on probe order. Hardcoding
   =/dev/input/event2= works until it doesn't.
2. *There is no =/dev/input/mouse0=.* That node comes from =mousedev=, and
   =CONFIG_INPUT_MOUSEDEV is not set= in our config. So the obvious trick —
   scan =/proc/bus/input/devices= for a =Handlers== line containing =mouse= —
   finds nothing. Our PS/2 mouse advertises only =Handlers=event2=.

So we classify by *capability* instead. [[file:../linux/drivers/input/input.c][=drivers/input/input.c=]]'s
=input_devices_seq_show= prints one block per device, blank-line separated:

#+begin_example
  I: Bus=0011 Vendor=0002 Product=0006 Version=0000
  N: Name="ImExPS/2 Generic Explorer Mouse"
  P: Phys=isa0060/serio1/input0
  S: Sysfs=/devices/platform/i8042/serio1/input/input4
  U: Uniq=
  H: Handlers=event2
  B: PROP=0
  B: EV=7
  B: KEY=70000 0 0 0 0
  B: REL=103
#+end_example

The =B: EV== line is a *bitmask of the event types this device can emit*, in hex —
one bit per =EV_*= constant. =EV=7= is bits 0,1,2 = =EV_SYN= + =EV_KEY= + =EV_REL=:
it has buttons and it moves relatively. That is a pointer, and no other kind of
device says so.

So the rules are one line each — [[file:../initramfs/fb-browser.lisp::defun input-device-kind][=input-device-kind=]]:

- *pointer* — EV_REL (bit 2) with =REL_X=, or EV_ABS (bit 3) with =ABS_X=. The
  axis matters, not just the event type: a USB keyboard's /Consumer Control/ node
  says =EV=1f= — it has =EV_REL= (for =REL_HWHEEL=, a horizontal-scroll key) and
  =EV_ABS= (for volume) and no X axis at all. =REL_X= / =ABS_X= are bit 0 of the
  =B: REL== / =B: ABS== bitmaps, whose low word is the *last* token on the line
  (see "one parsing subtlety" below).
- *keyboard* — EV_KEY (bit 1) *and* EV_REP (bit =0x14= = 20, autorepeat).

** The other bitmask on the line above: =B: PROP=

=EV= says *what kinds of event* a device emits. It does not say what they mean,
and for an absolute device that is the entire question. =B: PROP=- answers it, and
we spent a while ignoring it:

| bit | property               | what the positions mean                           |
|-----+------------------------+---------------------------------------------------|
|   0 | =INPUT_PROP_POINTER=   | a surface *under* your hand — a touchpad          |
|   1 | =INPUT_PROP_DIRECT=    | the surface *is* the screen — touchscreen, tablet |
|   2 | =INPUT_PROP_BUTTONPAD= | the whole pad is the button (a clickpad)          |

=usb-tablet= prints =PROP=0=. A PS/2 Synaptics pad prints =PROP=9=, the I2C one
=PROP=5= — both have bit 0. Same =EV=, opposite meaning.

** Ranking was the bug

There is usually more than one pointer, and until 2026-10-12 the answer to that
was a *ranking*: =find-mouse-device= asked for a tablet, then a relative mouse,
then a touchpad, and opened the first kind it found — one pointer, chosen once.
Its comment said "on a laptop there is no mouse, so rule 3 [the touchpad] is the
only rule that fires". That stopped being true the day an external mouse was
plugged in: the mouse rule fired, and the touchpad was never opened. §4¾ is the
whole story and the fix — every pointer is now open, each read as its own kind.

The kinds still matter, per device: a =:mouse= adds deltas, a =:tablet= maps
positions onto the screen, a =:pad= differences them (§4½).

The =EV_REP= half of the keyboard rule is not decoration. The ACPI *power button*
also registers as a keyboard-ish device (it emits =KEY_POWER=), and it also gets a
=kbd= handler — but it cannot autorepeat. Without the EV_REP bit we would happily
open the power button and wonder why Ctrl never seemed to be held.

*One parsing subtlety, and why it is safe.* =input_seq_print_bitmap= prints a
bitmap as space-separated 64-bit words, most significant first — see =B: KEY=
above. Our parser reads hex up to the first space, i.e. only the first word. For
=EV= that is exactly right and always will be: =EV_MAX= is =0x1f=, so the whole
mask is a single word and there is never a second one to miss. (Do not copy the
same parse for =B: KEY=, where it would silently read the wrong end.) The parser
now takes the *last* word instead, which is the same thing for =EV= and =PROP= and
the right thing for =REL= and =ABS=: =ABS=2e0800000000003= (the laptop's I2C pad,
on the host) is two words, and =ABS_X= lives in the second.

* 4½. The touchpad: absolute, but not a position

A laptop has no mouse. It has a pad about 90mm wide under your palm, and the
kernel describes that pad the way it describes a drawing tablet: =EV_ABS=,
=ABS_X=, =ABS_Y=, one position per packet. Read it the way we read a
=usb-tablet= and you get the most baffling-looking bug this project has had — the
cursor sits in the *top-left corner*, moves coherently inside a box a couple of
hundred pixels wide, barely moves vertically at all, and jumps whenever you lift
a finger. Every one of those symptoms has a cause, and there are two causes.

** Cause one: 0..32767 is not a range, it is one device's range

=usb-tablet= reports 0..32767 on both axes. That is *its* choice, not a property
of the protocol — and we had it written into the scaling as if it were. A PS/2
Synaptics pad reports roughly 1472..5472 across by 1408..4448 down. Scale those
as though they ran to 32767 and a full sweep of the pad reaches

: 5472 * 1920 / 32768 =  320 px   of 1920 across
: 4448 * 1080 / 32768 =  146 px   of 1080 down

— a box in the top-left corner, more than twice as wide as it is tall. That is
the bug report, arithmetic included: /it never goes down significantly/.

The fix is to stop assuming and *ask*. =EVIOCGABS(axis)= fills a
=struct input_absinfo= — six =__s32=: value, minimum, maximum, fuzz, flat,
resolution — and the middle two are the answer. One ioctl per axis, once, at open
time ([[file:../initramfs/fb-browser.lisp::defun evdev-abs-range][=evdev-abs-range=]]). The request number is =_IOR('E', 0x40+axis, 24)= =
=#x80184540 + axis=.

** Cause two: a pad is not a small screen

Fixing the range alone would map the pad onto the display one-to-one, and that is
still wrong — in a way that is harder to see, because it *looks* like it works.
On a directly-mapped pad the cursor is wherever your finger is: lift it, put it
down 3cm left, and the cursor teleports. There is no way to reach a far corner
with a short motion, and no way to nudge the cursor by two pixels at all.

A tablet genuinely wants that behaviour; a pad never does. =B: PROP=- is what
tells the two apart (§4 above), and bit 0 or bit 2 — POINTER or BUTTONPAD — means
*difference the positions, do not map them*.

** Differencing without the jumps

[[file:../initramfs/fb-browser.lisp::defun pad-motion][=pad-motion=]] remembers the last position and moves the cursor by the change,
scaled so that one full sweep of the pad crosses =*pad-speed*= screens (=3/2= by
default). Each axis is scaled by its own range, which quietly fixes the aspect
too: pads are wider than they are tall in device units in roughly the same
proportion as screens are, so the two factors come out nearly equal and motion
stays isotropic without a second constant.

Three details carry the whole thing:

1. *Per packet, not per record.* =ABS_X= and =ABS_Y= arrive as two records.
   Applying each as it lands moves the cursor in an L rather than along the line
   your finger drew. We gather them and act on =SYN_REPORT=, which is exactly
   what that event is for.

2. *Forget the last position whenever the contact changes.* =BTN_TOUCH= and
   =BTN_TOOL_{FINGER,DOUBLETAP,TRIPLETAP}= change value only when a finger lands,
   lifts, or is joined by another — and all three of those move the point the pad
   reports. Each clears the remembered position, so the first packet of a new
   contact yields *no* delta instead of a jump across the screen. A
   quarter-of-the-pad sanity limit backs it up for hardware that never bothers to
   report =BTN_TOUCH=.

3. *Carry the fraction.* At around 0.7px per pad unit, a slow drag is a run of
   deltas that each round to zero. Truncate them and the cursor simply refuses to
   move slowly; we keep the remainder as an exact rational and pay it out on
   later packets.

The first two are why the old code jumped, and the third is why differencing done
carelessly feels worse than the bug it replaces.

** The click that sends no button

A clickpad's physical press is a =BTN_LEFT= like any mouse button's, and that half
always worked. A *tap* sends no button at all: the finger lands, lifts, and the only
trace is =BTN_TOUCH= going =1= and then =0=. Everywhere else, =libinput= is the
thing that decides those two events were a click. There is no =libinput= here.

*Tap-to-click is OFF by default* (2026-10-16, the user's choice: click only when
you really click). =*tap-to-click*= is =NIL=, so a contact never opens a tap
candidate and only a physical press clicks. Put =(:tap-to-click t)= in
=~/.lol/settings= (read when the browser starts), or =(setf *tap-to-click* t)=
in the Workspace, to bring back the rule below.

When it is on, =read-mouse= decides. A contact becomes a click when four things hold:

1. *It was brief, but not fleeting* — under =*tap-max-us*=, 180ms, which is the
   figure libinput settled on (longer and you were resting a finger, not tapping),
   and at least =*tap-min-us*=, 30ms. A Synaptics pad sends a packet every 12.5ms,
   so a finger brushing past on its way somewhere is over in one or two of them.
2. *It did not travel* — no further from where it landed than =*tap-travel*=, a
   fortieth of the pad (about 2mm on a Synaptics pad), which forgives the roll of a
   finger lifting without admitting a drag.
3. *It was one finger, and pressed nothing.* A second finger means scroll — or a
   right-click we have no second button for — and either way the contact stops being
   a tap. A real =BTN_LEFT= disarms it too, so a press and the finger resting on the
   pad cannot fire twice.
4. *It pressed like a tap* — its peak =ABS_PRESSURE= reached =*tap-min-pressure*=,
   60. The pad reports pressure on every packet (0..255, Synaptics' "Z"), and the
   kernel already turns anything over 30 into =BTN_TOUCH= — that is the hysteresis
   at =if (hw.z > 30)= / =if (hw.z < 25)= in =linux/drivers/input/mouse/synaptics.c=.
   Synaptics' interfacing guide puts a very light finger near 30 and a normal one
   near 80; a graze lives between the two. A pad that reports no pressure skips this
   test rather than never tapping.

Rules 1's floor and 4 came later (2026-10-02), from use: with only the first three,
the lightest touch on the laptop's pad was a click, and an accidental one looks
exactly like a bug — something opened that you did not ask for. A *physical*
press is untouched by all of this: it is =BTN_LEFT=, and it always clicks.

*Tuning it.* The numbers are guesses about one person's fingers on one pad, so
the last contact is kept, as the rule saw it, in =*last-touch*= — =(:ms 75 :peak
80 :tap t)=. Print it in the Workspace right after a tap that misbehaved, and set
=*tap-min-pressure*= or =*tap-min-us*= there; both are ordinary special variables,
read on every contact.

*How it was verified* without a touchpad (QEMU emulates none): =read-mouse= takes an
fd, and a regular file is one, so a file of synthetic Synaptics-shaped records —
=BTN_TOUCH=, =ABS_X/Y=, =ABS_PRESSURE= every 12.5ms — replays a contact exactly. A
firm 80ms tap (peak 80) clicked; a graze of the same length (peak 45), a one-packet
brush, a 300ms rest and a sliding contact did not; a physical press did.

*This is what the timestamps were for.* Every record has carried a =struct timeval=
since §2 and we had never read one — the rule above is the first thing that needs
to know /how long/ rather than /what/. [[file:../initramfs/fb-browser.lisp::defun evdev-time-us][=evdev-time-us=]] reads the 16 bytes; the
gesture only ever takes a *difference* of two of them, so the clock behind it
(evdev's default is =CLOCK_REALTIME=) never has to mean anything absolute.

Two honest limits. *There is no tap-and-drag* — tap, then touch-and-hold to drag —
because a tap is decided only when the finger /lifts/, so there is nothing still
held to drag with; the pressed drag (next section) is the way to select. And
because =read-mouse= returns a click as a boolean, *two clicks inside one drain
collapse into one*; a drain is one =poll(2)= wake, so two taps that fast are not reachable by
hand, and a double-click gesture would need a real press/release pair rather than
this flag.

** Press and drag: selecting with the pointer

A press that lands in a text view places the caret there, and while the button stays
down, motion extends the selection from that caret to the pointer — [[file:../poc/shell.lisp::defun browser-drag][=browser-drag=]],
over the =tv-drag= the X11 editor prototype always had. On a clickpad that is: press
the pad down, and slide.

- *The button's state, not just its press.* =read-mouse= used to report =BTN_LEFT=
  only as "a click happened". It now also keeps =*button-down*= — value 1 sets it,
  0 clears it — and the loop treats any pointer motion while it is set as a drag.
- *Which view.* The press goes to the morph under the pointer — the text view's own
  body morph — and the *hand* remembers what it placed the caret in (its press,
  =(:text :tv … :origin …)=, [[file:../poc/morph.lisp::defclass hand (morph)][the hand]]'s =press= slot); the world sends the drag to
  that same morph (the hand's capture), so a drag extends that view even if the
  pointer wanders over another pane ([[file:morphic.org][morphic.org]] §12.5, §13.2). The release
  clears the press.
- *A press on a row waits for its release.* A press on a list row that opens
  something acts when the button comes up; a press that moves first (8 px,
  =+pick-up-travel+=) is not a click but a *pick-up*: the hand carries the row's
  subject to be dropped on another morph ([[file:morphic.org][morphic.org]] §13.3). A *tap* has no
  release of its own, so the loop marks its press =:tap= and it acts at once.
- *A slop of 3 pixels* (=+drag-slop+=) before the first extension. Pressing a
  clickpad rolls the fingertip, which nudges the pointer a pixel or two; without the
  slop, every press would select a character instead of placing the caret.
- *Two fingers do not scroll while the pad is pressed.* On a clickpad the press is
  often a thumb, and the finger that moves is a second one — which is otherwise the
  two-finger scroll (§6). So =pad-motion= scrolls only when the button is up.
  /Untested on the laptop's pad:/ which finger =ABS_X/Y= follows while two are
  down is the pad's choice, not ours, so pressing with one finger and sliding the
  same one is the sure way.

Verified in the guest by =check-pointer.lisp=, with QEMU's left button genuinely held
across real =EV_REL= motion: the press alone selects nothing, the drag selects and
follows the pointer down, the release is seen, and a still click clears it.

** Three buttons on a pad with one

The right button opens a context menu and the middle one a halo or X's paste
([[file:code-browser.org][code-browser.org]], "The right button and the halo"). A mouse has those buttons —
=BTN_RIGHT= =#x111= and =BTN_MIDDLE= =#x112=, decoded beside =BTN_LEFT=. A clickpad
has exactly one physical button, so *which button a press means* is read off the
pad at the moment it goes down ([[file:../initramfs/fb-browser.lisp::defun pad-press-button][=pad-press-button=]]):

| on the pad                             | means  | why                                                   |
|----------------------------------------+--------+-------------------------------------------------------|
| one finger, bottom-right corner, press | right  | the software-button zone every buttonless laptop uses |
| two fingers down, press                | middle | what was asked for; libinput's "clickfinger" pattern  |
| three fingers down, press              | right  | a second route to the menu that needs no aiming       |
| one finger anywhere else, press        | left   | the ordinary click (and the only one that drags)      |

The finger count is known by then: =synaptics_process_packet= reports
=BTN_TOOL_*= before =synaptics_report_buttons=, so =*pad-fingers*= is current when
=BTN_LEFT= arrives. The corner is =*pad-right-zone*= — right of 3/5 of the width,
below 4/5 of the height; =ABS_Y= grows /downwards/ on this pad (the driver inverts
the hardware's y in =synaptics_invert_y=).

Two keyboard routes for a pointer that has no middle button and a hand that is on
the keys anyway:

- *Alt-click* is the middle button. Alt is tracked from the keyboard's evdev
  (=KEY_LEFTALT= 56 / =KEY_RIGHTALT= 100), the same way Ctrl, Shift and Super are.
  (Ctrl-click was the other candidate, but it already jumps to a definition —
  which is the halo's most-used handle anyway.)
- The *Menu key* (=KEY_COMPOSE=, 127) and *Shift-F10* open the context menu at the
  caret or the selected row. The console sends no byte for the Menu key, so it too
  is read from evdev; Shift-F10 arrives as =ESC [ 34 ~= (the keymap calls it F20).
- *Ctrl-= and Ctrl-0* (the text-size chord =C-x C-= / C-x C-0=, [[file:fonts.org][fonts.org]] §6) are
  silent on the console too: the default keymap (=drivers/tty/vt/defkeymap.map=)
  gives keycodes 11 and 13 no =control= column, so no byte arrives.
  =note-modifier-key= reports them from evdev as =#\== / =#\+= / =#\0=, and the
  browser's loop hands them to =browser-key= with the Ctrl bit. (=Ctrl--= needs no
  help: =Control_underscore=, byte 31.)
- *Ctrl-, and Ctrl-.* (so also =C-<= / =C->=, start / end of the buffer in every text
  and in the minibuffer) are worse than silent. Keycode 51 has no =control= column,
  so Ctrl-, sends nothing, but the default keymap says =control keycode 52 = Compose=:
  Ctrl-. starts a compose sequence that eats the next keys. Two fixes:
  =note-modifier-key= reports both from evdev as =#\<= / =#\>= (Shift or not, since
  =<= and =>= are shifted keys anyway), and [[file:../initramfs/fb-browser.lisp::defun unbind-console-ctrl-dot][=unbind-console-ctrl-dot=]] takes Compose off
  that key once, when the environment starts. It does this with one =KDSKBENT= ioctl
  (=0x4B47=, =include/uapi/linux/kd.h=): table 4 (the Ctrl map), index 52, value
  =K_HOLE= (=K(KT_SPEC,0)= = =0x0200=, a key that sends nothing).
- *Ctrl-;* (comment the line or region, [[file:code-browser.org][code-browser.org]] Phase 3a) is silent for the
  same reason as Ctrl-,: keycode 39 has no =control= column. =note-modifier-key=
  reports it from evdev as =#\;=.
- *Ctrl + wheel* resizes the text, one step per notch, three at most per event, as in
  every web browser ([[file:fonts.org][fonts.org]] §6). The wheel handler in =poc/shell.lisp= reads the held
  Ctrl from =fb-browser.lisp='s =*ctrl-down*= by name, because =shell.lisp= loads first.
- *Shift-PageUp / Shift-PageDown* are the same story: the default keymap binds them
  to the console's own scrollback (=shift_map[104]= = Scroll_Backward) and sends no
  byte, so =note-modifier-key= reports them from evdev too. The terminal pane scrolls
  its history with them ([[file:terminal.org][terminal.org]] §8); elsewhere they reach =browser-key= as
  Shift-PageUp/Down.

A right or middle press is *not* a click to the overlays (the Spotter, the
debugger, the cheatsheet): =read-mouse= reports it in a third value, and only the
browser's own loop reads that one. Verified in the guest by
[[file:../check-clipboard.lisp][check-clipboard.lisp]] with QEMU's real right and middle buttons; the pad's
emulated ones, like the tap, by replaying synthetic Synaptics packets.

* 4¾. Every device at once, and the ones plugged in later

The report, from the real laptop (2026-10-12): /"I was not able to use an
external mouse and the trackpad at the same time."/ The user normally works with
an external USB mouse *and* an external USB keyboard, so this is the everyday
case, not an edge.

** What was wrong

The environment opened *one* pointer and *one* keyboard, chosen *once*, when it
started. Three separate failures follow from that sentence:

1. *One pointer.* =find-mouse-device= ranked the candidates (tablet, then a
   relative mouse, then a touchpad) and returned the best. With a USB mouse
   present, the mouse rule fires and the touchpad is never opened. Plug the mouse
   in /after/ the environment started and it is the other way round: the pad was
   opened, the mouse never is.
2. *One keyboard.* =find-keyboard-device= returned the /first/ device with
   =EV_KEY= + =EV_REP=. On a laptop that is the built-in keyboard — the i8042
   controller is probed long before USB — so the external keyboard's evdev was
   never read. Typing still worked, which is what hid this: *text* comes through
   the console (fd 0), and the console merges every keyboard. But Ctrl, Shift,
   Super and Alt are read from evdev (§1), so on the external keyboard Ctrl-click,
   Shift-arrow selection and every =SuperL-= binding were dead.
3. *Once.* Nothing ever looked again, so anything plugged in later did not exist.
   "Later" includes devices plugged in /before/ boot: USB enumerates
   asynchronously, after PID 1 is already running — the supervisor's two-second
   wait exists for exactly this ([[file:sbcl-init.org][sbcl-init.org]], "Why the startup =(sleep 2)=
   exists") — so a slow hub could leave the external mouse out of the one scan
   there was, and the touchpad would be what got opened.

What the laptop actually exposes, read on the build host — which /is/ the laptop,
with the external mouse and keyboard attached (=cat /proc/bus/input/devices=,
abridged; host Debian kernel, so the touchpad's node differs under ours — see §8):

| node    | name                                   | =EV=     | what the old rules made of it                 |
|---------+----------------------------------------+----------+-----------------------------------------------|
| event0  | AT Translated Set 2 keyboard           | =120013= | *the* keyboard — first with =EV_REP=          |
| event16 | PS/2 Synaptics TouchPad                | (pad)    | rule 3 — never reached while a mouse exists   |
| event17 | PixArt Microsoft USB Optical Mouse     | =17=     | rule 2, a mouse                               |
| event18 | SINO WEALTH Gaming KB                  | =120013= | a keyboard — never opened (event0 came first) |
| event20 | SINO WEALTH Gaming KB Consumer Control | =1f=     | rule 2, /also/ a "mouse": =EV_REL=, no X axis |
| event21 | SINO WEALTH Gaming KB Keyboard         | =100013= | a keyboard — never opened                     |
| event22 | SINO WEALTH Gaming KB Mouse            | =17=     | rule 2, a mouse                               |

Two things in that table go beyond the report. The keyboard's /Consumer Control/
node counted as a mouse under the old "any =EV_REL=" rule, so on a boot where USB
enumerated it before the real mouse, the one pointer the environment chose was a
volume knob — and /nothing/ moved the cursor. And a gaming keyboard like this one
exposes a second keyboard node (=Keyboard=, the N-key-rollover interface): which of
the two carries the modifiers is the keyboard's business, so both must be read.
Which node the guest really picked on the laptop was not observed (it cannot be
from here); the table is what the code /would/ do with this list.

** The fix

Every keyboard and every pointer is open at the same time, each an =input-dev=
in =*input-devices*= ([[file:../initramfs/fb-browser.lisp::defun rescan-input-devices][=rescan-input-devices=]]):

- *Classification by capability, per device* ([[file:../initramfs/fb-browser.lisp::defun input-device-kind][=input-device-kind=]]): =:mouse=,
  =:pad=, =:tablet= or =:keyboard= — with the pointer rule asking for an X axis
  (§4), which keeps Consumer Control out. A device that can do none of these (the
  power button, the lid switch, the PC speaker) is listed but not opened.
- *One poll over all of them.* [[file:../initramfs/fb-browser.lisp::defun poll-input-once][=poll-input-once=]] lays out one =pollfd= per
  device, after the tty's and the hotplug watch's (§5); it marks each device that
  has records, and [[file:../initramfs/fb-browser.lisp::defun read-pointers][=read-pointers=]] / [[file:../initramfs/fb-browser.lisp::defun read-keyboards][=read-keyboards=]] drain exactly those.
  Every loop in the browser — the main one, the debugger, the menus, the Spotter —
  still calls =(fbb-wait 0 *fb-mouse* *fb-kbd*)= and =(read-mouse *fb-mouse* w h)=:
  =*fb-mouse*= is now =:pointers= rather than an fd, and =read-mouse= given a
  non-fd reads every ready pointer. So none of those loops changed.
- *Per-device state without rewriting the decoder.* =read-mouse= and =pad-motion=
  keep their state in special variables — the pad's remembered finger, the tap in
  progress, the held button. Right for one device, wrong for two: a touchpad's last
  finger position must not be differenced against a mouse's packet.
  [[file:../initramfs/fb-browser.lisp::defmacro with-device-state][=with-device-state=]] rebinds those variables with =progv= to the device's
  own saved values for the length of one drain, and saves them back. The decoder
  does not know there is more than one device — which is also why replaying a
  file of records through it still works unchanged.

** What is shared, and what is not

One *cursor*: every pointer moves the same arrow, as under X. Held *buttons and
modifiers* are each device's own, and what the browser reads is their OR
([[file:../initramfs/fb-browser.lisp::defun sync-input-globals][=sync-input-globals=]]). So Ctrl held on the external keyboard makes a click on the
touchpad a Ctrl-click (jump to definition), and a press held on the pad while the
mouse moves is a drag.

The OR is not really a choice. The console's keyboard handler keeps a single
=shift_state= for all keyboards ([[file:../linux/drivers/tty/vt/keyboard.c::static int shift_state = 0;][=drivers/tty/vt/keyboard.c=]]), so Ctrl on one
keyboard and =a= on another already reach the tty as =C-a=; any other rule for
the evdev side would disagree with the text we receive. What per-device state
buys is *release*: a device that goes away takes its held keys with it, so
unplugging a keyboard with Ctrl down cannot leave Ctrl stuck.

** Hotplug: arriving, and leaving

*Arriving.* =CONFIG_INOTIFY_USER= (tag #26) lets us watch =/dev/input=;
devtmpfs creates a node through =vfs_mknod=, which notifies like any other create.
The watch fd sits in the poll set, and any event on it means "rescan" —
=/proc/bus/input/devices= is the source of truth, and reading it is cheap. Three
events matter:

| inotify     | means                                   |
|-------------+-----------------------------------------|
| =IN_CREATE= | devtmpfs made a node — a device arrived |
| =IN_ATTRIB= | its owner changed — see below           |
| =IN_DELETE= | a node went                             |

=IN_ATTRIB= is there because of who we are. With the laptop's disk found, PID 1
runs as the *user* ([[file:storage.org][storage.org]]), and devtmpfs creates every input node as
=root:root 0600= — the input class asks for no mode
([[file:../linux/drivers/input/input.c::static char *input_devnode][=input_devnode=]]). So at =IN_CREATE= the open fails with =EACCES=.
=lol-rootd= already handled this before any of the above existed: once a second
it chowns any =/dev/input/event*= not yet the user's ([[file:../initramfs/preinit.c::static void give_devices][=give_devices=]]), and only
those, so it causes one =IN_ATTRIB= per new node rather than one a second. That
event wakes us, the rescan retries, the open succeeds. *No change to preinit or
=lol-rootd= was needed.* A rescan is also re-run 400ms after any hotplug event, in
case the node, its =/proc= line and its owner did not all land at once; and
without inotify (an older kernel) the environment rescans every two seconds.

*Leaving.* An unplugged device does not just go quiet. =evdev_poll= answers
=EPOLLHUP | EPOLLERR= for it ([[file:../linux/drivers/input/evdev.c::static __poll_t evdev_poll][=drivers/input/evdev.c=]]), on /every/ call, at
once, and =read= says =ENODEV=. Ignore that and the loop spins at 100% CPU on a
corpse. So =POLLHUP= / =POLLERR= / =POLLNVAL= closes the fd and forgets the device
right there, before anything tries to read it.

*eventN numbers are reused.* Unplug a mouse and plug a keyboard, and the keyboard
may well be =event6= again. A device is therefore identified by its node /and/ its
=Sysfs== path, and a rescan closes anything the kernel no longer lists before it
opens anything new. (=check-input.lisp= hits exactly this: its hotplugged keyboard
and, after it, its hotplugged mouse both arrive as =event6=.)

*Housekeeping never returns from* =fbb-wait=. A hotplug wake is nothing the caller
asked about, and returning "nothing ready" would read to the main loop as "a
deadline fired"; so =fbb-wait= handles it and polls again for whatever is left of
the caller's timeout.

** Pointer speed

Two knobs, both ordinary special variables you can set in the Workspace:
=*pad-speed*= (screens per full sweep of the touchpad, =3/2=, §4½) and
=*mouse-speed*= (pixels per mouse count, =1= — what the console and X's flat profile
do; a 1000-dpi mouse crosses a 1920px screen in about 5cm). Both carry the
fraction, so any rational works. There is no acceleration curve.

** Seeing what the environment sees

=SuperL-Space=, type =input devices=: one row per open device (node, kind, name,
records read, clicks, what it is holding right now, where it hangs), then any it
wanted and could not open (with the errno — =EACCES= is "not yours yet"), then
every device it saw and did not want, and the recent arrivals and departures. Enter
on a device opens its =input-dev= in the inspector. At a REPL:
=(show-input-view)= (not =show-input-devices=, which is the supervisor's
boot-time list of what the kernel sees). It is the subject =subj-input-devices=, at the end of
[[file:../initramfs/fb-browser.lisp::defstruct (subj-input-devices][=fb-browser.lisp=]].

** How it was verified

[[file:../check-input.lisp][=check-input.lisp=]] boots with a PS/2 mouse, a USB mouse, a USB tablet, the PS/2
keyboard and a USB keyboard, as uid 1000 (=test-disk.img=), and drives each device
/on its own/ — =mouse_set= picks which mouse QEMU feeds; the USB keyboard is bound
to the VGA console (=display=vga0=) so key events sent with ="device":"vga0"= reach
it and the rest reach the PS/2 one. It asserts: all five open at once; each pointer
moves the cursor and its own record count grows; each one's click is seen; the
tablet lands where aimed; Ctrl through each keyboard's own node, held across the
two and released; Super on the USB keyboard; a synthetic touchpad replayed through
=with-device-state= moves by the difference (58px, as computed) with its finger
remembered per device; a hotplugged USB keyboard is opened and forgotten; a
hotplugged USB mouse is opened, moves, clicks, and on =device_del= is closed, the
environment survives, the PS/2 mouse still works, and the loop woke 5 times in 4
idle seconds afterwards (the clock and the pointer's hide; a spin would be tens of
thousands). 38 assertions, all pass; [[file:../check-pointer.lisp][=check-pointer=]], [[file:../check-scroll.lisp][=check-scroll=]] and
[[file:../check-clipboard.lisp][=check-clipboard=]] still pass.

** Ruled out (so nobody searches again)

- *A missing driver.* =USB_HID=, =HID_GENERIC=, xHCI and =MOUSE_PS2_SYNAPTICS= are
  all built (tag #26); every device is in =/proc/bus/input/devices=. Each pointer
  worked whenever it happened to be the one chosen.
- *Permissions.* Boot-time and hotplugged nodes are both handed to the user
  (=give_devices=, at boot and from =lol-rootd=); the hotplugged mouse in
  =check-input= opened as uid 1000.
- *inotify on devtmpfs.* It does fire for nodes the kernel creates; the hotplug was
  seen within about half a second.
- *virtio-input* (=virtio-mouse-pci= etc.) would be a third bus to test on, but
  =CONFIG_VIRTIO_INPUT= is off and the laptop has none; USB and PS/2 are its buses.
- *QEMU routing, a trap for the next test.* With no =device= argument QEMU sends
  keys to whichever keyboard it last activated, which after boot was the USB one —
  the PS/2 keyboard then sees nothing. A test that means "the PS/2 keyboard" must
  bind the other one to a console, as =check-input= does.

** Limits, honestly

- A device that is both a pointer and a keyboard is read as a pointer: its
  modifiers count, its Menu key does not.
- A key already held when a keyboard is plugged in is not seen until it is pressed
  again (=EVIOCGKEY= at open would fix it; not worth it yet).
- If the /last/ pointer is unplugged, its arrow stays on screen until the next
  redraw.
- Two presses from two devices in the same poll wake count as one click.

** Checklist on the real laptop

Boot the image with the external mouse and keyboard attached, then:

1. =SuperL-Space=, =input devices=, Enter. Expect *open*: the built-in keyboard,
   the USB keyboard (perhaps two nodes), the touchpad (=pad= — or =mouse= if the
   kernel gave it a relative node), the USB mouse. Nothing under /could not open/.
   Note what is under /seen, not read/ — that is the list to send if anything is
   missing.
2. Move the touchpad, then the mouse, then the touchpad again; Refresh the view
   (its only command) — both counts grew, one arrow followed both.
3. Click with each (the touchpad: a firm tap, or a press); hold Ctrl on the
   *external* keyboard and click a symbol in the Workspace with the touchpad —
   it should jump to the definition.
4. =SuperL-m= typed on the external keyboard opens the module index (Super read
   from its own node).
5. Unplug the mouse, keep using the touchpad; plug it back in — it works within a
   second and appears under /recent changes/. Same with the keyboard.
6. If the mouse feels slow or fast, set =*mouse-speed*= in the Workspace (=3/2=,
   =2/3=); the pad has =*pad-speed*=.

* 5. Waiting on many things at once: =poll(2)=

Several input sources — the tty, every device of §4¾, the hotplug watch — all of
which may be idle. Busy-polling would spin PID 1 at 100% CPU; blocking on any one
would ignore the others. =poll(2)= is the answer, and [[file:../initramfs/fb-browser.lisp::defun poll-input-once][=poll-input-once=]] (under
[[file:../initramfs/fb-browser.lisp::defun fbb-wait][=fbb-wait=]]) builds its argument array by hand:

#+begin_src c
  struct pollfd { int fd; short events; short revents; };   /* 8 bytes */
#+end_src

N of those is an =8N=-byte array: =fd= at offset =n*8=, =events= at =n*8+4=,
=revents= at =n*8+6=. Slot 0 is the tty, slot 1 the =/dev/input= watch, then one
per open device. We fill it in and pass timeout =-1= (wait forever) unless
something has a deadline. The loop therefore *sleeps* until something actually
happens, and the browser costs nothing when you are not touching it.

=revents= says more than "readable". Bit 0 (=POLLIN=) is records waiting; =POLLHUP=
(=0x10=) and =POLLERR= (=0x8=) are an unplugged device, which must be closed at once
or poll reports it again forever (§4¾).

Hand-laying-out a C struct is the price of there being no =poll= in =sb-posix= —
checked, and there is none, nor =select= nor =epoll= ([[file:processes.org][processes.org]] §6). So this
array stays ours, and it is worth writing the one field that is easy to get wrong
exactly once, which is what =%put-pollfd= now does for both callers.

*A bug this hid until 2026-09-20.* The =fd= field is a full 32-bit =int=, and we
were writing only its low byte. That is correct for as long as every descriptor is
a single digit — which, with a console and two evdev nodes, it always had been.
Force a descriptor above 255 and it silently polls a *different* fd: with a pipe's
read end at fd 300 and data waiting, the old code polled fd 44 (=300 & 0xff=) and
got =POLLNVAL= back, reporting "nothing to read" while the real descriptor had
data. It now writes all four bytes little-endian. This matters ahead of any fourth
slot holding a *socket* rather than a device node — see [[file:processes.org][processes.org]] §2.

A small robustness trick worth naming: an *absent* fd (no inotify, say) still gets
its slot, holding =fd -1= — poll ignores a negative fd and reports nothing for it —
so the revents offsets stay put and the "no watch" case needs no separate code
path. (With three fixed slots this used to be a zeroed slot, =fd 0= with
=events = 0=; -1 is the documented way to say "skip this one".)

* 6. The wheel, end to end

There is no scroll *axis* and no scroll *position* — the wheel is a relative
motion device that moves in detents. One notch is one record:

#+begin_example
  type=2 (EV_REL)  code=8 (REL_WHEEL)  value=+1   ; rolled away from you
  type=2 (EV_REL)  code=8 (REL_WHEEL)  value=-1   ; rolled toward you
#+end_example

[[file:../initramfs/fb-browser.lisp::defun read-mouse][=read-mouse=]] sums these across one drain and returns them beside the click, so a
fast flick becomes a single =wheel= of =+3= rather than three separate frames.
Then the main loop turns notches into lines:

#+begin_src lisp
  (unless (zerop wheel)
    (browser-scroll (* (- wheel) +wheel-lines+)))     ; +wheel-lines+ = 3
#+end_src

*The negation is a real sign-convention flip, not a fudge.* evdev's =+1= means
"the wheel rolled away from the user". [[file:../poc/shell.lisp::defun browser-scroll][=browser-scroll=]]'s argument means "move
this many lines further *down* the document". Rolling away conventionally moves
you *up* the document, so the two disagree and one =-= reconciles them.

=browser-scroll= then splits by pane kind:

- a *text* pane scrolls its viewport via [[file:../poc/textview.lisp::defun tv-wheel][=tv-wheel=]], leaving the caret where it
  is — scrolling is looking, not moving;
- a *list* pane moves the *selection* instead, because =draw-list-body= anchors
  the visible window to the selection and has no viewport of its own.

That second case is a known wart: scrolling a list drags the selection with it,
which is not what a scroll should do. Fixing it properly means giving lists a
viewport independent of the selection — i.e. a real scrollbar widget, which is
what phase 3's remaining toolkit work is for ([[file:code-browser.org][code-browser.org]] §8).

** The wheel a laptop does not have

A touchpad has no wheel. What it has is a second finger, and it says so:
=BTN_TOOL_DOUBLETAP=. While that is down, [[file:../initramfs/fb-browser.lisp::defun pad-motion][=pad-motion=]] stops moving the cursor
and turns vertical motion into notches instead — one per 1/24th of the pad's
height, about 2mm of travel.

The sign falls out of the convention above rather than needing a second one.
Dragging two fingers *toward* you is the same gesture as rolling a wheel toward
you, so it produces the same negative notch, and the same =(- wheel)= in the
caller turns it into "further down the document". Nothing downstream of
=read-mouse= can tell that there was no wheel.

* 7. The same gesture on the host: X11 buttons 4 and 5

On the dev host there is no evdev in play at all. The X server owns the devices
and hands us protocol events instead ([[file:x11.org][x11.org]]), and X has its own answer to the
wheel, from long before scroll axes existed: *the wheel is a pair of buttons*.

| gesture    | guest (evdev)                   | host (X11)                                             |
|------------+---------------------------------+--------------------------------------------------------|
| move       | =EV_REL= =REL_X/Y= deltas       | =MotionNotify= x,y                                     |
| left click | =EV_KEY= =BTN_LEFT= value 1     | =ButtonPress= detail =1=                               |
| drag       | =REL_X/Y= while =BTN_LEFT= is 1 | =MotionNotify= with =Button1Mask= (=#x100=) in =state= |
| wheel up   | =EV_REL= =REL_WHEEL= value =+1= | =ButtonPress= detail =4=                               |
| wheel down | =EV_REL= =REL_WHEEL= value =-1= | =ButtonPress= detail =5=                               |
| Ctrl held  | =EV_KEY= =KEY_LEFTCTRL= value 1 | the event's =state= bitmask                            |

[[file:../poc/x11.lisp][=x11.lisp=]] already decodes all of these — =:button-press= carries the button in
=event-detail=. The Ctrl row is the neat part: X *gives* you the modifier state on
every event, so the host needs no equivalent of the second keyboard fd. That
asymmetry is exactly why the guest has one.

[[file:../poc/run-browser.lisp][=run-browser.lisp=]] dispatches on the button: 1 clicks, 4 and 5 call =browser-scroll=
(this paragraph used to record them as silently dropped — closed since), and a
=:motion= whose state carries =Button1Mask= calls =browser-drag=.

* 8. What makes it work (kernel side)

| Option                            | State | Why                                                        |
|-----------------------------------+-------+------------------------------------------------------------|
| =CONFIG_INPUT_EVDEV=              | y     | creates =/dev/input/event*= — the whole mechanism above    |
| =CONFIG_INPUT_MOUSEDEV=           | *n*   | deliberately off; why there is no =mouseN= to look for     |
| =CONFIG_MOUSE_PS2=                | y     | the PS/2 mouse + laptop touchpad driver                    |
| =CONFIG_SERIO= + =KEYBOARD_ATKBD= | y     | the PS/2 keyboard QEMU gives us                            |
| =CONFIG_USB_HID= / =CONFIG_HID=   | y     | a USB mouse or keyboard                                    |
| =CONFIG_I2C_HID= + =_ACPI=        | y     | internal laptop touchpads/keyboards on the I2C-HID bus     |
| =CONFIG_MOUSE_PS2_SYNAPTICS=      | y     | the laptop touchpad the way we actually get it — see below |
| =CONFIG_I2C_DESIGNWARE_PLATFORM=  | *n*   | not built, which is *why* we get it that way               |
| =CONFIG_RMI4_CORE=                | *n*   | not built either, so there is no SMBus hand-off            |

*Why the laptop's touchpad arrives over PS/2.* =CONFIG_I2C_HID=y= is there and
looks sufficient, but I2C-HID needs an I2C *bus*, and on an Intel laptop that
controller wants =CONFIG_I2C_DESIGNWARE_PLATFORM=. Only the Designware *core* is
built (=i2c-designware-common.o= and =-master.o= exist under
=linux/drivers/i2c/busses/=; =i2c-designware-platdrv.o= does not), so the bus
never appears and neither does the I2C touchpad. =psmouse= picks the pad up over
the legacy i8042 port instead — and with =CONFIG_RMI4_CORE= off it cannot hand
over to SMBus either, so it stays in the *absolute* Synaptics PS/2 protocol. That
is the device §4½ is about.

Enabling the platform driver would additionally give the pad a relative node and
is a fair thing to do later, but it would not make §4½ optional: the PS/2 absolute
fallback is what every machine without that driver gets, and it has to be right.

Full table and the reasoning: [[file:kernel-config.org][kernel-config.org]]. Device nodes appear without us
listing them in the cpio because =/dev= is devtmpfs, mounted by [[file:../initramfs/preinit.c][=preinit.c=]]
([[file:sbcl-init.org][sbcl-init.org]]).

The cursor deserves the last word: there isn't one. No hardware sprite, no
overlay plane — =*cursor-x*= and =*cursor-y*= are two integers, and we paint a
little arrow from a string-art bitmap ourselves — into a patch composited over the
frame on its way to the screen, never into the frame itself ([[file:framebuffer.org][framebuffer.org]] §9.5). The
mouse pointer on this machine is drawn by the same =fill-rect= that draws the
tab strip.
