#+TITLE: Input devices — evdev, the mouse, the wheel, and the modifiers the tty hides
#+STARTUP: showall

How does the machine know the mouse moved, or the wheel turned? There's no X server,
no libinput, no udev and no mouse daemon. The answer is one character device, one
24-byte struct, and =poll(2)=.

Related: [[file:line-editing.org][line-editing.org]] (the other half of input — raw-mode termios and the
tty) · [[file:framebuffer.org][framebuffer.org]] (the output half, =/dev/fb0=) · [[file:kernel-config.org][kernel-config.org]] (the
options that create these device nodes) · [[file:code-browser.org::#guest-specifics][code-browser.org, Guest specifics (framebuffer)]] (what the browser
does with them).

* The one-sentence essence

The kernel turns every input device into a file at =/dev/input/eventN= that emits
*fixed 24-byte records* saying "this type of thing, this code, this value" — and the
whole mouse driver is a loop that reads 24 bytes at a time and adds the numbers up.

* 1. Why the tty is not enough
:PROPERTIES:
:CUSTOM_ID: tty-enough
:END:

The keyboard's text comes through the *terminal*: fd 0 in raw mode, one byte per
keystroke ([[file:line-editing.org][line-editing.org]]). That's right for text and useless for two things:

1. *The mouse.* The tty carries characters; a pointer has none.
2. *A bare modifier.* Hold Ctrl alone and the tty delivers *nothing* — there's no byte
   for "Ctrl is down". A modifier only shows up already *combined* with a key: =C-g=
   arrives as byte 7, and the Ctrl-ness is gone.

The browser needs both — a pointer, and =Ctrl-click= / =SuperL-click= as distinct
gestures ([[file:code-browser.org::#environment-trails-spotter-tiled][code-browser.org, The environment — trails, the Spotter, and the tiled shell]]). So it opens more doors onto the hardware,
underneath the terminal: the raw input devices.

** A bare modifier needs the keyboard's own evdev

Three kinds of fd, three jobs, deliberately not interchangeable:

| fd                            | carries                                      | why not one of the others                                                            |
|-------------------------------+----------------------------------------------+--------------------------------------------------------------------------------------|
| =0= (the console tty)         | typed *text*, escape sequences               | the only one that has been through the keymap — evdev gives key /codes/, not letters |
| every pointer's =eventN=      | motion, buttons, the wheel                   | the tty has no notion of a pointer                                                   |
| every keyboard's own =eventN= | *only* Ctrl / Shift / Super / Alt held state | the tty cannot report a bare modifier                                                |

"Every": a laptop with an external mouse and keyboard has two of each, all open at once
([[#every-device-once-ones][Every device at once, and the ones plugged in later]]).

The keyboard is read *twice*, on purpose. Text comes from the tty because that's where
the keymap lives (evdev would say "keycode 30", not =a=). Modifier *state* comes from
evdev because that's the only place it exists. The main loop =logior=s the evdev
modifier bits into the state word before dispatching the tty's key
([[file:../initramfs/fb-browser.lisp][=fb-browser.lisp=]]'s =run-browser-fb=).

** Keys the console sends no byte for

Some chords never reach the tty, so =note-modifier-key= reports them from the
keyboard's evdev instead:

- *Menu key* (=KEY_COMPOSE=, 127). No byte at all; it opens the context menu ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]).
- *Ctrl-= and Ctrl-0* (the text-size chord =C-x C-= / C-x C-0=, [[file:fonts.org::#size-change-reaches-every][fonts.org, How a size change reaches every pixel of layout]]). The
  default keymap (=drivers/tty/vt/defkeymap.map=) gives keycodes 11 and 13 no =control=
  column. Reported as =#\== / =#\+= / =#\0= and handed to =browser-key= with the Ctrl
  bit. (=Ctrl--= needs no help: =Control_underscore=, byte 31.)
- *Ctrl-, and Ctrl-.* (so also =C-<= / =C->=, start / end of buffer). Keycode 51 has no
  =control= column, and the default keymap says =control keycode 52 = Compose=, so
  Ctrl-. starts a compose sequence that eats the next keys. Both are reported as =#\<= /
  =#\>=, and [[file:../initramfs/fb-browser.lisp::defun unbind-console-ctrl-dot][=unbind-console-ctrl-dot=]] takes Compose off that key once at startup:
  one =KDSKBENT= ioctl (=0x4B47=, =include/uapi/linux/kd.h=) — table 4 (Ctrl), index 52,
  value =K_HOLE= (=K(KT_SPEC,0)= = =0x0200=, a key that sends nothing).
- *Ctrl-;* (comment line or region, [[file:code-browser.org][code-browser.org]] Phase 3a). Keycode 39 has no
  =control= column; reported as =#\;=.
- *Shift-PageUp / Shift-PageDown.* The default keymap binds them to the console's own
  scrollback (=shift_map[104]= = Scroll_Backward) and sends nothing. The terminal pane
  scrolls its history with them ([[file:terminal.org::#keys-become-bytes][terminal.org, Keys become bytes]]); elsewhere they reach =browser-key=.

Before binding any new Ctrl-digit or Ctrl-punctuation chord, check =defkeymap.map= for a
=control= line.

** Alt with the arrows, Return and Tab: what the console sends

Org's keys ([[file:org.org::#keys-console][org.org, The keys on the console]]) need Meta on keys the console treats specially.
[[file:../check-org.lisp][check-org.lisp]] presses each over QMP in the guest.

- *Alt-Up / Alt-Down arrive with their Alt.* In kernel 7.2, =k_cur= (the cursor-key
  handler, [[file:../linux/drivers/tty/vt/keyboard.c::static void k_cur][drivers/tty/vt/keyboard.c]]) encodes held modifiers as xterm does: Alt-Up
  is =ESC [ 1 ; 3 A=, Shift-Alt-Up =ESC [ 1 ; 4 A=. =fb-read-csi= decodes the parameter
  into the state bits.
- *Alt-Left / Alt-Right are rebound from VT switching.* By default =alt_map[105]= /
  =[106]= are =K_DECRCONSOLE= / =K_INCRCONSOLE= ([[file:web-browser.org::#user-sees][web-browser.org, What the user sees]]).
  [[file:../initramfs/fb-browser.lisp::defun unbind-console-alt-arrows][=unbind-console-alt-arrows=]] binds them, in every keymap table with the Alt bit, to
  plain =K_LEFT= / =K_RIGHT= (what alt_map already holds for Up and Down), so they
  arrive as =ESC [ 1 ; 3 D= / =C=. =Ctrl-Alt-F1…= still switch VTs. In a text view they
  move by word, as =M-b= / =M-f= (=tv-key=, [[file:../poc/textview.lisp][poc/textview.lisp]]); an Org pane uses them to
  promote / demote.
- *Shift-Alt-arrows need nothing.* The default keymap has no Shift+Alt table, and 7.2's
  =keyboard.c= falls back to the plain map for a cursor key when the modifier's table
  is missing; =k_cur= then adds the modifiers.
- *Alt-Return and Alt-Tab* arrive as =ESC CR= and =ESC TAB= (alt_map's Meta entries
  =0xf80d= / =0xf809=); =fb-read-key= returns =:return= / =:tab= with the Meta bit.
- *Shift-Tab* is a plain Tab byte; its Shift is the evdev's, folded in as for every key.

Ruled out:

- *Reading Alt-arrows from the evdev too* (as Shift-PageUp is). Alt-Shift-Right then
  demoted a heading *twice*: once for the evdev event, once for the tty's
  =ESC [ 1 ; 4 C=.
- *=K_HOLE= instead of =K_LEFT= for Alt-Left.* The fallback compares the entry with
  =K_HOLE=, but entries are stored as =U(val)= = =val ^ 0xf000= (=vt_kdskbent=,
  =kbd_kern.h=). A hole set by =KDSKBENT= reads =0xf200= there and never matches, so
  Alt-Left sent nothing. =KDGKBENT= hands entries back without the =0xf0= (=0x0210=, not
  the =0xf210= that =defkeymap.c_shipped= prints).

** Two layouts: pt-BR under Right Alt, Caps Lock to switch

When the host's =/etc/default/keyboard= lists =br= alongside =us= (e.g.
=XKBLAYOUT="us,br"=, =XKBOPTIONS="…,grp:switch,grp:caps_toggle,grp_led:caps"=), the
environment mirrors X ([[file:../initramfs/keyboard-layout.lisp][keyboard-layout.lisp]]): Right Alt *held* types the second
layout, Caps Lock *switches* to it and back (it's no longer a caps lock), and the Caps
light says which is on.

The text we read is translated by the *kernel's keymap*: one table per combination of
modifiers, keycode → keysym, changed one entry at a time with =KDSKBENT=
(=console-kbent=). The kernel already has what's needed:

- *Right Alt is the console's AltGr* (keycode 100, =K_ALTGR=), a modifier with its own
  tables: 2 (AltGr) and 3 (AltGr+Shift). Filled with pt-BR, Right Alt held types pt-BR
  — X's =grp:switch=.
- *Dead keys* (=KT_DEAD=: ´ ` ~ ^ ¨) and a composition table that already covers
  Portuguese: defkeymap's =accent_table= has =' a= → á, =~ a= → ã, =^ a= → â, =, c= → ç
  and the rest of Latin-1.
- *Unicode mode.* =vt.c='s =default_utf8= is true, so =ç= arrives as two UTF-8 bytes,
  which =fb-read-key= decodes.

*The layout's keys* come from the host's XKB file (=/usr/share/X11/xkb/symbols/br=, its
default "abnt2"): "latin" plus ten keys, which on a US keyboard are =`= → ='= / ="=,
=6= → 6 / dead ¨, =[= → dead ´ / dead `, =]= → =[= / ={=, =\= → =]= / =}=, =;= → =ç= /
=Ç=, ='= → dead ~ / dead ^, =/= → =;= / =:=, plus two keys only ISO/ABNT2 keyboards
have. Only levels 1 and 2: with =grp:switch= Right Alt is a group switch, so =br='s
third and fourth levels are out of reach in X too.

*Keysym values for =KDSKBENT=:* a dead key is =K(KT_DEAD, n)= (=#x400= + n); an ASCII
letter =K(KT_LETTER, c)=; a character past ASCII is Unicode, stored XORed with =#xF000=
(keyboard.c's =U()=) — so =ç= (U+00E7) is passed as =#xF0E7=.

*Caps Lock is handled in Lisp,* not by the kernel's =AltGr_Lock=, because no ioctl
READS a lock's state and the light and tray must tell the truth.

- *Its keymap entries become VoidSymbol;* its press is seen on the keyboard's evdev
  (=:layout-toggle=).
- *=toggle-layout=* swaps the plain tables to pt-BR and the AltGr tables to US, so Right
  Alt held while pt-BR is on gives US back, as in X.
- *Feedback.* The light is set with =KDSETLED= (caps = 4); the tray says =BR= while
  pt-BR is the plain layout. Neither changes while Right Alt is merely held.

*Tested* by [[file:../check-keyboard.lisp][check-keyboard.lisp]] (17 checks, =LOL_GUEST_HOSTROOT=1=, so the guest
reads the host's =/etc/default/keyboard=): Right Alt + =;= → ç, the three dead keys
(ã é ô), Caps Lock on (=;= → ç, ='= a → ã, =BR=, the light =4=, Right Alt giving =;=
back) and off, and =ç= reaching a program in a terminal.

* 2. What evdev is
:PROPERTIES:
:CUSTOM_ID: evdev
:END:

=CONFIG_INPUT_EVDEV=y= builds [[file:../linux/drivers/input/evdev.c][=drivers/input/evdev.c=]], a *generic* handler that
attaches to every input device and exposes each as a character device
=/dev/input/eventN=.

It doesn't know what a mouse is. It publishes the input subsystem's event stream
verbatim, and userland decides that a device emitting relative X and Y is a pointer.
Keyboard, mouse, touchpad and the ACPI power button all arrive through the same
interface, told apart only by *which kinds of event they can emit*.

** The record

Reading the device returns a whole number of =struct input_event= records
([[file:../linux/include/uapi/linux/input.h::struct input_event][=include/uapi/linux/input.h=]]). On 64-bit x86 one record is *24 bytes*:

| offset | size | field     | meaning                                            |
|--------+------+-----------+----------------------------------------------------|
|      0 |    8 | =tv_sec=  | timestamp, seconds — read by the tap gesture ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]) |
|      8 |    8 | =tv_usec= | timestamp, microseconds — likewise                 |
|     16 |    2 | =type=    | *what kind* of event (a key? motion?)              |
|     18 |    2 | =code=    | *which* one (which key, which axis)                |
|     20 |    4 | =value=   | signed 32-bit: how much / pressed?                 |

- *The timeval is the usual offset trap.* It's 16 bytes on 64-bit, which makes the
  record 24; on a 32-bit machine it's 8 and the record is 16.
- *No framing.* No length prefix, no escaping: records abut. [[file:../linux/drivers/input/evdev.c][=evdev.c=]] returns
  =-EINVAL= for a buffer smaller than one event and otherwise fills as many whole
  records as fit. "Read 24 bytes, decode, repeat" is the contract.

** Reading it in Lisp

The same =sb-alien= FFI style as [[file:../initramfs/net.lisp][net.lisp]], on the shipped =libc=. Open the node
non-blocking ([[file:../initramfs/fb-browser.lisp::defun open-evdev][=open-evdev=]]) and drain it ([[file:../initramfs/fb-browser.lisp::defun read-mouse][=read-mouse=]]):

#+begin_src lisp
  (let ((n (%fbb-read fd buf 24)))
    (when (< n 24) (return))                    ; queue empty — O_NONBLOCK
    (let* ((type (logior (deref e 16) (ash (deref e 17) 8)))            ; u16 LE
           (code (logior (deref e 18) (ash (deref e 19) 8)))            ; u16 LE
           (v    (logior (deref e 20) (ash (deref e 21) 8)
                         (ash (deref e 22) 16) (ash (deref e 23) 24)))
           (val  (if (>= v #x80000000) (- v #x100000000) v)))           ; s32
      …))
#+end_src

- *Little-endian reassembly by hand.* Bytes and shifts rather than a struct cast:
  honest about the wire format, and free.
- *Sign extension.* =value= is =__s32=. Moving left gives =-1=, which arrives as
  =#xFFFFFFFF=; the last line turns it back. Skip it and the cursor jumps four billion
  pixels right on the first leftward twitch.
- *The non-blocking read ends the drain.* With =O_NONBLOCK= an empty queue returns =-1=
  (=EAGAIN=), so =(< n 24)= means "nothing more now". Draining in a loop, not one record
  per frame, makes a fast flick smooth: several records become one cursor move and one
  redraw.

* 3. The events we actually decode

Of the ~30 event types, the browser needs four. Constants from
[[file:../linux/include/uapi/linux/input-event-codes.h::#define REL_WHEEL][=input-event-codes.h=]]:

| =type=       | =code=                                                | =value=                               | what we do                                                                        |
|--------------+-------------------------------------------------------+---------------------------------------+-----------------------------------------------------------------------------------|
| =2= =EV_REL= | =0= =REL_X=                                           | delta, signed                         | =(incf *cursor-x* val)=, clamped                                                  |
| =2= =EV_REL= | =1= =REL_Y=                                           | delta, signed                         | =(incf *cursor-y* val)=, clamped                                                  |
| =2= =EV_REL= | =8= =REL_WHEEL=                                       | notches, ±1                           | sum into =wheel= (see [[#wheel-end-end][The wheel, end to end]])                                                         |
| =3= =EV_ABS= | =0= / =1= =ABS_X/Y=                                   | absolute, in the *device's own* range | scale onto the screen, or difference it ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]])                                     |
| =1= =EV_KEY= | =#x110= =BTN_LEFT=                                    | =1= press / =0= release               | on press: a =:down= event, to the morph under the pointer (a pane's =pane-click=) |
| =1= =EV_KEY= | =#x14a= =BTN_TOUCH=, =#x145/#x14d/#x14e= =BTN_TOOL_*= | =1= down / =0= up                     | a contact changed: forget the last pad position, and open or close a *tap* ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]])  |
| =1= =EV_KEY= | =29=/=97= Ctrl, =42=/=54= Shift, =125=/=126= Meta     | =1= down =2= repeat =0= up            | set =*ctrl-down*= / =*shift-down*= / =*super-down*=                               |
| =1= =EV_KEY= | =115= / =114= =KEY_VOLUMEUP= / =DOWN=, =113= =KEY_MUTE=, =248= =KEY_MICMUTE= | =1= press, =2= repeat (volume only) | =mixer.lisp='s =audio-key= (tag #29): no tty byte exists for these keys |
| =0= =EV_SYN= | =0= =SYN_REPORT=                                      | —                                     | end of packet: apply the gathered position                                        |

- *Relative and absolute both matter.* QEMU's default PS/2 mouse is relative;
  =-device usb-tablet= is absolute and maps onto the screen (so a scripted click lands
  predictably — the QMP harness relies on it, [[file:code-browser.org::#phases][code-browser.org, Phases (each independently demoable — this repo likes screenshots)]]); a laptop
  *touchpad* is absolute but is not a screen ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]).
- *=EV_SYN= ends a packet.* A packet is several records — =ABS_X=, =ABS_Y=, perhaps
  =BTN_TOUCH= — and =SYN_REPORT= says "that was one report". Acting record by record
  moves an absolute pointer in an L instead of a line, so we gather and act at the
  =SYN=.
- *=EV_KEY= covers buttons and keys.* A mouse button is a key whose code is =0x110=.

* 4. Finding the device without udev
:PROPERTIES:
:CUSTOM_ID: finding-device-without-udev
:END:

[[file:../initramfs/fb-browser.lisp::defun scan-input-devices][=scan-input-devices=]] exists because of two non-obvious facts:

1. *=eventN= isn't stable.* The number depends on probe order; hardcoding
   =/dev/input/event2= works until it doesn't.
2. *There's no =/dev/input/mouse0=.* That node comes from =mousedev=, and
   =CONFIG_INPUT_MOUSEDEV= is off. So scanning =/proc/bus/input/devices= for a
   =Handlers== line containing =mouse= finds nothing; a PS/2 mouse shows only
   =Handlers=event2=.

So devices are classified by *capability*. [[file:../linux/drivers/input/input.c][=drivers/input/input.c=]]'s
=input_devices_seq_show= prints one block per device, blank-line separated:

#+begin_example
  I: Bus=0011 Vendor=0002 Product=0006 Version=0000
  N: Name="ImExPS/2 Generic Explorer Mouse"
  P: Phys=isa0060/serio1/input0
  S: Sysfs=/devices/platform/i8042/serio1/input/input4
  U: Uniq=
  H: Handlers=event2
  B: PROP=0
  B: EV=7
  B: KEY=70000 0 0 0 0
  B: REL=103
#+end_example

=B: EV== is a *bitmask of the event types the device can emit*, in hex, one bit per
=EV_*= constant. =EV=7= is bits 0, 1, 2 = =EV_SYN= + =EV_KEY= + =EV_REL=: buttons and
relative motion — a pointer.

The rules, one line each ([[file:../initramfs/fb-browser.lisp::defun input-device-kind][=input-device-kind=]]):

- *Pointer.* EV_REL (bit 2) with =REL_X=, or EV_ABS (bit 3) with =ABS_X=. The axis
  matters, not just the type: a USB keyboard's /Consumer Control/ node says =EV=1f= —
  =EV_REL= for =REL_HWHEEL= (a horizontal-scroll key), =EV_ABS= for volume — and has no
  X axis. =REL_X= / =ABS_X= are bit 0 of the =B: REL== / =B: ABS== bitmaps, whose low
  word is the *last* token on the line.
- *Keyboard.* EV_KEY (bit 1) *and* EV_REP (bit =0x14= = 20, autorepeat). The EV_REP half
  matters: the ACPI *power button* emits =KEY_POWER= and gets a =kbd= handler, but can't
  autorepeat. Without that bit we'd open the power button and wonder why Ctrl never
  seemed held.

Within the pointers, the kind decides how positions are read: a =:mouse= adds deltas, a
=:tablet= maps positions onto the screen, a =:pad= differences them ([[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]). Every
pointer is opened, each read as its own kind ([[#every-device-once-ones][Every device at once, and the ones plugged in later]]).

** The other bitmask on the line above: =B: PROP=

=EV= says *what kinds of event* a device emits, not what they mean — and for an
absolute device, meaning is the whole question. =B: PROP== answers it:

| bit | property               | what the positions mean                           |
|-----+------------------------+---------------------------------------------------|
|   0 | =INPUT_PROP_POINTER=   | a surface *under* your hand — a touchpad          |
|   1 | =INPUT_PROP_DIRECT=    | the surface *is* the screen — touchscreen, tablet |
|   2 | =INPUT_PROP_BUTTONPAD= | the whole pad is the button (a clickpad)          |

=usb-tablet= prints =PROP=0=. A PS/2 Synaptics pad prints =PROP=9=, an I2C one =PROP=5=
— both have bit 0. Same =EV=, opposite meaning.

** Parsing the bitmaps

=input_seq_print_bitmap= prints a bitmap as space-separated 64-bit words, most
significant first (see =B: KEY= above). The parser takes the *last* word. For =EV= and
=PROP= that's the whole mask (=EV_MAX= is =0x1f=, one word). For =REL= and =ABS= it's
the low word, where the X axis lives: =ABS=2e0800000000003= (an I2C touchpad) is two
words, and =ABS_X= is in the second. Taking the first word would silently read the
wrong end.

* 4½. The touchpad: absolute, but not a position
:PROPERTIES:
:CUSTOM_ID: touchpad-absolute-but-position
:END:

A laptop pad is described the way a drawing tablet is: =EV_ABS=, =ABS_X=, =ABS_Y=, one
position per packet. Read it like a =usb-tablet= and the cursor sits in the *top-left
corner*, moves inside a box a couple of hundred pixels wide, barely moves vertically,
and jumps whenever you lift a finger. There are two causes.

** Cause one: 0..32767 is not a range, it is one device's range

=usb-tablet= reports 0..32767 on both axes — *its* choice, not the protocol's. A PS/2
Synaptics pad reports roughly 1472..5472 across by 1408..4448 down. Scaled as though
they ran to 32767, a full sweep reaches:

: 5472 * 1920 / 32768 =  320 px   of 1920 across
: 4448 * 1080 / 32768 =  146 px   of 1080 down

So *ask*. =EVIOCGABS(axis)= fills a =struct input_absinfo= — six =__s32=: value,
minimum, maximum, fuzz, flat, resolution — and the middle two are the range. One ioctl
per axis, at open time ([[file:../initramfs/fb-browser.lisp::defun evdev-abs-range][=evdev-abs-range=]]). The request number is
=_IOR('E', 0x40+axis, 24)= = =#x80184540 + axis=.

** Cause two: a pad is not a small screen

Fixing the range alone maps the pad onto the display one-to-one, which *looks* like it
works. But then the cursor is wherever your finger is: lift it, put it down 3 cm left,
and the cursor teleports. A far corner can't be reached with a short motion, and the
cursor can't be nudged by two pixels.

A tablet wants that; a pad never does. =B: PROP= tells them apart ([[#finding-device-without-udev][Finding the device without udev]]): bit 0 or bit 2
— POINTER or BUTTONPAD — means *difference the positions, don't map them*.

** Differencing without the jumps

[[file:../initramfs/fb-browser.lisp::defun pad-motion][=pad-motion=]] remembers the last position and moves the cursor by the change, scaled
so one full sweep of the pad crosses =*pad-speed*= screens (=3/2= by default). Each axis
is scaled by its own range, which also fixes the aspect: pads and screens have roughly
the same proportions, so motion stays isotropic without a second constant.

1. *Per packet, not per record.* =ABS_X= and =ABS_Y= are two records; applying each as it
   lands draws an L. Gather them and act on =SYN_REPORT=.
2. *Forget the last position when the contact changes.* =BTN_TOUCH= and
   =BTN_TOOL_{FINGER,DOUBLETAP,TRIPLETAP}= change only when a finger lands, lifts or is
   joined by another — all of which move the reported point. Each clears the
   remembered position, so a new contact's first packet yields *no* delta instead of a
   jump. A quarter-of-the-pad sanity limit covers hardware that never reports
   =BTN_TOUCH=.
3. *Carry the fraction.* At about 0.7 px per pad unit, a slow drag is a run of deltas
   that each round to zero. The remainder is kept as an exact rational and paid out on
   later packets; truncating makes slow motion impossible.

** The click that sends no button

A clickpad's physical press is a =BTN_LEFT= like any mouse button's. A *tap* sends no
button: the finger lands and lifts, and the only trace is =BTN_TOUCH= going =1= then
=0=. Elsewhere libinput decides that was a click; there's no libinput here.

*Tap-to-click is off by default:* a click happens only when you press. =*tap-to-click*=
is =NIL=, so only a physical press clicks. Put =(:tap-to-click t)= in =~/.lol/settings=
(read when the browser starts), or =(setf *tap-to-click* t)= in the Workspace.

When it's on, =read-mouse= decides. A contact is a click when all four hold:

1. *Brief, but not fleeting.* Under =*tap-max-us*= (180 ms, libinput's figure — longer
   is a resting finger) and at least =*tap-min-us*= (30 ms). A Synaptics pad sends a
   packet every 12.5 ms, so a passing brush is over in one or two.
2. *It didn't travel.* No further from where it landed than =*tap-travel*=, a fortieth
   of the pad (about 2 mm on a Synaptics pad) — forgives a lifting finger's roll, not a
   drag.
3. *One finger, nothing pressed.* A second finger means scroll (or a right-click), so
   the contact stops being a tap. A real =BTN_LEFT= disarms it too, so a press with a
   resting finger can't fire twice.
4. *It pressed like a tap.* Peak =ABS_PRESSURE= reached =*tap-min-pressure*= (60). The
   pad reports pressure on every packet (0..255, Synaptics' "Z"), and the kernel turns
   anything over 30 into =BTN_TOUCH= (the hysteresis at =if (hw.z > 30)= /
   =if (hw.z < 25)= in =linux/drivers/input/mouse/synaptics.c=). Synaptics' interfacing
   guide puts a very light finger near 30 and a normal one near 80; a graze sits
   between. A pad that reports no pressure skips this test.

Rule 1's floor and rule 4 exist because without them the lightest touch clicks — and
an accidental click looks exactly like a bug.

- *Tuning.* The last contact is kept as the rule saw it in =*last-touch*= — =(:ms 75
  :peak 80 :tap t)=. Print it after a tap that misbehaved, and set =*tap-min-pressure*=
  or =*tap-min-us*=; both are read on every contact.
- *Timestamps.* [[file:../initramfs/fb-browser.lisp::defun evdev-time-us][=evdev-time-us=]] reads the record's 16-byte timeval. The gesture only
  takes a *difference* of two, so the clock behind it (evdev's default is
  =CLOCK_REALTIME=) never has to mean anything absolute.
- *Tested without a touchpad* (QEMU emulates none). =read-mouse= takes an fd, and a
  regular file is one, so a file of synthetic Synaptics-shaped records — =BTN_TOUCH=,
  =ABS_X/Y=, =ABS_PRESSURE= every 12.5 ms — replays a contact exactly. A firm 80 ms tap
  (peak 80) clicked; a graze of the same length (peak 45), a one-packet brush, a 300 ms
  rest and a sliding contact didn't; a physical press did.

Limits:

- *No tap-and-drag.* A tap is decided when the finger /lifts/, so nothing is still held
  to drag with; the pressed drag (next section) is the way to select.
- *Two taps in one drain are one click.* =read-mouse= returns a click as a boolean, and
  a drain is one =poll(2)= wake — unreachable by hand. A double-click gesture would need
  a real press/release pair.

** Press and drag: selecting with the pointer

A press in a text view places the caret; while the button stays down, motion extends
the selection from that caret to the pointer ([[file:../poc/shell.lisp::defun browser-drag][=browser-drag=]], over =tv-drag=). On a
clickpad: press the pad down, and slide.

- *The button's state, not just its press.* =read-mouse= keeps =*button-down*= (value 1
  sets it, 0 clears it), and the loop treats pointer motion while it's set as a drag.
- *The hand keeps the press.* The press goes to the morph under the pointer — the text
  view's body morph — and the *hand* remembers what it placed the caret in (its press,
  =(:text :tv … :origin …)=, [[file:../poc/morph.lisp::defclass hand (morph)][the hand]]'s =press= slot). The world sends the drag to
  that morph (the hand's capture), so a drag extends that view even when the pointer
  wanders over another pane ([[file:morphic.org::#routing-presses-keys][morphic.org, Routing presses and keys]], [[file:morphic.org::#press-progress][The press in progress]]). Release clears it.
- *A press on a row waits for its release.* A list row acts when the button comes up.
  A press that moves 8 px first (=+pick-up-travel+=) is a *pick-up*: the hand carries
  the row's subject to drop on another morph ([[file:morphic.org::#picking-up][morphic.org, Picking up]]). A *tap* has no
  release of its own, so its press is marked =:tap= and acts at once.
- *A 3-pixel slop* (=+drag-slop+=) before the first extension. Pressing a clickpad rolls
  the fingertip a pixel or two; without the slop every press would select a character.
- *No two-finger scroll while pressed.* On a clickpad the press is often a thumb and the
  moving finger a second one — otherwise the two-finger scroll ([[#wheel-end-end][The wheel, end to end]]). So =pad-motion=
  scrolls only with the button up. Which finger =ABS_X/Y= follows while two are down is
  the pad's choice; pressing and sliding the same finger is the sure way.

*Tested* by =check-pointer.lisp=, with QEMU's left button held across real =EV_REL=
motion: the press alone selects nothing, the drag selects and follows the pointer, the
release is seen, a still click clears it.

** Three buttons on a pad with one

The right button opens a context menu, the middle one a halo or X's paste
([[file:code-browser.org][code-browser.org]], "The right button and the halo"). A mouse has them — =BTN_RIGHT=
=#x111= and =BTN_MIDDLE= =#x112=, decoded beside =BTN_LEFT=. A clickpad has one
physical button, so *which button a press means* is read off the pad when it goes down
([[file:../initramfs/fb-browser.lisp::defun pad-press-button][=pad-press-button=]]):

| on the pad                             | means  | why                                                   |
|----------------------------------------+--------+-------------------------------------------------------|
| one finger, bottom-right corner, press | right  | the software-button zone every buttonless laptop uses |
| two fingers down, press                | middle | libinput's "clickfinger" pattern                      |
| three fingers down, press              | right  | a second route to the menu that needs no aiming       |
| one finger anywhere else, press        | left   | the ordinary click (and the only one that drags)      |

- *The finger count is current.* =synaptics_process_packet= reports =BTN_TOOL_*= before
  =synaptics_report_buttons=, so =*pad-fingers*= is up to date when =BTN_LEFT= arrives.
- *The corner* is =*pad-right-zone*=: right of 3/5 of the width, below 4/5 of the
  height. =ABS_Y= grows /downwards/ on a Synaptics pad (the driver inverts the hardware's
  y in =synaptics_invert_y=).

Keyboard routes, for a pointer without a middle button and a hand already on the keys:

- *Alt-click* is the middle button. Alt is tracked from the keyboard's evdev
  (=KEY_LEFTALT= 56 / =KEY_RIGHTALT= 100), like Ctrl, Shift and Super. (Ctrl-click
  already jumps to a definition.)
- *Menu key* (=KEY_COMPOSE=, 127, read from evdev — [[#tty-enough][Why the tty is not enough]]) and *Shift-F10* (=ESC [ 34 ~=,
  the keymap's F20) open the context menu at the caret or selected row.
- *Ctrl + wheel* resizes the text, one step per notch, three at most per event
  ([[file:fonts.org::#size-change-reaches-every][fonts.org, How a size change reaches every pixel of layout]]). The wheel handler in =poc/shell.lisp= reads =fb-browser.lisp='s
  =*ctrl-down*= by name, because =shell.lisp= loads first.

A right or middle press isn't a click to the overlays (Spotter, debugger, cheatsheet):
=read-mouse= reports it in a third value that only the browser's own loop reads.
*Tested* by [[file:../check-clipboard.lisp][check-clipboard.lisp]] with QEMU's real right and middle buttons; the pad's
emulated ones, like the tap, by replaying synthetic Synaptics packets.

* 4¾. Every device at once, and the ones plugged in later
:PROPERTIES:
:CUSTOM_ID: every-device-once-ones
:END:

A laptop used with an external USB mouse and keyboard has several pointers and several
keyboards, and any of them may come and go. The environment opens every keyboard and
every pointer at once, and watches =/dev/input= for more.

** Why one of each isn't enough

Opening one pointer and one keyboard, chosen once at startup, fails three ways:

1. *One pointer.* A ranking (tablet, then mouse, then touchpad) opens the external mouse
   and never the touchpad — or, if the mouse arrives later, the reverse.
2. *One keyboard.* The first device with =EV_KEY= + =EV_REP= is the built-in keyboard
   (the i8042 is probed long before USB), so an external keyboard's evdev is never read.
   Typing still works — the console merges every keyboard into fd 0 — which hides it,
   but Ctrl, Shift, Super and Alt come from evdev ([[#tty-enough][Why the tty is not enough]]), so Ctrl-click, Shift-arrow
   selection and every =SuperL-= binding die on the external keyboard.
3. *Once.* Anything plugged in later doesn't exist. That includes devices present at
   boot: USB enumerates asynchronously, after PID 1 is running (hence the supervisor's
   wait — [[file:sbcl-init.org][sbcl-init.org]], "Why the startup =(sleep 2)= exists"), so a slow hub can
   miss the one scan.

*An example* (=cat /proc/bus/input/devices= on a Dell XPS 13 9300 under Debian, with an
external USB mouse and gaming keyboard; abridged — the touchpad's node differs under our
kernel, [[#makes-work][What makes it work (kernel side)]]):

| node    | name                                   | =EV=     | what a one-of-each ranking makes of it        |
|---------+----------------------------------------+----------+-----------------------------------------------|
| event0  | AT Translated Set 2 keyboard           | =120013= | *the* keyboard — first with =EV_REP=          |
| event16 | PS/2 Synaptics TouchPad                | (pad)    | rule 3 — never reached while a mouse exists   |
| event17 | PixArt Microsoft USB Optical Mouse     | =17=     | rule 2, a mouse                               |
| event18 | SINO WEALTH Gaming KB                  | =120013= | a keyboard — never opened (event0 came first) |
| event20 | SINO WEALTH Gaming KB Consumer Control | =1f=     | rule 2, /also/ a "mouse": =EV_REL=, no X axis |
| event21 | SINO WEALTH Gaming KB Keyboard         | =100013= | a keyboard — never opened                     |
| event22 | SINO WEALTH Gaming KB Mouse            | =17=     | rule 2, a mouse                               |

- *Consumer Control as a mouse.* Under an "any =EV_REL=" rule the keyboard's volume knob
  counts as a pointer; if it's the one chosen, nothing moves the cursor. Hence [[#finding-device-without-udev][Finding the device without udev]]'s X
  axis requirement.
- *Two keyboard nodes.* Gaming keyboards expose a second one (the N-key-rollover
  interface); which carries the modifiers is the keyboard's business, so both are read.

** The fix

Every keyboard and every pointer is open at once, each an =input-dev= in
=*input-devices*= ([[file:../initramfs/fb-browser.lisp::defun rescan-input-devices][=rescan-input-devices=]]):

- *Classified per device* ([[file:../initramfs/fb-browser.lisp::defun input-device-kind][=input-device-kind=]]): =:mouse=, =:pad=, =:tablet= or
  =:keyboard=. A device that's none of these (power button, lid switch, PC speaker) is
  listed but not opened.
- *One poll over all.* [[file:../initramfs/fb-browser.lisp::defun poll-input-once][=poll-input-once=]] lays out one =pollfd= per device after the
  tty's and the hotplug watch's ([[#waiting-many-things-once][Waiting on many things at once: =poll(2)=]]), marks each device with records, and
  [[file:../initramfs/fb-browser.lisp::defun read-pointers][=read-pointers=]] / [[file:../initramfs/fb-browser.lisp::defun read-keyboards][=read-keyboards=]] drain exactly those. Loops still call
  =(fbb-wait 0 *fb-mouse* *fb-kbd*)= and =(read-mouse *fb-mouse* w h)=: =*fb-mouse*= is
  =:pointers=, and =read-mouse= given a non-fd reads every ready pointer.
- *Per-device state without rewriting the decoder.* =read-mouse= and =pad-motion= keep
  state in special variables — the pad's last finger, the tap in progress, the held
  button. A touchpad's last position must not be differenced against a mouse's packet.
  [[file:../initramfs/fb-browser.lisp::defmacro with-device-state][=with-device-state=]] rebinds those variables with =progv= to the device's own saved
  values for one drain, and saves them back. The decoder doesn't know there's more than
  one device, so replaying a file of records through it still works.

** What is shared, and what is not

- *One cursor.* Every pointer moves the same arrow, as under X.
- *Buttons and modifiers are per device;* the browser reads their OR
  ([[file:../initramfs/fb-browser.lisp::defun sync-input-globals][=sync-input-globals=]]). Ctrl on the external keyboard makes a touchpad click a
  Ctrl-click; a press held on the pad while the mouse moves is a drag.

The OR isn't really a choice: the console keeps one =shift_state= for all keyboards
([[file:../linux/drivers/tty/vt/keyboard.c::static int shift_state = 0;][=drivers/tty/vt/keyboard.c=]]), so Ctrl on one keyboard and =a= on another already
reach the tty as =C-a=. What per-device state buys is *release*: a device that goes
away takes its held keys with it, so unplugging a keyboard with Ctrl down can't leave
Ctrl stuck.

** Hotplug: arriving, and leaving

*Arriving.* =CONFIG_INOTIFY_USER= (tag #26) lets us watch =/dev/input=; devtmpfs creates
a node through =vfs_mknod=, which notifies like any create. The watch fd sits in the
poll set, and any event on it means "rescan" — =/proc/bus/input/devices= is the source
of truth, and cheap to read.

| inotify     | means                                   |
|-------------+-----------------------------------------|
| =IN_CREATE= | devtmpfs made a node — a device arrived |
| =IN_ATTRIB= | its owner changed — see below           |
| =IN_DELETE= | a node went                             |

- *Why =IN_ATTRIB=.* With a disk found, PID 1 runs as the *user* ([[file:storage.org][storage.org]]), and
  devtmpfs creates input nodes as =root:root 0600= (the input class asks for no mode,
  [[file:../linux/drivers/input/input.c::static char *input_devnode][=input_devnode=]]). So the open at =IN_CREATE= fails with =EACCES=. =lol-rootd= chowns
  any =/dev/input/event*= not yet the user's once a second ([[file:../initramfs/preinit.c::static void give_devices][=give_devices=]]), causing
  one =IN_ATTRIB= per new node; that wakes us, and the rescan's open succeeds.
- *A retry.* A rescan is re-run 400 ms after any hotplug event, in case the node, its
  =/proc= line and its owner didn't all land at once.
- *No inotify* (an older kernel): the environment rescans every two seconds.

*Leaving.* An unplugged device doesn't go quiet. =evdev_poll= answers
=EPOLLHUP | EPOLLERR= for it ([[file:../linux/drivers/input/evdev.c::static __poll_t evdev_poll][=drivers/input/evdev.c=]]) on /every/ call, and =read=
says =ENODEV=; ignore that and the loop spins at 100 % CPU. So =POLLHUP= / =POLLERR= /
=POLLNVAL= closes the fd and forgets the device before anything reads it.

- *eventN numbers are reused.* Unplug a mouse, plug a keyboard, and it may be =event6=
  again. A device is identified by its node /and/ its =Sysfs== path, and a rescan closes
  what the kernel no longer lists before opening anything new. (=check-input.lisp='s
  hotplugged keyboard and mouse both arrive as =event6=.)
- *Housekeeping never returns from =fbb-wait=.* A hotplug wake isn't what the caller
  asked about, and "nothing ready" would read as "a deadline fired"; so =fbb-wait=
  handles it and polls again for the rest of the caller's timeout.

** Pointer speed

Two special variables, settable in the Workspace: =*pad-speed*= (screens per full sweep
of the touchpad, =3/2=, [[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]) and =*mouse-speed*= (pixels per mouse count, =1= — what the
console and X's flat profile do; a 1000-dpi mouse crosses a 1920 px screen in about
5 cm). Both carry the fraction, so any rational works. There's no acceleration curve.

** Seeing what the environment sees
:PROPERTIES:
:CUSTOM_ID: seeing-what-environment-sees
:END:

=SuperL-Space=, type =input devices=: one row per open device (node, kind, name, records
read, clicks, what it holds now, where it hangs), then any it wanted and couldn't open
(with the errno — =EACCES= is "not yours yet"), every device it saw and didn't want, and
recent arrivals and departures. Enter on a device opens its =input-dev= in the
inspector. At a REPL: =(show-input-view)= (not =show-input-devices=, the supervisor's
boot-time list). The subject is =subj-input-devices=, at the end of
[[file:../initramfs/fb-browser.lisp::defstruct (subj-input-devices][=fb-browser.lisp=]].

** Tests

[[file:../check-input.lisp][=check-input.lisp=]] (38 assertions) boots with a PS/2 mouse, a USB mouse, a USB
tablet, the PS/2 keyboard and a USB keyboard, as uid 1000 (=test-disk.img=), and drives
each device /on its own/: =mouse_set= picks which mouse QEMU feeds, and the USB keyboard
is bound to =display=vga0= so keys sent with ="device":"vga0"= reach it and the rest
reach the PS/2 one. It asserts:

- *All five open at once;* each pointer moves the cursor and its own record count grows;
  each one's click is seen; the tablet lands where aimed.
- *Modifiers per keyboard:* Ctrl through each keyboard's own node, held across the two
  and released; Super on the USB keyboard.
- *A synthetic touchpad* replayed through =with-device-state= moves by the difference
  (58 px, as computed), its finger remembered per device.
- *Hotplug:* a USB keyboard is opened and forgotten; a USB mouse is opened, moves,
  clicks, and on =device_del= is closed, the environment survives, the PS/2 mouse still
  works, and the loop wakes 5 times in 4 idle seconds afterwards (the clock and the
  pointer's hide; a spin would be tens of thousands).

[[file:../check-pointer.lisp][=check-pointer=]], [[file:../check-scroll.lisp][=check-scroll=]] and [[file:../check-clipboard.lisp][=check-clipboard=]] also pass with all devices open.

** Ruled out (so nobody searches again)

- *A missing driver.* =USB_HID=, =HID_GENERIC=, xHCI and =MOUSE_PS2_SYNAPTICS= are all
  built (tag #26); every device is in =/proc/bus/input/devices=. Each pointer worked
  whenever it was the one chosen.
- *Permissions.* Boot-time and hotplugged nodes both go to the user (=give_devices=, at
  boot and from =lol-rootd=); the hotplugged mouse in =check-input= opened as uid 1000.
- *inotify on devtmpfs.* It fires for nodes the kernel creates; hotplug was seen within
  about half a second.
- *virtio-input* (=virtio-mouse-pci= etc.) would be a third bus to test, but
  =CONFIG_VIRTIO_INPUT= is off and laptops have none; USB and PS/2 are the buses.
- *QEMU routing, a trap for tests.* With no =device= argument QEMU sends keys to the
  keyboard it last activated — after boot, the USB one — so the PS/2 keyboard sees
  nothing. A test that means "the PS/2 keyboard" must bind the other to a console, as
  =check-input= does.

** Limits

- *A device that's both pointer and keyboard* is read as a pointer: its modifiers count,
  its Menu key doesn't.
- *A key held when a keyboard is plugged in* isn't seen until pressed again (=EVIOCGKEY=
  at open would fix it).
- *Unplugging the /last/ pointer* leaves its arrow on screen until the next redraw.
- *Two presses from two devices in one poll wake* count as one click.

** Checklist on real hardware

Boot with the external mouse and keyboard attached, then:

1. =SuperL-Space=, =input devices=, Enter. Expect *open*: the built-in keyboard, the
   USB keyboard (perhaps two nodes), the touchpad (=pad= — or =mouse= if the kernel gave
   it a relative node), the USB mouse. Nothing under /could not open/. What's under
   /seen, not read/ is the list to send if anything is missing.
2. Move the touchpad, the mouse, the touchpad again; Refresh the view (its only
   command). Both counts grew; one arrow followed both.
3. Click with each (touchpad: a press, or a firm tap if tap-to-click is on). Hold Ctrl
   on the *external* keyboard and click a symbol in the Workspace with the touchpad —
   it jumps to the definition.
4. =SuperL-m= on the external keyboard opens the module index (Super read from its own
   node).
5. Unplug the mouse, keep using the touchpad, plug it back — it works within a second
   and appears under /recent changes/. Same with the keyboard.
6. If the mouse feels slow or fast, set =*mouse-speed*= (=3/2=, =2/3=); the pad has
   =*pad-speed*=.

* 5. Waiting on many things at once: =poll(2)=
:PROPERTIES:
:CUSTOM_ID: waiting-many-things-once
:END:

The tty, every device of [[#every-device-once-ones][Every device at once, and the ones plugged in later]] and the hotplug watch may all be idle. Busy-polling would
spin PID 1 at 100 % CPU; blocking on one would ignore the rest. [[file:../initramfs/fb-browser.lisp::defun poll-input-once][=poll-input-once=]]
(under [[file:../initramfs/fb-browser.lisp::defun fbb-wait][=fbb-wait=]]) builds =poll(2)='s argument array by hand:

#+begin_src c
  struct pollfd { int fd; short events; short revents; };   /* 8 bytes */
#+end_src

- *Layout.* N slots are an =8N=-byte array: =fd= at =n*8=, =events= at =n*8+4=, =revents=
  at =n*8+6=. Slot 0 is the tty, slot 1 the =/dev/input= watch, then one per open
  device, then the fds of other services (the web pane, workers) — 40 slots in all.
- *Sleeping.* Timeout =-1= (forever) unless something has a deadline, so the loop sleeps
  until something happens and the browser costs nothing while untouched.
- *=revents=.* Bit 0 (=POLLIN=) is records waiting; =POLLHUP= (=0x10=) and =POLLERR=
  (=0x8=) are an unplugged device, which must be closed at once or poll reports it
  forever ([[#every-device-once-ones][Every device at once, and the ones plugged in later]]).
- *An absent fd* (no inotify, say) still gets its slot, holding =fd -1=: poll ignores a
  negative fd, so the offsets stay put and there's no separate code path.

=sb-posix= has no =poll= (nor =select= nor =epoll= — [[file:processes.org::#sb-posix-audit-nothing][processes.org, sb-posix — the audit, and why nothing was migrated]]), so the array is
ours, and =%put-pollfd= writes the one field that's easy to get wrong, for every caller.

*Pitfall: =fd= is a full 32-bit =int=.* Writing only its low byte works while every
descriptor is small, then silently polls a *different* fd: a pipe at fd 300 was polled
as fd 44 (=300 & 0xff=), which returned =POLLNVAL= — "nothing to read" while data
waited. All four bytes are written, little-endian. That matters for any slot holding a
socket or pipe ([[file:processes.org::#scenario-peer-sends-view][processes.org, Scenario A — a peer that sends a VIEW]]).

* 6. The wheel, end to end
:PROPERTIES:
:CUSTOM_ID: wheel-end-end
:END:

There's no scroll *axis* and no scroll *position*: the wheel is a relative device that
moves in detents. One notch is one record:

#+begin_example
  type=2 (EV_REL)  code=8 (REL_WHEEL)  value=+1   ; rolled away from you
  type=2 (EV_REL)  code=8 (REL_WHEEL)  value=-1   ; rolled toward you
#+end_example

[[file:../initramfs/fb-browser.lisp::defun read-mouse][=read-mouse=]] sums these across one drain and returns them beside the click, so a fast
flick is one =wheel= of =+3=, not three frames. The main loop turns notches into lines:

#+begin_src lisp
  (unless (zerop wheel)
    (browser-scroll (* (- wheel) +wheel-lines+)))     ; +wheel-lines+ = 3
#+end_src

*The negation is a real sign-convention flip.* evdev's =+1= means "rolled away from the
user"; [[file:../poc/shell.lisp::defun browser-scroll][=browser-scroll=]]'s argument means "this many lines further *down*". Rolling
away moves you *up* the document, so one =-= reconciles them.

=browser-scroll= then dispatches on the pane. Every kind scrolls its *view* and leaves
the caret or selection alone — scrolling is looking, not moving:

- *Ctrl held:* resizes the text instead ([[file:fonts.org::#size-change-reaches-every][fonts.org, How a size change reaches every pixel of layout]]).
- *A web page* gets the wheel sent to Chrome (=web-wheel=).
- *A terminal* scrolls its history, or passes the wheel to the program (=terminal-wheel=).
- *A text pane* scrolls its viewport via [[file:../poc/textview.lisp::defun tv-wheel][=tv-wheel=]], the caret staying put.
- *A list pane* moves =pane-top= with =pane-follow= off for that frame, so the widget
  doesn't drag the view straight back to the selection. The widget clamps at both ends.

** The wheel a laptop does not have

A touchpad has no wheel; it has a second finger, and says so: =BTN_TOOL_DOUBLETAP=.
While that's down, [[file:../initramfs/fb-browser.lisp::defun pad-motion][=pad-motion=]] stops moving the cursor and turns vertical motion
into notches — one per 1/24 of the pad's height, about 2 mm.

The sign follows the same convention: two fingers dragged *toward* you is the gesture
of rolling a wheel toward you, so it produces the same negative notch, and the same
=(- wheel)= makes it "further down". Nothing after =read-mouse= can tell there was no
wheel.

* 7. The same gesture on the host: X11 buttons 4 and 5
:PROPERTIES:
:CUSTOM_ID: same-gesture-host-x11
:END:

On the dev host the X server owns the devices and sends protocol events
([[file:x11.org][x11.org]]). X's answer to the wheel predates scroll axes: *the wheel is a pair of
buttons*.

| gesture    | guest (evdev)                   | host (X11)                                             |
|------------+---------------------------------+--------------------------------------------------------|
| move       | =EV_REL= =REL_X/Y= deltas       | =MotionNotify= x,y                                     |
| left click | =EV_KEY= =BTN_LEFT= value 1     | =ButtonPress= detail =1=                               |
| drag       | =REL_X/Y= while =BTN_LEFT= is 1 | =MotionNotify= with =Button1Mask= (=#x100=) in =state= |
| wheel up   | =EV_REL= =REL_WHEEL= value =+1= | =ButtonPress= detail =4=                               |
| wheel down | =EV_REL= =REL_WHEEL= value =-1= | =ButtonPress= detail =5=                               |
| Ctrl held  | =EV_KEY= =KEY_LEFTCTRL= value 1 | the event's =state= bitmask                            |

[[file:../poc/x11.lisp][=x11.lisp=]] decodes all of these (=:button-press= carries the button in
=event-detail=). X *gives* the modifier state on every event, so the host needs no
second keyboard fd — that asymmetry is why the guest has one.

[[file:../poc/run-browser.lisp][=run-browser.lisp=]] dispatches on the button: 1 clicks, 4 and 5 call =browser-scroll=,
and a =:motion= whose state carries =Button1Mask= calls =browser-drag=.

* 8. What makes it work (kernel side)
:PROPERTIES:
:CUSTOM_ID: makes-work
:END:

| Option                            | State | Why                                                        |
|-----------------------------------+-------+------------------------------------------------------------|
| =CONFIG_INPUT_EVDEV=              | y     | creates =/dev/input/event*= — the whole mechanism above    |
| =CONFIG_INPUT_MOUSEDEV=           | *n*   | deliberately off; why there is no =mouseN= to look for     |
| =CONFIG_MOUSE_PS2=                | y     | the PS/2 mouse + laptop touchpad driver                    |
| =CONFIG_SERIO= + =KEYBOARD_ATKBD= | y     | the PS/2 keyboard QEMU gives us                            |
| =CONFIG_USB_HID= / =CONFIG_HID=   | y     | a USB mouse or keyboard                                    |
| =CONFIG_I2C_HID= + =_ACPI=        | y     | internal laptop touchpads/keyboards on the I2C-HID bus     |
| =CONFIG_MOUSE_PS2_SYNAPTICS=      | y     | the laptop touchpad the way we actually get it — see below |
| =CONFIG_I2C_DESIGNWARE_PLATFORM=  | *n*   | not built, which is *why* we get it that way               |
| =CONFIG_RMI4_CORE=                | *n*   | not built either, so there is no SMBus hand-off            |

*Why a laptop touchpad arrives over PS/2.* =CONFIG_I2C_HID=y= looks sufficient, but
I2C-HID needs an I2C *bus*, and on an Intel laptop that controller wants
=CONFIG_I2C_DESIGNWARE_PLATFORM=. Only the Designware *core* is built
(=i2c-designware-common.o= and =-master.o= exist under =linux/drivers/i2c/busses/=;
=i2c-designware-platdrv.o= doesn't), so the bus never appears and neither does the I2C
touchpad. =psmouse= picks the pad up over the legacy i8042 port instead, and with
=CONFIG_RMI4_CORE= off it can't hand over to SMBus, so it stays in the *absolute*
Synaptics PS/2 protocol — the device [[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]] is about.

Enabling the platform driver would give the pad a relative node, but wouldn't make [[#touchpad-absolute-but-position][The touchpad: absolute, but not a position]]
optional: the PS/2 absolute fallback is what every machine without that driver gets.

Full table and reasoning: [[file:kernel-config.org][kernel-config.org]]. Device nodes appear without being listed
in the cpio because =/dev= is devtmpfs, mounted by [[file:../initramfs/preinit.c][=preinit.c=]] ([[file:sbcl-init.org][sbcl-init.org]]).
