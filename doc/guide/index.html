Start here: the big picture

A guide to reading the code of lisp-over-linux: what runs, in what order, and where each part lives. Every diagram box and every file:line below was checked against the source. The line numbers are generated, so they stay correct when the code moves.

How to use this guide

  • References look like browser-keypoc/shell.lisp:2638. The link opens the file. The grey file:line is for Emacs: M-x find-file, then M-g g to the line. Better still, open the definition in the running environment itself (Reading paths shows how).
  • The guide checks itself. sbcl --script doc/guide/regen.lisp rewrites every reference from the current source. It exits non-zero if a function was renamed or a file disappeared. It also re-derives the module map and stamps this sidebar. Run it after you change code, the same way you run ./check-links.sh after you change the docs.
  • The environment has a twin of this guide. In the running system, press SuperL-Space, type tour and press Enter. You get the same walk as a list of the image's own live definitions. The .org index of these pages is doc/tour.org.
  • The design documents in doc/*.org explain why things are the way they are. This guide is a map of where they are and how they connect, and it links to those documents when you need the why.

From the power button to the Workspace

This is the whole boot. Read it left to right, then down. Each box names the file, or the function, that does that step.

The same chain in words, with references

  1. firmware → BOOTX64.EFI There is no bootloader. The kernel's bzImage is an EFI application (the "EFI stub"), and build.sh copies it to iso_root/efi/boot/bootx64.efi (build.sh step 4build.sh:404). The kernel's command line is compiled in ( CONFIG_CMDLINEkernel/config-7.2.5:398). It says initrd=initramfs.cpio, so the stub loads the second file from the same partition. That is the "separate initrd", and it is why a Lisp change rebuilds in seconds without touching the kernel. More in micro-distro.org.
  2. /init in the cpio listinitramfs/initramfs.sbcl.list:30 The cpio list maps initramfs/preinit to /init and initramfs/lisp-init to /sbin/lisp. It also ships glibc's loader, libc and libm, because the SBCL runtime is a dynamically linked program.
  3. preinit maininitramfs/preinit.c:594 Why C first? An SBCL executable finds its own heap by reading /proc/self/exe, so /proc has to be mounted before SBCL starts. preinit then does the privileged work once, while it is still root: mount_storageinitramfs/preinit.c:270, start_rootdinitramfs/preinit.c:499, become_userinitramfs/preinit.c:562. Then it execves the Lisp. execve replaces the program, not the process, so the Lisp is PID 1. Details are on Storage, privilege, network.
  4. init-toplevelinitramfs/supervisor.lisp:168 save-lisp-and-die named this function as the image's :toplevel (How the image is built). One binary plays three roles, chosen by argv. The worker and job roles exist so that the image can run itself as a child process (processes.org).
  5. supervisor-maininitramfs/supervisor.lisp:84 It prints diagnostics, runs DHCP (configure-eth0initramfs/dhcp.lisp:480), starts the network REPL only if the boot asked for it, and then calls run-browser-fbinitramfs/fb-browser.lisp:1617. That function catches every error, so a broken environment drops you at the menu instead of killing PID 1. A kernel panics if PID 1 exits, so every path here either loops or powers off.
  6. run-browser-fbinitramfs/fb-browser.lisp:1617 The environment: one loop that redraws when something changed, then blocks in poll(2) on the keyboard and mouse. It opens on the Workspace. Everything from here on is the subject of present and the shell and Pixels and input.

Three ideas the rest hangs on

The image carries its own source

When the image is built, every module is loaded with load-recording, which also stores each definition's text in *registry*. The running system can show and edit its own code with no source files on disk. Build →

Everything is a subject

(present subject) returns a view: a title, items and maybe text. An item that carries a subject can be drilled. One generic function covers source, classes, files, processes and this tour. present →

Pixels are one vector

The canvas is a vector of #x00RRGGBB words, which is already the framebuffer's byte order. Showing a frame on /dev/fb0 is one pwrite. The X11 window and the headless renderer show the same vector. Pixels →
