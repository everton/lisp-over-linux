present and the shell

The environment has two halves. The protocol (present.lisp) turns any subject into a description: pure data, no pixels, no state. The shell (poc/shell.lisp) is the one stateful layer. It keeps the open trails, routes keys and draws. The full design is in code-browser.org §4½.

Subject → view → pane → trail

  • open-panepoc/shell.lisp:65 calls present, or present-preview for the right-hand preview column. It gives :source, :reference, :workspace and :file views a textview, focused (editable) for everything except :reference.
  • trail-pushpoc/shell.lisp:169, trail-poppoc/shell.lisp:174, new-trailpoc/shell.lisp:180 (a new tab: the Spotter, SuperL-Enter), open-environmentpoc/shell.lisp:236 (the first tabs).
  • The nav split: when a list pane's selected item has a subject, the right half shows (present-preview subject) live as you move (preview-forpoc/shell.lisp:1316). This is how the tour previews each stop's source.

Commands: content declares, the shell disposes

commands-forinitramfs/present.lisp:346 returns data. It never opens anything itself. The shell picks the commands for a surface (subject-commandspoc/shell.lisp:3006), builds menu entries from them (command-entriespoc/shell.lisp:3048) and runs the chosen one through run-commandpoc/shell.lisp:2985: call the action, or open the target in place or in a new trail. The right button (browser-context-menupoc/shell.lisp:3488) and the middle-button halo (browser-middle-clickpoc/shell.lisp:3492) both end in choose-and-runpoc/shell.lisp:3477. That function calls whatever *chooser* the backend installed: run-chooser-fb on the framebuffer, and none on the X11 host runner.

A keypress, end to end

What happens between pressing Enter on a list row and the new pane appearing on screen. Every name here is a real function. The solid arrows are calls and the dashed ones are returns.

  1. fbb-waitinitramfs/fb-browser.lisp:76 One poll(2) (poll-input-once) over the console tty (fd 0, cooked bytes), an inotify watch on /dev/input, and every open keyboard and pointer evdev node. A keyboard's evdev node is read only for the modifier state, which the tty cannot report. Hotplug is handled inside the wait and never returned.
  2. fb-read-keyinitramfs/fb-browser.lisp:165 Turns raw bytes into a key and a state mask: control bytes become a letter with the Ctrl bit, ESC [ sequences become arrows, ESC x becomes Meta-x. The mask uses X11's bit layout so both backends share browser-key: Shift bit 0, Ctrl 2, Meta 3, Super 6 (shift-ppoc/canvas.lisp:55).
  3. read-keyboardsinitramfs/fb-browser.lisp:1095 Every ready keyboard is drained, and the loop folds the OR of their held keys (*ctrl-down*, *shift-down*, *super-down*) into the state before routing. This is why SuperL-Space works on a bare console.
  4. browser-keypoc/shell.lisp:2340 One cond, in priority order: minibuffer, M-./M-,, Esc as Meta, C-g, the Super layer, the side pane, the stage, editable panes, read-only text, the subject's own keys, and last the list keys, where Enter calls trail-push.
  5. open-panepoc/shell.lisp:65 Presents the subject. A :source view's text goes into a new lol.textview.
  6. draw-browserpoc/shell.lisp:1450 Clears the canvas, then draws the tabs, the breadcrumb bars, the expanded pane (or the split) and the status line. It records what it drew where (*drawn*, used by the halo) and the hit maps used for clicks.
  7. show-frameinitramfs/fb-browser.lisp:1164 lol.fb:present-fb then the pointer. Pixels and input covers this half.
