Reading paths

Six walks through the code, each answering one question. Follow the stops in order with the source open. You can do it in Emacs with the file:lines, or in the running environment: put the caret on any name in a source pane and press M-. (walk 1 explains how that works). C-g comes back.

Walks: 1 · M-. on a symbol · 2 · the Workspace evaluates a form · 3 · C-c C-c changes the image · 4 · a file preview is decoded · 5 · the Spotter finds something · 6 · "who drew this pixel?"

1 · What happens when I press M-. on a symbol

  1. fb-read-keyinitramfs/fb-browser.lisp:167 On the console, Alt-. (or Esc then .) arrives as the bytes ESC .. An ESC followed within 20 ms by a printable byte becomes that character with the Meta bit (8) set. A lone ESC becomes :escape, which the shell keeps as a "sticky" Meta for the next key.
  2. run-browser-fbinitramfs/fb-browser.lisp:1719 The loop ORs in the held modifiers from evdev and calls browser-key.
  3. browser-keypoc/shell.lisp:2981 The first real branch: Meta and . in a pane with a textview. It comes before the editing branch, or the "." would be typed into the buffer.
  4. jump-at-pointpoc/shell.lisp:3276 → token-at-pointpoc/shell.lisp:3264 Takes the token under the caret, or the one just before it, because the caret usually rests after a word. A token is a run of non-delimiter characters (token-spanpoc/shell.lisp:3225). There is no reader involved, so pkg:name and *var* both work.
  5. resolve-symbolpoc/shell.lisp:3242 Finds an existing symbol: with a package prefix, in that package; otherwise CL-USER, then CL. It never interns, so clicking a typo creates nothing. jumpable-ppoc/shell.lisp:3259 requires a function, a variable or a class.
  6. trail-pushpoc/shell.lisp:356 Pushes (subj-defn sym). The jump is just a drill, so C-g undoes it.
  7. (present subj-defn)initramfs/present.lisp:595 Two outcomes. If the registry has the source (source-ofinitramfs/registry.lisp:293), the view is :source and editable. If not, it is a builtin, and show-referenceinitramfs/registry.lisp:310 prints what the image knows: kind, lambda list, docstring. When SBCL's source tree is on the mounted disk, it also appends the real source text (sbcl-definition-sourceinitramfs/sbcl-source.lisp:234), cut out of the file with a textual scanner that never READs SBCL's code.
  8. open-panepoc/shell.lisp:243 Wraps the text in a textview, focused only for :source. The loop redraws. M-, is the same path ending in (subj-xref :senders sym) (senders-at-pointpoc/shell.lisp:3288), answered by sb-introspect:who-calls (sendersinitramfs/registry.lisp:414).

2 · How does the Workspace evaluate a form (C-x C-e)?

  1. browser-keypoc/shell.lisp:2981 The Workspace is an editor pane (editor-pane-ppoc/shell.lisp:303), so the key goes to edit-pane-keypoc/shell.lisp:2855, which wraps every edit in an undo record.
  2. edit-pane-commandpoc/shell.lisp:2888 C-x only sets *pending-prefix* to :c-x and returns. The next key, C-e, finds the prefix and calls workspace-do-it. This is how every chord works: a tiny state machine of one variable.
  3. form-before-pointpoc/shell.lisp:821 Reads forms from the start of the buffer to the caret and keeps the last complete one. A fresh sentinel tells "read nothing" apart from "read NIL". A bare nil in the buffer once hid every form below it.
  4. ws-evalpoc/shell.lisp:861 eval with *standard-output* bound to a string stream, inside a handler-case on serious-condition. It returns success, value and output, and never signals.
  5. workspace-do-itpoc/shell.lisp:935 Writes form => value to *browser-status*. The redraw puts it in the status line (draw-status-linepoc/shell.lisp:1957). Print it, Inspect it and Debug it share steps 3 and 4 and differ only here.

3 · How does C-c C-c change the running image?

  1. edit-pane-commandpoc/shell.lisp:2888 C-c then C-c in an editable pane calls accept-pane.
  2. accept-panepoc/shell.lisp:2747 A source pane gives the whole buffer, plus the name, kind and method label from accept-targetinitramfs/present.lisp:961. The Workspace gives only the form before point, and that form names itself.
  3. accept-packageinitramfs/registry.lisp:203 The text is read in the package its original was read in. Without this, an edit of a lol.textview function would silently define a CL-USER twin.
  4. accept-sourceinitramfs/registry.lisp:238 (eval form) compiles the form and replaces the function object, so the next call runs the new code. Then the bookkeeping: the old text goes onto defn-versions, or a new DEFN is made with born t.
  5. (present subj-change-set)initramfs/present.lisp:1040 The change set is changed-definitionsinitramfs/registry.lisp:395: every DEFN with versions or born. Find it with SuperL-Space "change set", or the supervisor menu's c.

4 · How does a file preview get decoded?

Open the file manager (SuperL-f), select a PNG, and the right column shows it.

  1. expanded-columnspoc/shell.lisp:1831 The nav split: the selected row has a subject (subj-file), so the expanded pane's right column needs a preview — a pane too, the expanded pane's child morph.
  2. preview-forpoc/shell.lisp:1716 Each list pane caches its own preview pane and rebuilds it only when the selection moves: (open-pane subject :preview t), which calls present-preview, not present.
  3. file-viewinitramfs/file-views.lisp:665 lstats the path, follows a link, reads a capped prefix (read-prefixinitramfs/files.lisp:600) and identifies the bytes by magic number (sniffinitramfs/file-views.lisp:238), not by extension.
  4. image-viewinitramfs/file-views.lisp:583 Finds the decoder by name: (optional-fn "LOL.IMAGE" "DECODE-IMAGE"). Without it, the preview still says the format and size. Previews have a smaller size cap than opening the file.
  5. decode-imagepoc/image.lisp:1405 Dispatches on the format. PNG goes to decode-pngpoc/image.lisp:272, pure Lisp on top of lol.inflate. JPEG, PSD and HDR go to decode-stbipoc/image.lisp:866, which loads /usr/lib/lol/libstbi.so the first time it is needed (stbi-available-ppoc/image.lisp:843). Either way the result is #x00RRGGBB words, the canvas's own format. It never signals.
  6. draw-image-bodypoc/shell.lisp:1778 The view's kind is :image and its data holds the pixels. The shell fits them to the pane (scaled-pixelspoc/shell.lisp:1756, using lol.image:scale-to-fit when that package is loaded) and copies them into the canvas. Why JPEG is C and the rest is Lisp: previews.org.

5 · How does the Spotter find something?

  1. browser-keypoc/shell.lisp:2981 SuperL-Space: the Super branch calls open-spotter through funcall and fboundp, because the shell loads before poc/overlays.lisp.
  2. open-spotterpoc/overlays.lisp:65 An overlay: a morph on top of the world, which routes every key to it while it is up. It collects candidates once and re-filters on each keystroke; everything behind it keeps running.
  3. spotter-candidatesinitramfs/present.lisp:222 Surfaces, every module, every package, every registry name (a generic function opens its own view), plus whatever the functions on *spotter-sources*initramfs/present.lisp:329 add. The tour is added there (tour's sourceinitramfs/tour.lisp:154).
  4. spotter-resultspoc/shell.lisp:2085 → spotter-filterinitramfs/present.lisp:361 A query that looks like a path completes a folder instead. Otherwise matches are ranked exact < prefix < word boundary < subsequence (spotter-scoreinitramfs/present.lisp:211), then banded into groups.
  5. draw-spotter-cardpoc/shell.lisp:2147 The drawing lives in the shell, so render-frame --spotter can draw it on the host. Enter calls new-trail, which opens a new tab.

6 · "Who drew this pixel?" — the halo

  1. pane-middle-clickpoc/shell.lisp:4172 A middle click (or Alt-click) in text you can edit pastes PRIMARY. Anywhere else it opens the halo.
  2. halo-layerspoc/morphic.lisp:1645 Every thing on screen is a morph that draws itself, so "who drew this pixel" is the morph tree: the thing the pointer is on (a word, a row), then each morph from the deepest under the point out — the text view in the pane, the pane, what it shows, its trail area, the shell or the window — each offering itself and its drawing functions.
  3. halo-entriespoc/shell.lisp:3951 The handles: Inspect the object, Code (the function that drew it), Source, and so on. Each one is a command.
  4. run-chooserpoc/overlays.lisp:152 The chooser overlay draws the halo and waits for the pick by turning the environment's own loop; the caller runs the chosen handle. Try it on the host with render-frame.lisp modules --halo 300,200.
