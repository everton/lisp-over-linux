How the image is built

./build.sh makes the two files a USB stick carries: bootx64.efi (the kernel) and initramfs.cpio (everything else). The interesting part is the middle step, where one SBCL process loads every module and is then saved, heap and all, as a single executable.

The pipeline

Where each step is

  • Load order: LISP_SOURCESbuild.sh:64. Each entry has a comment saying what it is and what it needs.
  • The generated build script: BUILD_LISPbuild.sh:192 through save-lisp-and-diebuild.sh:212. It exists only in a temp file. sbcl-init.org reproduces its shape.
  • The cpio's contents: initramfs.sbcl.listinitramfs/initramfs.sbcl.list, a plain list of dir / nod / file lines.
  • --install-host copies the two files to /boot/lisp for a GRUB entry (install-hostbuild.sh:349).

The frozen heap: why save-lisp-and-die matters

An SBCL "core" is a snapshot of the whole Lisp heap: every function, class, hash table and string that exists at the moment of saving. save-lisp-and-die writes the running process's heap to a file and exits. With :executable t the runtime is prepended, so the result is a program that wakes up with that heap already in memory and calls :toplevel, here init-toplevelinitramfs/supervisor.lisp:150.

So the image's contents are fixed when it is saved. Hence a rule from AGENTS.md: anything the image needs must be loaded before the save. The two SBCL contribs (sb-bsd-sockets, sb-introspect) are required by the build script and frozen in, because there are no contrib fasls in the guest. Three things do not survive a save, and the code handles each one:

  • File descriptors. lol.fb caches the open /dev/fb0 and pushes a function on sb-ext:*init-hooks* to forget the cache at startup (*init-hooks*poc/fb.lisp:91).
  • Threads. The net REPL thread is started at run time by start-net-replinitramfs/net.lisp:392, never at build time.
  • The time zone. The image has no zoneinfo, so the build bakes in one UTC offset ((set-utc-offset …) above; systray.org).

Values computed at build time do survive. *sbcl-source-root* (*sbcl-source-root*initramfs/sbcl-source.lisp:35) and *tour-root* (*tour-root*initramfs/tour.lisp:30) both remember a path from the build host, and on the laptop that path exists again under the mounted /home.

load-recording and the registry

The compiled image keeps no source files, and the source locations SBCL records point at the build host. So how does the browser show source? The build loads each module through load-recordinginitramfs/registry.lisp:132 instead of load:

  • The DEFN record: defninitramfs/registry.lisp:22. What counts as a definition: defn-name-and-kindinitramfs/registry.lisp:90. A method is told apart from its siblings by method-labelinitramfs/registry.lisp:77, the one printer shared with model.lisp.
  • A source span runs from the end of the previous form to the end of this one, so the comment above a defun is captured with it.
  • registry.lisp itself is loaded with plain load, because it is the file that defines load-recording. Its last form records its own text (self-recordinitramfs/registry.lisp:369).
Until 2026-10-12, registry.lisp was the one module missing from its own registry. Drilling accept-source showed a "reference — SBCL's own, compiled into the core" view instead of our editable source. Writing the tour found this. The fix is the self-record above, and check-tour.lisp now asserts it in the booted guest.

Load order, and which orderings actually matter

The order below is read from build.sh by regen.lisp. Not every adjacency is a constraint. Here is how each kind of dependency behaves:

If module A…then B must load first?Why
calls B's function (CL-USER, unqualified)NoThe call is resolved when it runs. SBCL only emits a style warning at compile time. A few calls go through (funcall 'name …) to say so on purpose, e.g. the shell calling run-debugger-fb.
expands B's macroYesA macro is expanded when A is compiled. If it is missing, the form compiles as a call to an undefined function. E.g. with-raw-mode (line-editor → repl, fb-browser), with-graphics-console (fb → fb-browser).
writes lol.canvas:draw-string (a package prefix)YesThe reader needs the package to exist to read the symbol at all.
reaches B by name: (find-package "LOL.IMAGE")NoOn purpose, so A still loads when B is absent. See optional-fn in optional-fninitramfs/file-views.lisp:75.
specialises a method on B's class/structYesdefmethod needs the class when it is evaluated.
