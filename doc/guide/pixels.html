Pixels and input

There is no display server, no GPU driver and no font library. The environment draws every pixel itself into a Lisp vector and copies that vector to the screen. Input arrives as bytes on a tty and as 24-byte event records from the kernel. Deep dives: framebuffer.org, fonts.org, input.org, x11.org.

Rendering: one canvas, three ways out

  • Everything on screen is a morph (morphic.org, §12): an object with bounds that draws itself. world-repairpoc/morph.lisp:647 redraws only what is damaged, and in each damaged rect only the morphs over it, back to front from the topmost opaque one. A pane is one of them: a breadcrumb bar (draw-crumbpoc/shell.lisp:1480), the expanded pane's panel (draw-pane-expandedpoc/shell.lisp:1651), or the column beside it — and what is IN a pane, its body, is a morph of its own (a list, a text view, a grid, a stage, a page, a terminal: pane-bodypoc/shell.lisp:143). A key in a text view redraws the lines it changed, nothing else; what else changed is found by each morph's signature (desk-syncpoc/morphic.lisp:1427).
  • make-canvaspoc/canvas.lisp:78, draw-stringpoc/canvas.lisp:464: for each character, paint the pixels the glyph covers, blended over what is there (a TrueType glyph rasterised by poc/ttf.lisp and cached per size; or, for the fallback font, the bits that are on). load-fontpoc/canvas.lisp:418 reads the fallback .lolf blob (magic LF, width, height, then 256 glyphs).
  • draw-listpoc/widgets.lisp:324 returns (values top hits). hits is an alist of the screen y of each painted row and its index. A click is resolved against that map (hit-rowpoc/widgets.lisp:360). The map is needed because section headers make "row N on screen" differ from "item N".
  • tv-drawpoc/textview.lisp:1114 colours Lisp with a small line lexer (lex-linepoc/textview.lisp:1007). The editing keys are in tv-keypoc/textview.lisp:1302. The buffer is a vector of line strings that is replaced on each edit, never mutated in place, so undo just keeps the old vectors (clipboard.org §6½).
  • blit-fbpoc/fb.lisp:104 pins the pixel vector (so the GC cannot move it during the syscall) and issues one pwrite for a full frame. with-graphics-consolepoc/fb.lisp:41 puts the VT in KD_GRAPHICS so the kernel console stops drawing over us.
  • presentpoc/x11.lisp:243 is the host twin: the X11 wire protocol over a Unix socket, written in Lisp. It is deliberately not in the image.
  • The pointer is not part of the frame. put-cursorinitramfs/fb-browser.lisp:1236 composites it on top, and move-cursorinitramfs/fb-browser.lisp:1282 repairs only the old and new rectangles, so moving the mouse never redraws the browser (check-pointer.lisp asserts this).

Input: from a finger to a command

As of the multi-device input work (input.org §4¾, merged 2026-10-12), every keyboard and every pointer is open at once, and devices plugged in later are picked up.

  • Finding devices without udev: scan-input-devicesinitramfs/fb-browser.lisp:218 reads /proc/bus/input/devices, and input-device-kindinitramfs/fb-browser.lisp:392 classifies each one by its bitmasks: :mouse (REL_X), :pad or :tablet (ABS_X, with PROP deciding), :keyboard (EV_KEY + EV_REP, which rules out the power button).
  • The device set: open-input-devicesinitramfs/fb-browser.lisp:1053 opens everything and starts the inotify watch (INOTIFY_USER, tag #26). rescan-input-devicesinitramfs/fb-browser.lisp:1001 keeps the open set equal to what the kernel lists. poll-input-onceinitramfs/fb-browser.lisp:1099 drops a device that reports POLLHUP (unplugged) before anyone reads it.
  • One decoder, many devices: with-device-stateinitramfs/fb-browser.lisp:951 rebinds the decoder's special variables to one device's saved values (progv) for one drain. read-mouse does not know there is more than one device.
  • *fb-mouse* / *fb-kbd* are now the markers :pointers / :keyboards, not fds. (read-mouse *fb-mouse* w h) means "every ready pointer" (read-pointersinitramfs/fb-browser.lisp:1155), so the older loops (debugger, Spotter) did not change.
  • An absolute device reports positions in its own range, read with EVIOCGABS (evdev-abs-rangeinitramfs/fb-browser.lisp:426). A touchpad's motion is integrated as relative (pad-motioninitramfs/fb-browser.lisp:625), and a tap is a click.
  • A press goes to the morph under the pointer, in that morph's coordinates: a tab, a breadcrumb, a window's title bar — or a pane's body, whose press (pane-clickpoc/shell.lisp:3114) decides what was under the pointer from what that body recorded when it last drew: its list rows, its text, its grid's cells. A press on a row that moves is not a click: the hand picks the row's subject up, to be dropped on another morph (world-droppoc/morph.lisp:719).
