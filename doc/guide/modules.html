The module map

Every initramfs/*.lisp and poc/*.lisp module, grouped into layers. The edges are derived from the code: a module uses another when it mentions a name the other one defines. Click a module to see what it uses and what uses it.

This page is generated data. sbcl --script doc/guide/regen.lisp re-scans the source and rewrites deps-data.js. Its header explains the rules for counting a mention: calls and quoted names only, binding positions excluded, strings and comments stripped. The rules lean towards missing an edge rather than inventing one. The layer of each file is a hand-written table in the same script (+layers+). That table is a judgement call. The edges are not.

Reading the map

  • The spine runs registry → model → present → shell → fb-browser → supervisor. Read those six files in that order and you know how the environment works.
  • The toolkit knows nothing about Lisp. canvas, widgets and textview do not use present. The shell adapts between them (item->rowpoc/shell.lisp:992 converts a protocol item into a widget row). That is why the same widgets draw a package, the Spotter and the debugger's restarts.
  • The protocol does not know about pixels. present.lisp uses only model and registry. You can run it at a plain REPL: (show-view (subj-modules)).
  • Late-bound edges are deliberate. For example, the shell calls run-debugger-fb through (funcall 'run-debugger-fb). On the host there is no fb-browser.lisp, and the same shell still runs in an X11 window and in render-frame.
  • Packages. Most of the image lives in CL-USER. The toolkit modules have their own packages (lol.canvas, lol.widgets, lol.textview, lol.fb, lol.clipboard, lol.inflate, lol.image, lol.examples, and host-only lol.x11, lol.scene), so a qualified name like lol.widgets:draw-list tells you which file to open.
