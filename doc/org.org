#+TITLE: Org in the environment — outlines, folding and links, in Lisp
#+STARTUP: showall

Sibling docs: [[file:code-browser.org][code-browser.org]] (the =present= protocol and the accordion an outline is shown in) ·
[[file:file-manager.org][file-manager.org]] (how a file becomes a subject and opens in an editor) ·
[[file:clipboard.org::#undo-other-history-beside][clipboard.org, Undo — the other history beside the kill ring]] (the editor's undo, which this design leans on) ·
[[file:morphic.org::#text-view-damages-rows][morphic.org, A text view damages rows, not the pane]] (per-row damage in a text view, which folding must keep true).

*Status: built.* =.org= files are coloured, folded, navigated by heading, edited by
subtree, have their links followed, and show as a drillable outline. A mention of a
definition (=draw-string=) leads to the live one, and a Lisp source block runs with
=C-c C-c= ([[#live-code-document][Live code in a document]]). It's a stated subset of Org, re-implemented in
Lisp, with every fold, motion, structure edit and result placement checked against
Emacs 30.2 / Org 9.7.11 in batch mode ([[#tests][Tests]]).

* The one-sentence essence

An Org file is *plain text whose structure is in the first characters of its
lines*, so "Org mode" is three things on top of an editor that already exists: a
reader that turns lines into an outline, a *view* of that outline (which the
browser already draws — it's a drill-down), and an editor that can *hide* lines —
the only part that changes how the text view thinks.

* 1. What Org is, and which part of it we implement

** 1.1 Structure as text

Org has no file format beyond text. A line starting with one or more stars and a
space is a /headline/; the number of stars is its /level/; everything up to the
next headline of the same or a higher level is its /subtree/. Nothing marks where a
section ends — the next headline does. So the outline is a function of the lines,
recomputable at any moment, and the file on disk is always what you see with
everything shown.

- *A headline* holds, after the stars: an optional /TODO keyword/ (=TODO=, =DONE=,
  or whatever =#+TODO:= declares), an optional /priority/ (=[#A]=), the title, and
  optional /tags/ (=:lisp:ui:=). Below it may sit a /drawer/ — lines between
  =:PROPERTIES:= and =:END:=.
- *Elements* fill a section, each recognised by how its lines start: a /list item/
  (=- =, =+ =, =1. =), a /table/ row (=|=), a /block/ (=#+begin_src lisp= …
  =#+end_src=), a /keyword/ line (=#+TITLE:=), a /comment/ (=# =), a /fixed-width/
  line (=: =), a rule (=-----=).
- *Objects* sit within the text: links (=[[target][description]]=), emphasis
  (=*bold*=, =/italic/=, =~code~=, ==verbatim==), timestamps.

Emacs's implementation is =org-element.el=, a full parser into a tree of typed
elements; the grammar's authority is Worg's "Org Syntax". We port neither: Emacs
Lisp has a different buffer model, and the full grammar (affiliated keywords, inline
tasks, footnotes, babel headers, LaTeX fragments) is far more than reading and
writing docs needs. Instead we *re-implement a stated subset*, line at a time, pure,
host-tested.

| =[[file:…]]= links              |  1670 | links matter as much as headings            |
| … with a =::search= anchor      |   519 | anchors into code are common                |
| … into an =.org= with =::=      |     3 | heading anchors across files are rare       |
| internal =[[*Heading]]= links   | a few | must work                                   |
| =#+begin_src= blocks            |   116 | colour Lisp inside them                     |
| table rows                      |  1588 | display them; aligning them is out ([[#out-scope-would-cost][Out of scope, and what it would cost]])     |
| TODO/DONE headlines             |     0 | the keywords: cheap, but rarely needed      |
| =:PROPERTIES:= drawers          |     0 | recognise and fold; nothing more            |
| =#+STARTUP:=                    |    31 | =showall= 28, =overview= 1, =showall content= 2 |

*No soft wrap.* 2 048 lines were longer than 100 columns, but 1 179 of those are
table rows, which Emacs doesn't wrap either. The rest are prose and links, and the
text view already scrolls sideways to follow the caret (=tv-hscroll=,
[[file:fonts.org::#font-object-glyph-cache][fonts.org, The FONT object, the glyph cache, and blending]]).

** 1.3 The scope

- *In.* Reading the outline (headlines, levels, keywords, tags, drawers, blocks,
  lists, tables as lines), colouring it, showing it as a drillable subject,
  following links, folding (TAB / S-TAB and =#+STARTUP=), moving between headings,
  editing the structure (new heading, promote/demote, move a subtree, TODO
  cycling), and live code: mentions as links to definitions, and running a Lisp
  source block in the image (Babel's =C-c C-c=, for Common Lisp only).
- *Out* ([[#out-scope-would-cost][Out of scope, and what it would cost]]). Table alignment and formulas, the agenda, export, timestamps
  as dates, capture, clocking, footnotes, inline images, soft wrap; Babel beyond
  =C-c C-c= on a Lisp block.

* 2. What it builds on
:PROPERTIES:
:CUSTOM_ID: builds
:END:

Each of these existed before Org and kept the work small:

- *The text view takes a colouring syntax.* =textview='s =syntax= slot
  ([[file:../poc/textview.lisp::(syntax :lisp)][poc/textview.lisp]]) is =:lisp=, =:plain=, a function =(line-index line) → runs=
  (run panes colour ANSI output this way, [[file:../initramfs/runs.lisp:::syntax (lambda (li line)][initramfs/runs.lisp]]), or a keyword
  registered in =*syntaxes*= ([[#colour-syntax-org][Colour — =:syntax :org=]]).
- *The Lisp lexer is reusable inside a block.* =lex-line= takes and returns the
  paren depth and an open-string flag, so a =#+begin_src lisp= block is coloured by
  threading that state down from its first line.
- *Unchanged lines are shared.* Every edit builds a new line vector but keeps the
  untouched strings =EQ= (=replace-line=, =insert-newline=). Damage
  (=tv-prefix-same-p=) and folding ([[#folds-through-edits][Folds through edits]]) both rely on it.
- *Undo is free.* The buffer is persistent, so a structural command is a new vector
  like any keystroke, and =C-_= takes it back ([[file:clipboard.org::#undo-other-history-beside][clipboard.org, Undo — the other history beside the kill ring]]).
- *A file is a subject.* =subj-file= presents as an editable =:file= view when it's
  text under =+edit-cap+= (2 MiB) ([[file:../initramfs/file-views.lisp::defun file-view][initramfs/file-views.lisp]]); =.org= files get
  =:syntax :org=.
- *The browser is a drill-down.* =present= returns a =view= of items, each carrying
  the subject to present next; =present-preview= is what the nav split shows on
  selection ([[file:../initramfs/present.lisp::defgeneric present-preview][initramfs/present.lisp]]). An outline is exactly that shape.
- *The desk and the Spotter are open.* =desk-ref= / =desk-subject=
  ([[file:../initramfs/desk.lisp::defun desk-subject][initramfs/desk.lisp]]) save tabs as references and rebuild them through a
  whitelist; =*spotter-sources*= lets a module add candidates.
- *Links are already checked.* [[file:../check-links.sh][check-links.sh]] resolves every =[[file:…]]= and its
  =::search= anchor (as a substring of the target). The link resolver ([[#links][Links]])
  follows the same rule, so a link that passes the check also opens.
- *One place for an editor's keys.* =edit-pane-command= ([[file:../poc/shell.lisp::defun edit-pane-command][poc/shell.lisp]]) handles
  prefixes (=C-c=, =C-x=, =C-x r=), the clipboard keys, Tab as completion, and the
  rest goes to =tv-key=. There's no per-mode keymap, so Org gets a hook there ([[#key-hook][A key hook]]).

* 3. The reader — =lol.org=
:PROPERTIES:
:CUSTOM_ID: reader-lol-org
:END:

A pure package, [[file:../poc/org.lisp][poc/org.lisp]], in the shape of =poc/clipboard.lisp=: no

** 3.1 Lines first
:PROPERTIES:
:CUSTOM_ID: lines-first
:END:

Every line is classified on its own by its first characters — headline, keyword,
block begin/end, drawer begin/end, list item, table row, comment, fixed-width,
rule, blank, paragraph. Only blocks need state across lines: inside one, a line
starting with =#+= or =:= is code, not a keyword or a drawer. So the reader is one
pass carrying one variable: "inside which block, if any".

*A =* = line inside a block IS a headline*, and ends the block. That's Org's rule
(Org 9.7.11 lists =* not-a-heading?= inside a =#+begin_src= as a headline), and why
Org asks you to escape such lines with a comma (=,* x=).
[[file:../poc/org.lisp::defun analyze-uncached][=analyze-uncached=]] does the same, and [[file:../poc/org-test.lisp][poc/org-test.lisp]] asserts it.

** 3.2 The outline is an index, never a copy
:PROPERTIES:
:CUSTOM_ID: outline-index-never-copy
:END:

=analyze= returns, for a line vector, a vector of =headline= structs:

| slot          | meaning                                                 |
|---------------+---------------------------------------------------------|
| =line=        | its line index                                          |
| =level=       | the number of stars                                     |
| =keyword=     | =TODO=/=DONE=/… or NIL                                  |
| =priority=    | a character or NIL                                      |
| =title=       | the text, without stars, keyword, priority or tags     |
| =title-start= | the column the title starts at                          |
| =tags=        | a list of strings                                       |
| =end=         | the first line *after* its subtree                      |

The buffer stays the line vector the text view already edits. The outline is
*derived*, recomputed when the vector changes, so it can never disagree with the
text. The result is *cached on the vector* (=EQ=): one pass per edit, shared by
every read in a frame.

*Measured* (host): a pass over =code-browser.org= (2 592 lines) takes 0.9 ms; the
slowest over 32 =.org= files is 4 ms (=poc/org-test.lisp= prints it).

** 3.3 Objects within a line
:PROPERTIES:
:CUSTOM_ID: objects-within-line
:END:

=line-objects= scans a line for links, emphasis and inline code, for the colourer
([[#colour-syntax-org][Colour — =:syntax :org=]]) and for "what link is at the caret" ([[#links][Links]]).

- *Emphasis boundaries.* A marker counts when the character before it is space or
  punctuation and the one after isn't space — Org's rule, loosely; the test notes
  where it differs.
- *The object that opens first wins*, reading left to right as Org does. So
  verbatim text that opens before a =[[= hides the link — what lets a doc show a
  link's /syntax/ inside =verbatim= markers without it being listed as a link.
- *No nesting.* A link inside bold isn't seen (Org would nest them; this flat list
  doesn't).

* 4. Seeing an Org file
:PROPERTIES:
:CUSTOM_ID: seeing-org-file
:END:

** 4.1 Colour — =:syntax :org=
:PROPERTIES:
:CUSTOM_ID: colour-syntax-org
:END:

=file-view= gives =.org= files =:syntax :org=. The colouring =org-runs=
([[file:../poc/org-mode.lisp][poc/org-mode.lisp]]) colours headlines by level (three palette colours, the stars
dimmed), keywords, tags, links (description in the link colour, brackets dimmed),
=~code~= and ==verbatim==, keyword lines and comments in the gutter colour, blocks
— and Lisp inside =#+begin_src lisp= by =lex-line=. The palette is the semantic one
([[file:code-browser.org][code-browser.org]]); nothing is highlighted in the accent.

*Why a registered keyword, not a function.* A line's colour depends on other lines
(the block it's in), so a function of =(line-index line)= isn't enough. A syntax
can be a keyword registered in =lol.textview:*syntaxes*=, whose function is called
with the whole line vector; it reads the cached analysis ([[#outline-index-never-copy][The outline is an index, never a copy]]). The view's syntax
stays the printable =:org=.

** 4.2 The outline as a subject — =subj-org=

The browser's native gesture is the drill-down, and an outline /is/ one. So an Org
file has a second face beside its editor:

- *=(subj-org path)=* presents the file's top-level headings as rows (child count,
  tags, line), plus "Edit the file".
- *=(subj-org path titles)=* is one heading, named by its *chain of titles* from the
  top. It lists "Edit here" (the editor at that line), its child sections, its
  links as rows that open them, and the definitions its section mentions ([[#mentions-live-code][Mentions — =name= is the definition]]).
- *Previews read the document.* A heading's =present-preview= is the section's own
  text (up to 400 lines), read-only and coloured — so moving down an outline reads
  the document in the nav split, and drilling goes deeper.
- *Commands.* A heading offers "Open the file" and "The whole outline"; an =.org=
  file pane or row offers "Outline" (=C-c C-j=).
- *The desk* saves =(:org path)= or =(:org path titles)=. Saving by titles, not
  line number, means a desk saved before the file was edited still finds the
  heading; one that's gone says so and offers the whole outline.
- *The Spotter's "headings"* lists every heading of the Org files open in a tab
  (not every =.org= on the disk).

** 4.3 Links
:PROPERTIES:
:CUSTOM_ID: links
:END:

=C-c C-o= on a link (and a click in the outline view) opens it the way Org does,
for the forms we write:

| link                         | opens                                                    |
|------------------------------+----------------------------------------------------------|
| =file:path=                  | =subj-file= of the path, resolved from the file's folder |
| =file:path::*Heading=        | that file, at the heading with that title                |
| =file:path::text=            | that file, at the first line containing /text/ — the rule =check-links.sh= checks |
| =file:x.lisp::defun NAME=    | the *live definition* (source, Accept, Senders), when the registry has exactly one named NAME; else as above |
| =file:path::NNN=             | that file, at line NNN                                   |
| =file:path::#id=             | that file, at the heading whose =CUSTOM_ID= property is /id/ |
| =*Heading=                   | the heading in this file                                 |
| =#id=                        | the heading in this file with that =CUSTOM_ID=           |
| =https:= / =http:=           | a web tab ([[file:web-browser.org][web-browser.org]]) |

A target into =./linux= or =./sbcl= works when the tree is reachable (e.g. under the
mounted =/home=; [[file:storage.org][storage.org]]). A link that doesn't resolve says so in the
status line. Implementation: =org-follow-link=.

*** Links outside Org files

Code cites a doc section with a *plain link* — no brackets, the way Org itself reads
=file:...= in running text:

#+begin_src lisp
;;; The layout is in file:../doc/containers.org::#layout
#+end_src

- *Any text pane.* =C-c C-o= on such a link in a Lisp or C file, or in a definition's
  source pane, follows it like Emacs's =org-open-at-point-global=. Without a link
  under the caret the chord stays the pane's own (a conversation opens a tool call).
- *Relative to the source.* The path resolves from the file the text came from: a
  file pane's file, or for a definition the source file it was built from
  (=pane-source-file=). The Workspace has no file, and says so.
- *Ids, not numbers.* A section is cited by its =CUSTOM_ID=, so reorganising a doc
  never breaks the citation; =check-links.sh= resolves every one and refuses a
  section number (=x.org §4=) in code.
- *Plain links end* at a blank or a closing bracket or quote; trailing punctuation
  belongs to the sentence (=line-file-links= in [[file:../poc/org.lisp][=poc/org.lisp=]]).

* 5. Folding — the one change to the text view
:PROPERTIES:
:CUSTOM_ID: folding-change-text-view
:END:

** 5.1 What had to change

Without folding a screen row shows buffer line =tv-scroll + row=. With hidden lines,
row ↔ line goes through a *display map*. Inside [[file:../poc/textview.lisp][poc/textview.lisp]] that touches
drawing, motion, paging, the wheel, hit testing (=line-at-y=, =tv-pos-at=),
=tv-row-keys=, =tv-row-rect= and the scroll thumb. Outside it, callers that computed
a row from =tv-scroll= themselves (in =poc/morphic.lisp= and =poc/shell.lisp=) now
ask the text view. A run pane never folds, so =initramfs/runs.lisp='s arithmetic
stays right.

** 5.2 The display map

- *One new slot, =hidden=*: NIL (nothing folded — every existing view, at no cost)
  or a bit vector over the buffer's lines.
- *A =rows= vector* of visible line indices is built on demand and cached against
  the =(lines, hidden)= pair. =tv-scroll= counts *rows*.
- *Two functions answer every caller*: =line-row= (buffer line → row) and
  =row-line=. A hidden line maps to the row of the visible line above it. With
  =hidden= NIL both are the identity, so nothing that doesn't fold notices.
- *Damage needs no new rule.* A folded heading is drawn with Org's ellipsis, =...=,
  and the ellipsis is part of the row's key, so per-row damage repairs a heading
  when it folds or opens. Rows below a fold show different lines, which
  =tv-row-keys= already detects (each key carries its line index and text).
  =poc/morphic-test.lisp='s invariant — the incremental repair equals a fresh paint
  — is the test.

** 5.3 Folds through edits
:PROPERTIES:
:CUSTOM_ID: folds-through-edits
:END:

Fold state is per heading, but headings move when lines are inserted above them.
The bits follow the text *lazily*: they're spliced when the view next looks at them
after an edit, not by each edit, so the text view needn't know which command
edited it.

- *Prefix and suffix.* The old and new line vectors share an =EQ= prefix and
  suffix; the bits are spliced between them (an O(n) comparison).
- *Moved lines keep their bit.* A line in between keeps the bit of the identical
  (=EQ=) string it was, so a folded subtree moved by =M-<down>= stays folded.

** 5.4 The rules, taken from Org
:PROPERTIES:
:CUSTOM_ID: rules-taken-org
:END:

- *The caret never sits in hidden text.* Motion skips hidden lines. A command that
  lands inside a fold — a link, the outline view's "Edit here", an isearch match —
  opens the folds on the way, as Emacs's =org-reveal= does (=reveal-line=).
- *TAB on a headline* cycles that subtree: FOLDED → CHILDREN → SUBTREE → FOLDED
  (=cycle-subtree=). Elsewhere TAB keeps doing what it does (completion).
- *S-TAB* cycles the buffer: OVERVIEW (level 1 only) → CONTENTS (all headlines) →
  SHOW ALL (=cycle-global=).
- *=#+STARTUP:=* chooses the state on open: =overview=, =content=, =showall=,
  =showeverything=. With none, Org's default =org-startup-folded= is
  =showeverything=. Applied as the pane opens, through =*pane-opened-hooks*=
  (=org-prepare-pane=), not at the first key.
- *Drawers and blocks* fold on TAB on their first line.
- *Fold state is per pane*, not saved by the desk; =#+STARTUP= decides on each
  open.

*Edits near hidden text* follow Org's =org-fold-catch-invisible-edits= default,
=smart=: the fold is opened, and the edit goes through only when it's next to
visible text, never deleting a hidden character. =org-guard-hidden= implements it:

- *Delete, =C-d= or =C-k= at the end of a folded line* opens the fold and is
  refused once.
- *Backspace at the start of the line after a fold* does the same.
- *Enter at the end of a folded headline* opens the fold first.
- *Typing on the folded line itself* goes through.

A refused edit says why in the status line.

* 6. Moving and editing
:PROPERTIES:
:CUSTOM_ID: moving-editing
:END:

** 6.1 A key hook
:PROPERTIES:
:CUSTOM_ID: key-hook
:END:

=edit-pane-command= offers every key to =org-key= ([[file:../poc/org-mode.lisp][poc/org-mode.lisp]]) first when
the pane's syntax is =:org=; it returns true if it took the key. A general per-mode
keymap would be cleaner, but this single hook is enough.

Every structural command is a line-vector function in =lol.org= (=promote-subtree=,
=move-subtree-up=, =insert-heading=, =cycle-todo=, …) that returns a new vector —
pure and host-tested — and the shell only installs the result. Undo comes free
([[#builds][What it builds on]]).

** 6.2 The keys
:PROPERTIES:
:CUSTOM_ID: keys
:END:

Org's own bindings:

| key                  | Org command               | does                                          |
|----------------------+---------------------------+-----------------------------------------------|
| =TAB= on a headline  | =org-cycle=               | fold cycle ([[#rules-taken-org][The rules, taken from Org]])                             |
| =S-TAB=              | =org-global-cycle=        | buffer cycle                                  |
| =C-c C-n= / =C-c C-p=| next / previous heading   | any level, visible ones                      |
| =C-c C-f= / =C-c C-b=| forward / backward, same level |                                         |
| =C-c C-u=            | up to the parent heading  |                                              |
| =C-c C-j=            | =org-goto=                | "Goto heading:" in the minibuffer, Tab completes titles |
| =M-RET=              | =org-meta-return=         | new heading (or list item) at this level     |
| =M-←= / =M-→=        | promote / demote          | the heading alone                             |
| =M-S-←= / =M-S-→=    | promote / demote subtree  |                                               |
| =M-↑= / =M-↓=        | move subtree              | past its sibling                              |
| =C-c C-t=            | =org-todo=                | cycle TODO → DONE → none                      |
| =C-c C-o=            | =org-open-at-point=       | follow the link ([[#links][Links]])                        |
| =C-c C-l=            | =org-insert-link=         | minibuffer for target, then description       |
| =C-c C-c= in a src block | =org-babel-execute-src-block= | run a Lisp block, write its results ([[#running-src-block][Running a source block]]) |
| =M-.= / =M-,= on =name= | (the shell's)         | the definition / its senders ([[#mentions-live-code][Mentions]]) |

- *=C-c C-j=* is Org's =org-goto= minus its outline buffer, which the outline subject
  already is.
- *=M-RET='s blank line* follows one case of Org's =auto= rule: a blank line before
  the new heading when the headline whose level it copies has one before it. Org's
  full heuristic isn't reproduced.
- *The cheatsheet* (=SuperL-?=) has an "Org files" group.

** 6.3 The keys on the console
:PROPERTIES:
:CUSTOM_ID: keys-console
:END:

On the bare framebuffer the keys come through the Linux console's keymap
([[file:input.org::#tty-enough][input.org, Why the tty is not enough]]), which needed three fixes in [[file:../initramfs/fb-browser.lisp][fb-browser.lisp]]:

- *Alt-arrows.* Kernel 7.2's console already sends a cursor key with its modifiers,
  xterm's way (=ESC [ 1 ; 3 A= for Alt-Up), and falls back to the plain map when a
  modifier has no table (so Alt-Shift-arrows arrive as =ESC [ 1 ; 4 x=). Only
  Alt-Left/Right needed work: the default keymap gives them to VT switching, so
  =unbind-console-alt-arrows= rebinds them to the cursor keys.
- *=S-TAB=* arrives as a plain Tab; its Shift comes from the keyboard's evdev,
  folded in as for every key. (Under X it's =ISO_Left_Tab=.)
- *=M-RET=* is =ESC CR=, which the key decoder now keeps.

*Ruled out:*

- *Reading Alt-Left/Right from the evdev.* Alt-Shift-Right then acted twice.
- *=K_HOLE= instead of =K_LEFT= in the keymap.* The kernel's fallback never matches
  a hole set by ioctl, because entries are stored as =val ^ 0xf000=; Alt-Left then
  sent nothing.

* 7. Live code in a document
:PROPERTIES:
:CUSTOM_ID: live-code-document
:END:

A doc in this project is about code that is *running* in the image it's read in.
Two things connect them: a mention of a definition leads to the definition, and a
Lisp source block can be run where it stands. This is the first part of the
"live documents" horizon in [[file:code-browser.org::#horizon-live-documents-browsable][code-browser.org, Horizon — live documents & browsable third-party code]].

** 7.1 Mentions — =name= is the definition
:PROPERTIES:
:CUSTOM_ID: mentions-live-code
:END:

A doc names code in inline code: =draw-string=, ~tv-scroll~, =lol.org:analyze=. That
markup is already the link; nothing has to be written differently.

- *=M-.=* on it opens the live definition (source, Accept, Senders) and *=M-,=* its
  senders, as on a word in Lisp source. So does Ctrl-click. In an Org pane they
  read the inline code under the caret (=code-at= in [[file:../poc/org.lisp][=poc/org.lisp=]]), markers
  and all, before falling back to the word as Lisp. The shell asks through
  =*mention-at-point*= ([[file:../poc/shell.lisp][=poc/shell.lisp=]]), which =org-mode.lisp= sets.
- *A heading's view* lists the definitions its section mentions, as rows under
  "code it mentions", once each in reading order, with their kind, file and line.
  So drilling a doc's outline reaches the code it explains. Lines inside blocks
  are skipped: they are code, not mentions.
- *What a name resolves to* (=mention-symbol=). First the way the shell reads a
  word: the pane's package, =CL-USER=, =CL=, with =pkg:name= honoured. Failing that,
  the registry's definitions in *every* package, when exactly one symbol has that
  name. A doc writes =tv-scroll=, not =lol.textview:tv-scroll=, and that is enough.
  A name two packages define is ambiguous and names nothing.
- *What names nothing:* a keyword (=:org=), =t= and =nil=, a form (=(present x)=), a
  path (=/dev/fb0=), a phrase, and a word with no letter in it. Docs write =+= and
  =-= for keys, not for the functions.

Measured on the docs themselves: [[file:fonts.org][fonts.org]] mentions 41 definitions this way,
[[file:morphic.org][morphic.org]] 146.

** 7.2 Running a source block — =C-c C-c=
:PROPERTIES:
:CUSTOM_ID: running-src-block
:END:

=C-c C-c= with the caret anywhere in a =#+begin_src lisp= block (its marker lines
included) is Org Babel's =org-babel-execute-src-block=, for Common Lisp only:

1. *It asks first*, as Org does by default (=org-confirm-babel-evaluate=): "Evaluate
   this lisp code block in the image? (y/n)". A file may come from anywhere. The
   setting =:org-confirm-evaluate nil= in =~/.lol/settings= stops the asking.
2. *The block's forms are read and evaluated in this image*, one after another, by
   the Workspace's =ws-eval=: an error goes to the status line and is never thrown,
   and the compiler's notes follow the message. Nothing is written for an error.
3. *The result is written where Org writes it* (=insert-results=), and =C-_= takes
   that back in one step.

Header arguments (=header-args=):

| argument            | does                                                         |
|---------------------+--------------------------------------------------------------|
| (none) / =:results value= | the last form's value is the result                    |
| =:results output=   | what the forms printed is the result                         |
| =:results silent= / =none= | the value goes to the status line; nothing is written |
| =:package NAME=     | the forms are read and evaluated in that package (Org's ob-lisp has it too) |

*The rules for where a result goes* were taken from Emacs, not guessed:
[[file:../poc/org-data/babel-probe.el][=poc/org-data/babel-probe.el=]] runs =org-ctrl-c-ctrl-c= on 22 fixtures and prints the
buffer, and [[file:../poc/org-test.lisp][=poc/org-test.lisp=]] reproduces each answer.

- A *blank line*, then =#+RESULTS:=, then the result, right under =#+end_src=. One
  more blank line follows when text came right after the block.
- *Results already there are replaced.* "There" means the first thing after the
  block, past blank lines, is a =#+RESULTS:= line. Its element is replaced: a run
  of =:= lines, a table, an example block, a drawer. What follows it stays as it
  was. A paragraph under =#+RESULTS:= isn't a result, and stays.
- *The text of a result.* A string is itself, without quotes. =nil= or an empty
  string is a bare =#+RESULTS:=. Trailing newlines are dropped. Fewer than 10 lines
  become =: = fixed-width lines (a blank line is =: = with its space). 10 or more
  become a =#+begin_example= block, where a line that would read as a headline or
  a =#+= keyword gets a comma (Org's =org-escape-code-in-string=).
- A block named by =#+name: foo= writes =#+RESULTS: foo=. An indented block gets
  indented results.

*Where we differ, on purpose:*

- *A list is printed, not made into a table.* Org's default turns =(1 2)= into
  =| 1 | 2 |=. Here every value other than a string is printed readably (=prin1=,
  pretty, 78 columns): Org's =:results verbatim=. A table can't be read back as
  the value it came from.
- *Only Common Lisp runs* (=lisp=, =common-lisp=, =cl=). An =emacs-lisp= or =sh=
  block says so. Emacs Lisp is coloured as Lisp but isn't Common Lisp.
- *No sessions, no =:var=, no other header arguments.* Every block runs in the one
  image, so state already persists between blocks, as in Org's =:session=.

* 9. Out of scope, and what it would cost
:PROPERTIES:
:CUSTOM_ID: out-scope-would-cost
:END:

- *Tables*: aligning on TAB and =C-c C-c=, column motion, formulas. Alignment alone
  is about 300 lines (width of each cell, rewrite the rows — the narrow part of
  =org-table.el=); formulas are a calculator.
- *Soft wrap* ([[#sizing-subset][Sizing the subset]]): the display map of [[#folding-change-text-view][Folding — the one change to the text view]] is the hard half; wrapping a line into
  several rows is the other.
- *More of Babel* than =C-c C-c= on a Lisp block ([[#running-src-block][Running a source block]]): other
  languages (a shell block could run in the container, [[file:containers.org][containers.org]]), =:var=,
  =:session=, tables as results, =C-c C-v= keys, tangling. Each is small alone;
  none was needed by a doc here.
- *Agenda, capture, clocking, timestamps as dates, export, footnotes, inline
  images.* Each is an application on top of the outline. Inline images would be
  cheaper than most, since =lol.image= already decodes the formats.

*Known limits:*

- *The outline is of the file on disk.* An open editor's unsaved edits aren't in
  the outline view until =C-x C-s=.
- *A section preview numbers its lines from 1*, not from where the section starts
  (the gutter has no offset); the preview's title says the real line.
- *Nested objects* (a link inside bold) aren't seen ([[#objects-within-line][Objects within a line]]).
