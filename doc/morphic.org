#+TITLE: Morphic — the browser as the first window of a Lisp window system
#+STARTUP: showall

The code browser runs on a small Morphic: everything on screen is a CLOS object with
bounds that draws itself and takes events, in one tree, driven by one loop. Tabs,
panes, a pane's list or text view, windows, menus and the debugger are all morphs.
Windows overlap, damage is repaired per morph, live panes step themselves, and a
subject can be dragged from one morph and dropped on another.

*Status: built.* This is Phase 7 of the code browser ([[file:code-browser.org][code-browser.org]], "Phases").
What's not built is in [[#known-limits][Known limits]].

Code: [[file:../poc/morph.lisp][poc/morph.lisp]] (=lol.morph=, the backend-blind core),
[[file:../poc/morphic.lisp][poc/morphic.lisp]] (the desk: the shell as morphs, windows, layout, damage, drag and
drop), [[file:../poc/overlays.lisp][poc/overlays.lisp]] (modal cards as overlay morphs),
[[file:../poc/shell.lisp][poc/shell.lisp]] (the =pane= and its bodies), [[file:../initramfs/fb-browser.lisp][fb-browser.lisp]] (the guest's loop) and
[[file:../poc/run-browser.lisp][run-browser.lisp]] (the X11 host's). Claims about Self and Squeak below come from the
literature, not from a running Squeak image.

* 1. What Morphic is

Morphic is the user interface of Self (Maloney and Smith, /Directness and Liveness
in the Morphic User Interface Construction Environment/, UIST 1995), carried into
Squeak by John Maloney and still the ground Pharo stands on. Its ideas, in the
vocabulary this doc uses:

- *A morph* is an object that's on screen. It has *bounds* (a rectangle), an
  *owner* and *submorphs* (a tree), and it answers two kinds of message: /draw
  yourself/ and /here is an event/. A button, a text editor, a window and a sprite
  are all morphs; they differ only in which methods they override.
- *The World* is the root morph: the whole screen. The order of its children is the
  *z-order*: later is on top.
- *The Hand* is the pointer, as a morph. It carries what you're dragging and offers
  it to whatever is under it when you let go.
- *Damage.* A morph that changes says which rectangle of the screen is now wrong
  ("invalidate"). Once per cycle the World redraws only those rectangles, and in each
  only the morphs that overlap it. That's what makes overlapping windows affordable.
- *Stepping.* A morph may ask to be stepped every N milliseconds. That's how things
  move on their own, with no thread per morph.
- *The halo.* A ring of handles around any morph — move, resize, inspect — on any
  morph, including ones nobody wrote handles for. There's no separate "edit mode":
  the running UI is the thing you edit.

The project's slogan, from [[file:code-browser.org::#framebuffer-x-question-answered][code-browser.org, Framebuffer or X? — the question, answered]]: /Smalltalk was never an X
application; Smalltalk was the window system./ This is that sentence taken literally.

* 2. The design
:PROPERTIES:
:CUSTOM_ID: design
:END:

** 2.1 Principles
:PROPERTIES:
:CUSTOM_ID: principles
:END:

- *Morphs are CLOS objects.* =morph= is a =standard-class=, so the model layer, the
  Inspector, =all-instances= and the halo understand it with no extra code.
- *The World owns the one event loop.* Poll, turn input into events, dispatch, step,
  repair damage, present. There are no nested modal loops: a menu waits by turning the
  same loop ([[#overlays-modal-cards-loop][Overlays: modal cards in the one loop]]).
- *Everything on screen is a morph.* There's one way to be on screen, not a tree of
  morphs around a monolithic painter. The tab strip, a breadcrumb, a pane, the list
  inside it and a window's title bar each draw themselves, take their own events and
  are damaged on their own.
- *Content stays pure.* =present= is still a pure =subject → view= and =commands-for=
  still /declares/ affordances. Morphs are the shell's side of "content proposes, the
  shell disposes".
- *Not a compositor.* It composes Lisp objects in one process, never other
  processes' pixels ([[file:processes.org][processes.org]] says why), and it's no retained scene graph of
  every glyph.

The rendering budget made this cheap to adopt: before Morphic a whole frame at
1920×1200 cost about 5 ms (=draw-browser= 3.92 ms + =present-fb= 1.12 ms,
[[file:framebuffer.org][framebuffer.org]], tag #24) and a pointer move 6 µs. Damage repair is about keeping a
window drag cheap and making room for many live morphs, not about rescuing a slow
renderer.

** 2.2 Choices and their reasons

- *Tiled by default.* Until you tear a trail off, the screen looks like the plain tiled
  shell. Windows are opt-in.
- *Opaque drag.* A window's contents move with the pointer. Every mainstream desktop
  drags opaque by default (macOS, Windows since the late 1990s, GNOME and KDE); outline
  dragging is what slow machines did, because repainting what the window uncovered was
  too expensive. Squeak's Morphic drags the morph itself. Here a moved window is a copy
  of its backing store ([[#surfaces][Surfaces]]), well under a millisecond ([[#costs][What it costs]]).
- *Keyboard first, still.* Every window operation has a key ([[#keys-gestures][Keys and gestures]]); the mouse is an
  accelerant. Every window key is in the =SuperL-?= cheatsheet, group "Windows".
- *A minimal title bar* in the tab strip's own style ([[#window][What a window is]]).

* 3. The core: =lol.morph=
:PROPERTIES:
:CUSTOM_ID: core-lol-morph
:END:

[[file:../poc/morph.lisp][poc/morph.lisp]] knows nothing about the browser. It's the toolkit; [[file:../poc/morphic.lisp][poc/morphic.lisp]]
builds the browser's morphs on it, in =CL-USER= beside the shell.

** 3.1 =morph=

[[file:../poc/morph.lisp::defclass morph ()][=morph=]] has =bounds= (=(x y w h)=), =owner=, =children= (back to front: the last is on
top), =step-ms= (NIL: never stepped), =subject= (what it shows, if anything), and a
=draws= counter the damage tests read. Its generic functions:

| generic             | does                                                                                 |
|---------------------+--------------------------------------------------------------------------------------|
| =draw-morph=        | paint yourself; the canvas is already clipped to the damaged rect                    |
| =handle-event=      | take an event; NIL lets it bubble to the owner                                       |
| =step-morph=        | liveness; =invalidate= if you changed                                                |
| =morph-affordances= | the halo's handles on this morph                                                     |
| =morph-opaque-p=    | does it paint every pixel of its bounds? (repair starts at the topmost opaque cover) |
| =morph-hit-p=       | is a point /on/ it? default: in its bounds; a window's frame is hit only at its grip |
| =drop-morph=        | the hand let go of this morph after carrying it                                      |
| =accept-drop=       | will you take what the hand carries? ([[#dropping][Dropping]])                                          |

Two rules:

- *Bounds are world coordinates*, never owner-relative, as in Squeak. Hit testing and
  damage compare plain rectangles with no transform stack. Moving a morph offsets its
  subtree's bounds.
- *=subject= is a slot, not a subclass.* A morph that shows a subject keeps it; the
  =pane= class merges its own =subject= slot with this one (a CLOS slot specifier of the
  same name merges), so there's one record of what a pane shows.

** 3.2 =world= and =hand=

A [[file:../poc/morph.lisp::defclass world (morph)][=world=]] is a morph the size of the screen plus the loop's state: the damage list,
the keyboard focus, each stepping morph's deadline, and the hand.

The [[file:../poc/morph.lisp::defclass hand (morph)][=hand=]] is *not* drawn into the canvas. The arrow is composited as a patch after
the frame ([[file:framebuffer.org::#pointer-part-frame][framebuffer.org, The pointer is not part of the frame]]), so a bare pointer move costs microseconds and
repairs nothing. What the hand holds:

- *=hand-capture=* — the morph the last press went to. Its drag and its release go
  there too, wherever the pointer wanders.
- *=hand-carrying=* — a morph being moved or resized (a window), with its grab offset.
- *=hand-press=* — the press in progress, described by the morph that took it ([[#press-progress][The press in progress]]).
- *=hand-clicks=* — the last press, from which [[file:../poc/morph.lisp::defun hand-count-click][=hand-count-click=]] counts a double or
  triple click.
- *A payload* — a subject picked up to be dropped (=hand-carry-payload=, [[#hand-press-progress-drag][The hand: the press in progress, drag and drop]]).

** 3.3 Events and dispatch
:PROPERTIES:
:CUSTOM_ID: events-dispatch
:END:

One event struct, built from what the backend's loop decodes:

| kind        | from                                   | carries                           |
|-------------+----------------------------------------+-----------------------------------|
| =:key=      | the tty / the keyboard's evdev         | key, modifier state (=super-p= …) |
| =:down/:up= | evdev buttons, the pad's emulated ones | button, x, y, click count         |
| =:move=     | evdev =REL/ABS=                        | x, y, buttons held                |
| =:wheel=    | =REL_WHEEL=                            | notches, x, y                     |
| =:service=  | an =*fb-services*= fd woke the poll    | which service                     |

[[file:../poc/morph.lisp::defun world-dispatch][=world-dispatch=]] routes them:

- *Keys go to the focus* and bubble up through the owners.
- *Pointer events go to the topmost morph under the point* (=morph-at=, a back-to-front
  walk asking =morph-hit-p=) and bubble likewise.
- *A press's drag and release go to its capture.* A morph carried with no button held
  (the halo's Move) is put down by the next press, which belongs to the hand, not to
  the morph under it.
- *Each morph gets the event in its own surface's coordinates* (=localize-event=). The
  event also carries its screen point (=wx=, =wy=) for things placed on the screen, like
  a menu card or the halo.

A bare pointer move is an event too; it damages nothing.

** 3.4 Surfaces
:PROPERTIES:
:CUSTOM_ID: surfaces
:END:

A [[file:../poc/morph.lisp::defclass surface (morph)][=surface=]] draws its subtree into a *backing store* of its own — a canvas its
size — which the world then copies onto the screen. A window is a surface.

- *Descendants draw and take events in surface coordinates*: the surface's top-left is
  their 0,0. Their bounds stay world coordinates, so =morph-at= and damage still compare
  plain rectangles (=morph-local-bounds=, =morph-surface=).
- *Moving a surface is a copy.* It offsets its subtree's bounds and changes nothing in
  its canvas or in anything recorded in it, so the repair blits the store at the new
  place and redraws nothing inside.
- *Damage inside a surface goes to both places.* =invalidate= on a morph inside one
  damages its rect on screen /and/ in the surface's canvas. A key in a window's pane
  redraws that pane in the backing store ([[file:../poc/morph.lisp::defun surface-refresh][=surface-refresh=]]) and copies that rect
  out, not the whole window.

This differs from Squeak, which draws a morph straight onto the screen. The backing
store is what makes opaque drag nearly free.

* 4. Drawing and damage
:PROPERTIES:
:CUSTOM_ID: drawing-damage
:END:

** 4.1 The canvas clip rectangle
:PROPERTIES:
:CUSTOM_ID: canvas-clip-rectangle
:END:

Damage repair needs every pixel writer to stay inside the rect being repaired, or a
pane redrawing itself would scribble over a window above it.
[[file:../poc/canvas.lisp::defmacro with-clip][=with-clip=]] in [[file:../poc/canvas.lisp][canvas.lisp]] provides it:

- *Half-open edges.* The canvas carries the clip's edges as =x0 <= x < x1=, the form a
  fill loop wants. A fresh canvas clips to itself, so code that never says =with-clip=
  behaves as before.
- *Clips nest by intersection.* A body can't widen the clip it was given, and
  =unwind-protect= puts it back, so a debugger restart out of a drawing function can't
  leave the screen half-clipped.
- *Every writer honours it*: =fill-rect=, =draw-rect=, =draw-line=, =draw-poly=,
  =draw-circle=, =blit-rgba=, both glyph blitters, the modal [[file:../poc/widgets.lisp::defun scrim][=scrim=]], a web frame
  ([[file:../initramfs/web.lisp::defun web-blit][=web-blit=]]) and an image pane's picture ([[file:../poc/shell.lisp::defun draw-image-body][=draw-image-body=]]), the last two
  through =blit-pixels=. The halo's [[file:../poc/shell.lisp::defun spotlight][=spotlight=]] puts back rows it copied itself
  (rewriting a pixel's own value is harmless), and the pointer patch
  ([[file:../initramfs/fb-browser.lisp::defun put-cursor][=put-cursor=]]) only /reads/ the canvas.
- *Off-clip lines are skipped.* A =draw-string= whose line lies wholly above or below
  the clip returns at once, with a full cell of margin either side.

*The rule for code outside canvas.lisp: copy pixel vectors with =blit-pixels= (or
=blit-canvas=), never by indexing =canvas-pixels=.* A writer that indexes the vector
itself escapes the clip. =blit-pixels= is a =REPLACE= per row, so it costs nothing.

** 4.2 The cycle and the repair
:PROPERTIES:
:CUSTOM_ID: cycle-repair
:END:

#+begin_example
poll → events → dispatch → step due morphs → layout (desk-sync) → damage list
     → for each rect: with-clip, draw every morph overlapping it, back to front
     → send each rect to the screen → put-cursor
#+end_example

- *=invalidate morph [rect]=* pushes a rect (default: the morph's bounds) onto the
  world's damage list. =add-morph=, =remove-morph= and =set-morph-bounds= damage the old
  and new bounds themselves.
- *Repair starts at the topmost opaque morph covering the rect.* Nothing under it can
  show. That's why a moved window costs a copy, not a repaint of the shell beneath it.
- *Rects merge only when they overlap.* A window moved down a few pixels leaves a thin
  strip /touching/ its new bounds; merged, they'd be a window and a half of shell to
  redraw, while apart they're a strip of shell plus a window-sized copy. More than 16
  rects (=+max-damage-rects+=), or one covering the screen, become one full repair.
- *The world lays out first.* =world-before-repair= is where the desk runs
  =desk-sync= ([[#layout-container-s-policy][Layout is a container's policy]]), so a change made from the net REPL, the agent's thread or a
  service is laid out and found by its signature ([[#damage-per-morph][Damage per morph]]) at the next repair, with nobody
  having to announce it.
- *[[file:../poc/morph.lisp::defun world-repair][=world-repair=]] returns the rects it drew*; the backend sends just those.
  =world-last-repair= records, per rect, which morphs drew in it (=:per-rect=) — the
  tests' instrument.
- *[[file:../poc/morph.lisp::defun world-paint][=world-paint=]]* draws the whole tree once; =:fresh= draws every surface anew rather
  than copying its store. That's what the tests compare an incremental repair against.
  =draw-browser= survives only as a name for "paint the whole world afresh".

** 4.3 Painted rects: the fast paths
:PROPERTIES:
:CUSTOM_ID: painted-rects-fast-paths
:END:

Some things paint straight into a canvas without a full morph draw: the tray's clock
(=tick-tray=), a terminal's dirty rows, a web page's newest frame. Each paints into
whichever canvas its morph draws into — the screen for a tiled pane, the backing store
for a window's ([[file:../poc/morphic.lisp::defun paint-into][=paint-into=]]).

They hand the rect to the world as /painted/ ([[file:../poc/morph.lisp::defun note-painted][=note-painted=]]). The next repair draws
only what lies above the painting morph in that rect — a window's store, an overlay's
scrim and card — and does it /before/ the damaged rects, since a rect drawn whole and
then composited again would be dimmed twice. Painted-only repairs don't touch
=world-last-repair= or =world-repairs=, which describe repairs of damage.

** 4.4 Damage per morph
:PROPERTIES:
:CUSTOM_ID: damage-per-morph
:END:

- *An event damages the morph it reached*: a key the body it was typed into
  ([[file:../poc/shell.lisp::defun focused-body][=focused-body=]]: the side's when the side has the keys), a click the body clicked,
  the wheel the pane's own body.
- *Every other change is found, not announced.* Each watched morph has a /signature/
  (=morph-signature=): the few values its picture is a function of. The tab strip's
  titles, tints, numbers, agent dots and focused tab; the tray's items (not the clock,
  which ticks on its own); the status line's text, minibuffer or hints; a window's
  title and focus. A pane's is its view, side, preview, selection and side focus, plus
  what its subject adds (a web tab's address, load state and title). =desk-sync=
  compares each signature with the last one and damages only the morphs whose picture
  changed ([[file:../poc/morphic.lisp::defmethod check-morph ((p pane))][=check-morph=]]).
- *An expanded pane whose split held damages only its header band.* Everything below
  the header belongs to its bodies, which check themselves.

So the agent streaming into a conversation damages that conversation's body, a web
page's title its pane and its tab, a file saved in one folder pane the other folder
panes that show it.

What a signature must and mustn't hold:

- *Local bounds, never world ones.* With world bounds, every pane of a window would be
  damaged on every drag step.
- *Not where text and lists are scrolled to.* Drawing moves them (to keep the caret or
  the selection in view), so including them made every selection move draw twice. The
  wheel, which scrolls, is an event and damages anyway.
- *Everything the drawing reads, not only what the morph owns.* The stage body's
  heads-up line (=applicable: (missile missile) no will signal=) is drawn from
  =collide='s /methods/, which live outside the stage. Accepting a method beside a
  paused stage changed that line with nothing in the stage moving, so it stayed stale
  until the next step. [[file:../poc/morphic.lisp::defmethod morph-signature ((b stage-body))][The stage body's signature]] now includes =stage-hud-line=
  itself (two =compute-applicable-methods=, cheap at a stage's ten bodies). It also
  includes where the stage's bodies are, so an eval beside a paused stage that moves a
  ship is found.

** 4.5 A text view damages rows, not the pane
:PROPERTIES:
:CUSTOM_ID: text-view-damages-rows
:END:

[[file:../poc/textview.lisp][lol.textview]] describes its own picture in two parts, by the rules =tv-draw= paints by:

- *The frame* ([[file:../poc/textview.lisp::defun tv-frame-key][=tv-frame-key=]]): its rect, the font, the scroll, the scrollbar's thumb,
  the focus.
- *The rows* ([[file:../poc/textview.lisp::defun tv-row-keys][=tv-row-keys=]]): per screen row its line number, its text, the lexer's
  state entering it, the current-line band, the selection band, the caret.

The =text-body= keeps both as drawn. [[file:../poc/morphic.lisp::defmethod check-morph ((b text-body))][=check-morph=]] damages the whole view only when
the frame changed, else just the rows that differ, a run of neighbours as one band.

- *Computed, not tracked.* No edit records which lines it touched; the body compares
  what each row shows now with what it showed. That catches changes no edit command
  made: the agent streaming, a Workspace print, a replaced buffer.
- *Lexer state is in the key.* A quote opened at the top recolours every line below
  it, and all of them are found, as one band.
- *No lexing above the view.* =tv-draw= returns the lexer's state at the first visible
  line; a changed line above the view is a frame change ([[file:../poc/textview.lisp::defun tv-prefix-same-p][=tv-prefix-same-p=]]).

A key in a text view repairs one band of =line-h= + 3 pixels across one column, and a
list beside it isn't drawn at all.

** 4.6 What still damages the whole world

Only what is world-wide: a font size change (every metric moves), a new world
(=make-desk=: the console and back), and render-frame's final frame, meant as a whole
fresh paint. Everything else is per morph:

| change                                       | damages                                                  |
|----------------------------------------------+----------------------------------------------------------|
| a key, a click                               | the body it acted on                                     |
| the wheel over a pane                        | that pane's body                                         |
| a running stage's step                       | its stage body; the layout damages anything it moves     |
| a live worker's view arrived (=damage-pane=) | its body (the header by signature, if its title changed) |
| a run pane's step                            | its body — a text view, so its changed rows              |
| X11 =Expose=                                 | the exposed rect                                         |
| render-frame's =wheel:= with an odd count    | the current pane's body                                  |

=environment-changed= is =desk-sync=: it damages by signature.

The classes:

├── lol.morph:world  ──── desk                        poc/morphic.lisp

                (poc/overlays.lisp), debugger-overlay source-overlay
                agent-view-overlay cheatsheet-overlay (initramfs/fb-browser.lisp)
#+end_example

A pane watches its own signature in its own slot (=pane-sig=). The tree on screen:

#+begin_example

│   ├── tab-strip                    tabs, +, the …N overflow buttons
│   │   └── tray                     right end: clipboard icon, battery, clock
│   ├── trail-area                   between strip and status line
│   │   ├── pane  (collapsed)        a breadcrumb bar, per ancestor
│   │   ├── pane  (collapsed)
│   │   └── pane  (expanded)         its panel: title, tint, badge, a split's divider
│   │       ├── list-body | text-body | …     its body, in the main column
│   │       └── pane  (side)         a pinned side pane or the nav split's preview
│   │           └── list-body | text-body | …
│   └── status-line                  the status line / the minibuffer
├── minibuffer-panel             the minibuffer's candidates, when it has any
├── trail-window  (a surface)
│   ├── title-bar
│   ├── trail-area                   the SAME class, laying out the same panes
│   │   └── pane …
│   └── window-frame                 drawn last: the outline and the grip
└── overlay …                    the Spotter, a menu, the debugger
#+end_example

The =minibuffer-panel= is a child of the desk, not the shell, so the panes under it
keep their size (a web page isn't resized because you typed into its address). It
isn't an overlay: the keys stay the minibuffer's.

** 5.2 =PANE= is the morph
:PROPERTIES:
:CUSTOM_ID: pane-morph
:END:

[[file:../poc/shell.lisp::defclass pane (lol.morph:morph)][=pane=]] is a CLOS morph with the old struct's slot names and accessors
(=pane-subject=, =pane-view=, =pane-sel=, =pane-top=, =pane-tv=, =pane-side= …, and
=make-pane= / =pane-p= as functions). =*trails*= is still a list of lists of panes, and
the guest checks still read =(pane-top (current-pane))= over the net REPL.

A pane on screen is a child of a trail area. A pane in a hidden tab has no owner,
draws nothing and costs nothing.

What the old monolithic painter left in per-frame specials for click handlers to read
back now lives on the morph that drew it, in that morph's coordinates:

| was a special                                                    | is now                                                         |
|------------------------------------------------------------------+----------------------------------------------------------------|
| =*crumb-rects*=                                                  | each ancestor /is/ a collapsed pane morph: its bounds          |
| =*content-top*=, =*split-x*=                                     | =pane-body-top=, =pane-split-x=                                |
| =*list-rows*=, =*side-rows*=, =*matrix-cells*=, =*stage-rect*=   | the body's records: =body-rows=, =body-cells=, =body-viewport= |
| =*preview-pane*=, =*preview-subject*=                            | =pane-preview= (the side child), per list pane                 |
| =*editing-side*=                                                 | =pane-editing-side=                                            |
| =*tab-rects*=, =*tab-close-rects*=, =*tab-plus-rect*=            | slots of the =tab-strip=                                       |
| =*tray-rect*=, =*tray-clip-rect*=                                | the =tray='s bounds, and a slot                                |
| =*mb-clear-rect*=                                                | a slot of the =status-line=                                    |
| =*web-page-rect*=, =*web-bar-rects*=, =*web-bar-y*=              | slots of the =WEB-TAB= the pane shows (web.lisp)               |
| the cards' =*spotter-hits*=, =*menu-hits*=, =*clip-hits*= …      | the hit map each card's drawer returns, kept by its overlay    |
| =*drawn*=, =note-drawn=                                          | gone: the halo walks the morph tree ([[#halo-walks-tree][The halo walks the tree]])                     |
| the drag specials (=*drag-tv*=, =*last-press*=, =*web-press*= …) | =hand-press=, =hand-clicks= ([[#press-progress][The press in progress]])                             |

=pane-rows=, =pane-cells=, =pane-stage-rect= and =pane-body-rect= remain as readers of
the pane's body, under the names the click and halo code uses.

=*editing-side*= ("the keyboard is in the right-hand column") was one special for the
whole screen. As a slot it's about /that pane/, so switching tabs no longer carries a
side focus from one tab to another. Two mirrors stay global only for the guest checks
to read: =*chooser-state*= and =*dbg-state*=; no click reads them.

** 5.3 Layout is a container's policy
:PROPERTIES:
:CUSTOM_ID: layout-container-s-policy
:END:

[[file:../poc/morphic.lisp::defun desk-sync][=desk-sync=]] runs before every repair and around every event. It asks the trails
what should be on screen and makes the tree agree:

- *A =trail-area= lays out its trail as the accordion* ([[file:../poc/morphic.lisp::defun layout-trail-area][=layout-trail-area=]]):
  ancestors /collapsed/ to a bar each, the last pane /expanded/ to the rest of its
  height.
- *The expanded pane is split by [[file:../poc/morphic.lisp::defun layout-expanded][=layout-expanded=]]* (=expanded-columns= decides): its
  side pane or preview goes in the right-hand column — a text pane with a list beside,
  the stage with its Workspace, a pinned side pane, or the nav split's preview.
- *Each pane's body is placed* ([[file:../poc/morphic.lisp::defun place-body][=place-body=]], [[file:../poc/morphic.lisp::defun ensure-body][=ensure-body=]]): the same morph for as
  long as the view's kind holds, a new one when it changes. A breadcrumb has no body.
- *The focus follows =*active*=*, and the focused window is kept on top (below any
  overlay) by every sync.

Tiling is that one policy. The =shell-morph= puts its trail area between the tab strip
and the status line; a window puts the same class under its title bar. Nothing else
changes layout.

Each morph then draws only itself, at its bounds, with the painters the old monolith
called — =draw-tabs=, =draw-tray=, =draw-crumb=, =draw-pane-expanded=,
=draw-status-line= — back to front in the same order. A pane draws with =*active*=
bound to /its/ trail, so code inside that asks for the current pane gets its own, and
it draws inside its bounds (=with-clip=): a split's long column header can't run into
the gutter.

** 5.4 A pane's body is a morph
:PROPERTIES:
:CUSTOM_ID: pane-s-body-morph
:END:

The body is the pane's child for what lies under its header, of the class its view
kind asks for ([[file:../poc/shell.lisp::defun body-class-for][=body-class-for=]]):

| class           | draws                                                   | keeps (what it drew where)                 |
|-----------------+---------------------------------------------------------+--------------------------------------------|
| =list-body=     | rows, sections, selection, scrollbar (=draw-list-body=) | =body-rows=, the hit map                   |
| =text-body=     | a text view (=tv-draw=)                                 | what each screen row showed (=body-drawn=) |
| =grid-body=     | the dispatch matrix (=draw-matrix-body=)                | =body-cells=                               |
| =stage-body=    | the stage, its heads-up line, the transcript            | =body-viewport=                            |
| =image-body=    | a picture on its checkerboard                           | —                                          |
| =web-body=      | the toolbar and Chrome's newest frame                   | (the =WEB-TAB='s page rect)                |
| =terminal-body= | the grid of cells                                       | (the session's geometry)                   |

The expanded pane itself draws only its panel: title, tint, badge, and a split's
divider, column header and accent rule. A side pane stays a /pane/ holding a body,
not a body itself: it has its own subject, view, selection and text, and becomes a
trail's pane when promoted.

** 5.5 Routing presses and keys
:PROPERTIES:
:CUSTOM_ID: routing-presses-keys
:END:

- *A body takes its own press* through [[file:../poc/shell.lisp::defgeneric body-press][=body-press=]], one method per class: the
  list's row, the text's caret or Ctrl-jump, the grid's cell, the stage's sprite, the
  page, the terminal.
- *The pane knows the split.* [[file:../poc/shell.lisp::defun pane-click][=pane-click=]] sends a press in the right-hand column to
  [[file:../poc/shell.lisp::defun column-press][=column-press=]] (the pinned side's rules, the preview's "put me over there").
- *Chrome morphs take their own*: a tab or the =+= (the tab strip), the clipboard icon
  (the tray), the minibuffer's clear box (the status line), a breadcrumb (a collapsed
  pane: back to that level), the title bar, the grip.
- *A press in a gutter* (between breadcrumbs, beside the panel, on the status line)
  reaches the trail area or the shell, which hand it on with the old rules — a
  breadcrumb's band with its bottom edge, the whole width; otherwise the expanded
  pane. No click changed meaning when the monolith became a tree.
- *Focus changes are the desk's.* A press sets =*active*= to that trail and raises its
  window before routing.
- *The keyboard focus is the expanded pane* of the focused trail, in the shell or a
  window, and =browser-key= is its =handle-event=. The desk sees every key first, for
  =SuperL-g= and the grab mode.
- *Menus, the halo and the wheel* go on to the pane and the trail area.

** 5.6 The halo walks the tree
:PROPERTIES:
:CUSTOM_ID: halo-walks-tree
:END:

[[file:../poc/morphic.lisp::defun halo-layers][=halo-layers=]] is the target under the pointer (the word, the row, the sprite), then
for each morph from the deepest out, the layers it offers (=morph-halo-layers=):

- *A body* is a layer of its own: a text view's =TEXT-BODY= (Code: =tv-draw=,
  =tv-row-keys=), a list's =LIST-BODY= (Code: =draw-list-body=, =item->row=,
  =draw-list=). A sprite is the stage body's innermost layer.
- *Then the pane*, then what it shows; a breadcrumb itself; the tab strip a tab and
  itself; the tray the clipboard icon and itself; the status line the minibuffer and
  itself; a window its title bar and itself.
- *The outermost layer is the =SHELL-MORPH= or the window.* Inside a window the walk
  ends on the window: the tiled shell under it isn't its owner. Each container (trail
  area, tab strip, status line) is a layer of its own.
- *Overlays are left out*, since an open halo is one itself.

Inspect on a body shows the morph — its bounds, its records — not the model object
(the =TEXTVIEW= struct, the =VIEW=); the model is a click further, through the pane's
fields.

* 6. Windows
:PROPERTIES:
:CUSTOM_ID: windows
:END:

** 6.1 What a window is
:PROPERTIES:
:CUSTOM_ID: window
:END:

A [[file:../poc/morphic.lisp::defclass trail-window][=trail-window=]] is a trail torn off the tab strip: a surface ([[#surfaces][Surfaces]]) with a
=title-bar=, a =trail-area= of the same pane morphs, and a =window-frame=.

- *A trail, still in =*trails*=.* A trail is either in the tab strip or in a window.
  Everything that walks =*trails*= — the terminal sweep, the web sweep, the desk file,
  =SuperL-q='s "unsaved files?", the agent — sees it unchanged. The window finds its
  trail by the trail's *root pane*, which never changes identity. The tab strip skips
  windowed trails; each keeps its number, so =SuperL-N= still reaches it, and the title
  bar shows the number.
- *Tearing off moves morphs.* =tear-off-trail= reparents the trail's pane morphs from
  the shell's trail area into the window's (=add-morph=); =retile-window= moves them
  back. No trail is ever drawn "in another context".
- *Focus is =*active*=.* When the focused trail is a window's, that window has the
  keyboard and is on top. So =SuperL-Tab= and =SuperL-1..9= reach and raise windows with
  no code of their own.
- *The title bar*: the trail's kind stripe, its number, its title (the accent when
  focused), a close box =×=. A one-pixel outline (accent when focused) and a
  three-stroke resize grip in the bottom-right corner. Every size is asked of the font
  (=char-w=, =line-h=, =+bar-h+=), so a bigger font grows the bar and the grip
  ([[file:fonts.org][fonts.org]]).
- *The last tiled trail stays tiled.* =SuperL-g= on the only tab refuses and says so.
  Every drawing path of the tiled shell assumes a trail; an empty desktop behind the
  windows would be a design of its own.

** 6.2 Keys and gestures
:PROPERTIES:
:CUSTOM_ID: keys-gestures
:END:

| keys                                    | does                                                                          |
|-----------------------------------------+-------------------------------------------------------------------------------|
| =SuperL-g= on a tiled trail             | tear it off into a window, focused, and enter *grab mode*                     |
| =SuperL-g= on a window                  | enter grab mode                                                               |
| in grab mode: arrows                    | move the window one cell (=char-w= across, =line-h= down); Shift: eight       |
| in grab mode: =C-=arrows                | resize it by a cell                                                           |
| in grab mode: =t= or =SuperL-g=         | re-tile: back into the tab strip, focused                                     |
| in grab mode: =Ret= / =Esc=             | done; any other key ends the mode and then goes where keys go                 |
| drag a tab down                         | tear it off, the window carried by the pointer from there                     |
| drag the title bar                      | move (opaque); drop it on the tab strip: re-tile                              |
| drag the corner grip                    | resize                                                                        |
| click =×= / =SuperL-w=                  | close the window's trail                                                      |
| =SuperL-Tab=, =SuperL-1..9=, =SuperL-t= | reach windows too, raising each (=SuperL-t='s tab list marks them =(window)=) |

Re-tiling from the keyboard is =SuperL-g= then =t= (or =SuperL-g= twice), because the
first press on a window has to mean "grab it", or a window couldn't be moved without
the mouse.

Grab mode isn't a nested loop: it's a slot of the desk (=desk-grab=), and the desk sees
every key before the focus does ([[file:../poc/morphic.lisp::defun grab-key][=grab-key=]]). Nothing else stops while it's on.

** 6.3 The halo's window handles
:PROPERTIES:
:CUSTOM_ID: halo-s-window-handles
:END:

On a window's layer the halo offers Morphic's handles first
([[file:../poc/morphic.lisp::defmethod lol.morph:morph-affordances ((w trail-window))][=morph-affordances=]] of =trail-window=), then Inspect, Code and Class as on any layer.
Squeak's halo also puts move and resize first. The shell morph has no affordances:
moving the tiled shell means nothing.

| handle  | does                                                                                                                  |
|---------+-----------------------------------------------------------------------------------------------------------------------|
| Move    | the hand picks the window up where the pointer is: it follows the pointer with *no button held*; a click puts it down |
| Resize  | the same, by the bottom-right corner                                                                                  |
| Raise   | focus it (its trail becomes =*active*=), so it comes to the top                                                       |
| Close   | close its trail, as the =×= box                                                                                       |
| Re-tile | back into the tab strip                                                                                               |

Move and Resize turn grab mode on as well ([[file:../poc/morphic.lisp::defun halo-carry][=halo-carry=]]), so the arrows still work
during the carry and Return or Esc put the window down where it is.

*Settable bounds.* Inspect on the window shows the =trail-window= instance, and its
=BOUNDS= row is settable: =C-c C-c= with =(list 60 90 700 420)= moves and resizes it on
screen. [[file:../initramfs/model.lisp::defun inspect-places][=inspect-places=]] asks the generic [[file:../initramfs/model.lisp::defgeneric inspect-slot-setter][=inspect-slot-setter=]] (default: =(setf
slot-value)=, which would change the number and nothing on screen), and a morph's
=bounds= answers [[file:../poc/morph.lisp::defun set-morph-bounds][=set-morph-bounds=]], which damages. =owner= and =children= — the tree,
which only =add-morph= / =remove-morph= may change — say "not settable". That's the
Self/Squeak directness, reached through the existing inspector.

** 6.4 Windows across sessions

=desk-data= (desk.lisp) records =:windows=: each window's trail (by its index among the
trails kept) and bounds, back to front. At boot =restore-desk= hands them to
=*windows-to-restore*=, and [[file:../poc/morphic.lisp::defun make-desk][=make-desk=]] tears those trails off again, cut to the
current screen, in that order — so z-order and focus come back too.

The same path keeps windows across a trip to the console and back (=b=):
=run-browser-fb= hands the old world's layout ([[file:../poc/morphic.lisp::defun desk-window-layout][=desk-window-layout=]]) to the new one.
A fresh world lets the panes go from the old one first, since a morph can be in only
one tree.

* 7. Overlays: modal cards in the one loop
:PROPERTIES:
:CUSTOM_ID: overlays-modal-cards-loop
:END:

Every modal card is an [[file:../poc/morphic.lisp::defclass overlay (lol.morph:morph)][=overlay=]]: a morph on top of the desk that the world draws
(clipped, back to front, so a scrim dims what's under it /as it is now/) and that takes
every input event while it's up. The desk routes them to the topmost one
([[file:../poc/morphic.lisp::defmethod lol.morph:handle-event ((desk desk) e)][the desk's =handle-event=]]). Each overlay says only which key means what
(=overlay-event=) and what it draws (=overlay-draw=, calling the shell's own
=draw-spotter-card=, =draw-context-menu=, =draw-halo=, =draw-clipboard-card=).

- *Backend-blind ones* are in [[file:../poc/overlays.lisp][poc/overlays.lisp]]: [[file:../poc/overlays.lisp::defun open-spotter][=open-spotter=]], [[file:../poc/overlays.lisp::defun run-chooser][=run-chooser=]]
  (menus, the halo, a web page's =<select>=), [[file:../poc/overlays.lisp::defun run-clipboard-manager][=run-clipboard-manager=]],
  [[file:../poc/overlays.lisp::defun run-value-prompt][=run-value-prompt=]].
- *The rest* stay in fb-browser.lisp beside their drawing: the debugger
  ([[file:../initramfs/fb-browser.lisp::defun %run-debugger-fb][=%run-debugger-fb=]]), its source viewer ([[file:../initramfs/fb-browser.lisp::defun open-frame-source][=open-frame-source=]]), the agent's ASK
  view ([[file:../initramfs/fb-browser.lisp::defun run-agent-view][=run-agent-view=]]) and the cheatsheet ([[file:../initramfs/fb-browser.lisp::defun open-cheatsheet][=open-cheatsheet=]]).

** 7.1 Two ways to be opened

Most cards answer a /caller/ that wants a value — =choose-and-run= wants the pick,
=set-field= the typed text — and the debugger must keep the erroring stack standing
under it. Rewriting every caller as a callback wasn't worth it, so there are two ways:

- *=open-overlay=* puts it up and returns at once: the Spotter, the cheatsheet, the
  source viewer. What they do (open a trail), they do themselves.
- *[[file:../poc/morphic.lisp::defun run-overlay][=run-overlay=]]* puts it up and *waits* by turning the backend's own loop —
  [[file:../initramfs/fb-browser.lisp::defun fb-cycle][=fb-cycle=]] in the guest, =host-cycle= on X11, installed as =*world-cycle*= — until
  the overlay closes. The same loop, not a copy: a terminal keeps printing behind a
  menu, the clock ticks behind the debugger, a web page's frames arrive. Squeak's modal
  dialogs wait the same way, looping =doOneCycle=. A restart invoked from the debugger
  unwinds straight through the wait; the overlay goes on the way out
  (=unwind-protect=). With no =*world-cycle*=, a waiting chooser answers NIL at once.

** 7.2 What stops behind a waiting overlay
:PROPERTIES:
:CUSTOM_ID: stops-behind-waiting-overlay
:END:

*Stepping ([[#stepping][Stepping]]) and the agent's tick.* The computation that waits may be the very one a
step would run again: a stage whose contact raised the debugger would raise it again
every 33 ms. The agent's tick runs tool calls on this thread. Input, the services,
repair and the clock go on.

** 7.3 Damage and input rules

- *Damage.* An overlay damages its whole bounds when what it shows changes. Moving the
  selection in a menu, the Spotter or the clipboard manager damages only the card
  (=card-damage-rect=, drop shadow included). The value prompt is an opaque band along
  the bottom, so the repair starts at it.
- *Hit maps.* Each card's drawer returns what it drew where, and the overlay keeps it.
  =chooser-layer= is the layer an open halo is about.
- *Evdev-only keys are ignored.* A modal never reads a key the console didn't see (a
  Ctrl chord or Shift-PageUp that came only from the keyboard's evdev). Those events are
  marked =:evdev= and overlays skip them (=overlay-key=).
- *Kept from the old loops*: every key and click each one understood, the left button
  only where a loop read only it.

** 7.4 Before and after: one view built both ways

The clipboard manager (=SuperL-h=) as a function with its own loop, before Morphic
(=git show 198fe92:initramfs/fb-browser.lisp=, abridged):

#+begin_src lisp
(loop with dirty = t do
  (when dirty
    (draw-clipboard-card canvas w h query results sel)   ; repaint the whole screen
    (show-frame canvas)                                  ; send all of it to /dev/fb0
    (setf dirty nil))
  (fbb-wait 0 *fb-mouse* *fb-kbd*)                       ; its own poll(2)
  (cond ((eq key :escape) (return)) ...))                ; its own keys, its own clicks
#+end_src

The view owned the poll, the input decoding and the redraw. While it was open the
rest of the system stood still. Any change set =dirty=, and the whole screen was drawn
and sent again.

As an overlay ([[file:../poc/overlays.lisp::defclass clipboard-overlay][=clipboard-overlay=]], abridged):

#+begin_src lisp
(defclass clipboard-overlay (overlay) (query sel))

(defmethod overlay-draw ((o clipboard-overlay) canvas w h)   ; how to draw it
  (draw-clipboard-card canvas w h (clip-query o) ...))

(defmethod overlay-event ((o clipboard-overlay) e)           ; what an event does
  (cond ((eq key :escape) (close-overlay o))
        ((eq key :down) (incf (clip-sel o))
                        (overlay-changed o (card-damage-rect *clip-rect*))) ...))

(run-overlay (make-instance 'clipboard-overlay))             ; into the World; wait for the pick
#+end_src

The view says how to draw itself and what an event does. The World does the rest: one
poll, each event to the morph on top, and a repair of just the card's rectangle.

|                               | Before                                   | After                                                      |
|-------------------------------+------------------------------------------+------------------------------------------------------------|
| a view is                     | a function with a loop                   | a CLOS object (a morph)                                    |
| event loops                   | 1 main + 6 modal                         | 1, the World's                                             |
| a change means                | =dirty=: draw and send the whole screen  | =invalidate= a rect: draw and send that rect               |
| an open modal                 | everything else freezes                  | everything else runs, except stepping and the agent's tick |
| overlap                       | none: a fixed paint order                | z-order: windows and overlays are the World's children     |
| things that move on their own | each one a special case in the main loop | =step-morph= on a per-morph deadline; idle sleeps          |

* 8. Stepping
:PROPERTIES:
:CUSTOM_ID: stepping
:END:

The world keeps a deadline per stepping morph ([[file:../poc/morph.lisp::defun world-step][=world-step=]],
[[file:../poc/morph.lisp::defun world-step-timeout][=world-step-timeout=]]: -1 when nothing steps). =morph-step-ms= is read afresh every
turn, so a morph answers NIL the moment it has nothing to animate and the poll sleeps
until input.

| what                       | step                            | damages                                                                                 |
|----------------------------+---------------------------------+-----------------------------------------------------------------------------------------|
| a running stage            | 33 ms                           | its stage body only (viewport, heads-up line, transcript), drawn by its pane alone      |
| a run pane, live or behind | 100 ms                          | its body; a run in a hidden tab costs nothing                                           |
| a terminal's rows          | (its pty wakes the poll)        | the rows, painted on screen for a tiled terminal, into the backing store for a window's |
| a live worker's view       | (its pipe)                      | its body (=damage-pane=)                                                                |
| the agent's ASK view       | 66 ms while answering, 500 idle | itself (an overlay that steps)                                                          |

- *Stage panes* step through [[file:../poc/morphic.lisp::defun step-stage-pane][=step-stage-pane=]], for any pane on screen, each stage with
  its own last-tick time.
- *Run panes* are stepped by whoever shows them (runs.lisp,
  [[file:../initramfs/runs.lisp::defun run-pane-step-ms][=run-pane-step-ms=]], [[file:../initramfs/runs.lisp::defun step-run-panes][=step-run-panes=]]); =runs-timeout= only wakes the loop for a
  stop awaiting its SIGKILL.
- *Live workers* count every trail on screen as visible, windows included
  (=visible-trails=).

* 9. The hand: the press in progress, drag and drop
:PROPERTIES:
:CUSTOM_ID: hand-press-progress-drag
:END:

** 9.1 The press in progress
:PROPERTIES:
:CUSTOM_ID: press-progress
:END:

There's one pointer, so there's one press. =hand-press= is a plist whose first key says
whose it is:

- =(:text :tv … :origin …)= — a selection being dragged out in a text view
- =(:terminal :subject … :x … :y …)= — a selection in a terminal
- =(:web :tab … :cx …)= — a press sent into a web page
- =(:row …)= — a press on a list row, waiting for its release
- =(:drag …)= — something picked up to be dropped

=hand-clicks= counts double and triple clicks for text and pages alike. The world
clears the press when the button comes up. A terminal's mouse report asks the hand
for the point in the pane's own coordinates (=screen-to-pane=), which matters in a
window.

*A press on a row acts on its release*, so a press that moves can pick the row up. The
press waits as =(:row …)= and the click happens on release, unless it moved first. A
touchpad *tap* has no release of its own: the guest's loop marks its press =:tap= and
it acts at once (=input-events=, fb-browser.lisp). A press in text still acts at once
(the caret, a selection drag); a sprite is selected at once and picked up if the press
moves. render-frame's =click:= token is a press and its release.

** 9.2 Picking up
:PROPERTIES:
:CUSTOM_ID: picking-up
:END:

What the hand carries is a *subject*:

| picked up                                                                        | how                                                               |
|----------------------------------------------------------------------------------+-------------------------------------------------------------------|
| a list row's subject — a definition, a class, a file, an inspector field's value | a press on the row that moves more than 8 px (=+pick-up-travel+=) |
| a sprite's instance (the stage)                                                  | a press on it that moves                                          |
| the selected row, the selected sprite, the definition (or symbol) at the caret   | =SuperL-p=                                                        |

It's let go by the button's release; by the next press, when picked up with a key (no
button held, as the halo's Move carries a window); or by =SuperL-d= at the keyboard
focus (=SuperL-S-d=: on the tab strip). =Esc= puts it back. The status line says what's
carried and where it can go ([[file:../poc/shell.lisp::defun carrying-hints][=carrying-hints=]]); nothing is drawn beside the arrow,
so a carry costs no repair. Code: =start-carry=, =keyboard-pick-up=, =keyboard-drop=.

** 9.3 Dropping
:PROPERTIES:
:CUSTOM_ID: dropping
:END:

The world asks the morph under the hand, then its owners, whether they take it
([[file:../poc/morph.lisp::defgeneric accept-drop][=lol.morph:accept-drop=]], [[file:../poc/morph.lisp::defun world-drop][=world-drop=]]). Each answers T (taken; it says what it did),
a string (refused; the walk stops and the string is shown), or NIL (ask my owner).

| dropped on                                                            | does                                                                                                                                                    |
|-----------------------------------------------------------------------+---------------------------------------------------------------------------------------------------------------------------------------------------------|
| editable text (Workspace, source, a file, a pinned side)              | inserts a *readable reference* where it lands, one undoable edit; spaces added where it would run into a word                                           |
| an inspector's field                                                  | sets it to the *value*, through the field's own setter with no confirmation — the path =C-c C-c= takes ([[file:../poc/shell.lisp::defun set-field-to][=set-field-to=]]); a field with no setter refuses |
| a terminal                                                            | types the reference into its program                                                                                                                    |
| the tab strip                                                         | opens it as a new trail                                                                                                                                 |
| any other pane (a breadcrumb, a read-only text), a window's title bar | drills it there, at the end of that trail, which gets the keys                                                                                          |
| a web page                                                            | refuses: a page takes no drops                                                                                                                          |

** 9.4 A subject's two readings
:PROPERTIES:
:CUSTOM_ID: subject-s-readings
:END:

A subject has two readings, and they agree ([[file:../poc/shell.lisp::defun drop-value][=drop-value=]], [[file:../poc/shell.lisp::defun drop-reference][=drop-reference=]]):

- *As a VALUE*: a definition is its name, a file its path, an inspected value itself.
  A browser's handle on a view (a module, a cross-reference) is no value at all.
- *As TEXT that evaluates back to that value*: ='draw-alien= (not =#'f= or
  =(source-of 'f)=), =#'car=, =(find-class 'ship)=, =(find-package "COMMON-LISP-USER")=,
  ="/home/<user>/x.lisp"=, =42=, or anything else that prints readably /and reads back
  without =#.=/.

So the text a drop inserts in the Workspace evaluates to what the same drop would store
in a field. Something with no such text (an instance from the stage, a hash table) is
refused by a text, with the reason, rather than inserted as =#<…>=, and is still taken
by a field or the tab strip.

* 10. Backends
:PROPERTIES:
:CUSTOM_ID: backends
:END:

The core is backend-blind; each backend decodes its input into events, turns the
world's cycle, and sends what the world repaired.

- *The guest* ([[file:../initramfs/fb-browser.lisp::defun run-browser-fb][=run-browser-fb=]]): [[file:../initramfs/fb-browser.lisp::defun input-events][=input-events=]] decodes the keyboard's evdev, then the
  console, then the pointers, in that order; one turn is [[file:../initramfs/fb-browser.lisp::defun fb-cycle][=fb-cycle=]]. The stall
  watcher's =note-main-idle= / =note-main-busy= live in =poll-input-once=, and
  =*fb-services*= run every turn. The pointer stays the composited patch of
  [[file:framebuffer.org::#pointer-part-frame][framebuffer.org, The pointer is not part of the frame]].
- *The X11 host* ([[file:../poc/run-browser.lisp][poc/run-browser.lisp]]): one turn is [[file:../poc/run-browser.lisp::defun host-cycle][=host-cycle=]] — repair and present,
  wait for an X event or the earliest step deadline, route, step — installed as
  =*world-cycle*= exactly as the guest installs =fb-cycle=, so every overlay waits there
  too. The runner loads =overlays.lisp= and =fb-browser.lisp= (nothing there touches
  =/dev/fb0= before =run-browser-fb=); the cheatsheet, the frame-source viewer and the
  agent view size themselves from the world. An =Expose= damages the exposed rect. The
  leave menu's entries just end the runner. Details: [[file:x11.org::#host-s-loop-world][x11.org, The host's loop is the world's cycle]].
- *Headless frames* ([[file:../poc/render-frame.lisp][poc/render-frame.lisp]]): its =-k= script goes through
  =world-dispatch=; =drag:X1,Y1,X2,Y2= drags.

* 11. What it costs
:PROPERTIES:
:CUSTOM_ID: costs
:END:

Guest: QEMU with KVM on an i7-1065G7 host, =-cpu qemu64=, 1280×800, averaged over 50
runs (the guest's clock reads in 4 ms ticks), each event or damage repaired and sent.
=check-morphic.lisp= section H prints them; ranges are over four runs, three beside
other guests.

| what                                            | guest        |
|-------------------------------------------------+--------------|
| a key in a text view beside a list              | 0.32–0.40 ms |
| a key in a window (its list, moved)             | 0.96–1.04 ms |
| a window moved 10 px                            | 0.56–0.88 ms |
| a key in a tiled pane, whole pane (before [[#text-view-damages-rows][A text view damages rows, not the pane]]) | 2.64–3.36 ms |
| a stage step (its body)                         | 2.00–2.24 ms |
| a stage step as a full repair                   | 2.96–3.60 ms |
| a full repair (shell + one window)              | 4.32–4.80 ms |
| loop turns in 5 idle seconds                    | 5            |
| stage steps in 2 s                              | 56           |

- *A key in a text view* repairs a tenth of what a whole pane did, and the list beside
  it isn't drawn.
- *A key in a list* costs about what a pane does: its list body, its preview and its
  header band are most of the pane.
- *A window move* is a strip of shell plus a copy, about a sixth of a full repair.
- *The full repair* draws a layer of body morphs over each panel and records what each
  text row shows — the price of line-sized repairs, paid only on a whole repaint.
  =draw-browser=, a whole-world paint with every window redrawn rather than copied,
  measured 4.56–5.04 ms.

Host ([[file:../poc/morphic-test.lisp][morphic-test]], 30 runs, drawing only): a key in the tiled list 0.5–0.7 ms.

* 13. Pitfalls and false leads

- *A body's signature must cover what its drawing reads*, not only what it owns
  ([[#damage-per-morph][Damage per morph]]: the stage's heads-up line).
- *=world-repair= with nothing to repair must return =(values nil nil)=.* Returning one
  value killed the loop's =multiple-value-call= at the first wake, and every check
  failed with nothing on the console: the environment's =handler-case= dropped to the
  menu, and a diskless guest has no session log. It was caught by rebinding
  =log-condition= over the net REPL and re-entering with =b=.
- *Name clashes with silent symptoms.* A mixin first called =SIGNED= is
  =sb-alien:signed= (package lock): now =watched-morph=. An accessor first called
  =PANE-COLUMNS= silently replaced a pty-width function in runs.lisp, and the first
  frame died with "invalid number of arguments": now =pane-split-plan=.
- *The halo walk wrapped past the outer layer* in one guest run because the probe
  counted =halo-layers= while the halo, itself an overlay, was open. Overlays are now
  left out of the halo's layers.
- *A clock tick overwrote =world-last-repair=*, failing "a key repairs … as one rect".
  Painted-only repairs no longer touch it.
- *Not a finding: Chrome "hanging" a page in a window.* Six guest runs of check-web
  failed with a page loading forever. It looked like Chrome hanging a resized page with
  two tabs open. It was the check's own HTTP server serving one connection at a time
  while Chrome held a preconnect open, so the real request waited behind an idle one.
  The server now serves each connection in its own thread; a speculative =web.lisp=
  change was reverted. (Also: =C-l= opens the prompt holding the current address, so
  the check clears it with =C-u= first.)
- *Not a finding: checks that changed with the code.* Checks that counted
  =draw-browser= calls as "a frame" count the world's repairs that drew something;
  check-scroll's long definition is now =draw-pane-expanded=; check-pointer times
  =present-frame=; check-clipboard's halo on the Workspace is about the =TEXT-BODY=.
- *No Xvfb on the build host*, so the X11 loop is tested headless ([[#tests][Tests]]). The real
  runner has been started against an X server and runs without error, which shows only
  that it starts.

* 14. Known limits
:PROPERTIES:
:CUSTOM_ID: known-limits
:END:

- *No picture of the carried thing* beside the arrow; the status line says what's
  carried.
- *No dragging a text selection* out of a text view: =SuperL-p= picks up only the name
  at the caret.
- *Nothing drops onto the stage.*
- *No empty desktop.* The last tiled trail can't be torn off ([[#window][What a window is]]).
