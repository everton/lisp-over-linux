* What this file is

The theory companion: the firmware, CPU and hardware concepts the other docs
assume. The other docs explain *why this machine is the way it is* and end at
something in this repo; this one is the general computing knowledge beneath that.
Each section closes with an *In this project* line tying it back to something
concrete. You can build and boot without reading it.

* 1. Firmware: what runs before Linux (BIOS vs UEFI)

*Firmware is a tiny operating system in a flash chip on the motherboard; it owns
the machine from power-on until it hands control to ours.*

At power-on the CPU executes from a fixed address wired into the silicon (the
*reset vector*, =0xFFFFFFF0=, near the top of the 32-bit address space), which is
mapped to the flash chip. The firmware brings up RAM, trains the memory controller,
enumerates buses, then finds and launches an operating system.

- *BIOS* (legacy, ~1981–2010s). 16-bit and tiny. It read the first 512 bytes of a
  disk (the *MBR boot sector*) and jumped to them. It also offered *callable
  routines* (software interrupts like =INT 13h= for disk, =INT 10h= for video) the
  OS could use until it had its own drivers.
- *UEFI* (every machine since ~2012). A far larger 32/64-bit firmware — a small OS
  with a driver model, a shell, a filesystem reader and a real executable loader.
  It doesn't read a boot sector: it reads a *file* off a FAT partition and runs it
  as a program.

UEFI carries drivers for exactly what *it* needs during boot: storage to read the
boot file, a keyboard and console for its menus, a display. They're minimal and
disposable (§3, §5): they exist to load an OS, not to run one.

*In this project:* under QEMU the firmware is *OVMF* (open-source UEFI); on real
hardware it's the vendor's UEFI. There's no BIOS, MBR or boot sector anywhere in the
design, which is why the no-bootloader trick works.

* 2. The x86 mode staircase — the CPU does NOT start in 64-bit

*An x86-64 CPU powers on as a 16-bit 8086 and has to be walked up to 64-bit — and
firmware does the walking before our kernel runs.*

Every x86-64 core starts in *16-bit real mode*: compatible with the original 8086,
~1 MB addressable, no memory protection. The climb is a series of steps, each
unlocked by setting control-register bits and each needing the previous one's
machinery (a descriptor table, then page tables):

  16-bit *real mode*        (reset state — 8086, no protection)
     | set CR0.PE, load a GDT |
     v
  32-bit *protected mode*   (80386, 1985 — 32-bit + paging; the privilege
                             rings themselves came first, on the 80286, 1982)
     | build page tables, set EFER.LME + CR0.PG |
     v
  64-bit *long mode*        (AMD64, 2003 — the mode everything runs in today)

*UEFI does the whole climb itself.* When it launches a boot application the CPU is
already in long mode with paging on, so the kernel's EFI entry point starts in
64-bit. A legacy-BIOS kernel gets the CPU in real mode and must climb in its own
early boot code.

*In this project:* this is why a no-bootloader EFISTUB kernel is feasible. The
fiddly real → protected → long climb is done before =BOOTX64.EFI= runs.

* 3. The handoff: how UEFI launches the kernel and lets go

*UEFI loads our kernel like any other program and calls it with a table of
services; the kernel uses them to learn the machine, then tells UEFI to exit, and
from then on owns the hardware alone.*

** 3.1 The kernel is a UEFI executable (PE32+, EFISTUB)

UEFI runs programs in its own executable format, *PE32+* (PE/COFF, the family of
Windows =.exe= files; ELF is Linux's native format). Its loader parses headers and
sections, applies relocations and calls the entry point.

*EFISTUB* (=CONFIG_EFI_STUB=) prepends a valid PE32+ header to the kernel image, so
the file is both a bootable Linux kernel and a UEFI application. UEFI sees =MZ= /
=PE\0\0= and runs it; the stub code bridges from "UEFI app" into "Linux boot".

(This is the =file= check in [[file:../micro-distro.org][micro-distro.org]]: the image must report "Linux
kernel … 64-bit EFI handoff entry point" *and* start with the bytes =MZ=. Two
identities, one file.)

** 3.2 The EFI System Table and Boot Services

UEFI calls the entry point with an *image handle* and a pointer to the *EFI System
Table*, the doorway to the firmware's *Boot Services* — functions alive only during
boot. The stub uses them to learn what only firmware knows:

- *GOP* (Graphics Output Protocol) → the framebuffer (§4).
- *Memory map* → which physical ranges are RAM and which are reserved.
- *ACPI tables* → the hardware description (CPUs, buses, power).

** 3.3 ExitBootServices() — the point of no return

When the kernel has what it needs it calls *=ExitBootServices()=*. The firmware
tears down Boot Services and *every disposable driver behind them* (storage,
keyboard, console). The kernel now owns the machine; anything it didn't grab
before this call is gone (which is why the framebuffer details in §4 must be
captured first).

** 3.4 Runtime Services — the sliver that survives

A small set of *Runtime Services* stays alive for the OS's whole life: the hardware
clock, *EFI variables* (=/sys/firmware/efi/efivars=; =efibootmgr= edits boot entries
through them), firmware-assisted reset and capsule updates. It's the narrow modern
analog of the BIOS =INT= routines: housekeeping, not general I/O.

*In this project:* =BOOTX64.EFI= *is* the kernel, launched straight by UEFI's PE
loader off the FAT ESP, no GRUB in between. Boot Services are how EFISTUB learns
the framebuffer and memory map; ExitBootServices is why those are grabbed early.
Runtime Services are the efivars we *could* touch but don't: power-off goes through
the kernel's ACPI path, not UEFI reset ([[file:../micro-distro.org][micro-distro.org]] §"Real-hardware input").

* 4. Inheriting the framebuffer (GOP) — a pointer, not a duplicate

UEFI has already put the GPU in a working graphical mode for its menus and exposes
the parameters (framebuffer address, width, height, pitch, pixel format) through
the *GOP*. EFISTUB reads them during Boot Services and stashes them for the
kernel's =efifb= driver, which *reuses the firmware's framebuffer* instead of
driving the GPU.

This is the one place the kernel keeps a UEFI-provided resource. It's covered end
to end in [[file:../framebuffer.org][framebuffer.org]] §3 ("Getting a framebuffer without a GPU driver").

*In this project:* the framebuffer is the *only* hardware the kernel inherits from
firmware; everything else is re-enumerated (§5).

* 5. Why Linux re-enumerates the hardware (and the keyboard delay)

*UEFI's drivers exist to load an OS, not to run one, so the kernel discards them at
ExitBootServices and binds its own drivers to the same hardware — and that takes a
moment our code has to allow for.*

UEFI's storage and keyboard drivers were Boot Services drivers; they died at
ExitBootServices (§3.3). The kernel rediscovers the hardware with its own:

- *Storage* → the kernel's block/USB/NVMe stack.
- *Keyboard and mouse* → the kernel's *USB-HID* stack (and I2C-HID on laptops).
- *Everything on PCI* → re-enumerated by the PCI subsystem.

The framebuffer (§4) is the one deliberate exception.

*The keyboard chain bites in practice.* A laptop keyboard is a USB-HID (or I2C-HID)
device on an *xHCI USB controller*, itself a *PCI device*, so the kernel must bring
up PCI → USB → xHCI → HID → input device. That binding is *asynchronous*: it
completes a short time after the kernel starts userspace. (The =CONFIG_PCI / USB /
HID= story, including how a missing =CONFIG_PCI= killed both the keyboard and ACPI
power-off, is in [[file:../micro-distro.org][micro-distro.org]] §"Real-hardware input".)

*In this project:* this is why =supervisor-main= in
[[file:../../initramfs/supervisor.lisp][initramfs/supervisor.lisp]] does =(sleep 2)= "give USB a moment to enumerate"
before reading input, and why =show-input-devices= prints
=/proc/bus/input/devices= — a direct check that the HID binding completed. UEFI
having had a working keyboard doesn't carry over.

* 6. Multicore bring-up: one core boots, the rest are woken

*A multicore CPU doesn't power on as N running cores: exactly one boots, and it
must wake the others with a hardware signal.*

- *BSP and APs.* At power-on the hardware elects one *BSP* (BootStrap Processor) to
  run the firmware and early kernel; the *APs* (Application Processors) are parked.
  This is an architectural fact: bit 8 (=BSP=) of the =IA32_APIC_BASE= MSR is set on
  exactly one core. Every core also has a unique *APIC ID*, its name on the
  interrupt bus.
- *INIT–SIPI–SIPI.* The BSP uses its *Local APIC* (each core's interrupt gateway)
  to send the APs a fixed wake-up handshake. The SIPI ("Startup IPI") carries an
  8-bit *vector*; the woken AP starts at physical address =vector << 12= (=vector ×
  0x1000=) in low memory, not the ROM reset vector. The OS places a small real-mode
  *trampoline* there; each AP climbs the mode staircase (§2) and reports in. (An
  *IPI*, Inter-Processor Interrupt, is one core interrupting another; §7 covers the
  rest.)
- *Counting cores.* The kernel learns how many cores exist and their APIC IDs from
  the *ACPI MADT* table (found via Boot Services, §3.2).

Once running, Linux is a *fully distributed* SMP kernel: each core has its own
scheduler runqueue, current task, kernel stack and per-CPU data; shared state is
protected by fine-grained locks (spinlocks, RCU). The BSP is special only at boot;
afterwards it's just core 0.

*In this project:* the kernel is SMP since tag #30 (=CONFIG_NR_CPUS=16=). QEMU boots
the guest with =-smp 4= (=build.sh= and the guest checks; =QEMU_SMP= /
=LOL_QEMU_SMP= change it) and real hardware brings up all its cores. The SBCL
userland is multithreaded — the agent's turns, the network daemon, the recorder's
writer, the run panes' readers — and those threads run truly in parallel
([[file:../kernel-config.org][kernel-config.org]] §10). Before #30 the kernel was uniprocessor: only a BSP, no
APs, no trampoline.

* 7. Interrupts on a multicore machine — who gets poked

*Each core has a private interrupt gateway (its Local APIC); a shared router (the
I/O APIC), or increasingly the device itself (MSI), decides which core's gateway an
interrupt knocks on; cores poke each other through IPIs.*

Three kinds of interrupt, routed differently:

1. *External device interrupts* (a keypress, a packet, a disk completion):

   #+begin_src
   device raises IRQ
      -> I/O APIC      (a shared chip; its table picks a target core + vector)
      -> that core's Local APIC
      -> the core is interrupted
      -> CPU indexes the vector in its IDT -> runs the handler
   #+end_src

   The *IDT* (Interrupt Descriptor Table) maps an 8-bit vector to a handler. The
   kernel decides which core fields which IRQ (*interrupt affinity*): it can pin a
   device to one core or spread load (the =irqbalance= idea), so network
   interrupts don't all pile onto core 0.

2. *Local (per-core) interrupts* — sources inside a core's own Local APIC that
   never route anywhere: the *Local APIC timer* (each core's scheduler tick),
   thermal sensors, performance-counter overflow.

3. *IPIs* — core to core, sent by writing the Local APIC. Waking the APs (§6) is
   the first use; at run time the kernel sends a *reschedule* poke, a *TLB
   shootdown* (one core changed a page mapping, so the others flush stale
   entries), or a *function-call* IPI ("run this over there").

*MSI / MSI-X* (Message-Signaled Interrupts) is the modern path: a PCIe device
raises an interrupt by a *memory write* to a magic address that the target Local
APIC decodes; the address encodes the destination core and vector. One NIC can own
dozens of vectors (a queue and interrupt *per core*) with no shared routing chip in
the way. It's the dominant mechanism today.

Once an interrupt lands, a core finishes the current instruction, masks
equal/lower-priority interrupts, indexes the *IDT*, runs the handler (Linux keeps
this half tiny and defers real work to a softirq or threaded IRQ), then writes
*EOI* (End Of Interrupt) to the Local APIC so it can deliver the next.

*In this project:* with SMP on (§6) all of this is live: the guest's several cores
each have a Local APIC, and IPIs fire for rescheduling and TLB shootdowns. On a
single-CPU boot (=LOL_QEMU_SMP=1=) there is one Local APIC, nothing to route, and no
IPIs.

* 8. Entropy and the CRNG — the "random: crng init done" message

The kernel keeps a cryptographic random number generator (the *CRNG*, a
ChaCha-based CSPRNG) behind =/dev/urandom= and =getrandom()=. At boot it's
*unseeded*. It gathers entropy from unpredictable physical events — interrupt
timing, input events (keystrokes), disk completions — and, on capable hardware,
from =RDRAND=/=RDSEED= or a hardware/virtio RNG. At about 256 bits it marks the CRNG
seeded and prints =random: crng init done=, once per boot. After that
=getrandom()= stops blocking. The message is informational, not a warning.

*In this project:* the machine has few entropy sources. =CONFIG_HW_RANDOM= is off
(no hwrng framework, no =virtio-rng= driver), the QEMU line passes no RNG device,
and under TCG the CPU's =RDRAND= isn't a trusted early seed. So on a near-idle VM
the pool fills *slowly*, mostly from interrupt timing, and your *keystrokes* (via
the kernel's =add_input_randomness=) often tip it over. That's why =crng init done=
tends to appear as you start typing in the REPL; kernel =printk= shares the
framebuffer console (=console=tty0=, [[file:../sbcl-init.org][sbcl-init.org]]), so it lands mid-prompt.

This is deliberate: nothing here needs secure randomness at boot. To seed
instantly, enable =CONFIG_HW_RANDOM= + =CONFIG_HW_RANDOM_VIRTIO= and add =-device
virtio-rng-pci= to the QEMU line ([[file:../kernel-config.org][kernel-config.org]], "Deliberately OFF").
