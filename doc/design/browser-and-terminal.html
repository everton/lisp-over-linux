The browser and the terminal

Two programs that are not Lisp — Google Chrome and bash — living inside an environment where one Lisp process draws every pixel. How they get there, how they talk to us, and how what they produce ends up on the framebuffer.

1. The big picture

Everything you see is drawn by one process: the SBCL image that is PID 1. It owns /dev/fb0 and the keyboard and mouse devices. Chrome and bash never touch the screen or your input. They are child processes that the Lisp starts, talks to through file descriptors, and draws on their behalf.

Why not let Chrome draw itself?

There is no X server or Wayland compositor here, and doc/processes.org §1 keeps one rule: only the Lisp writes to the framebuffer. So Chrome runs headless and sends us pictures of the page, which we blit like any image.

Why containers?

Our root filesystem is a small initramfs: no libc programs, no fonts, no shell. Chrome needs 81 shared libraries, fontconfig and /proc/self/exe; bash needs a distribution. A container lends them the laptop's own Debian, read-only, as their /.

2. The shared foundation: a container

Both panes ask container-command-line (containers.lisp) for the command that runs a program "inside". It returns an argv for /sbin/lol-ct, a small static C program shipped in the initramfs:

(container-command-line '("bash" "-l") :cwd "/home/everton")
=> ("/sbin/lol-ct" "-n" "default" "-C" "/home/everton" "--" "bash" "-l")

Why a separate C helper? unshare(CLONE_NEWUSER) refuses a process with more than one thread, and our Lisp has several. So the namespace work needs a fresh, single-threaded process. lol-ct does it in three generations:

Three consequences you can feel:

  • You are yourself inside. The uid map is 1000 → 1000, so files you create in /home are yours, outside as well. Host files owned by anyone else show as nobody, which is why apt-get install fails inside: the container can run the host's distribution but not administer it.
  • Changes to /usr, /etc, /var, /opt persist across runs and boots, in the overlay's upper layer under ~/.lol/ct/<name>/. Deleting that directory resets the container. Each name is its own container: Chrome gets web, your shell gets default, so their writes never mix.
  • The network is shared (no NET namespace). A rails s on :3000 inside is reachable from the Lisp, and DNS works the same in and out.

3. The browser

The web pane contains no web engine. It drives one: Chrome, through the Chrome DevTools Protocol (CDP), the same JSON protocol that Chrome's F12 panel, Puppeteer and Playwright use. Three kinds of message make up the whole grammar:

;; a COMMAND, from us
{"id":7, "method":"Page.navigate", "params":{"url":"https://example.com"}}
;; its RESPONSE, same id
{"id":7, "result":{"frameId":"…"}}
;; an EVENT, whenever Chrome likes, no id
{"method":"Page.screencastFrame", "params":{"data":"/9j/4AAQ…", "sessionId":…}}

3.1 The wire: a pipe on fds 3 and 4

Chrome usually serves CDP on a TCP port. Started with --remote-debugging-pipe, it reads commands from fd 3 and writes replies and events to fd 4, each message ending with a NUL byte (which JSON text never contains). No port another program could reach, no WebSocket framing. SBCL's run-program only gives a child pipes on stdin and stdout, so a tiny shell moves them before becoming Chrome (pipe-wrapper, start-chrome-process):

/sbin/lol-ct -n web -e LANG=C.UTF-8 -- /bin/sh -c \
  'exec 3<&0 4>&1 >>/tmp/lol-chrome-1.log 2>&1 </dev/null;
   exec /usr/bin/google-chrome --headless=new --remote-debugging-pipe \
        --user-data-dir=~/.lol/web/chrome --password-store=basic ...'

3.3 Pixels: the screencast

Page.startScreencast makes Chrome send a Page.screencastFrame event every time the page repaints: the frame as a JPEG, base64-encoded inside the JSON. We decode it (base64, then stb_image, the same decoder the image previews use) into the canvas's own pixels and blit it into the pane. Three rules keep this cheap:

  • Flow control by ack. Each frame is answered with Page.screencastFrameAck, and Chrome sends no new frame until it gets one. A slow reader (us, under QEMU) gets fewer frames, never a growing backlog.
  • Only the newest frame is decoded. A frame replaced before we drew it is dropped undecoded. An idle page sends nothing at all, so it costs no CPU.
  • Only the visible tab streams. Switching tabs sends Page.stopScreencast to the one you left. When only the page changed, just the page rectangle goes to the screen.

The pane's size becomes the page's: Emulation.setDeviceMetricsOverride lays the page out as if the window were exactly the pane. Zoom (C-+) is its deviceScaleFactor, so text is re-laid-out larger, not a stretched picture.

3.5 Tabs are trails

Each web tab is a trail of its own, in the same tab strip as the Workspace and the file manager. SuperL-1…9 reach it, SuperL-w closes it. Closing needs no hook: every turn, web-service notices a tab that no trail holds any more and closes its Chrome target. A link that opens a new window (target=_blank, Ctrl-click) arrives as Chrome's Target.targetCreated event and becomes a new trail.

3.6 The things headless Chrome cannot show us

Pickers

A <select>'s list, a date or colour picker are drawn by the browser's UI, not the page, and the screencast only sees the page. So web.lisp injects a small script (web-picker-setup) that reports when one opens; we draw the choices ourselves and send the pick back.

Being "Chrome" to websites

Headless Chrome says HeadlessChrome in its user agent, and some sites refuse it. We override the UA and, since today, its client hints (web-ua-metadata). Without them Chrome sends no Sec-CH-UA headers, which Google's sign-in reads as an automated browser.

3.7 Its life

Its profile lives in ~/.lol/web/chrome, so logins and cookies survive reboots. If Chrome dies, every tab says so and r restarts it. At power-off, web-shutdown sends Browser.close first, so Chrome writes its profile while /home is still writable. Measured in the guest with one simple page: Chrome's processes total about 436 MB (PSS).

4. The terminal

A program like bash or vim does not write "to the screen". It writes to its standard output, and behaves interactively (prompt, line editing, colours, full-screen drawing) only if that output is a terminal. Give it a pipe and it becomes a batch program. So the terminal pane gives bash a pseudo-terminal: a pair of devices the kernel makes on demand, so a process (us) can be the terminal for another one.

4.1 Starting it: SuperL-Return

open-default-terminal asks default-terminal-command for "as good a shell as this machine offers", and takes the first that works:

  1. bash in the container default, when lol-ct and the host root are there: lol-ct -n default -C <where you were> -- bash -l. The tab says "shell in default". This is the normal case on the laptop.
  2. the host's bash run straight from /mnt/host through its dynamic loader ("host bash (limited)");
  3. a Lisp REPL (/sbin/lisp repl);
  4. on the development host itself, its own $SHELL.

pty-spawn (pty.lisp) then starts that argv on a fresh pty. The child must make the slave its controlling terminal, or bash says "no job control" and ^C kills nothing. That takes setsid() and then opening the slave. SBCL's own run-program :pty does not call setsid, so pty.lisp uses posix_spawn with glibc's POSIX_SPAWN_SETSID, plus a file action that opens the slave on fd 0. posix_spawn is vfork+exec done inside libc: the child runs no Lisp at all, which is what makes it safe from a garbage-collected image.

4.2 Output: bytes → grid of cells → pixels

What bash prints is not text but a stream of bytes with control sequences mixed in: ESC[1;32m means "bold green", ESC[2J "clear the screen", ESC[?1049h "switch to the alternate screen" (vim, less). poc/terminal.lisp is a VT engine: term-feed takes bytes and updates a grid of cells (character, colours, attributes). It knows no pixels and no file descriptors, so it is tested on the host against output recorded from real programs.

Its parser is Paul Williams' DEC-compatible state machine: every byte belongs to exactly one state, so a terminal never prints half an escape sequence, and CAN, SUB or ESC can always pull it back to the ground state. Click a state to see what it does:

Then terminal-paint-dirty repaints only the rows that changed, with the browser's own font (box-drawing characters are drawn as lines, so they join cell to cell). A shell echoing one character sends one row to /dev/fb0, not the frame.

4.3 Input: keys → the bytes a program expects

terminal-key sends everything to the program, except the SuperL layer (tabs, the Spotter, leaving), which stays the environment's on every pane. So C-c, C-g, Esc belong to bash or vim, as in any terminal. encode-key turns a key into bytes: ↑ becomes ESC[A (or ESC O A when the program asked for application cursor mode), C-c becomes byte 3, which the line discipline turns into SIGINT.

  • Shift-PageUp/PageDown and the wheel scroll the history; Shift-Insert pastes (bracketed, if the program asked).
  • Press and drag selects text into our clipboard. If the program asked for the mouse (vim's mouse=a, htop), it gets the clicks instead, and Shift takes them back for selecting, as in xterm.
  • A font change re-flows the grid: the new size goes to the program by TIOCSWINSZ, and the kernel sends it SIGWINCH, exactly as when an xterm window is resized.
  • Close the tab and terminal-sweep hangs the program up; dead children are reaped (pty-reap-orphans).

5. How both fit the event loop

The environment's loop (fb-browser.lisp) sleeps in one poll(2) on every file descriptor that can wake it, and wakes only when one has something. Chrome's reply pipe and each terminal's pty master are simply more fds in that poll. Each pane registers a service (fb-register-service): :fd says what to watch, :run what to do when it is ready.
