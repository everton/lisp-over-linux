#+TITLE: The framebuffer — from pixels in RAM to text on the laptop panel
#+STARTUP: showall

Parent doc: [[file:micro-distro.org][micro-distro.org]] · kernel options:
[[file:kernel-config.org][kernel-config.org]] (Display section) · Lisp side:
[[file:sbcl-init.org][sbcl-init.org]]. Companion: [[file:fonts.org][fonts.org]] — how *our own* Lisp renderer turns a
character into pixels (glyphs → pixels), where this file covers pixels → panel.

Why this file exists: the framebuffer is what was missing the day the laptop
booted to a *black screen*. Understanding it explains that bug, the four Display
=CONFIG_= options, and how we could draw graphics from Lisp.

* The one-sentence essence

A framebuffer is *a region of memory where each pixel is a number*; the display
hardware continuously *scans that memory out* to the panel. "Drawing" is just
writing bytes into that region. Everything else is plumbing.

* 1. What a framebuffer physically is

Reserve a block of RAM with one slot per pixel (you have 32 bpp => 4 bytes:
blue, green, red, pad). The GPU's display controller has a register pointing at
the start of that block and, ~60x/second, walks it in order pushing each pixel
to the panel. That walk is *scanout*. The screen is a *view onto memory*: store
a color into a pixel's slot and it appears on the next scanout — no API, just a
memory write.

Two numbers define the layout:
- *bpp* — BITS per pixel (you: 32, i.e. 4 bytes). The name is bits, which is why
  the formula below divides by 8; sysfs calls it =bits_per_pixel= for that reason.
- *pitch* / *stride* — bytes from the start of one row to the start of the next
  (usually width*bpp, but may be padded for alignment, so it is its OWN number).

The address of pixel (x, y) — the only math in the whole subsystem:

#+begin_src
offset = y * pitch + x * (bpp / 8)
#+end_src

* 2. Text mode vs framebuffer — and the black-screen bug

*Old VGA text mode* stored CHARACTERS, not pixels: a region at =0xB8000= held
2 bytes per cell (ASCII code + color), and the video card's *font ROM* turned
code =0x41= into the pixels of an "A" in hardware. The CPU never touched a
pixel. The BIOS guaranteed this existed at power-on for ~30 years.

*Modern UEFI* boots straight into a graphical framebuffer and, on most laptops,
provides *NO legacy VGA text mode at all* — no character memory, no font ROM.
The panel is pure pixels.

That is exactly the original bug: the kernel ran fine but assumed it could write
characters to a text mode that did not exist on real UEFI => healthy kernel,
black screen. The fix was not "fix the kernel" but "give the kernel a way to
render text AS pixels" => =FB_EFI= + =FRAMEBUFFER_CONSOLE=.

* 3. Getting a framebuffer without a GPU driver (efifb)

Writing a real driver for the laptop's specific GPU is huge and vendor-specific.
We do NONE of it. UEFI firmware has *already* programmed the GPU and set up a
working framebuffer (it needs one for its own menus) and exposes the details via
the *GOP — Graphics Output Protocol*: framebuffer physical address, width,
height, pitch, pixel format.

The EFISTUB kernel reads those GOP values; then =CONFIG_FB_EFI= (=efifb=) is a
deliberately DUMB driver: it does not program the GPU, it just *reuses the
framebuffer the firmware already set up*. It inherits the mode, cannot change
resolution, does zero acceleration — but it is tiny and works on virtually any
UEFI machine. Right trade-off for a minimal distro.

* 4. fbcon — turning printk/format into pixels

A framebuffer only knows pixels; the kernel speaks characters (printk, tty, SBCL
=format=). =CONFIG_FRAMEBUFFER_CONSOLE= (=fbcon=) bridges them: it is the *font
ROM reimplemented in software*. It carries a built-in bitmap font; when the
console says "put 'A' at row 5 col 12" it looks up the glyph bitmap and writes
its pixels into the framebuffer (using the offset math above, scaled by the font
cell size). It does in the CPU what the VGA card did in hardware.

The full stack the "Supervisor up" banner travels through:

#+begin_src
SBCL (format t ...) / kernel printk
   |  characters
   v
 tty layer            (CONFIG_TTY)
   |
 virtual terminal     (CONFIG_VT, VT_CONSOLE)   scrollback, cursor
   |  "draw glyph G at cell (row,col)"
   v
 fbcon                (FRAMEBUFFER_CONSOLE)      software font: glyph -> pixels
   |  pixel writes
   v
 efifb                (FB_EFI) -> /dev/fb0       firmware's framebuffer memory
   |
   v
 GPU scanout -> the laptop panel
#+end_src

Every box is one of the Display =CONFIG_= options. Remove fbcon and the chain
breaks at "glyph -> pixels": black screen again. That is why FB + FB_EFI +
FRAMEBUFFER_CONSOLE + VT/TTY must all be on together.

* 5. /dev/fb0 — driving the pixels yourself

Because we have =CONFIG_FB= + =CONFIG_FB_DEVICE= + devtmpfs, the raw framebuffer
is the device file */dev/fb0*. That file IS the pixel memory. Use it via:
- *seek + write*: lseek to =y*pitch + x*bpp=, write the pixel bytes; or
- *mmap*: map it into your address space and store directly (the fast path).

Mode parameters are not guesswork:
- =/sys/class/graphics/fb0/virtual_size=   -> "WxH"
- =/sys/class/graphics/fb0/stride=         -> pitch in bytes
- =/sys/class/graphics/fb0/bits_per_pixel= -> bpp
- color channel offsets (which byte is R/G/B): =ioctl(FBIOGET_VSCREENINFO)=
  (sysfs does not expose them; efifb is commonly 32bpp BGRX = bytes [B,G,R,pad]).

SBCL can do all of this — plain binary file I/O on /dev/fb0, or =sb-alien= mmap,
the same FFI it already uses for =reboot(2)=. So the Lisp machine is not limited
to text; it can paint the screen. (No extra kernel option needed — FB is already
on; drawing is PURE USERLAND.)

* 5½. A memory area, or a file? — what =/dev/fb0= actually is

§1 says the framebuffer is *memory*; §5 says it is a *file*. Both are true, and
the ambiguity trips people up, so: a quick note on which is which.

*It is a character device, not a synthesised file.* Compare =/proc/meminfo=:
nothing anywhere holds those bytes: the kernel *generates* them, freshly
formatted, each time you read. =/dev/fb0= is the opposite. The bytes genuinely
exist, in hardware, whether or not anyone opens the file. The file is a *handle
on real storage*, the way =/dev/sda= is.

*The kernel is a doorway, not a translator.* Byte /N/ of the file is byte /N/ of
the framebuffer. No format conversion, no offset remapping, no bookkeeping in
between. That is precisely why one line of arithmetic (§1's
=y*pitch + x*(bpp/8)=) is the whole subsystem: there is no second coordinate
system to translate into.

*"Byte-addressed" is not about word size.* Every byte has its own address; 64-bit
describes how much the CPU moves per instruction and how wide a pointer is —
*not* the granularity of memory. Pixels are densely packed 4-byte cells, so a
64-bit word spans exactly *two* pixels. Nothing is padded out to word size.

Two things that *are* padding, and are easy to confuse with that:

- *The =X= byte inside each pixel* (the =pad= in BGR*X*). A colour needs 3 bytes;
  the fourth exists so a pixel is a power of two, making the address a *shift*
  instead of a multiply-by-3. A hypothetical 24bpp framebuffer would have pixels
  straddling word boundaries — which is exactly why our code bails out unless
  =bpp = 32=.
- *Stride padding at the end of each row* (§1's warning that pitch may exceed
  =width*bpp/8=). That is a scanout alignment property of the hardware, nothing
  to do with the CPU.

*Where the memory physically is.* Usually *not* ordinary system RAM: it is VRAM
sitting behind a PCI BAR, or "stolen" system RAM that the GPU owns — either way
mapped into the CPU's physical address space by the firmware. That is *MMIO*:
the same =mov= instruction, but the address decodes to a device rather than to a
DIMM. Two consequences we actually feel:

- Writes are slower than RAM writes and behave differently under caching, which
  is why the kernel maps it write-combining (=ioremap_wc=).
- Each =write(2)= additionally costs a *syscall*. That is the whole reason
  [[file:../initramfs/framebuffer.lisp::defun draw-alien][=draw-alien=]] and [[file:../poc/fb.lisp::defun present-fb][=present-fb=]] build an entire row in a plain Lisp array and
  issue *one* =write-sequence= per row: 150 syscalls for the alien, not 38,400.

*Two doors onto the same memory*, then — and the unit differs between them:

| door             | you index by | using       |
|------------------+--------------+-------------|
| file I/O (§5)    | *bytes*      | =stride=    |
| =mmap= (§5, §9.4)| *words*      | =stride/4=  |

Same memory, two granularities. That is why this document insists on writing
=bpp/8= rather than leaving the unit implicit — the =/8= is the only thing
keeping the two readings apart.

* 6. Limits: efifb vs DRM/KMS

| capability            | efifb (what we have)        | DRM/KMS (real GPU driver)   |
|-----------------------+-----------------------------+-----------------------------|
| programs the GPU      | no — inherits firmware mode | yes — full modesetting      |
| change resolution     | no (locked to firmware)     | yes                         |
| 2D/3D acceleration    | none — CPU writes pixels    | hardware-accelerated        |
| size / complexity     | tiny, universal             | large, vendor-specific      |
| right for minimal?    | YES                         | overkill                    |

efifb is the lowest-common-denominator that always works. Acceleration, a
window system, or changing resolution would mean the real DRM/KMS driver for the
laptop's chip — much bigger, against this project's spirit.

* 6½. No GPU — what we give up, and what a real driver would cost

§6's table says *what* efifb cannot do. Now that the code browser
([[file:code-browser.org][code-browser.org]]) paints the entire screen rather than one alien in a corner,
it is worth being concrete about *which of our own code* is paying for that, and
about what the alternative would actually involve. This section does not change
the verdict in §6 — it makes both sides of it honest.

** (a) What we have today that would benefit

Every item here is real code in this repo, not generic GPU marketing.

- *Full-screen repaint is a CPU copy.* [[file:../poc/fb.lisp::defun present-fb][=present-fb=]] renders a 1280×800 canvas in
  Lisp and pushes it with *800 =write(2)= calls per frame* (§9.1). With a GPU we
  would not push anything: the canvas would already live in a GPU buffer, and
  "presenting" would be a *page flip* — telling the display controller to scan
  out a different address. A pointer swap instead of 4 MB of copying.
- *The §9.4 memcpy TODO exists only because we hand bytes to the kernel.* We
  unpack each 32-bit canvas word into four byte slots to satisfy the file-I/O
  interface, a copy that §9.2 shows is semantically a no-op. A DRM *dumb buffer*
  is mapped straight into our address space, so the renderer would draw *into*
  the scanout memory and the copy would vanish rather than be optimised.
- *No vsync, no double buffering → tearing.* This is the honest current
  limitation. We write directly into the memory being scanned out, so a repaint
  can be caught halfway by the display controller and the panel shows the top of
  the new frame above the bottom of the old one. DRM/KMS's answer is a page flip
  *scheduled on vblank*: the flip takes effect between refreshes, so a frame is
  never half-visible. There is no way to get that with efifb — there is no vblank
  event to wait on.
- *Resolution is whatever the firmware chose.* §6 already records that efifb
  cannot modeset; the consequences are that we cannot change resolution, drive a
  second monitor, or rotate the panel. The browser simply reads =virtual_size=
  and adapts.
- *Font scaling and any future TrueType path are pure CPU rasterisation.*
  [[file:fonts.org][fonts.org]] §7's Path C (outline fonts) means rasterising glyphs in Lisp; a GPU
  would normally cache glyphs in a texture atlas and composite them. Today every
  glyph is stamped bit by bit by [[file:../poc/canvas.lisp::defun draw-string][=draw-string=]].

** (b) What shipping a real driver would require

The card in this laptop is =00:02.0 [8086:8a52] Intel Iris Plus Graphics G7=
(Ice Lake-LP), driver *=i915=*. Four layers, mirroring the Wi-Fi analysis in
[[file:networking.org][networking.org]] §7:

- *Kernel side*, all =y= since we ship no modules: =CONFIG_DRM= plus the vendor
  driver (=CONFIG_DRM_I915=), and =CONFIG_DRM_FBDEV_EMULATION= to keep a working
  text console on top of it — without that we would trade our console away for
  the GPU.
- *Firmware blobs.* Modern Intel graphics will not fully come up without them,
  and for Ice Lake =i915= asks for three: =i915/icl_dmc_ver1_09.bin= (display
  microcontroller — the part that owns power states), =i915/icl_guc_70.1.1.bin=
  and =i915/icl_huc_9.0.0.bin= (graphics/HEVC microcontrollers). Proprietary,
  binary-only, from =linux-firmware=. The distinction is the same one §7 of
  networking.org draws for Wi-Fi: *the driver is in-tree GPL, the firmware is the
  proprietary part, and firmware is data, not code.* The rule this project
  already adopted applies unchanged — *fetch at pack time, never commit*, which
  keeps the repo MIT and source-only. =CONFIG_EXTRA_FIRMWARE= is the alternative
  that bakes the blob into the bzImage and likewise never touches git.
- *Userland gets much heavier.* DRM is not =seek= + =write= on a device file; it
  is an *ioctl/GEM* API. The minimum path to a pixel is
  =DRM_IOCTL_MODE_CREATE_DUMB= → =DRM_IOCTL_MODE_MAP_DUMB= → =mmap= →
  =DRM_IOCTL_MODE_ADDFB= → =DRM_IOCTL_MODE_SETCRTC=, and then
  =DRM_IOCTL_MODE_PAGE_FLIP= per frame, plus reading connectors and encoders to
  find out what to set the mode *to*. All of it is doable in =sb-alien= — it is
  the same FFI that already drives =reboot(2)=, =ioctl=, =poll= and =KDSETMODE= —
  but it is a genuine subsystem to write and debug, not an afternoon.
- *Size, honestly.* In this tree =drivers/gpu/drm/i915= is *14 MB of source,
  418,079 lines* of =.c= and =.h=. Our entire project — every Lisp module, the C
  preinit, all the shell — is *7,222 lines*. The driver is roughly *58×* the
  whole thing we are building. By contrast [[file:../linux/drivers/video/fbdev/efifb.c][=efifb.c=]] is *607 lines*: that ratio,
  ~690:1, is the trade-off §6's table summarises in one word.

** Verdict (unchanged)

efifb remains right for this project. We are not rendering video or running a
compositor; we repaint a text-dense browser on keystrokes, and a CPU-drawn
1280×800 frame is fast enough today (§9.4 says as much). The cost of the
alternative is not "a config option" but a 418k-line driver, three proprietary
blobs that would have to be fetched rather than committed, and an ioctl-based
graphics stack to write in Lisp — for benefits (page flips, vsync, modesetting,
acceleration) that a browser bound by keypresses barely notices. The one genuine
loss we accept in exchange is *tearing*, and that is worth stating plainly rather
than pretending direct scanout writes are free.

* 7. Increasing the fbcon font size — *REVERTED to the default 8x16*

*Update:* the 16x32 switch below was later undone — we went back to the mainline
default *8x16* (=# CONFIG_FONT_TER16x32 is not set=, and the =fbcon=font:= param
dropped from =CONFIG_CMDLINE=). Reason: 80x25 was too cramped, and fbcon has *no
scrollback* on mainline, so whatever scrolls off tty0 is gone. 8x16 gives
*160x50* — twice the rows and columns, so multi-line output (a REPL session, the
=m)= memory readout) stays on screen instead of scrolling away. The larger font
was solving a "too small on the panel" problem that the extra screen real estate
matters more than. The section below is kept as the record of how it was done
(and how to redo it); just invert the two config lines and rebuild.

fbcon renders a *fixed bitmap font*; "bigger text" means selecting a font with a
larger cell, not magnifying. fbcon computes
=cols = xres/cell_w=, =rows = yres/cell_h=, so a bigger cell => bigger glyphs and
fewer rows/cols. There is no integer-scaling knob in mainline fbcon. Concretely
on the 1280x800 framebuffer: 8x16 gave 160x50; TER16x32 gives 80x25.

The default 8x16 was too small on the real laptop panel, so we switched to
*Terminus 16x32* (double the height). What was changed:

1. Kernel config: =CONFIG_FONTS=y= + =CONFIG_FONT_TER16x32=y= (kept
   =CONFIG_FONT_8x16=y= as fallback).
2. Cmdline (=CONFIG_CMDLINE= is baked in this build): appended
   =fbcon=font:TER16x32=. Final value:
   ="console=ttyS0,115200 console=tty0 initrd=initramfs.cpio fbcon=font:TER16x32"=
3. Rebuilt the kernel (=build.sh --kernel=). Incremental rebuild on 8 cores took
   *~27 s* wall (it is just a few font objects + the vmlinux relink + bzImage);
   a no-op make is ~3 s. The build counter auto-bumped #19 -> #20.

Gotcha hit while doing it: =scripts/config --enable FONT_TER16x32= silently did
NOT set the symbol on this tree; a plain =sed= edit (then =make olddefconfig=)
did, and the value survived because its deps (=FRAMEBUFFER_CONSOLE=y=, not SPARC,
=FONTS=y=) are met.

Notes:
- Largest mainline built-in is TER16x32; beyond that needs a custom font.
- =setfont= (kbd package) could change fonts at runtime, but we do not ship that
  userland, so compile-in + cmdline is the realistic path here.
- The supervisor clears the screen for its menu and repaints the alien *after*
  the menu each cycle, so it stays in the corner regardless of font size (see
  section 8).

* 8. Drawing an image (the Land-of-Lisp alien) in a corner — *IMPLEMENTED*

Drawing a raster image is PURE USERLAND (no new kernel option — /dev/fb0
exists). The supervisor now paints the official Lisperati alien into the
top-right corner at boot and on the =a= menu key. Verified in QEMU+OVMF:
"alien drawn at (1008,16) on a 1280x800 framebuffer." with correct colours.

How it is wired up:

1. *Source -> raw pixels at build time (one-off)*: the sprite is
   =lisplogo_alien_256.png= (256x150, RGBA with a real alpha channel),
   converted ONCE on the dev host to a raw RGBA blob and committed:
   #+begin_src sh
   convert alien256.png -depth 8 RGBA:alien.rgba   # 256*150*4 = 153600 bytes
   #+end_src
   It is shipped as =/alien.rgba= via a =file= line in =initramfs.sbcl.list=.
   (We pre-generate rather than convert in =build.sh= so the build needs no
   ImageMagick and no network. Both =alien.rgba= and the source PNG live in
   =initramfs/=.)
2. *Read the framebuffer geometry at runtime* from sysfs — =read-fb-geometry=
   parses =virtual_size= ("W,H"), =stride=, =bits_per_pixel=. We do NOT assume
   pitch = width*bpp; we read =stride=.
3. *Place it top-right*: =x0 = max(0, xres - 256 - margin)=, =y0 = margin=
   (margin 16). Height is clamped to the screen.
4. *Blit row by row into /dev/fb0* (=draw-alien=, opened =:direction :io=):
   for each sprite row, seek to =(y0+y)*stride + x0*4=, READ the existing
   background row, overlay only pixels whose *alpha >= 128*, then write the row
   back. The read-modify-write is what gives a clean transparent cutout instead
   of a black rectangle — and it is the hook for true alpha blending later.
5. *Pixel format*: efifb here is 32bpp *BGRX* (bytes Blue,Green,Red,pad), so we
   write =B,G,R= from the source =R,G,B=. Confirmed correct (alien is green, not
   magenta). If a different machine reports swapped colours, exchange the two
   marked B/R lines in =draw-alien=.

Persistence: fbcon shares the framebuffer, so console scrolling overwrites the
alien. The supervisor handles this by clearing the screen before its menu and
calling =draw-alien= *after* printing the menu on every cycle — so the alien
sits in the (otherwise blank) top-right corner and is repainted each prompt.
=draw-alien= is silent during these routine redraws; the =a)= menu key calls it
with =:announce t= to print the "alien drawn at …" status line.

Dependencies:
- Build host (one-off only): ImageMagick =convert= + the source PNG. Not needed
  for normal rebuilds.
- Runtime: /dev/fb0 + file I/O (already present). NO kernel rebuild needed —
  =build.sh= (no =--kernel=) suffices.

This is the clean contrast with the font question (section 7): bigger fonts = a
KERNEL change; drawing an image = USERLAND only.

See: =draw-alien= / =read-fb-geometry= in =initramfs/framebuffer.lisp=
(=supervisor.lisp= only calls them: from =print-menu=, and from the =a)= key).

* 9. Full-screen: =present-fb= and KD_GRAPHICS

Sections 5–8 were written when the alien was the only thing we painted. The code
browser ([[file:code-browser.org][code-browser.org]]) is now the *main* consumer of /dev/fb0, and it added two
things worth recording here.

** 9.1 =present-fb= — =draw-alien= generalised

=lol.fb:present-fb= ([[file:../poc/fb.lisp][poc/fb.lisp]]) blits a whole *canvas* instead of one sprite,
but the mechanism is unchanged: read the geometry from sysfs, then, per row,
=file-position= to =(y0+y)*stride + x0*4= and =write-sequence= the row. Its own
header says so — "the same file-position + write-sequence path draw-alien
already uses — proven to work on this machine". Same 32bpp bail-out, same
never-assume-stride rule. =lol.fb:fb-geometry= is =read-fb-geometry= under
another name, in the POC's package.

The difference from =draw-alien= is what it does NOT do: no read-modify-write.
The alien needs to read the background back to honour its alpha cutout (§8.4);
a full-screen canvas *owns* every pixel it covers, so it just overwrites.

*Row at a time, not pixel at a time* — deliberately. Each =write-sequence= is
one =write(2)=; the row buffer is built in ordinary Lisp memory first. A
1280x800 repaint is 800 syscalls, not 1,024,000.

** 9.2 The pixel format lines up for free

The canvas stores one =(unsigned-byte 32)= per pixel as =#x00RRGGBB=. On x86
(little-endian) that word sits in memory as the bytes =B,G,R,00= — which *is*
BGRX, exactly what efifb scans out (§8.5). No conversion, no swizzle table: the
in-memory representation the renderer wants and the one the panel wants are the
same bytes. That is not luck, it is why =#x00RRGGBB= was chosen.

** 9.3 KD_GRAPHICS — telling fbcon to stand down

§8 solved fbcon sharing the framebuffer by *ordering*: repaint the alien after
the menu, every cycle. A full-screen app cannot win that way — fbcon's cursor
blink and any stray =printk= would crawl across the picture.

The real fix is =ioctl(KDSETMODE, KD_GRAPHICS)= on =/dev/tty0=, wrapped as
=lol.fb:with-graphics-console=. It tells the kernel console to *stop rendering*.
Two properties make it the right tool:

- It stops fbcon *drawing*, not the tty *delivering keys* — so the existing
  raw-mode keyboard path needed no changes at all.
- The macro restores =KD_TEXT= in an =unwind-protect=. Non-negotiable: leave the
  VT in graphics mode and you are staring at a dead console with no way back.

Note this is the console-blanking counterpart of everything in §4: §4 turns
fbcon *on* so text appears; §9.3 turns it off so it does not vandalise our
pixels. Both are the same shared-resource problem seen from opposite ends.

Used by =run-browser-fb= ([[file:../initramfs/fb-browser.lisp][fb-browser.lisp]]) around its whole event loop, and by
=poc/run-guest.lisp=.

** 9.4 TODO (near future): make the blit a real memcpy

=present-fb= currently *unpacks each pixel by hand* ([[file:../poc/fb.lisp][fb.lisp]], the =dotimes (x w)=
body): it masks and shifts the 32-bit canvas word into four =(unsigned-byte 8)=
slots of a row buffer, one pixel at a time, before writing the row.

Per §9.2 this copy is *semantically a no-op* — source and destination bytes are
already identical. It exists only because SBCL will not let you view an
=(unsigned-byte 32)= array as an =(unsigned-byte 8)= array without going through
=sb-alien= (or a displaced-array trick). So we pay a per-pixel mask/shift/store
loop to move bytes to where they already were.

The fix, when full-screen repaints start to feel slow:

1. =mmap= /dev/fb0 via =sb-alien= (§5 already flags mmap as the fast path; we
   have the FFI — it is what =reboot(2)=, =ioctl=, and =poll= already use).
2. Keep the canvas as 32-bit words and copy word-wise. Each aligned 64-bit store
   carries *two pixels* (pixels are densely packed 4-byte cells; nothing is
   padded to word size).
3. That also drops the syscall per row to zero — stores go straight to the
   mapped MMIO region.

Not urgent: the row-at-a-time path is fast enough for the browser today, and it
is a great deal less code. Filed here so the reason for the ugly inner loop is
on the record, and so the optimisation is not re-derived from scratch later.
