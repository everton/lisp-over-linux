#+TITLE: The framebuffer — from pixels in RAM to text on the laptop panel
#+STARTUP: showall

This doc is the *output* half of the machine's interactive surface: pixels → panel.
The *input* half — keyboard, mouse, wheel, the raw =/dev/input/event*= devices — is
[[file:input.org][input.org]]. How our own Lisp renderer turns a character into pixels is
[[file:fonts.org][fonts.org]].

Related: [[file:micro-distro.org][micro-distro.org]] (the boot chain), [[file:kernel-config.org][kernel-config.org]] (Display section),
[[file:sbcl-init.org][sbcl-init.org]] (the Lisp side).

Without a framebuffer, a UEFI laptop boots a healthy kernel to a *black screen*.
Understanding it explains that failure, the four Display =CONFIG_= options, and how
Lisp draws graphics.

* The one-sentence essence

A framebuffer is *a region of memory where each pixel is a number*; the display
hardware continuously *scans that memory out* to the panel. Drawing is writing bytes
into that region. Everything else is plumbing.

* 1. What a framebuffer physically is

A block of memory holds one slot per pixel — at 32 bpp, 4 bytes: blue, green, red,
pad. The GPU's display controller has a register pointing at its start and, about 60
times a second, walks it in order pushing each pixel to the panel. That walk is
*scanout*. Store a colour into a pixel's slot and it appears on the next scanout: no
API, just a memory write.

Two numbers define the layout:

- *bpp.* BITS per pixel (here 32, i.e. 4 bytes). It's bits, which is why the formula
  divides by 8; sysfs calls it =bits_per_pixel=.
- *pitch / stride.* Bytes from the start of one row to the start of the next. Usually
  width × bpp/8, but it may be padded for alignment, so it's its *own* number.

The address of pixel (x, y) — the only math in the whole subsystem:

#+begin_src
offset = y * pitch + x * (bpp / 8)
#+end_src

* 2. Text mode vs framebuffer — and the black-screen bug

- *VGA text mode* stored CHARACTERS, not pixels. A region at =0xB8000= held 2 bytes per
  cell (ASCII code + colour), and the card's *font ROM* turned =0x41= into the pixels
  of an "A" in hardware. The BIOS guaranteed it at power-on for about 30 years.
- *Modern UEFI* boots straight into a graphical framebuffer and, on most laptops,
  provides *no legacy text mode at all* — no character memory, no font ROM.

A kernel that writes characters to a text mode that doesn't exist runs fine and shows a
black screen. The fix isn't in the kernel's logic: it's giving the kernel a way to
render text *as pixels* — =FB_EFI= + =FRAMEBUFFER_CONSOLE=.

* 3. Getting a framebuffer without a GPU driver (efifb)

A real driver for a specific GPU is huge and vendor-specific; we write none of it. UEFI
firmware has *already* programmed the GPU and set up a working framebuffer (it needs
one for its own menus). It describes it through the *GOP — Graphics Output Protocol*:
physical address, width, height, pitch, pixel format.

The EFISTUB kernel reads those GOP values, and =CONFIG_FB_EFI= (=efifb=) is a
deliberately dumb driver: it *reuses the framebuffer the firmware set up*. It inherits
the mode, can't change resolution, does no acceleration — and it's tiny and works on
virtually any UEFI machine.

The whole driver is [[file:../linux/drivers/video/fbdev/efifb.c][=drivers/video/fbdev/efifb.c=]] — about 600 lines, worth reading
once. [[file:../linux/drivers/video/fbdev/efifb.c::static int efifb_probe][=efifb_probe=]] is the part that matters:

- *Takes the firmware's numbers* from =screen_info= (=si->lfb_width=,
  =si->lfb_linelength=, =__screen_info_lfb_base=).
- *Maps the address* into kernel space — normally =ioremap_wc=, write-combining (§5½),
  with =ioremap=/=memremap= fallbacks when the EFI memory map asks for other
  attributes.
- *Registers the result.* Nothing programs the display controller, because there's
  nothing efifb could set.

* 4. fbcon — turning printk/format into pixels

A framebuffer knows pixels; the kernel speaks characters (printk, tty, SBCL =format=).
=CONFIG_FRAMEBUFFER_CONSOLE= (=fbcon=) bridges them: it's the *font ROM reimplemented
in software*. It carries a built-in bitmap font; when the console says "put 'A' at row
5 col 12" it looks up the glyph and writes its pixels into the framebuffer, using §1's
offset math scaled by the cell size.

- *[[file:../linux/drivers/video/fbdev/core/fbcon.c][=core/fbcon.c=]]* is the console driver: rows, columns, cursor, scrolling.
- *[[file:../linux/drivers/video/fbdev/core/bitblit.c::static void bit_putcs][=core/bitblit.c='s =bit_putcs=]]* does the stamping — "put a string of
  characters", walking a run of glyph bitmaps and writing their pixels. It's the
  kernel's version of what [[file:fonts.org][fonts.org]] describes our renderer doing in Lisp.

The stack a line of console output travels through:

#+begin_src
SBCL (format t ...) / kernel printk
   |  characters
   v
 tty layer            (CONFIG_TTY)
   |
 virtual terminal     (CONFIG_VT, VT_CONSOLE)   scrollback, cursor
   |  "draw glyph G at cell (row,col)"
   v
 fbcon                (FRAMEBUFFER_CONSOLE)      software font: glyph -> pixels
   |  pixel writes
   v
 efifb                (FB_EFI) -> /dev/fb0       firmware's framebuffer memory
   |
   v
 GPU scanout -> the laptop panel
#+end_src

Every box is one of the Display =CONFIG_= options. Remove fbcon and the chain breaks at
"glyph -> pixels": black screen again. So FB + FB_EFI + FRAMEBUFFER_CONSOLE + VT/TTY
must all be on together.

* 5. /dev/fb0 — driving the pixels yourself

With =CONFIG_FB= + =CONFIG_FB_DEVICE= + devtmpfs, the raw framebuffer is the device
file */dev/fb0*, and that file IS the pixel memory. Two ways in:

- *seek + write.* =lseek= to =y*pitch + x*bpp/8=, write the pixel bytes.
- *mmap.* Map it into your address space and store directly.

Both doors are in one short file, [[file:../linux/drivers/video/fbdev/core/fb_chrdev.c][=core/fb_chrdev.c=]] — the code that makes
=/dev/fb0= a file at all. Its [[file:../linux/drivers/video/fbdev/core/fb_chrdev.c::static const struct file_operations fb_fops][=fb_fops=]] table is §5½'s "doorway, not translator" in
source form: [[file:../linux/drivers/video/fbdev/core/fb_chrdev.c::static ssize_t fb_write][=fb_write=]] bounds-checks your offset and copies your bytes into the
mapped framebuffer, [[file:../linux/drivers/video/fbdev/core/fb_chrdev.c::static ssize_t fb_read][=fb_read=]] copies them back, [[file:../linux/drivers/video/fbdev/core/fb_chrdev.c::static int fb_mmap][=fb_mmap=]] hands the pages to your
process. No transformation in any of them. Device registration lives next door in
[[file:../linux/drivers/video/fbdev/core/fbmem.c][=core/fbmem.c=]].

The mode parameters come from the kernel, not guesswork:

- =/sys/class/graphics/fb0/virtual_size= → "W,H"
- =/sys/class/graphics/fb0/stride= → pitch in bytes
- =/sys/class/graphics/fb0/bits_per_pixel= → bpp
- *Channel offsets* (which byte is R/G/B): =ioctl(FBIOGET_VSCREENINFO)=; sysfs doesn't
  expose them. efifb is commonly 32 bpp BGRX = bytes [B,G,R,pad].

*What sysfs is.* =/sys= is a *virtual filesystem* — no disk behind it — exposing the
kernel's *device model* as a directory tree. Every device gets a directory; every
readable or tunable property becomes a *file* holding a short line of ASCII. Reading
one calls a kernel function that formats the answer on the spot (like =/proc/meminfo=,
and the opposite of =/dev/fb0=, §5½).

So =read-fb-geometry= is plain: to ask how big the screen is, =open= a file and parse
the number. No library, no ioctl, no struct layout. =/sys/class/graphics/= is the
graphics *class* — the kernel groups devices by what they *are* as well as where
they're plugged in — and =fb0= is our one framebuffer.

SBCL does all of this with plain binary file I/O or =sb-alien=, the same FFI it uses
for =reboot(2)=. Drawing needs no extra kernel option: it's pure userland.

* 5½. A memory area, or a file? — what =/dev/fb0= actually is

§1 says the framebuffer is *memory*; §5 says it's a *file*. Both are true.

- *A character device, not a synthesised file.* Nothing holds =/proc/meminfo='s
  bytes: the kernel generates them on each read. =/dev/fb0='s bytes exist in hardware
  whether or not anyone opens the file. It's a *handle on real storage*, like
  =/dev/sda=.
- *A doorway, not a translator.* Byte /N/ of the file is byte /N/ of the framebuffer.
  No format conversion, no remapping — which is why §1's one line of arithmetic is the
  whole subsystem.
- *"Byte-addressed" isn't about word size.* Every byte has its own address; 64-bit
  describes how much the CPU moves per instruction, not memory granularity. Pixels are
  densely packed 4-byte cells, so a 64-bit word spans exactly two pixels.

Two things that *are* padding, easy to confuse with that:

- *The =X= byte in each pixel* (the pad in BGR*X*). A colour needs 3 bytes; the fourth
  makes a pixel a power of two, so the address is a *shift*, not a multiply by 3. A
  24 bpp framebuffer would have pixels straddling word boundaries — which is why our
  code bails out unless =bpp = 32=.
- *Stride padding at the end of each row* (§1). A scanout alignment property of the
  hardware, nothing to do with the CPU.

*Where the memory is.* Usually not ordinary RAM: VRAM behind a PCI BAR, or "stolen"
system RAM the GPU owns, mapped into the CPU's physical address space by the firmware.
That's *MMIO*: the same =mov=, but the address decodes to a device. Two consequences:

- *Slower, different caching.* Hence the kernel's write-combining mapping
  (=ioremap_wc=).
- *Each =write(2)= costs a syscall.* So [[file:../initramfs/framebuffer.lisp::defun draw-alien][=draw-alien=]] builds a whole row in a Lisp
  array and issues *one* =write-sequence= per row: 150 syscalls for the alien, not
  38,400. [[file:../poc/fb.lisp::defun present-fb][=present-fb=]] goes to the end — one syscall per frame (§9.4).

*Two doors onto the same memory*, with different units:

| door              | you index by | using      |
|-------------------+--------------+------------|
| file I/O (§5)     | *bytes*      | =stride=   |
| =mmap= (§5, §9.4) | *words*      | =stride/4= |

That's why this doc writes =bpp/8= rather than leaving the unit implicit — the =/8=
keeps the two readings apart.

* 6. Limits: efifb vs DRM/KMS

| capability         | efifb (what we have)        | DRM/KMS (real GPU driver) |
|--------------------+-----------------------------+---------------------------|
| programs the GPU   | no — inherits firmware mode | yes — full modesetting    |
| change resolution  | no (locked to firmware)     | yes                       |
| 2D/3D acceleration | none — CPU writes pixels    | hardware-accelerated      |
| size / complexity  | tiny, universal             | large, vendor-specific    |
| right for minimal? | YES                         | overkill                  |

efifb is the lowest common denominator that always works. Acceleration or changing
resolution would need the real DRM/KMS driver for the chip — much bigger, against the
project's spirit.

* 6½. No GPU — what we give up, and what a real driver would cost

The code browser paints the whole screen, so §6's trade-off has concrete costs on both
sides.

** (a) What we have today that would benefit

- *Full-screen repaint is a CPU copy.* [[file:../poc/fb.lisp::defun present-fb][=present-fb=]] pushes the Lisp canvas into scanout
  memory with one =pwrite(2)= per frame (§9.4) — 4 MB at 1280×800, every time. With a
  GPU the canvas would live in a GPU buffer and presenting would be a *page flip*:
  telling the display controller to scan out a different address.
- *The copy exists because we hand bytes to the kernel.* A DRM *dumb buffer* is mapped
  into our address space, so the renderer would draw *into* scanout memory and the
  copy would vanish.
- *No vsync, no double buffering → tearing.* We write into the memory being scanned
  out, so a repaint can be caught halfway: the top of the new frame over the bottom of
  the old. DRM/KMS answers with a page flip *scheduled on vblank*. efifb has no vblank
  event to wait on.
- *Resolution is whatever the firmware chose.* No resolution change, second monitor or
  rotation. The browser reads =virtual_size= and adapts.
- *Fonts are pure CPU rasterisation.* TrueType glyphs are rasterised in Lisp
  ([[file:fonts.org][fonts.org]] §4), cached per size, and blended pixel by pixel by
  [[file:../poc/canvas.lisp::defun draw-string][=draw-string=]]; a GPU would composite from a texture atlas. Measured, it doesn't
  matter: a full 1920×1080 screen of text draws in about 5 ms (fonts.org §5). (§7 is
  the /kernel console's/ font, a different thing.)

** (b) What shipping a real driver would require

The Dell XPS 13 9300's GPU is =00:02.0 [8086:8a52] Intel Iris Plus Graphics G7=
(Ice Lake-LP), driver *=i915=*. Four layers, mirroring the Wi-Fi analysis in
[[file:networking.org][networking.org]] §7:

- *Kernel side,* all =y= since we ship no modules: =CONFIG_DRM=, the vendor driver
  (=CONFIG_DRM_I915=), and =CONFIG_DRM_FBDEV_EMULATION= to keep a text console on top —
  without it the console is traded away for the GPU.
- *Firmware blobs.* For Ice Lake, =i915= asks for three: =i915/icl_dmc_ver1_09.bin=
  (display microcontroller — power states), =i915/icl_guc_70.1.1.bin= and
  =i915/icl_huc_9.0.0.bin= (graphics/HEVC microcontrollers). Proprietary, from
  =linux-firmware=. *The driver is in-tree GPL; the firmware is data, not code.* The
  project's rule applies: *fetch at pack time, never commit* (or bake it into the
  bzImage with =CONFIG_EXTRA_FIRMWARE=, which also stays out of git).
- *A much heavier userland.* DRM is an *ioctl/GEM* API, not =seek= + =write=. The
  minimum path to a pixel is =DRM_IOCTL_MODE_CREATE_DUMB= → =DRM_IOCTL_MODE_MAP_DUMB= →
  =mmap= → =DRM_IOCTL_MODE_ADDFB= → =DRM_IOCTL_MODE_SETCRTC=, then
  =DRM_IOCTL_MODE_PAGE_FLIP= per frame, plus reading connectors and encoders to choose
  a mode. Doable in =sb-alien= (the FFI that drives =ioctl=, =poll=, =KDSETMODE=), but a
  real subsystem to write and debug.
- *Acceleration brings a libc problem.* The dumb-buffer path is pure =ioctl(2)=. Real
  2D/3D goes through *Mesa*, whose driver modules (=dri/iris_dri.so= for this chip — on
  current Mesa a symlink into the =libdril_dri.so= megadriver) are *glibc-linked*
  objects loaded with =dlopen=. Our userland is musl-static ([[file:micro-distro.org][micro-distro.org]]
  § "Shrinking init with musl libc"), and musl and glibc aren't ABI-compatible.
  [[https://github.com/pg83/solo][pg83/solo]] bridges a glibc =.so= onto musl with its own ELF loader and ABI shim —
  another loader to carry. Modesetting and page flips need none of it.
- *Size.* =drivers/gpu/drm/i915= is about 419,000 lines of =.c= and =.h= (kernel
  7.2.5); [[file:../linux/drivers/video/fbdev/efifb.c][=efifb.c=]] is about 600. That ~690:1 ratio is §6's table in one number.

** Verdict (unchanged)

efifb stays. We don't render video or run a compositor; we repaint a text-dense
browser on keystrokes, and a CPU-drawn 1280×800 frame takes about 3 ms drawn and sent
under KVM (§9.4). The alternative is a 419k-line driver, three proprietary blobs and an
ioctl graphics stack in Lisp — for page flips, vsync, modesetting and acceleration that
a keypress-driven browser barely notices. The one real loss is *tearing*.

* 7. The fbcon font size: the default 8x16

The kernel console uses mainline's default *8x16* font (=CONFIG_FONT_8x16=y=, no
=fbcon=font:= on the command line). fbcon has *no scrollback* on mainline, so screen
real estate matters more than glyph size: 8x16 on a 1280×800 framebuffer gives 160×50,
where Terminus 16x32 gives 80×25.

fbcon renders a *fixed bitmap font*; bigger text means a font with a larger cell, not
magnification (=cols = xres/cell_w=, =rows = yres/cell_h=). Mainline fbcon has no
integer-scaling knob. To switch to Terminus 16x32:

1. *Kernel config.* =CONFIG_FONTS=y= + =CONFIG_FONT_TER16x32=y= (keep
   =CONFIG_FONT_8x16=y= as fallback).
2. *Command line.* Append =fbcon=font:TER16x32= to =CONFIG_CMDLINE= (baked into the
   build).
3. *Rebuild* with =build.sh --kernel= — an incremental rebuild is about 27 s on 8
   cores (a few font objects, the vmlinux relink, the bzImage).

Notes:

- *=scripts/config --enable FONT_TER16x32= silently didn't set the symbol* on this
  tree; a plain =sed= edit then =make olddefconfig= did (its deps —
  =FRAMEBUFFER_CONSOLE=y=, not SPARC, =FONTS=y= — are met).
- *TER16x32 is the largest* mainline built-in; beyond it needs a custom font.
- *=setfont=* (kbd) changes fonts at runtime, but we don't ship that userland.

This font only affects the text console. The environment draws its own text
([[file:fonts.org][fonts.org]]).

* 8. Drawing an image (the Land-of-Lisp alien) in a corner

Drawing a raster image is pure userland. The supervisor paints the Lisperati alien
into the top-right corner of the text console at boot and on the =a= menu key
([[file:../initramfs/framebuffer.lisp::defun draw-alien][=draw-alien=]], [[file:../initramfs/framebuffer.lisp::defun read-fb-geometry][=read-fb-geometry=]] in [[file:../initramfs/framebuffer.lisp][=initramfs/framebuffer.lisp=]];
[[file:../initramfs/supervisor.lisp][=supervisor.lisp=]] calls them from =print-menu= and the =a)= key).

1. *Raw pixels, made once.* The sprite =lisplogo_alien_256.png= (256×150, RGBA with
   real alpha) was converted on the dev host and committed:
   #+begin_src sh
   convert alien256.png -depth 8 RGBA:alien.rgba   # 256*150*4 = 153600 bytes
   #+end_src
   It ships as =/alien.rgba= via a =file= line in =initramfs.sbcl.list=. Pre-generating
   keeps ImageMagick out of the build. Both files live in =initramfs/=.
2. *Geometry at runtime.* [[file:../initramfs/framebuffer.lisp::defun read-fb-geometry][=read-fb-geometry=]] parses =virtual_size= ("W,H"),
   =stride= and =bits_per_pixel= from sysfs. It never assumes pitch = width × bpp.
3. *Top-right placement.* =x0 = max(0, xres - 256 - margin)=, =y0 = margin= (16).
   Height is clamped to the screen.
4. *Row by row into /dev/fb0* (opened =:direction :io=). For each sprite row, seek to
   =(y0+y)*stride + x0*4=, READ the background row, overlay pixels whose *alpha ≥ 128*,
   write the row back. The read-modify-write gives a transparent cutout instead of a
   black rectangle.
5. *Pixel format.* efifb is 32 bpp *BGRX*, so =B,G,R= are written from the source
   =R,G,B=. If a machine shows swapped colours (a magenta alien), exchange the two
   marked B/R lines in =draw-alien=.

*Living with fbcon.* fbcon shares the framebuffer, so console scrolling overwrites the
alien. The supervisor clears the screen before its menu and calls =draw-alien= *after*
printing the menu each cycle. Routine redraws are silent; =a)= passes =:announce t= to
print "alien drawn at …".

Bigger console fonts are a *kernel* change (§7); drawing an image is *userland* only —
=build.sh= without =--kernel=.

* 9. Full-screen: =present-fb= and KD_GRAPHICS

The code browser ([[file:code-browser.org][code-browser.org]]) is the main consumer of =/dev/fb0=. It needs a
whole-canvas blit and a console that stays out of the way.

** 9.1 =present-fb= — =draw-alien= generalised

=lol.fb:present-fb= ([[file:../poc/fb.lisp][poc/fb.lisp]]) blits a whole *canvas* instead of one sprite, with
a single =pwrite(2)= from the canvas (§9.4). It keeps =draw-alien='s addressing: the
32 bpp bail-out, the never-assume-stride rule, the byte offset =(y0+y)*stride + x0*4=
for a row whenever rows aren't contiguous. =lol.fb:fb-geometry= is =read-fb-geometry=
in the toolkit's package.

- *No read-modify-write.* The alien reads the background for its alpha cutout (§8);
  a full-screen canvas *owns* every pixel it covers and just overwrites.
- *Never a pixel at a time.* One =write(2)= per pixel would be 1,024,000 syscalls a
  frame at 1280×800. It's one call a frame, or one per row only when the screen's
  =stride= is wider than the canvas.

** 9.2 The pixel format lines up for free

The canvas stores one =(unsigned-byte 32)= per pixel as =#x00RRGGBB=. On x86 that word
sits in memory as =B,G,R,00= — which *is* BGRX, what efifb scans out (§8). No
conversion, no swizzle: =#x00RRGGBB= was chosen for exactly that.

*Endianness* is which end of a multi-byte number goes at the lowest address.
*Little-endian* (x86, ARM in practice) puts the *least significant byte first*, so
=#x00RRGGBB= lands in memory reversed:

#+begin_src
  the value:            #x00RRGGBB
  significance:          00 RR GG BB      (most significant -> least)
  in memory (x86):       BB GG RR 00      (lowest address -> highest)
  what efifb wants:      B  G  R  X       = BGRX
                         ^^^^^^^^^^^ identical
#+end_src

- *The pad byte lands last* because it's the *top* byte of the value — hence
  =#x00RRGGBB=, not =#xRRGGBB00=.
- *A portability assumption.* On a big-endian machine every colour would be wrong.
  The project is x86-only, so we take it. ([[file:../poc/x11.lisp][=poc/x11.lisp=]] is where byte order stops
  being free: X11 carries an explicit byte-order flag, and we declare =l=.)

** 9.3 KD_GRAPHICS — telling fbcon to stand down

Repainting after the console (§8) can't work full-screen: fbcon's cursor blink and any
stray =printk= would crawl across the picture.

=ioctl(KDSETMODE, KD_GRAPHICS)= on =/dev/tty0=, wrapped as
[[file:../poc/fb.lisp::defmacro with-graphics-console][=lol.fb:with-graphics-console=]], tells the kernel console to *stop rendering*. The
kernel side is [[file:../linux/drivers/tty/vt/vt_ioctl.c::case KDSETMODE][=drivers/tty/vt/vt_ioctl.c=, =case KDSETMODE=]]. (What an ioctl is:
[[file:line-editing.org][line-editing.org]].)

- *It stops drawing, not key delivery.* The raw-mode keyboard path is unchanged.
- *=KD_TEXT= comes back in an =unwind-protect=.* Non-negotiable: a VT left in graphics
  mode is a dead console with no way back.

It's §4's mirror image: §4 turns fbcon *on* so text appears; this turns it off so it
doesn't vandalise our pixels. Used by =run-browser-fb= ([[file:../initramfs/fb-browser.lisp][fb-browser.lisp]]) around its
event loop, and by =poc/run-guest.lisp=.

** 9.4 DONE: the blit is a single copy

[[file:../poc/fb.lisp::defun blit-fb][=blit-fb=]] in poc/fb.lisp:

1. *Open once.* =/dev/fb0= is opened once and kept, with its geometry, in =*fb*=. A
   variable survives =save-lisp-and-die= but a file descriptor doesn't, so an
   =sb-ext:*init-hooks*= entry forgets the cache when the image starts.
2. *The canvas goes to the kernel as it is.* =sb-sys:with-pinned-objects= stops the GC
   moving the vector during the call (SBCL's GC moves objects; the kernel is reading
   that memory); =sb-sys:vector-sap= is the address of its first element. That's how
   a =(unsigned-byte 32)= array is viewed as bytes — one =sb-alien= call.
3. *One =pwrite(2)=* — a write at an explicit offset, so no seek — sends the whole frame
   when rows are contiguous on both sides (=stride = width × 4=), else one per row. The
   kernel's [[file:../linux/drivers/video/fbdev/core/fb_io_fops.c::ssize_t fb_io_write][=fb_io_write=]] copies a page at a time and advances by what it copied, so
   one call writes the whole 4 MB.

Per §9.2, unpacking each pixel into bytes would be a no-op; the old per-pixel unpack,
per-row seek and per-frame reopen of =/dev/fb0= are gone.

*Why not =mmap=.* Both end in one copy of the canvas into scanout memory; =mmap= only
moves that copy from the kernel into our loop. Making the copy vanish would mean
drawing *into* the mapping, and the canvas must stay an ordinary Lisp vector (the
toolkit draws into it on the host and in the guest alike). =pwrite= gets the same copy
with one FFI routine and no chance of the GC meeting a device mapping.

*Measured* at tag #24, 1280×800, module index, averaged over 50 frames in the booted
guest (=check-pointer.lisp=, against a baseline of the old per-pixel code):

| per frame                   | before, KVM | after, KVM | before, TCG | after, TCG |
|-----------------------------+-------------+------------+-------------+------------|
| =draw-browser= alone        | 2.2 ms      | (same)     | 18.8 ms     | (same)     |
| =present-fb= alone          | 4.0 ms      | 0.2–0.6 ms | 47.7 ms     | ~2 ms (*)  |
| full frame (draw + present) | 6.5 ms      | 2.9–3.3 ms | 67.0 ms     | 21.0 ms    |

(*) By subtraction: the full frame minus =draw-browser=. The KVM "after" was measured
directly; subtraction overestimated it.

- *Why 50 frames.* SBCL's =get-internal-real-time= reads =CLOCK_MONOTONIC_COARSE= on
  Linux, which moves once per kernel tick — every 4 ms at =CONFIG_HZ=250=. One frame
  can't be timed.
- *KVM vs TCG.* The same image under QEMU with and without hardware virtualisation; see
  the "KVM vs TCG" paragraph of [[file:micro-distro.org::Prerequisites (host packages)][micro-distro.org → Prerequisites]].
- *Load skews it.* With another process holding the host's CPUs, the same guest
  measured an 8.6 ms frame instead of 2.6 ms.

*On real hardware* (Dell XPS 13 9300, 1920×1200, tag #24). The net-REPL harness can't
reach a machine without a NIC our kernel drives, so a temporary supervisor menu entry
timed draw / present / frame / pointer (warm-up untimed, best of three rounds). It's
removed; the git tag =bench-render-f= keeps it (=git show
bench-render-f:initramfs/bench.lisp=; restoring it is that file, its line in
=build.sh='s =LISP_SOURCES=, and one menu line). 1920×1200 is 2.25× the pixels of the
QEMU reference, so the last column scales down:

| per frame      | laptop, 1920×1200 | QEMU + KVM, 1280×800 | laptop ÷ 2.25 |
|----------------+-------------------+----------------------+---------------|
| =draw-browser= | 3.92 ms           | 2.2 ms               | 1.74 ms       |
| =present-fb=   | 1.12 ms           | 0.4 ms               | 0.50 ms       |
| full frame     | 5.04 ms           | 2.9 ms               | 2.24 ms       |
| pointer move   | 0.006 ms          | 0.012 ms             | (fixed size)  |

- *Rendering isn't the bottleneck.* A full-resolution frame is 5 ms, about 200 a
  second; a pointer move is 6 µs.
- *=pwrite= is enough; =mmap= isn't owed.* 9.2 MB (1920 × 1200 × 4) into real video
  memory in 1.12 ms is about 8 GB/s.
- *Drawing is the remaining cost,* about 80 % of the frame. The scaling column is only
  indicative: a taller screen also shows more rows of text.

** 9.5 The pointer is not part of the frame

Nothing the browser *draws* depends on where the pointer is (there are no hover
effects), so a bare move needs no redraw — only the arrow moves. That works because
the canvas never contains the arrow:

- *[[file:../initramfs/fb-browser.lisp::defun present-frame][=present-frame=]]* sends a freshly drawn canvas; then [[file:../initramfs/fb-browser.lisp::defun put-cursor][=put-cursor=]] composites the
  arrow into a *patch* the size of its box (copying the canvas pixels under it first,
  so transparent cells show the right thing) and sends only that.
- *[[file:../initramfs/fb-browser.lisp::defun move-cursor][=move-cursor=]]* handles a bare move: the pixels under the *old* position are
  untouched in the canvas, so erasing is re-sending that small rectangle
  (=lol.fb:present-fb-rect=), then =put-cursor= at the new position.

| per pointer move | a full frame | the patch |
|------------------+--------------+-----------|
| KVM              | 6.5 ms       | 12 µs     |
| TCG              | 67 ms        | 0.13 ms   |

*Shapes.* The pointer has three: arrow, pointing hand, I-beam (=*cursor-shapes*=, each
a bitmap and its /hotspot/ — the pixel that is the point: the arrow's tip, the
forefinger's tip, the I-beam's middle). A web page chooses among them
([[file:web-browser.org][web-browser.org]] §4.10); everything else shows the arrow.

- *One box for all.* The patch is a box every shape fits in, placed by
  [[file:../initramfs/fb-browser.lisp::defun cursor-box][=cursor-box=]] so each shape's hotspot lands on the point (17×27 pixels, its corner
  5 left of and 7 above the point). Drawing, moving and hiding work the same for every
  shape; [[file:../initramfs/fb-browser.lisp::defun set-cursor-shape][=set-cursor-shape=]] redraws the box in place when only the shape changes.
- *The arrow* ([[file:../initramfs/fb-browser.lisp::defparameter *cursor-bits*][=*cursor-bits*=]], 12×20) draws its tail along the arrow's own axis,
  one pixel right every two rows, like the classic X and Windows arrows; a vertical
  tail reads as bent against a head pointing up-left.

*Live-editable.* Accept a new =*cursor-bits*= (=C-c C-c= on its =defparameter=) and the
next move draws the new arrow. That needs two indirections:

- *Bitmaps by variable.* =*cursor-shapes*= names each bitmap by its /variable/, and
  [[file:../initramfs/fb-browser.lisp::defun cursor-shape][=cursor-shape=]] reads it at draw time. A table holding the vector keeps the old one:
  re-evaluating a =defparameter= gives the variable a /new/ object.
- *A box measured each time.* =+cursor-w+= and friends are symbol macros over
  [[file:../initramfs/fb-browser.lisp::defun cursor-box-geometry][=cursor-box-geometry=]], which measures the bitmaps on every use (a few µs per
  move). Erasing uses the box =put-cursor= last /sent/ (=*cursor-shown-rect*=), so an
  arrow that shrank between two draws leaves nothing behind.

*With Morphic* ([[file:morphic.org][morphic.org]]) the loop hands decoded input to a /world/
([[file:../poc/morph.lisp][poc/morph.lisp]]) and sends what it repaired —
[[file:../initramfs/fb-browser.lisp::defun present-repair][=present-repair=]]: the whole frame (=present-frame=, then the arrow) when the repair
covered the screen, else each repaired rect with =present-fb-rect=, the arrow put back
if a rect ran under it. The hand is a morph that's *not* drawn into the canvas, and a
bare move damages nothing. Modals (Spotter, menus, debugger) are /overlays/ the world
draws like any other morph; one that waits for an answer turns this same loop.

- *Fast paths.* The clock's tick, a terminal's dirty rows and a web page's new frame
  paint straight into the canvas their morph draws into — the screen for a tiled pane,
  a window's backing store otherwise — through [[file:../poc/morphic.lisp::defun paint-into][=paint-into=]].
- *Painted, then composited.* They don't send their rect themselves: they hand it to
  the world as /painted/ (=lol.morph:note-painted=), and the next repair draws, in that
  rect only, whatever lies /above/ the painting morph — a window, an overlay's scrim and
  card. So a window over the tray stays on top while the clock ticks, and a terminal
  printing behind an open menu shows dimmed.
- *Poll is level-triggered.* Every input fd must be read when it's readable, or the
  loop spins: an unread mouse is readable forever.

*Hiding when idle.* After =+cursor-idle-ms+= (3 s) with no motion, button or wheel,
[[file:../initramfs/fb-browser.lisp::defun hide-cursor][=hide-cursor=]] re-sends the canvas rectangle under the arrow and stops drawing it.
The next motion, click or notch brings it back ([[file:../initramfs/fb-browser.lisp::defun pointer-activity][=pointer-activity=]]); typing never
does, since an arrow parked over text is in the way while typing. The deadline joins
the poll timeout ([[file:../initramfs/fb-browser.lisp::defun earliest-timeout][=earliest-timeout=]]) beside the stage's frame and the systray's
clock ([[file:systray.org][systray.org]] §5), so an idle browser sleeps until something is due.

*Tested.* =check-pointer.lisp= counts the world's repairs across real QMP pointer
motion (zero), checks the screendump (arrow at the new place, the canvas's pixel back
at the old one), and checks the canvas never holds the arrow.
