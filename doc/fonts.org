#+TITLE: Fonts — from an outline in a .ttf to letters on the panel, at any size
#+STARTUP: showall

Companion to [[file:framebuffer.org][framebuffer.org]] (which explains *pixels → panel*); this file explains
*glyphs → pixels* — how a character becomes light on the screen in our pure-Lisp
renderer, and how its size can change while the environment runs. Code:

- [[file:../poc/ttf.lisp][poc/ttf.lisp]] — =lol.ttf=: reading a TrueType file and rasterising its outlines;
- [[file:../poc/canvas.lisp][poc/canvas.lisp]] — the =font= object, its glyph cache, =draw-string=, and the
  bitmap fallback;
- [[file:../poc/widgets.lisp][poc/widgets.lisp]], [[file:../poc/textview.lisp][poc/textview.lisp]], [[file:../poc/shell.lisp][poc/shell.lisp]] — layout, which asks the
  font for every distance;
- [[file:../initramfs/settings.lisp][initramfs/settings.lisp]] — where the chosen size is remembered.

Design history: [[file:code-browser.org][code-browser.org §6.2]]. Read this top to bottom once and you will
know what a font file contains, how a curve becomes grey pixels, and why pressing
=SuperL-== makes every row, bar and hit box in the environment grow together.

* 0. The one-paragraph essence

A *bitmap* font stores each character as a little grid of on/off pixels, drawn once
by a person at one size. An *outline* font stores each character as *curves* in an
abstract grid, and the computer draws the pixels itself, at whatever size is asked
for. We now ship an outline font (DejaVu Sans Mono, copied from the build host),
rasterised by about 500 lines of Lisp; the old bitmap font (Cozette 6×15) stays as
the fallback. The size lives in *one font object* everyone shares; changing it and
redrawing re-lays out the whole screen, because nothing that positions text holds a
number of its own any more — it asks the font.

* 1. Two kinds of font

*Bitmap.* A glyph is a rectangle of bits: 1 = ink, 0 = background. Our Cozette is 6
pixels wide and 15 tall, one byte per row (most significant bit = leftmost pixel), 256
glyphs indexed by character code. Drawing is copying lit bits. Crisp and trivially
fast — and *fixed*: the only way to make it bigger is to stamp every pixel as a 2×2
block, which looks like what it is (§8).

*Outline.* A glyph is a set of closed *contours* — the boundary of the ink, like a
cookie cutter. The coordinates live in *font units* on an "em square" (DejaVu Sans
Mono's is 2048 units a side; the em is, historically, the height of the metal block
a letter was cast on). To draw at 18 pixels, multiply every coordinate by 18/2048 and
ask, for each pixel, how much of it lies inside the contours. Any size, one file.

The price of outlines is that a curve rarely lands on pixel boundaries, so an edge
pixel is *partly* inside. Painting it fully on or off gives jagged stairs; painting it
in proportion — a grey — gives smooth edges. That proportion is the pixel's
*coverage*, and computing it exactly is the rasteriser's whole job (§4).

* 2. Inside a .ttf: a directory of tables

A TrueType file is a small *table directory* followed by the tables. The first 12
bytes hold a version (=0x00010000=) and the number of tables; then come 16-byte
records — a 4-letter *tag*, a checksum, an offset, a length. Every number in the file
is *big-endian* (most significant byte first — the format came from 1990s Apple; x86
is little-endian, so we assemble each number from its bytes by hand, =u16= / =u32= in
[[file:../poc/ttf.lisp][ttf.lisp]]). [[file:../poc/ttf.lisp::defun parse-ttf][=parse-ttf=]] reads the whole file into one octet vector and
records where each table starts; nothing is copied out.

The tables a monospace font needs, and what we take from each:

| table  | holds                                       | we use                                                       |
|--------+---------------------------------------------+--------------------------------------------------------------|
| =head= | global facts                                | =unitsPerEm= (2048); whether =loca= is 16- or 32-bit          |
| =hhea= | horizontal layout header                    | ascender 1901, descender −483, lineGap 0; how many glyphs have their own advance |
| =maxp= | limits                                      | the number of glyphs (3377 in DejaVu Sans Mono)               |
| =cmap= | character code → glyph number               | the format 12 subtable (all of Unicode), else format 4 (U+0000–U+FFFF) |
| =hmtx= | per-glyph advance width + left bearing      | the advance — 1233 units for *every* glyph here              |
| =loca= | where each glyph's outline starts in =glyf= | offsets; equal neighbours mean "no outline" (a space)         |
| =glyf= | the outlines                                | contours of points, and composite glyphs                      |
| =name= | human-readable strings                      | the full name, "DejaVu Sans Mono", for the status line        |

(The numbers were checked against the file with an independent reader — Perl's
=unpack= on the raw bytes — and the charset with =fc-query=, not against our parser;
[[file:../poc/font-test.lisp][poc/font-test.lisp]] asserts them.)

*cmap, the lookup.* Format 4 cuts the 16-bit range into *segments* =[start, end]=; a
code in a segment maps to =code + delta= or, when the segment has an
=idRangeOffset=, to an entry of a glyph array that the offset points at — relative to
the address of the offset word *itself*, a celebrated piece of 1990s pointer
arithmetic ([[file:../poc/ttf.lisp::defun glyph-index][=glyph-index=]]). Format 12 is a sorted list of =(start end first-glyph)=
groups and covers emoji and mathematics too. We binary-search either. A character the
font lacks maps to *glyph 0*, =.notdef= — the font's own "missing" box, which is
exactly the fallback glyph we want on screen. The host test checks that formats 4 and
12 agree on every code from 0 to =#x2FFF=.

*hmtx, the advance.* Pairs of (advance, left side bearing) for the first
=numberOfHMetrics= glyphs; every later glyph shares the *last* advance. DejaVu Sans
Mono has =numberOfHMetrics= = 4: one width for three thousand glyphs, which is what
"monospace" looks like inside the file.

*glyf, the outlines.* A *simple* glyph lists the index of each contour's last point,
skips some hinting bytecode, then stores its points compactly: one *flags* byte per
point (with a "repeat" bit, so runs share a byte), then all the x's, then all the
y's, each a *delta* from the previous point in one byte or two
([[file:../poc/ttf.lisp::defun simple-glyph][=simple-glyph=]]). A *composite* glyph instead references other glyphs with an offset
and maybe a scale or a 2×2 matrix — =é= is =e= plus an acute accent, placed;
[[file:../poc/ttf.lisp::defun glyph-outline][=glyph-outline=]] resolves them recursively, with a depth guard for a broken font.

*What we deliberately skip.* *Hinting* — TrueType's bytecode virtual machine that
nudges outlines onto the pixel grid at small sizes; *kerning and shaping* — a
monospace cell grid needs neither; *CFF* outlines (the cubic curves of
OpenType/PostScript =.otf= files — =parse-ttf= refuses them by name); colour and
bitmap-strike tables. Without hinting, small sizes are a little softer than a desktop
renders them (§4 shows what the gamma buys back).

* 3. Quadratic Béziers: what the points mean

Each point carries an *on-curve* flag. Two on-curve points in a row are joined by a
straight line. An *off-curve* point between two on-curve ones is a *control point*:
the segment is a quadratic Bézier curve

#+begin_src
  B(t) = (1-t)² P0  +  2t(1-t) C  +  t² P1        t from 0 to 1
#+end_src

which leaves =P0= heading toward =C=, arrives at =P1= coming from =C=, and never
leaves the triangle the three points make (so the points' bounding box bounds the
glyph — [[file:../poc/ttf.lisp::defun rasterize-glyph][=rasterize-glyph=]] relies on it). The format's space-saving trick: *two*
off-curve points in a row imply an on-curve point exactly halfway between them. A
circle can be four control points and no on-curve point at all.
[[file:../poc/ttf.lisp::defun walk-contour][=walk-contour=]] turns a contour into line and curve calls under those rules,
inventing the implied points, and first finds an on-curve starting point (inventing
one between the last and first points when there is none).

A rasteriser wants straight edges, so each curve is *flattened* into short lines.
How many: [[file:../poc/ttf.lisp::defun accumulate-quad][=accumulate-quad=]] measures the curve's bend, =|P0 − 2C + P1|= (zero for a
straight one), and uses =1 + ⌊√√(3·bend²)⌋= pieces — the font-rs rule, enough that no
piece strays a visible fraction of a pixel from the true curve. B(t) is evaluated by
"lerping twice": the point =t= of the way from =P0= to =C=, the point =t= of the way
from =C= to =P1=, then =t= of the way between those two.

* 4. Coverage: the signed-area accumulator

The rasteriser is the method Raph Levien popularised in *font-rs*
([[file:../poc/ttf.lisp::defun accumulate-line][=accumulate-line=]]). It needs no sorting of edges, no scanline lists and no
supersampling, and it is exact.

Picture one row of pixels and a downward edge crossing it. Everything to the right of
the edge, within the vertical slice the edge sweeps in this row, is *inside* the
shape (for an upward edge, *outside* — that is the edge's sign). Instead of adding
that slice height to every pixel to the right, the edge *deposits* it once, where it
is: the pixel(s) it passes through get the part lying to their right (a trapezoid's
area, cut per pixel), and the next pixel gets the rest. Then one *running sum along
the row* carries the deposit rightward — until the shape's other edge deposits the
opposite amount and the sum falls back to zero. After the pass:

#+begin_src
  coverage(pixel) = min(1, |running sum at that pixel|)
#+end_src

The =abs= makes the winding direction irrelevant (TrueType draws outer contours
clockwise and holes anticlockwise — a hole's edges deposit the opposite sign, so the
=O= keeps its counter; the host test checks the centre pixel of an =O= is empty). The
=min 1= handles parts that overlap (an accent touching its letter). The sum runs over
the whole buffer row-major, not row by row: each row's deposits add up to zero for a
closed outline, so nothing leaks into the next row.

*Gamma.* Exact coverage looks *thin* for light text on a dark ground: the eye does
not respond linearly, and without hinting a one-pixel stem often lands half on each of
two pixels — two half-lit greys instead of one lit pixel. So coverage is raised to
=1/γ= before it becomes a byte (=lol.ttf:*gamma*=, 1.45). It was chosen by rendering
the same line at 11–18 px with γ = 1.0, 1.45 and 1.8 and looking: 1.0 is spindly at
12 px, 1.8 starts to look bold at 18, 1.45 keeps =0O=, =1lI= and =;:= distinct at
every size from 11 up. Changing it needs the glyph caches emptied
(=lol.canvas::clear-font-cache=).

* 5. The FONT object, the glyph cache, and blending

=lol.canvas:font= has two kinds ([[file:../poc/canvas.lisp::defstruct font][=defstruct font=]]): a *bitmap* one (the 256 glyph
vectors) and an *outline* one (a =lol.ttf:face=). Both answer the questions layout
asks — =font-cw= and =font-ch=, the *cell* width and height — so nothing above the
canvas knows which kind it has.

*The size, and the cell it implies.* [[file:../poc/canvas.lisp::defun set-font-size][=set-font-size=]] sets the font's pixel size
(the em) *in place* and recomputes the cell from the font's own metrics, rounded to
whole pixels because a grid can only be whole pixels:

#+begin_src
  scale    = size / unitsPerEm
  cw       = round(advance('M') × scale)              ; every glyph's, in a monospace font
  ch       = round((ascender − descender + lineGap) × scale)
  baseline = round((ascender + lineGap/2) × scale)    ; pixels below the cell's top
#+end_src

For DejaVu Sans Mono (computed with the code itself, one line per size):

| size | cell  | baseline | columns × list rows on 1920×1080 |
|------+-------+----------+----------------------------------|
|   12 | 7×14  |       11 | 274 × 56                         |
|   14 | 8×16  |       13 | 240 × 51                         |
|   16 | 10×19 |       15 | 192 × 45                         |
| *18* | 11×21 |       17 | 174 × 41 — the default           |
|   20 | 12×23 |       19 | 160 × 38                         |
|   23 | 14×27 |       21 | 137 × 33                         |
|   29 | 17×34 |       27 | 112 × 27                         |
|   40 | 24×47 |       37 | 80 × 20                          |

*Why 18 px by default.* The laptop is a 14-inch 1920×1080 panel, about 157 pixels to
the inch; the old 6×15 bitmap's capitals were about 1.5 mm tall there — the complaint
that started this. At 18 px a capital is about 2.2 mm (close to 10-point type held at
arm's length), and a full-width pane still holds 170 columns.
=lol.canvas:*default-font-size*= holds it; the user's own choice overrides it (§6).

*The cache.* Rasterising is cheap but not free, and a screen repeats the same few
dozen glyphs thousands of times, so [[file:../poc/canvas.lisp::defun font-glyph][=font-glyph=]] keeps every glyph it makes, keyed
by *(size, codepoint)* packed into one fixnum (=size × 2²¹ + code= — codepoints stop
below 2²¹), in a per-font =eql= hash table: the cheapest lookup there is. A size
change throws nothing away; going back to a size finds its glyphs waiting. Each
cached glyph is a coverage bitmap plus where its top-left sits relative to the pen
and the baseline; it is shifted by a fraction of a pixel so it is *centred* in its
rounded cell (the rounding error goes half to each side).

*Blending.* [[file:../poc/canvas.lisp::defun draw-string-outline][=draw-string-outline=]] composites each glyph over whatever is already in
the canvas, channel by channel:

#+begin_src
  out = (ink × a + old × (255 − a)) / 255        a = coverage, 0..255
#+end_src

Full coverage is a plain store (most of a stem); zero is skipped (most of a cell). The
canvas has no alpha channel and needs none: the "background" is simply the pixels
already there — a panel colour, a selection band.

*Numbers* (host, [[file:../poc/font-test.lisp][poc/font-test.lisp]]'s timing block, 18 px): the 94 printable ASCII
glyphs rasterise *cold* in 0.6 ms; a full 1920×1080 screen of cached text (170×51
cells) draws in about 5 ms, against 1.6 ms for the same glyph count with the bitmap
font. In the guest under KVM at 1280×800 (tag #26), [[file:../check-pointer.lisp][check-pointer.lisp]] measured a
whole frame (draw + present) at 4 ms. That is why stb_truetype (the C route
[[file:previews.org][previews.org]] took for JPEG) was *not* needed: pure Lisp is fast enough by a wide
margin.

* 6. How a size change reaches every pixel of layout

The rule that makes runtime resizing work: *no layout code may hold a text metric in
a constant.* Every distance that depends on text is computed from the current font
*at draw time*. There is exactly one font object — =*bfont*= in the shell, the same
object as =lol.widgets:*font*= and every text view's =tv-font= — and
=set-font-size= mutates it. So "change the size, redraw" is the whole mechanism; there
is no relayout pass, because layout is redone every frame anyway.

*The metric accessors* ([[file:../poc/widgets.lisp][poc/widgets.lisp]] unless noted), and what they were as
constants:

| accessor                       | is                                           | at 6×15 (the old constant) |
|--------------------------------+----------------------------------------------+----------------------------|
| =char-w=, =line-h=             | the font's cell                              | 6, 15                      |
| =+row-h+= → =(row-h)=          | a list row: cell + 5                         | 20                         |
| =+bar-h+= → =(bar-h)=          | a header band / breadcrumb / the tab strip   | 20                         |
| =card-head-h=                  | a card's title strip: cell + 9              | 24                         |
| =+cell-w+=, =+cell-h+=         | a dispatch-matrix cell: 13 chars × (cell + 3) | 78 × 18                   |
| =text-dy=                      | how far down a band to draw text, centred    | (was =(+ y 3)=)            |
| =status-h= (shell)             | the status line / minibuffer: cell + 7       | 22                         |
| =tv-gutter-w= (textview)       | the line-number gutter: 4 chars + 16         | 40 (=*gutter-w*=)          |
| =tv-line-height= (textview)    | a text-view line: cell + 3                   | 18 (always derived)        |
| =stage-transcript-h=, =dbg-row-h=, =dbg-band-h= | the stage strip, debugger rows and title band | 92, 17, 24 |

=+row-h+= and friends kept their names as *symbol macros*: the compiler replaces the
symbol with a call, =(row-h)=, at each of the hundred places that use it. That kept
the diff small and means code anyone writes with =+row-h+= is automatically right;
the price is a "+constant+" that varies, which is why this table exists.

*What consumes them:* row heights and the list viewport, the tab strip and its close
boxes, the systray, breadcrumbs, the status line, the minibuffer and its caret, the
Spotter and clipboard cards (their heights and how many rows fit), the context menu's
width, the halo's caption and handle labels (and their hit boxes), the dispatch
matrix, the stage's heads-up line and transcript, image captions, the debugger (title
band, restart and frame rows, locals strip, source viewer, value prompt), the
=SuperL-?= cheatsheet (which now pours its groups into as many pages as the size
needs — PageDown or Space turns them), and the hit maps all of these record, which
are made from the same numbers as the drawing so a click and a pixel cannot
disagree. Mouse → (line, column) in a text view is =col-at-x=, which divides by the
current =tv-cw=.

*Long lines.* With a 6-pixel font a line rarely reached a pane's edge; at 28 px most
do. So the text view now *clips* at its edge (it used to draw over the frame) and
*scrolls sideways* to keep the caret visible (=tv-hscroll=, followed in =tv-draw=,
counted by =x-of-col= / =col-at-x= so clicks still land).

*The keys* (=browser-key= in [[file:../poc/shell.lisp][shell.lisp]], calling [[file:../poc/shell.lisp::defun change-font-size][=change-font-size=]]):

| keys                                           | does                                         |
|------------------------------------------------+----------------------------------------------|
| =SuperL-== or =SuperL-+=                       | bigger                                       |
| =SuperL--=                                     | smaller                                      |
| =SuperL-0=                                     | back to the size the font was loaded at      |
| =C-x C-== (or =C-x C-+=), =C-x C--=, =C-x C-0= | the same, Emacs's =text-scale-adjust= keys   |
| then a bare =+= (or ===), =-=, =0=             | repeats, without the =C-x= — as in Emacs     |
| =Ctrl= + wheel                                 | up bigger, down smaller, as in web browsers  |

Steps are 2 px below 20 and 3 px above (one pixel at 12 px is 8 %, at 30 px 3 % and
too small to notice), clamped to 10–40 px; from 18 the sizes go 20, 23, 26, 29 … 40.
The status line says the result — =font: DejaVu Sans Mono 20px (12x23)= — and "at the
largest end" when there is no further to go.

*Two chords the console does not send.* On the framebuffer the characters come from
the cooked tty and only the modifiers from the keyboard's evdev ([[file:input.org][input.org]]). The
kernel's default keymap (=drivers/tty/vt/defkeymap.map=) gives keycodes 11 (=0=) and 13
(===) *no control column*, so =Ctrl-0= and =Ctrl-== produce *no byte at all* — found
when [[file:../check-font.lisp][check-font.lisp]]'s =C-x C-== did nothing and the next plain === completed the
chord instead. =Ctrl--= is fine (=Control_underscore=, byte 31, reaching us as =C-_=).
So =note-modifier-key= in [[file:../initramfs/fb-browser.lisp][fb-browser.lisp]] reports those two chords from evdev, the
way it already reported the Menu key.

*Remembering the size.* Every change is written to =~/.lol/settings=
(=~/.config/lol/settings= until 2026-10-17; a file there is moved at boot,
[[file:session-persistence.org][session-persistence.org]] §3), a plist
the Lisp reader reads back — =(:FONT-SIZE 20)= — by =save-setting=
([[file:../initramfs/settings.lisp][initramfs/settings.lisp]]), atomically (a temp file and a rename). =run-browser-fb=
reads it at start. Neither direction ever signals, =*read-eval*= is off when reading,
and nothing is written when there is no real home: a diskless boot has =HOME=/=, a
tmpfs that dies at power-off. Because =/home= is the laptop's own =/home=
([[file:storage.org][storage.org]]), the image on the laptop finds the size you last chose there.
(=render-frame.lisp= never loads it, so a rendered frame does not depend on your
preferences.)

* 7. Which font ships, and changing it

*At build time.* [[file:../build.sh][build.sh]] copies a monospace TrueType file *from the build host*
into the gitignored =initramfs/mono.ttf=, and the cpio list puts it at
=/usr/share/lol/mono.ttf= (343 140 bytes for DejaVu Sans Mono). It is someone else's
work, so — like firmware — it is never committed. =LOL_FONT=/path/to/font.ttf= picks
one; the default is =/usr/share/fonts/truetype/dejavu/DejaVuSansMono.ttf=, else
whatever =fc-match monospace= names. Its licence (the Bitstream Vera licence; DejaVu's
own changes are public domain) is in [[file:../README.org][README.org]]'s licensing table. If the host has no
TrueType font at all, build.sh ships an *empty* file, the image fails to parse it, and
falls back to the bitmap — harder to read, never broken.

*On the host.* =render-frame.lisp=, =run-browser.lisp= (X11) and the host tests take
=$LOL_FONT=, else the host's DejaVu, else =poc/cozette.lolf=.
=sbcl --script poc/render-frame.lisp workspace --size 28= renders a frame at 28 px;
=--font PATH= tries another file (a =.lolf= path selects the bitmap fallback).

*At run time.* =(set-font "/mnt/host/usr/share/fonts/truetype/cascadia-code/CascadiaMono.ttf")=
in the Workspace switches the whole environment to any TrueType file the laptop has
(=/mnt/host= is its root, read-only — [[file:storage.org][storage.org]]), keeping the size. It replaces the
font object and repoints the open text views at the new one. A proportional font will
draw, but on the monospace grid — every glyph centred in a cell as wide as its =M=.

* 8. The bitmap fallback

What shipped before, and still ships as =/cozette.lolf=: Cozette (MIT), 6×15, converted
from its BDF by [[file:../poc/bdf2font.lisp][=bdf2font.lisp=]] into our own =.lolf= blob — magic =LF=, a width byte, a
height byte, then 256 glyphs of one byte per row, *indexed by real codepoint*. (A
console *PSF1* font, read by =load-psf=, is the same idea with an implicit,
Latin-1-ish glyph order — which is how =·= once drew as =Ö=; owning the order in
=.lolf= is what fixed that.) =draw-string-bitmap= stamps the lit bits, testing
=(logbitp (- 7 col) bits)= because column 0 is the *most* significant bit.

It is the fallback when no TrueType file loads, and it *still resizes*: a bitmap
cannot be redrawn at another size, only magnified, so =set-font-size= rounds to the
nearest whole multiple of 15 and stamps each pixel as a k×k block (size 30 gives 12×30
cells). Because the cell metrics follow, layout is right at either size; only the
letters are blocky.

Its 256-glyph limit is why the chrome folds characters past Latin-1 to ASCII cousins
(an em dash to =-=, an ellipsis to =.= — =glyph-index= in canvas.lisp) and why
elisions are two dots. The outline font has none of these limits: it maps anything
its =cmap= covers and draws =.notdef= for the rest.

* 9. Testing it

- *Host, the engine:* =sbcl --script poc/font-test.lisp= — 43 checks: the tables, cmap
  (both formats, agreeing), advances, rasterised coverage (a space is empty, =l= has a
  solid stem *and* grey edges, =g= descends, =O= keeps its hole, =é= is a composite),
  the cell at 18 px, clamping, the cache (one miss per distinct glyph, then hits; a new
  size misses again), blending, the bitmap fallback's magnification; then the timings
  of §5.
- *Host, the pixels:* =poc/render-frame.lisp SUBJECT --size N= at 12, 18 and 28 — look
  at the frames; =-k "s-= s-="= replays the keys and shows the status line.
- *Guest, the machine:* =LOL_GUEST_DISK=test-disk.img sbcl --script check-font.lisp=
  boots the image and presses the keys through QMP: the TTF loaded, the default size,
  =SuperL-= / - / 0=, =C-x C-= / C-- / C-0= and the bare repeat, the row height
  following the cell, the world having repaired the screen (=draw-browser= having run,
  before Morphic's §12 made every pane a morph), the screendump differing, the status
  line, a letter typed after the chord not being swallowed, and the size landing in
  =~/.lol/settings= (diskless: that nothing is written) — 18/18 at tag #26; 19/19 with the disk on
  2026-10-17, which adds that the file is =HOME/.lol/settings=.
  =check-scroll=, =check-clipboard= and =check-pointer= pass at 18 px
  (=check-clipboard= needed =*gutter-w*= → =tv-gutter-w=).

* 11. Gotchas, and what was ruled out

- *Never copy a metric into a constant.* A =(defparameter +foo-h+ 20)= sized for one
  font is the bug this change removed; ask =line-h= at draw time. Every track's code is
  held to the same rule ([[file:code-browser.org][code-browser.org §6.2]]).
- *Cell vs glyph.* =cw=/=ch= are the *cell*; ink usually fills less, and =g=/=y= descend
  below the baseline into the cell's bottom. Drawing takes the cell's top-left, not
  the baseline.
- *A pane's text is clipped, not wrapped.* Long lines scroll sideways with the caret
  (§6); lists elide with =..=.
- *Ruled out: stb_truetype.* The plan allowed a C rasteriser through the existing
  =libstbi.so= pattern if pure Lisp proved too slow or too ugly. Measured (§5), it is
  neither, so there is no C here.
- *Not a finding:* one early timing printed "0.0 ms" for rasterising 94 glyphs — a
  single run too short to time reliably; the test now times twenty cold runs and
  reports 0.6 ms.
- *Ctrl-= and Ctrl-0 are silent on the console* (§6). Any future Ctrl-digit or
  Ctrl-punctuation binding will meet the same keymap gap: check =defkeymap.map= for a
  =control= line before assuming a byte arrives.
