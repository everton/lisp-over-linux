#+TITLE: Fonts — from an outline in a .ttf to letters on the panel, at any size
#+STARTUP: showall

This doc explains *glyphs → pixels*: how a character becomes light on the screen in
the pure-Lisp renderer, and how its size changes while the environment runs. Its
companion [[file:framebuffer.org][framebuffer.org]] explains *pixels → panel*.

Code:

- [[file:../poc/ttf.lisp][poc/ttf.lisp]] — =lol.ttf=: reading a TrueType file and rasterising its outlines.
- [[file:../poc/canvas.lisp][poc/canvas.lisp]] — the =font= object, its glyph cache, =draw-string=, the bitmap
  fallback.
- [[file:../poc/widgets.lisp][poc/widgets.lisp]], [[file:../poc/textview.lisp][poc/textview.lisp]], [[file:../poc/shell.lisp][poc/shell.lisp]] — layout, which asks the
  font for every distance.
- [[file:../initramfs/settings.lisp][initramfs/settings.lisp]] — where the chosen size is remembered.

Design context: [[file:code-browser.org][[[file:code-browser.org::#must-write-ourselves][code-browser.org, What we must write ourselves]]]].

* 0. The one-paragraph essence

A *bitmap* font stores each character as a small grid of on/off pixels, drawn once at
one size. An *outline* font stores each character as *curves*, and the computer draws
the pixels itself at whatever size is asked for. The image ships an outline font
(DejaVu Sans Mono, copied from the build host), rasterised by about 500 lines of Lisp;
a bitmap font (Cozette 6×15) stays as the fallback. The size lives in *one font
object* everyone shares. Changing it and redrawing re-lays out the whole screen,
because nothing that positions text holds a number of its own — it asks the font.

* 1. Two kinds of font

- *Bitmap.* A glyph is a rectangle of bits: 1 = ink, 0 = background. Cozette is 6
  pixels wide and 15 tall, one byte per row (most significant bit = leftmost pixel),
  256 glyphs indexed by character code. Drawing copies lit bits: crisp, fast, and
  *fixed* — making it bigger means stamping each pixel as a 2×2 block ([[#bitmap-fallback][The bitmap fallback]]).
- *Outline.* A glyph is a set of closed *contours* — the boundary of the ink, like a
  cookie cutter. Coordinates are in *font units* on an "em square" (2048 units a side
  in DejaVu Sans Mono; the em was historically the height of the metal block a letter
  was cast on). To draw at 18 px, scale every coordinate by 18/2048 and ask, for each
  pixel, how much of it lies inside the contours.

A curve rarely lands on pixel boundaries, so an edge pixel is *partly* inside. Painting
it fully on or off gives jagged stairs; painting it in proportion — a grey — gives
smooth edges. That proportion is the pixel's *coverage*, and computing it exactly is
the rasteriser's whole job ([[#coverage-signed-area-accumulator][Coverage: the signed-area accumulator]]).

* 2. Inside a .ttf: a directory of tables

A TrueType file is a small *table directory* followed by the tables. The first 12
bytes hold a version (=0x00010000=) and the number of tables; then come 16-byte
records — a 4-letter *tag*, a checksum, an offset, a length.

Every number is *big-endian* (most significant byte first; the format came from Apple).
x86 is little-endian, so =u16= / =u32= in [[file:../poc/ttf.lisp][ttf.lisp]] assemble each number from its
bytes. [[file:../poc/ttf.lisp::defun parse-ttf][=parse-ttf=]] reads the whole file into one octet vector and records where each
table starts; nothing is copied out.

The tables a monospace font needs, and what we take from each:

| table  | holds                                       | we use                                                                           |
|--------+---------------------------------------------+----------------------------------------------------------------------------------|
| =head= | global facts                                | =unitsPerEm= (2048); whether =loca= is 16- or 32-bit                             |
| =hhea= | horizontal layout header                    | ascender 1901, descender −483, lineGap 0; how many glyphs have their own advance |
| =maxp= | limits                                      | the number of glyphs (3377 in DejaVu Sans Mono)                                  |
| =cmap= | character code → glyph number               | the format 12 subtable (all of Unicode), else format 4 (U+0000–U+FFFF)           |
| =hmtx= | per-glyph advance width + left bearing      | the advance — 1233 units for *every* glyph here                                  |
| =loca= | where each glyph's outline starts in =glyf= | offsets; equal neighbours mean "no outline" (a space)                            |
| =glyf= | the outlines                                | contours of points, and composite glyphs                                         |
| =name= | human-readable strings                      | the full name, "DejaVu Sans Mono", for the status line                           |

The numbers were checked with an independent reader (Perl's =unpack= on the raw bytes,
and =fc-query= for the charset), not with our parser; [[file:../poc/font-test.lisp][poc/font-test.lisp]] asserts them.

- *cmap, the lookup.* Format 4 cuts the 16-bit range into *segments* =[start, end]=. A
  code in a segment maps to =code + delta=, or, when the segment has an
  =idRangeOffset=, to an entry of a glyph array the offset points at — relative to the
  address of the offset word *itself* ([[file:../poc/ttf.lisp::defun glyph-index][=glyph-index=]]). Format 12 is a sorted list of
  =(start end first-glyph)= groups and covers emoji and mathematics too. Both are
  binary-searched. A missing character maps to *glyph 0*, =.notdef= — the font's own
  "missing" box, which is the fallback we want on screen. The host test checks that
  formats 4 and 12 agree on every code from 0 to =#x2FFF=.
- *hmtx, the advance.* Pairs of (advance, left side bearing) for the first
  =numberOfHMetrics= glyphs; every later glyph shares the *last* advance. DejaVu Sans
  Mono has =numberOfHMetrics= = 4: one width for three thousand glyphs — what
  "monospace" looks like inside the file.
- *glyf, simple glyphs.* The index of each contour's last point, some hinting bytecode
  (skipped), then the points packed: one *flags* byte per point (with a "repeat" bit,
  so runs share a byte), then all the x's, then all the y's, each a one- or two-byte
  *delta* from the previous point ([[file:../poc/ttf.lisp::defun simple-glyph][=simple-glyph=]]).
- *glyf, composite glyphs.* References to other glyphs with an offset and maybe a scale
  or 2×2 matrix — =é= is =e= plus an acute accent, placed. [[file:../poc/ttf.lisp::defun glyph-outline][=glyph-outline=]] resolves
  them recursively, with a depth guard for a broken font.

*Deliberately skipped:*

- *Hinting* — TrueType's bytecode VM that nudges outlines onto the pixel grid at small
  sizes. Without it, small sizes are a little softer than a desktop renders them ([[#coverage-signed-area-accumulator][Coverage: the signed-area accumulator]]'s
  gamma buys some of that back).
- *Kerning and shaping* — a monospace cell grid needs neither.
- *CFF outlines* — the cubic curves of OpenType/PostScript =.otf= files; =parse-ttf=
  refuses them by name.
- *Colour and bitmap-strike tables.*

* 3. Quadratic Béziers: what the points mean

Each point carries an *on-curve* flag. Two on-curve points in a row are joined by a
straight line. An *off-curve* point between two on-curve ones is a *control point*,
and the segment is a quadratic Bézier curve:

#+begin_src
  B(t) = (1-t)² P0  +  2t(1-t) C  +  t² P1        t from 0 to 1
#+end_src

It leaves =P0= heading toward =C=, arrives at =P1= coming from =C=, and never leaves the
triangle of the three points. So the points' bounding box bounds the glyph, which
[[file:../poc/ttf.lisp::defun rasterize-glyph][=rasterize-glyph=]] relies on.

- *Implied points.* *Two* off-curve points in a row imply an on-curve point halfway
  between them; a circle can be four control points and no on-curve point at all.
  [[file:../poc/ttf.lisp::defun walk-contour][=walk-contour=]] turns a contour into line and curve calls, inventing the implied
  points, and first finds an on-curve start (inventing one between the last and first
  points when there is none).
- *Flattening.* A rasteriser wants straight edges, so each curve becomes short lines.
  [[file:../poc/ttf.lisp::defun accumulate-quad][=accumulate-quad=]] measures the bend, =|P0 − 2C + P1|= (zero for a straight one), and
  uses =1 + ⌊√√(3·bend²)⌋= pieces — the font-rs rule, enough that no piece strays a
  visible fraction of a pixel from the curve.
- *Evaluating B(t).* "Lerp twice": the point =t= of the way from =P0= to =C=, the point
  =t= of the way from =C= to =P1=, then =t= of the way between those two.

* 4. Coverage: the signed-area accumulator
:PROPERTIES:
:CUSTOM_ID: coverage-signed-area-accumulator
:END:

The rasteriser is the method Raph Levien popularised in *font-rs*
([[file:../poc/ttf.lisp::defun accumulate-line][=accumulate-line=]]). It needs no edge sorting, no scanline lists and no
supersampling, and it's exact.

Picture one row of pixels and a downward edge crossing it. Everything to the right of
the edge, within the vertical slice the edge sweeps in this row, is *inside* the shape
(for an upward edge, *outside* — that's the edge's sign). Instead of adding that slice
height to every pixel to the right, the edge *deposits* it once: the pixels it passes
through get the part lying to their right (a trapezoid's area, cut per pixel), and the
next pixel gets the rest. One *running sum along the row* then carries the deposit
rightward, until the shape's other edge deposits the opposite amount. After the pass:

#+begin_src
  coverage(pixel) = min(1, |running sum at that pixel|)
#+end_src

- *=abs= ignores winding direction.* TrueType draws outer contours clockwise and holes
  anticlockwise; a hole's edges deposit the opposite sign, so =O= keeps its counter
  (the host test checks the centre pixel of an =O= is empty).
- *=min 1= handles overlaps* — an accent touching its letter.
- *One sum over the whole buffer.* It runs row-major, not row by row: each row's
  deposits add up to zero for a closed outline, so nothing leaks into the next row.

*Gamma.* Exact coverage looks *thin* for light text on a dark ground: the eye isn't
linear, and without hinting a one-pixel stem often lands half on each of two pixels.
So coverage is raised to =1/γ= before it becomes a byte (=lol.ttf:*gamma*=, 1.45).

- *How 1.45 was chosen.* The same line rendered at 11–18 px with γ = 1.0, 1.45 and 1.8:
  1.0 is spindly at 12 px, 1.8 starts to look bold at 18, 1.45 keeps =0O=, =1lI= and
  =;:= distinct at every size from 11 up.
- *Changing it* needs the glyph caches emptied (=lol.canvas::clear-font-cache=).

* 5. The FONT object, the glyph cache, and blending
:PROPERTIES:
:CUSTOM_ID: font-object-glyph-cache
:END:

=lol.canvas:font= has two kinds ([[file:../poc/canvas.lisp::defstruct font][=defstruct font=]]): a *bitmap* one (the 256 glyph
vectors) and an *outline* one (a =lol.ttf:face=). Both answer the questions layout asks
— =font-cw= and =font-ch=, the *cell* width and height — so nothing above the canvas
knows which kind it has.

** The size and the cell it implies

[[file:../poc/canvas.lisp::defun set-font-size][=set-font-size=]] sets the font's pixel size (the em) *in place* and recomputes the
cell from the font's own metrics, rounded to whole pixels:

#+begin_src
  scale    = size / unitsPerEm
  cw       = round(advance('M') × scale)              ; every glyph's, in a monospace font
  ch       = round((ascender − descender + lineGap) × scale)
  baseline = round((ascender + lineGap/2) × scale)    ; pixels below the cell's top
#+end_src

For DejaVu Sans Mono (computed with the code itself):

| size | cell  | baseline | columns × list rows on 1920×1200 |
|------+-------+----------+----------------------------------|
|   12 | 7×14  |       11 | 274 × 63                         |
|   14 | 8×16  |       13 | 240 × 57                         |
|   16 | 10×19 |       15 | 192 × 50                         |
| *18* | 11×21 |       17 | 174 × 46 — the default           |
|   20 | 12×23 |       19 | 160 × 42                         |
|   23 | 14×27 |       21 | 137 × 37                         |
|   29 | 17×34 |       27 | 112 × 30                         |
|   40 | 24×47 |       37 | 80 × 23                          |

*Why 18 px by default.* On a 13.4-inch 1920×1200 panel (a Dell XPS 13 9300; EDID
29 × 18 cm, about 168 pixels to the inch), the 6×15 bitmap's capitals are about 1.4 mm
tall. At 18 px a capital is about 2.1 mm (close to 10-point type at arm's length), and
a full-width pane still holds 170 columns. =lol.canvas:*default-font-size*= holds it;
a saved choice overrides it ([[#size-change-reaches-every][How a size change reaches every pixel of layout]]).

** The glyph cache

A screen repeats the same few dozen glyphs thousands of times, so
[[file:../poc/canvas.lisp::defun font-glyph][=font-glyph=]] keeps every glyph it makes.

- *Key.* *(size, codepoint)* packed into one fixnum, =size × 2²¹ + code= (codepoints
  stop below 2²¹), in a per-font =eql= hash table — the cheapest lookup there is.
- *Sizes coexist.* A size change throws nothing away; going back to a size finds its
  glyphs waiting.
- *Entry.* A coverage bitmap plus where its top-left sits relative to the pen and the
  baseline, shifted by a fraction of a pixel so it's *centred* in its rounded cell
  (the rounding error goes half to each side).

** Blending

[[file:../poc/canvas.lisp::defun draw-string-outline][=draw-string-outline=]] composites each glyph over what's already in the canvas,
channel by channel:

#+begin_src
  out = (ink × a + old × (255 − a)) / 255        a = coverage, 0..255
#+end_src

Full coverage is a plain store (most of a stem); zero is skipped (most of a cell). The
canvas has no alpha channel and needs none: the background is the pixels already there
— a panel colour, a selection band.

** Cost

- *Host* ([[file:../poc/font-test.lisp][poc/font-test.lisp]]'s timing block, 18 px): the 94 printable ASCII glyphs
  rasterise *cold* in 0.6 ms; a full 1920×1080 screen of cached text (170×51 cells)
  draws in about 5 ms, against 1.6 ms for the same glyph count in the bitmap font.
- *Guest* (KVM, 1280×800, tag #26): [[file:../check-pointer.lisp][check-pointer.lisp]] measured a whole frame
  (draw + present) at 4 ms.

That's why there's no C rasteriser here ([[#gotchas-was-ruled-out][Gotchas, and what was ruled out]]).

* 6. How a size change reaches every pixel of layout
:PROPERTIES:
:CUSTOM_ID: size-change-reaches-every
:END:

The rule: *no layout code may hold a text metric in a constant.* Every distance that
depends on text is computed from the current font *at draw time*.

There's exactly one font object — =*bfont*= in the shell, the same object as
=lol.widgets:*font*= and every text view's =tv-font= — and =set-font-size= mutates it.
"Change the size, redraw" is the whole mechanism. There's no relayout pass, because
layout is redone every frame anyway.

** The metric accessors

In [[file:../poc/widgets.lisp][poc/widgets.lisp]] unless noted, with the value each had as a constant at 6×15:

| accessor                                        | is                                            | at 6×15 (the old constant) |
|-------------------------------------------------+-----------------------------------------------+----------------------------|
| =char-w=, =line-h=                              | the font's cell                               | 6, 15                      |
| =+row-h+= → =(row-h)=                           | a list row: cell + 5                          | 20                         |
| =+bar-h+= → =(bar-h)=                           | a header band / breadcrumb / the tab strip    | 20                         |
| =card-head-h=                                   | a card's title strip: cell + 9                | 24                         |
| =+cell-w+=, =+cell-h+=                          | a dispatch-matrix cell: 13 chars × (cell + 3) | 78 × 18                    |
| =text-dy=                                       | how far down a band to draw text, centred     | (was =(+ y 3)=)            |
| =status-h= (shell)                              | the status line / minibuffer: cell + 7        | 22                         |
| =tv-gutter-w= (textview)                        | the line-number gutter: 4 chars + 16          | 40 (=*gutter-w*=)          |
| =tv-line-height= (textview)                     | a text-view line: cell + 3                    | 18 (always derived)        |
| =stage-transcript-h=, =dbg-row-h=, =dbg-band-h= | the stage strip, debugger rows and title band | 92, 17, 24                 |

=+row-h+= and friends are *symbol macros*: the compiler replaces the symbol with a
call, =(row-h)=, at each of the hundred places that use it. Code written with
=+row-h+= is automatically right; the price is a "+constant+" that varies, which is
why this table exists.

- *What consumes them.* Row heights and the list viewport, the tab strip and its close
  boxes, the systray, breadcrumbs, the status line, the minibuffer and its caret, the
  Spotter and clipboard cards, the context menu's width, the halo's labels, the
  dispatch matrix, the stage's heads-up line and transcript, image captions, the
  debugger (title band, restart and frame rows, locals strip, source viewer, value
  prompt), and the =SuperL-?= cheatsheet (which pours its groups into as many pages as
  the size needs — PageDown or Space turns them).
- *Hit maps follow.* Every hit map is made from the same numbers as the drawing, so a
  click and a pixel can't disagree. Mouse → (line, column) in a text view is
  =col-at-x=, which divides by the current =tv-cw=.
- *Long lines.* At large sizes most lines reach a pane's edge, so the text view
  *clips* at its edge and *scrolls sideways* to keep the caret visible (=tv-hscroll=,
  followed in =tv-draw=, counted by =x-of-col= / =col-at-x= so clicks still land).

** The keys

=browser-key= in [[file:../poc/shell.lisp][shell.lisp]] calls [[file:../poc/shell.lisp::defun change-font-size][=change-font-size=]]:

| keys                                           | does                                        |
|------------------------------------------------+---------------------------------------------|
| =SuperL-== or =SuperL-+=                       | bigger                                      |
| =SuperL--=                                     | smaller                                     |
| =SuperL-0=                                     | back to the size the font was loaded at     |
| =C-x C-== (or =C-x C-+=), =C-x C--=, =C-x C-0= | the same, Emacs's =text-scale-adjust= keys  |
| then a bare =+= (or ===), =-=, =0=             | repeats, without the =C-x= — as in Emacs    |
| =Ctrl= + wheel                                 | up bigger, down smaller, as in web browsers |

- *Steps.* 2 px below 20 and 3 px above (one pixel at 12 px is 8 %, at 30 px 3 % and
  too small to notice), clamped to 10–40 px; from 18 the sizes go 20, 23, 26, 29 … 40.
- *Feedback.* The status line says the result — =font: DejaVu Sans Mono 20px (12x23)=
  — and "at the largest end" when there's no further to go.

** Two chords the console doesn't send

On the framebuffer the characters come from the cooked tty and only the modifiers from
the keyboard's evdev ([[file:input.org][input.org]]). The kernel's default keymap
(=drivers/tty/vt/defkeymap.map=) gives keycodes 11 (=0=) and 13 (===) *no control
column*, so =Ctrl-0= and =Ctrl-== produce *no byte at all*. =Ctrl--= is fine
(=Control_underscore=, byte 31, reaching us as =C-_=). So =note-modifier-key= in
[[file:../initramfs/fb-browser.lisp][fb-browser.lisp]] reports those two chords from evdev, as it reports the Menu key.

** Remembering the size

Every change is written to =~/.lol/settings= as a plist the Lisp reader reads back —
=(:FONT-SIZE 20)= — by =save-setting= ([[file:../initramfs/settings.lisp][initramfs/settings.lisp]]), atomically (a temp
file and a rename). =run-browser-fb= reads it at start.

- *Never signals,* in either direction; =*read-eval*= is off when reading.
- *Nothing written without a real home.* A diskless boot has =HOME=/=, a tmpfs that
  dies at power-off.
- *Survives reboots* because =/home= is the host's own =/home= ([[file:storage.org][storage.org]]).
- *Older location.* A file at =~/.config/lol/settings= is moved into =~/.lol= at boot
  ([[file:session-persistence.org::#where-things-live-when][session-persistence.org, Where things live, and when there is no disk]]).
- *Not in rendered frames.* =render-frame.lisp= never loads it, so a rendered frame
  doesn't depend on your preferences.

* 7. Which font ships, and changing it
:PROPERTIES:
:CUSTOM_ID: which-font-ships-changing
:END:

- *At build time.* [[file:../build.sh][build.sh]] copies a monospace TrueType file *from the build host*
  into the gitignored =initramfs/mono.ttf=, and the cpio list puts it at
  =/usr/share/lol/mono.ttf= (343 140 bytes for DejaVu Sans Mono). It's someone else's
  work, so — like firmware — it's never committed. =LOL_FONT=/path/to/font.ttf= picks
  one; the default is =/usr/share/fonts/truetype/dejavu/DejaVuSansMono.ttf=, else
  whatever =fc-match monospace= names. Its licence (Bitstream Vera; DejaVu's own
  changes are public domain) is in [[file:../README.org][README.org]]'s licensing table.
- *No TrueType on the host.* build.sh ships an *empty* file, the image fails to parse
  it and falls back to the bitmap — harder to read, never broken.
- *On the host.* =render-frame.lisp=, =run-browser.lisp= (X11) and the host tests take
  =$LOL_FONT=, else the host's DejaVu, else =poc/cozette.lolf=.
  =sbcl --script poc/render-frame.lisp workspace --size 28= renders a frame at 28 px;
  =--font PATH= tries another file (a =.lolf= path selects the bitmap fallback).
- *At run time.* =(set-font "/mnt/host/usr/share/fonts/truetype/cascadia-code/CascadiaMono.ttf")=
  in the Workspace switches the whole environment to any TrueType file the host has
  (=/mnt/host= is its root, read-only — [[file:storage.org][storage.org]]), keeping the size. It replaces
  the font object and repoints the open text views at it. A proportional font draws,
  but on the monospace grid — each glyph centred in a cell as wide as its =M=.

* 8. The bitmap fallback
:PROPERTIES:
:CUSTOM_ID: bitmap-fallback
:END:

Cozette (MIT), 6×15, ships as =/cozette.lolf=. [[file:../poc/bdf2font.lisp][=bdf2font.lisp=]] converts it from its BDF
into our own =.lolf= blob: magic =LF=, a width byte, a height byte, then 256 glyphs of
one byte per row, *indexed by real codepoint*.

- *Why not PSF.* A console *PSF1* font (read by =load-psf=) is the same idea with an
  implicit, Latin-1-ish glyph order — which made =·= draw as =Ö=. Owning the order in
  =.lolf= fixes that.
- *Drawing.* =draw-string-bitmap= stamps the lit bits, testing =(logbitp (- 7 col) bits)=
  because column 0 is the *most* significant bit.
- *Resizing.* A bitmap can't be redrawn at another size, only magnified, so
  =set-font-size= rounds to the nearest whole multiple of 15 and stamps each pixel as a
  k×k block (size 30 gives 12×30 cells). The cell metrics follow, so layout is right;
  only the letters are blocky.
- *256 glyphs.* That's why the chrome folds characters past Latin-1 to ASCII cousins
  (an em dash to =-=, an ellipsis to =.= — =glyph-index= in canvas.lisp) and why
  elisions are two dots. The outline font maps anything its =cmap= covers and draws
  =.notdef= for the rest.

* 9. Testing it

- *Host, the engine.* =sbcl --script poc/font-test.lisp= — 43 checks: the tables, cmap
  (both formats, agreeing), advances, rasterised coverage (a space is empty, =l= has a
  solid stem *and* grey edges, =g= descends, =O= keeps its hole, =é= is a composite),
  the cell at 18 px, clamping, the cache (one miss per distinct glyph, then hits; a new
  size misses again), blending, the bitmap fallback's magnification; then [[#font-object-glyph-cache][The FONT object, the glyph cache, and blending]]'s
  timings.
- *Host, the pixels.* =poc/render-frame.lisp SUBJECT --size N= at 12, 18 and 28 — look
  at the frames; =-k "s-= s-="= replays the keys and shows the status line.
- *Guest, the machine.* =LOL_GUEST_DISK=test-disk.img sbcl --script check-font.lisp=
  boots the image and presses the keys through QMP: the TTF loaded, the default size,
  =SuperL-= / - / 0=, =C-x C-= / C-- / C-0= and the bare repeat, the row height
  following the cell, the world having repaired the screen, the screendump differing,
  the status line, a letter typed after the chord not swallowed, and the size landing
  in =HOME/.lol/settings= (diskless: nothing written). 19 checks with the disk.
- *Other guest checks.* =check-scroll=, =check-clipboard= and =check-pointer= pass at
  18 px.

* 11. Gotchas, and what was ruled out
:PROPERTIES:
:CUSTOM_ID: gotchas-was-ruled-out
:END:

- *Never copy a metric into a constant.* A =(defparameter +foo-h+ 20)= sized for one
  font is exactly the bug runtime resizing removed; ask =line-h= at draw time. Every
  track's code is held to this rule ([[file:code-browser.org][[[file:code-browser.org::#must-write-ourselves][code-browser.org, What we must write ourselves]]]]).
- *Cell vs glyph.* =cw=/=ch= are the *cell*; ink usually fills less, and =g=/=y= descend
  below the baseline into the cell's bottom. Drawing takes the cell's top-left, not the
  baseline.
- *A pane's text is clipped, not wrapped.* Long lines scroll sideways with the caret
  ([[#size-change-reaches-every][How a size change reaches every pixel of layout]]); lists elide with =..=.
- *Ctrl-digit and Ctrl-punctuation may be silent on the console* ([[#size-change-reaches-every][How a size change reaches every pixel of layout]]). Before binding
  one, check =defkeymap.map= for a =control= line, or read the chord from evdev.
- *Ruled out: stb_truetype.* A C rasteriser through the =libstbi.so= pattern
  ([[file:previews.org][previews.org]]) was the fallback if pure Lisp proved too slow or too ugly. Measured
  ([[#font-object-glyph-cache][The FONT object, the glyph cache, and blending]]), it's neither.
- *Not a finding: "0.0 ms".* A single cold run of 94 glyphs is too short to time; the
  test times twenty cold runs and reports 0.6 ms.
