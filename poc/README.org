#+TITLE: poc/ — the graphics proof-of-concept for the code browser
#+STARTUP: showall

Plan this validates: [[file:../doc/code-browser.org][doc/code-browser.org]] (§1, "one pixel buffer, two backends").

* What this proves

The code-browser plan rests on one claim:

#+begin_quote
The browser draws into a pixel buffer it owns, in pure Lisp. A *backend* does
nothing but *present* that buffer and hand back events. So the same browser runs
on the bare framebuffer AND in a window on the dev host — and "supporting X"
never means running an X *server*, only writing a small X *client*.
#+end_quote

Everything except the X11 client was already proven by =draw-alien=
([[file:../doc/framebuffer.org][framebuffer.org §8]]). The X11 client was *not*. This POC settles it.

*Result: the claim holds.* The identical =canvas.lisp= + =scene.lisp= render the
same mock browser in an X11 window on the host and on =/dev/fb0= with SBCL as
PID 1. No C, no Xlib, no CLX, no DRM, no kernel change.

* Run it

The font (=cozette.lolf=) is committed, so there is no setup — just run:

#+begin_src sh
  sbcl --script poc/run-host.lisp   # a window on your desktop. arrows/click; q quits.
  ./poc/build-poc.sh                # boots the LoL machine; writes poc/screen-fb.png
#+end_src

=run-host.lisp= needs =$DISPLAY= and =$XAUTHORITY= (an ordinary X session).
=build-poc.sh= touches *nothing* in =initramfs/= — it builds its own image and
reuses only =preinit=, =alien.rgba= and the already-built =bootx64.efi=.

* What it settles, concretely

- *X11 from scratch is small.* Because we do all our own drawing, the client
  never asks X to render a glyph or a line — we hand it one finished image via
  =PutImage=. Connection handshake + MIT-MAGIC-COOKIE-1 + =CreateWindow= +
  =MapWindow= + =CreateGC= + =PutImage= + five event types is the *whole* protocol
  surface we need.
- *One pixel format serves both.* The canvas stores =#x00RRGGBB= words, which sit
  in memory little-endian as =B,G,R,0= — exactly BGRX, exactly what efifb scans
  out *and* what the X server wants at depth 24 on x86. Both backends ship the
  buffer with zero conversion. (Confirmed by the alien coming out green, not
  magenta.)
- *Text is not a problem.* PSF1 is a 4-byte header and 256 glyph bitmaps. Parsing
  it is 15 lines; blitting it is 20. Crisp, fast, and enough for a browser.
- *=KD_GRAPHICS= works and is cheap* — one ioctl, and fbcon stops fighting us. It
  does *not* stop key delivery, so the existing raw-mode keyboard survives intact.
- *The mouse is already there — and now read.* The guest's boot log shows
  =input: ImExPS/2 Generic Explorer Mouse=; =CONFIG_INPUT_EVDEV=y= is already set,
  so it is live under QEMU with no kernel change. =fb-browser.lisp= reads it: a
  cursor tracks motion, left-click drills, and the wheel scrolls. The device is
  *not* a fixed =eventN= and has no =mouseN= handler (=mousedev= is not built), so
  =input-device-kind= finds it by *capability* — a block in
  =/proc/bus/input/devices= whose =B: EV=- mask has EV_REL (bit 2) or EV_ABS
  (bit 3) with an X axis. Every such pointer (and every keyboard) is opened, and
  hotplugged ones too. The whole mechanism —
  the 24-byte =input_event= record, the =poll(2)= over every device, the wheel's sign
  convention, and why a bare Ctrl needs the keyboard's *own* evdev — is written up
  in [[file:../doc/input.org][doc/input.org]].

* Verifying a visual change

The browser is pixels, so a change to it is only "done" when somebody has *looked*
at the result. Doing that through the guest means a full =./build.sh=, a QEMU boot
and a QMP key sequence — minutes, for a two-pixel colour tweak. =render-frame.lisp=
collapses that to about a second:

#+begin_src sh
  sbcl --script poc/render-frame.lisp modules                  # the default root
  sbcl --script poc/render-frame.lisp matrix:collide           # the dispatch grid
  sbcl --script poc/render-frame.lisp defn:draw-alien          # a source pane
  sbcl --script poc/render-frame.lisp class:stream -k "down down ret"
  sbcl --script poc/render-frame.lisp -h                       # every subject form
#+end_src

It loads the real stack in the real order — =registry= -> =model= -> =present= ->
=canvas= -> =textview= -> =shell=, the same modules =build.sh= bakes into the image,
minus the ones that want hardware — seeds the environment with =open-environment=
(so tab 1 is your subject and tab 2 the Workspace, exactly as in the guest), makes
the *real* world (=make-desk=: the tab strip, the trail area of pane morphs, the
status line — [[file:../doc/morphic.org][doc/morphic.org]] §12) and lets it repair itself into a canvas, every
morph drawing itself as it does on the panel. Nothing is mocked and nothing is
re-implemented; if a frame looks right here it looks right on the panel.

*Why the pixels are trustworthy.* The guest does not re-render anything: =lol.fb=
copies this very canvas — =#x00RRGGBB= words — into =/dev/fb0= byte for byte, which
is the "one pixel format serves both" property above. So the PPM is not an
approximation of the framebuffer, it is its contents. Pass =-s 1280x800= to match
QEMU's geometry exactly.

Output defaults to =poc/out/frame.ppm= (already gitignored). PPM is deliberately
dependency-free — a short ASCII header and raw RGB — and =pnmtopng= or =convert=
makes a PNG if your viewer wants one.

*Reaching a state that is not a root.* =-k= replays a script through the real world's
event routing (=lol.morph:world-dispatch=: keys to the focused pane's =browser-key=, a
click to the morph under it), so a frame can show a drilled pane, a split, or a
matrix cell's onion:

#+begin_src sh
  -k "down down ret"        # drill the third row
  -k "down S-ret"           # open the selection BESIDE the list (the editable split)
  -k "click:180,92"         # click a dispatch-matrix cell -> its effective-method onion
  -k "s-g right right esc"  # tear the tab off into a window, move it two cells (doc/morphic.org)
  -k "drag:60,10,700,300"   # press, move held, release: here, a tab dragged out into a window
  -k "s-2"                  # SuperL-2: switch to the Workspace tab
  -k "wheel:20"             # scroll the viewport (the selection stays where it was)
  -k "s-= s-="              # SuperL-= twice: a bigger font, and the status line says so
#+end_src

*At another font size.* =--size N= sets the font's pixel size (10–40; default 18),
=--font PATH= another TrueType file, or a =.lolf= for the bitmap fallback. Any change
to layout should be looked at at three sizes — 12, 18 and 28 cover it — because a
distance that does not follow the font only shows when the font moves
([[file:../doc/fonts.org][doc/fonts.org]] §6).

*The Spotter too.* =--spotter QUERY= draws the palette over whatever subject you
named, filtered by QUERY — so the finder can be looked at without booting the guest
and holding down Super:

#+begin_src sh
  sbcl --script poc/render-frame.lisp modules --spotter coll   # 9 matches, banded
  sbcl --script poc/render-frame.lisp modules --spotter ""     # the recents band
  sbcl --script poc/render-frame.lisp workspace --spotter "~/"  # a PATH: completions
#+end_src

*The file manager.* =dir:PATH= opens it on a folder and =file:PATH= drills a file
(an editor for text); PATH may be absolute, =~/…= or relative. With =-k=, its letters
replay like any key, so the minibuffer prompts render too
([[file:../doc/file-manager.org][doc/file-manager.org]]):

#+begin_src sh
  sbcl --script poc/render-frame.lisp dir:~/lisp-over-linux/poc                 # listing + preview
  sbcl --script poc/render-frame.lisp dir:~/lisp-over-linux/poc -k "/ l i s p"  # the live filter
  sbcl --script poc/render-frame.lisp dir:~ -k ". s"          # dot files shown, sorted by date
  sbcl --script poc/render-frame.lisp dir:/tmp -k "down r"    # the rename prompt
#+end_src

/Careful: a replayed key really runs. =-k "… C-x C-s"= writes the file and =-k "d y"=
deletes — point =dir:= at a scratch copy for those./

*And the halo.* =--halo X,Y[,D]= opens the middle-button halo at X,Y on layer D (0 is
the innermost thing under the point) and prints the layers and the handles — the
quickest way to see what a point on the screen is made of:

#+begin_src sh
  sbcl --script poc/render-frame.lisp workspace --halo 110,280     # the symbol LAUNCH
  sbcl --script poc/render-frame.lisp workspace --halo 110,280,1   # the TEXTVIEW holding it
#+end_src

That works because the Spotter's *drawing* lives in =shell.lisp= with the rest of the
shell's; only its modal input loop is in =fb-browser.lisp=. The same split is why the
palette's colours could be fixed by looking at a frame rather than by guessing: the
matched characters were being lit in the accent, which is also every function row's
colour, so the highlight was invisible on exactly the rows that matter.

The canvas is repaired between script steps, because clicks hit-test against
geometry each morph records as it draws (a pane's =pane-rows=, =pane-body-top=,
=pane-cells=; the tab strip's tabs). That is deliberate: a scripted click therefore
exercises the same draw/hit-test agreement a real one does, instead of testing a stale
layout.

*What it does NOT cover*, and still needs the guest: input plumbing (evdev, the
wheel, =poll(2)= — [[file:../doc/input.org][doc/input.org]]), the live debugger (=fb-browser.lisp=, not loaded
here), and anything about =present-fb= itself. Its module index is correspondingly a
subset of the guest's.

For the half it cannot reach there is [[file:../check-scroll.lisp][=check-scroll.lisp=]] in the project root (and
[[file:../check-pointer.lisp][=check-pointer.lisp=]] beside it, for the pointer not redrawing the frame): it boots
the real image and asserts what the machine *does* with real input — QMP keys and
genuine evdev =REL_WHEEL= records — reading =pane-top= / =pane-sel= / =tv-scroll=
back over the net REPL rather than guessing from pixels. The two harnesses divide
the work cleanly: =render-frame.lisp= for how a frame looks, =check-scroll.lisp= for
how the machine behaves.

* Known rough edges (it is a POC)

- The framebuffer path redraws and pushes a *full frame* whenever the state changes
  (no damage tracking) — one =pwrite(2)= of the canvas, ~3 ms a frame under KVM
  (doc/framebuffer.org §9.4). The mouse pointer is the one exception: it is
  composited on the way out, so a bare move re-sends two arrow-sized patches and
  redraws nothing (§9.5). Dirty rectangles for the rest are still owed.
- =run-guest.lisp= (the standalone POC scene) draws once and parks and does not
  read the mouse; the shipped =fb-browser.lisp= does read it (see above).
- Keys are raw X11 keycodes (evdev layout), not keysyms — no keymap.

** Browser shell — known gaps / TODO (=shell.lisp=, =run-browser.lisp=)

- *Scrolling — DONE, on both backends.* =tv-wheel= scrolls a text pane's viewport
  without moving the caret, =move-page= pages the caret, and a list pane has a
  viewport of its own (=lol.widgets:draw-list=): the wheel moves it and leaves the
  selection alone — scrolling is /looking/ — while touching the selection
  re-attaches the view to it. The guest decodes evdev =REL_WHEEL= in =read-mouse=;
  X delivers the wheel as button 4/5 press events, which =run-browser.lisp= and
  =run-editor.lisp= route to =browser-scroll= / =tv-wheel=. =+wheel-lines+= (3 lines
  a notch) lives in =shell.lisp= so both backends share it. /Verified in the booted
  guest over QMP against the browser's own state — twelve assertions, all passing
  (see [[file:../doc/code-browser.org][code-browser.org]], phase 5)./ See [[file:../doc/input.org][doc/input.org]] §6-7 for the wheel end to
  end on both backends.
- Trail *tabs* and the *Spotter* are DONE (§4¾) — =draw-tabs= here, the palette in
  =draw-spotter-card= here too, candidates from [[file:../initramfs/present.lisp][=present.lisp=]]. Note that only the
  Spotter's *input loop* lives in [[file:../initramfs/fb-browser.lisp][=fb-browser.lisp=]] — its drawing moved into
  =shell.lisp= with the rest of the shell's, which is what lets =render-frame.lisp=
  render the palette on the host (=--spotter Q=). Summoning it, and the debugger,
  still needs the guest: the host X11 runner reaches them via =(fboundp …)= and
  simply does nothing when that file was not loaded.
- *Jump-to-definition — done for the mouse* (=shell.lisp=: =jump-to-definition=,
  =click-token=, =resolve-symbol=): =Ctrl-click= a symbol in a source pane resolves
  it (=find-symbol=, so a typo can't intern) and drills into its definition on a new
  trail level — source if we recorded it, else a =sb-introspect= reference. A plain
  click in code is inert (reserved for future caret placement). *=M-.= from the
  keyboard is now done too* — Esc is decoded as the Emacs Meta prefix
  (=fb-read-key= / =lol.canvas:meta-p=) and resolves the symbol at point through
  the same =jump-at-point=. Holding Ctrl over the console needs the keyboard's own
  evdev (the cooked tty can't report a bare modifier) — the framebuffer browser
  does this; the X11 runner reads Ctrl straight from the button event's modifier
  state.
- Chrome markers are ASCII (=>= / =v= / =>=); the 6×15 blob is 256 codepoints, so
  no ▸▾→ glyphs — draw chrome as shapes later (§6.2). (The TrueType font has them;
  the markers stay ASCII so the fallback draws the same chrome.)

* The fonts — DejaVu Sans Mono (TrueType), Cozette (MIT) as the fallback

The environment draws with a TrueType font rasterised by =ttf.lisp= — by default the
host's =/usr/share/fonts/truetype/dejavu/DejaVuSansMono.ttf=, or =$LOL_FONT= — at a
size =SuperL-= / =SuperL--= / =SuperL-0= change at run time. =render-frame.lisp=
takes =--size N= and =--font PATH=. Everything below is about the fallback; the
whole story is [[file:../doc/fonts.org][doc/fonts.org]].

The fallback font is *Cozette* (=cozette.lolf=, MIT — see =cozette-LICENSE.txt=),
chosen from a side-by-side comparison. It is baked into our own tiny =.lolf= blob
(6x15, glyphs indexed by codepoint) by =bdf2font.lisp=, the way =alien.rgba= is
pre-generated and committed. Note the kernel's built-in =font_8x16= is *GPL* and
must not be lifted; Cozette's MIT license is committed alongside the blob.

To *regenerate* =cozette.lolf= (the blob is committed, so this is only for updates):

#+begin_src sh
  curl -fsSL -o /tmp/cozette.bdf \
    https://github.com/slavfox/Cozette/releases/latest/download/cozette.bdf
  sbcl --script poc/bdf2font.lisp /tmp/cozette.bdf poc/cozette.lolf
#+end_src

The =.lolf= format and the whole glyph→pixel path are documented in [[file:../doc/fonts.org][doc/fonts.org]].
