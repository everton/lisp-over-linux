#+TITLE: poc/ — the graphics proof-of-concept for the code browser
#+STARTUP: showall

The design this validates: [[file:../doc/code-browser.org][doc/code-browser.org]] (§1, "one pixel buffer, two
backends"). It began as a proof of concept and is now the browser's pixel toolkit
and shell, loaded in place by =build.sh=.

* What this proves

The code browser rests on one claim:

#+begin_quote
The browser draws into a pixel buffer it owns, in pure Lisp. A *backend* does
nothing but *present* that buffer and hand back events. So the same browser runs
on the bare framebuffer AND in a window on the dev host — and "supporting X"
never means running an X *server*, only writing a small X *client*.
#+end_quote

*The claim holds.* The identical =canvas.lisp= + =scene.lisp= render the same mock
browser in an X11 window on the host and on =/dev/fb0= with SBCL as PID 1. No C,
no Xlib, no CLX, no DRM, no kernel change. (The framebuffer half was already
proven by =draw-alien=, [[file:../doc/framebuffer.org][framebuffer.org §8]]; the X11 client was the open question.)

* Run it

The fallback font is committed, so there's no setup:

#+begin_src sh
  sbcl --script poc/run-host.lisp      # the POC scene in a window. arrows/click; q quits.
  sbcl --script poc/run-browser.lisp   # the real browser in a window
  ./poc/build-poc.sh                   # boots the POC scene as PID 1; writes poc/screen-fb.png
#+end_src

- *X11 runners* need =$DISPLAY= and =$XAUTHORITY= (an ordinary X session).
- *=build-poc.sh=* touches nothing in =initramfs/=: it builds its own image and
  reuses only =preinit=, =alien.rgba= and the already-built =bootx64.efi=.

* What it settles

- *X11 from scratch is small.* We do all our own drawing, so the client never asks
  X to render a glyph or a line — it hands over one finished image via =PutImage=.
  The handshake, MIT-MAGIC-COOKIE-1, =CreateWindow=, =MapWindow=, =CreateGC=,
  =PutImage=, the keymap and a handful of event types are the whole protocol
  surface.
- *One pixel format serves both.* The canvas stores =#x00RRGGBB= words, which sit
  in memory little-endian as =B,G,R,0= — exactly BGRX, which efifb scans out *and*
  the X server wants at depth 24 on x86. Both backends ship the buffer with zero
  conversion. (The alien comes out green, not magenta.)
- *Text is not a problem.* The bitmap fallback is a 256-glyph blob (PSF1 is just a
  4-byte header in front of the same thing): a few lines to parse, a few to blit.
  The default is a TrueType font rasterised by =ttf.lisp=.
- *=KD_GRAPHICS= works and is cheap.* One ioctl, and fbcon stops fighting us. It
  does *not* stop key delivery, so the raw-mode keyboard keeps working.
- *The mouse needs no kernel change.* =CONFIG_INPUT_EVDEV=y= is set and QEMU's PS/2
  mouse is live. It isn't a fixed =eventN= and has no =mouseN= handler (=mousedev= is
  not built), so =input-device-kind= finds pointers by *capability*: a block in
  =/proc/bus/input/devices= whose =B: EV== mask has EV_REL (bit 2) or EV_ABS (bit 3)
  with an X axis. The whole input path is in [[file:../doc/input.org][doc/input.org]].

* Verifying a visual change

The browser is pixels, so a change is only done when someone has *looked* at it.
Through the guest that's a full =./build.sh=, a QEMU boot and a QMP key sequence —
minutes. =render-frame.lisp= takes about a second:

#+begin_src sh
  sbcl --script poc/render-frame.lisp modules                  # the default root
  sbcl --script poc/render-frame.lisp matrix:collide           # the dispatch grid
  sbcl --script poc/render-frame.lisp defn:draw-alien          # a source pane
  sbcl --script poc/render-frame.lisp class:stream -k "down down ret"
  sbcl --script poc/render-frame.lisp -h                       # every subject form
#+end_src

- *Nothing is mocked.* It loads the real stack in the real order (=registry= →
  =model= → =present= → =canvas= → =textview= → =shell=, the modules =build.sh=
  bakes in, minus those that want hardware), seeds the environment with
  =open-environment= (tab 1 your subject, tab 2 the Workspace, as in the guest),
  makes the *real* world (=make-desk=, [[file:../doc/morphic.org][doc/morphic.org]] §5) and lets it repair
  itself into a canvas.
- *The pixels are the framebuffer's.* The guest doesn't re-render: =lol.fb= copies
  this very canvas into =/dev/fb0= byte for byte. The PPM is the framebuffer's
  contents, not an approximation of them.
- *Size.* =-s WxH= sets the canvas (default 1280x720); =-s 1280x800= matches the
  guest checks' QEMU.
- *Output.* =poc/out/frame.ppm= by default (gitignored; =-o FILE= elsewhere). PPM
  is dependency-free; =pnmtopng= or =convert= makes a PNG.

** Reaching a state that isn't a root

=-k= replays a script through the real world's event routing
(=lol.morph:world-dispatch=: keys to the focused pane, a click to the morph under
it), so a frame can show a drilled pane, a split, or a matrix cell's onion:

#+begin_src sh
  -k "down down ret"        # drill the third row
  -k "down S-ret"           # open the selection BESIDE the list (the editable split)
  -k "click:180,92"         # click a dispatch-matrix cell -> its effective-method onion
  -k "s-g right right esc"  # tear the tab off into a window, move it two cells (doc/morphic.org)
  -k "drag:60,10,700,300"   # press, move held, release: here, a tab dragged out into a window
  -k "s-2"                  # SuperL-2: switch to the Workspace tab
  -k "wheel:20"             # scroll the viewport (the selection stays where it was)
  -k "s-= s-="              # SuperL-= twice: a bigger font, and the status line says so
#+end_src

The canvas is repaired between steps, because clicks hit-test against geometry each
morph records as it draws (a list body's rows, a pane's =pane-body-top=, a grid
body's cells, the tab strip's tabs). A =click:X,Y= is a press and its release; a
press on a row acts on the release (one that moves picks the row up instead —
[[file:../doc/morphic.org][doc/morphic.org]] §9.1). So a scripted click exercises the same draw/hit-test
agreement a real one does.

** Other options and subjects

- *Font size.* =--size N= sets the pixel size (10–40; default 18), =--font PATH=
  another TrueType file or a =.lolf=. Look at any layout change at 12, 18 and 28: a
  distance that doesn't follow the font only shows when the font moves
  ([[file:../doc/fonts.org][doc/fonts.org]] §6).
- *The Spotter.* =--spotter QUERY= draws the palette over the subject, filtered by
  QUERY. Its drawing lives in =shell.lisp= (its input loop in =overlays.lisp=),
  which is why the host can render it.
- *Org files* ([[file:../doc/org.org][doc/org.org]]). =org:PATH= opens a file's outline; an =.org=
  opened with =file:PATH= is the Org editor, so its keys replay too.
- *The file manager* ([[file:../doc/file-manager.org][doc/file-manager.org]]). =dir:PATH= opens a folder, =file:PATH=
  drills a file (an editor for text); PATH may be absolute, =~/…= or relative.
- *The halo.* =--halo X,Y[,D]= opens the middle-button halo at X,Y on layer D (0 is
  the innermost thing under the point) and prints the layers and handles.

#+begin_src sh
  sbcl --script poc/render-frame.lisp modules --spotter coll             # banded matches
  sbcl --script poc/render-frame.lisp workspace --spotter "~/"           # a PATH: completions
  sbcl --script poc/render-frame.lisp org:doc/org.org -k "down down"     # outline + a section's preview
  sbcl --script poc/render-frame.lisp file:doc/org.org -k "S-tab"        # OVERVIEW: every top heading folded
  sbcl --script poc/render-frame.lisp dir:poc -k "/ l i s p"             # the live filter
  sbcl --script poc/render-frame.lisp dir:/tmp -k "down r"               # the rename prompt
  sbcl --script poc/render-frame.lisp workspace --halo 110,280           # the symbol under the point
  sbcl --script poc/render-frame.lisp workspace --halo 110,280,1         # the TEXTVIEW holding it
#+end_src

/Careful: a replayed key really runs. =-k "… C-x C-s"= writes the file and =-k "d y"=
deletes — point =dir:= at a scratch copy for those./

** What it doesn't cover

- *Input plumbing.* evdev, the wheel, =poll(2)= ([[file:../doc/input.org][doc/input.org]]).
- *The live debugger.* It's in =fb-browser.lisp=, which isn't loaded here.
- *=present-fb= itself.* The module index here is correspondingly a subset of the
  guest's.

For that half there are the guest checks, e.g. [[file:../check-scroll.lisp][=check-scroll.lisp=]] and
[[file:../check-pointer.lisp][=check-pointer.lisp=]] in the project root: they boot the real image, send QMP keys
and genuine evdev =REL_WHEEL= records, and read =pane-top= / =pane-sel= /
=tv-scroll= back over the net REPL rather than guessing from pixels. Split:
=render-frame.lisp= for how a frame looks, the =check-*.lisp= files for how the
machine behaves.

* Known limits

- *=run-guest.lisp= is the POC scene only.* It draws once and parks, and doesn't
  read the mouse; the shipped =fb-browser.lisp= does.
- *A bare Ctrl on the console* needs the keyboard's own evdev (the cooked tty can't
  report a bare modifier), which =fb-browser.lisp= reads; the X11 runner takes Ctrl
  from the event's modifier state.

* The fonts

The environment draws with a TrueType font rasterised by =ttf.lisp= — by default the
host's =/usr/share/fonts/truetype/dejavu/DejaVuSansMono.ttf=, or =$LOL_FONT= — at a
size =SuperL-= / =SuperL--= / =SuperL-0= change at run time. The whole story is
[[file:../doc/fonts.org][doc/fonts.org]]; what follows is about the fallback.

- *Cozette, MIT.* =cozette.lolf= (licence in =cozette-LICENSE.txt=) is used when no
  TrueType file loads. =bdf2font.lisp= bakes it into our 6×15 =.lolf= blob (glyphs
  indexed by codepoint), pre-generated and committed like =alien.rgba=.
- *Not the kernel's font.* The kernel's built-in =font_8x16= is GPL and must not be
  lifted.

To regenerate =cozette.lolf= (only for updates; the blob is committed):

#+begin_src sh
  curl -fsSL -o /tmp/cozette.bdf \
    https://github.com/slavfox/Cozette/releases/latest/download/cozette.bdf
  sbcl --script poc/bdf2font.lisp /tmp/cozette.bdf poc/cozette.lolf
#+end_src
