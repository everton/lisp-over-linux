#+TITLE: poc/ — the graphics proof-of-concept for the code browser
#+STARTUP: showall

Plan this validates: [[file:../doc/code-browser.org][doc/code-browser.org]] (§1, "one pixel buffer, two backends").

* What this proves

The code-browser plan rests on one claim:

#+begin_quote
The browser draws into a pixel buffer it owns, in pure Lisp. A *backend* does
nothing but *present* that buffer and hand back events. So the same browser runs
on the bare framebuffer AND in a window on the dev host — and "supporting X"
never means running an X *server*, only writing a small X *client*.
#+end_quote

Everything except the X11 client was already proven by =draw-alien=
([[file:../doc/framebuffer.org][framebuffer.org §8]]). The X11 client was *not*. This POC settles it.

*Result: the claim holds.* The identical =canvas.lisp= + =scene.lisp= render the
same mock browser in an X11 window on the host and on =/dev/fb0= with SBCL as
PID 1. No C, no Xlib, no CLX, no DRM, no kernel change.

| file             | role                                                             |
|------------------+------------------------------------------------------------------|
| =canvas.lisp=    | the pixel buffer + =fill-rect= / =blit-rgba= / PSF font + =draw-string=. *Backend-blind.* |
| =scene.lisp=     | what we draw: a mock code browser (tabs, 3 list panes, syntax-coloured source, the alien). *Backend-blind.* |
| =x11.lisp=       | a minimal X11 *client* in pure Lisp: auth, CreateWindow, PutImage, events. ~250 lines. |
| =fb.lisp=        | the =/dev/fb0= presenter + =KD_GRAPHICS= (stop fbcon scribbling on us). |
| =run-host.lisp=  | host entry: present via X11.                                      |
| =run-guest.lisp= | guest entry: present via =/dev/fb0=. PID 1, so it never returns.  |
| =shell.lisp=     | the drill-down accordion shell: renders =present= (a stack of panes) into pixels; drill / breadcrumb / commands. Drives the real =initramfs/= registry+model+present. |
| =run-browser.lisp= | *the code browser, live in an X11 window.* =sbcl --script poc/run-browser.lisp= — root at CL-USER, drill definitions, read source, browse the browser itself. |
| =build-poc.sh=   | builds a throwaway =lisp-init= + initramfs and boots it headless in QEMU. |
| =cozette.lolf=   | the font, *committed*: Cozette (MIT) baked to our tiny 6x15 blob. How the font path works end to end: [[file:../doc/fonts.org][doc/fonts.org]]. |
| =bdf2font.py=    | build-host converter: a BDF font → the =.lolf= blob (indexed by codepoint). |
| =cozette-LICENSE.txt= | Cozette's MIT license (required to ship the font). |

* Run it

The font (=cozette.lolf=) is committed, so there is no setup — just run:

#+begin_src sh
  sbcl --script poc/run-host.lisp   # a window on your desktop. arrows/click; q quits.
  ./poc/build-poc.sh                # boots the LoL machine; writes poc/screen-fb.png
#+end_src

=run-host.lisp= needs =$DISPLAY= and =$XAUTHORITY= (an ordinary X session).
=build-poc.sh= touches *nothing* in =initramfs/= — it builds its own image and
reuses only =preinit=, =alien.rgba= and the already-built =bootx64.efi=.

* What it settles, concretely

- *X11 from scratch is small.* Because we do all our own drawing, the client
  never asks X to render a glyph or a line — we hand it one finished image via
  =PutImage=. Connection handshake + MIT-MAGIC-COOKIE-1 + =CreateWindow= +
  =MapWindow= + =CreateGC= + =PutImage= + five event types is the *whole* protocol
  surface we need.
- *One pixel format serves both.* The canvas stores =#x00RRGGBB= words, which sit
  in memory little-endian as =B,G,R,0= — exactly BGRX, exactly what efifb scans
  out *and* what the X server wants at depth 24 on x86. Both backends ship the
  buffer with zero conversion. (Confirmed by the alien coming out green, not
  magenta.)
- *Text is not a problem.* PSF1 is a 4-byte header and 256 glyph bitmaps. Parsing
  it is 15 lines; blitting it is 20. Crisp, fast, and enough for a browser.
- *=KD_GRAPHICS= works and is cheap* — one ioctl, and fbcon stops fighting us. It
  does *not* stop key delivery, so the existing raw-mode keyboard survives intact.
- *The mouse is already there — and now read.* The guest's boot log shows
  =input: ImExPS/2 Generic Explorer Mouse=; =CONFIG_INPUT_EVDEV=y= is already set,
  so it is live under QEMU with no kernel change. =fb-browser.lisp= reads it: a
  cursor tracks motion and left-click drills. Note the device is *not* a fixed
  =eventN= and has no =mouseN= handler (=mousedev= is not loaded) — =find-mouse-device=
  locates it by capability instead, scanning =/proc/bus/input/devices= for the block
  whose =B: EV=- mask has EV_REL (bit 2) or EV_ABS (bit 3) set. Here that resolves
  to =/dev/input/event2=.

* Known rough edges (it is a POC)

- The framebuffer path pushes a *full frame* per present (no damage tracking) and
  writes it row-by-row rather than via =mmap=. Fine for a static scene; the real
  toolkit needs dirty rectangles.
- =run-guest.lisp= (the standalone POC scene) draws once and parks and does not
  read the mouse; the shipped =fb-browser.lisp= does read it (see above).
- Keys are raw X11 keycodes (evdev layout), not keysyms — no keymap.

** Browser shell — known gaps / TODO (=shell.lisp=, =run-browser.lisp=)

- *Scrolling is caret/selection-driven only.* A source pane scrolls only when the
  caret moves off-screen (=↑↓=); a list pane scrolls only when the selection moves.
  Missing: *mouse-wheel / touchpad scroll* (X sends the wheel as button 4/5 press
  events — =run-browser= handles only button 1, so they are ignored) and
  *PageUp/PageDown*. Fix: handle button 4/5 in the event loop → scroll the current
  pane; add =:page-up=/=:page-down= (already decoded by =x11.lisp=) to =browser-key=
  and a viewport-scroll that is independent of the caret.
- No trail *tabs* / *Spotter* yet (single trail; §4¾).
- *Jump-to-definition* not wired yet: =Ctrl-click= / =M-.= on a symbol → resolve →
  drill (the "symbols are presentations" design, §4½ / §4¾).
- Chrome markers are ASCII (=>= / =v= / =>=); the 6×15 blob is 256 codepoints, so
  no ▸▾→ glyphs — draw chrome as shapes later (§6.2).

* The font — Cozette (MIT)

The shipped font is *Cozette* (=cozette.lolf=, MIT — see =cozette-LICENSE.txt=),
chosen from a side-by-side comparison. It is baked into our own tiny =.lolf= blob
(6x15, glyphs indexed by codepoint) by =bdf2font.py=, the way =alien.rgba= is
pre-generated and committed. Note the kernel's built-in =font_8x16= is *GPL* and
must not be lifted; Cozette's MIT license is committed alongside the blob.

To *regenerate* =cozette.lolf= (the blob is committed, so this is only for updates):

#+begin_src sh
  curl -fsSL -o /tmp/cozette.bdf \
    https://github.com/slavfox/Cozette/releases/latest/download/cozette.bdf
  python3 poc/bdf2font.py /tmp/cozette.bdf poc/cozette.lolf
#+end_src

The =.lolf= format and the whole glyph→pixel path are documented in [[file:../doc/fonts.org][doc/fonts.org]].
