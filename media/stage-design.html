1The argument

Why a moving picture earns its place in a code browser, which is otherwise a strictly textual instrument.

Every view in the browser so far presents definitions — a list, a class DAG, a source pane, a dispatch grid. They answer what is written. The matrix comes closest to the running system and still stops short: it counts methods per cell, which is a fact about the source, not about anything that ever happened.

collide is the one specimen in the image whose whole point is behaviour at a pair of types. Reading its ten methods teaches multiple dispatch the way reading a recipe teaches cooking. Watching a missile reach a ship and seeing (:DESTROYED "Kestrel") come back — then watching that same missile reach a station and get (:DENTED "Anvil") instead, from the same call site — teaches it in one gesture.

So the Stage is not a game and shouldn't grow into one. It is a presentation of instances, the way a list is a presentation of definitions. Position is just the layout the subject happens to want.

2The loop that makes it a browser

Four beats. Each hands off to a view the environment already has, which is the test of whether this belongs here at all.

BEAT 1

Watch it dispatch

Two objects touch. The stage calls it both ways and the transcript records each call with its value. Both matrix cells flash; a disagreement is flagged amber.

BEAT 2

Hit a hole

Two ships touch and neither direction is applicable, so the debugger opens on the standing stack — the same run-debugger-fb, no new code.

BEAT 3

Write the method

The [define-method] restart drops a defmethod template into the Workspace, specialisers already filled from the two arguments.

BEAT 4

Accept, and watch it change

C-c C-c compiles it into the image. The matrix grows a cell, the change set grows an entry, and the next contact behaves differently.

That last beat is the one the project exists to demonstrate, and it has never had a demo where the consequence of a redefinition is visible at a glance. A recompiled report-memory prints slightly different text. A recompiled collide method changes what you are watching, while you watch it.

3Two generic functions, cleanly split

The didactic specimen must not be contaminated by the demo. That constraint drives the whole structure.

collide returns data and touches nothing: (:HULL-BREACH "Kestrel"). It stays exactly as written in initramfs/examples.lisp — a clean multiple-dispatch specimen with no idea a stage exists.

A second generic function, enact, turns that value into an effect, and dispatches with eql specialisers on the returned tag:

  • (defmethod enact ((tag (eql :destroyed)) a b) …) removes the target.
  • (defmethod enact ((tag (eql :dock)) a b) …) parks the ship on the station's rim.
  • (defmethod enact ((tag (eql :shatter)) a b) …) replaces both rocks with fragments.

This buys three things. The example stays pure. The stage's behaviour is a consequence of return values, so redefining a collide method visibly changes the world without the stage knowing anything about it. And enact becomes the browser's first eql-specialised generic function — a dispatch shape the matrix view can't draw yet, which is a useful thing to discover from a real specimen rather than from a hypothetical.

Both directions, every contact

Contact is symmetric and collide is not, so the stage calls it both ways and prints both lines. That settles the ordering question by refusing it, and it turns out to pay for itself twice.

First, it makes the author's symmetric pairs legible: (ship asteroid) is written to delegate to (asteroid ship), and seeing the two calls return the same value is the only way that intent is ever visible. Where they don't agree, the transcript flags it amber — and one pair already doesn't: (:SHATTER "Ceres-9" "Vesta-4") against (:SHATTER "Vesta-4" "Ceres-9"). Harmless, and exactly the kind of thing you would never notice reading the source.

Second, it makes the matrix's missing missile column load-bearing instead of a footnote. Nothing specialises argument B on a missile, so every missile hit now prints one value and one ⊘ no applicable method. The asymmetry in how the example was written stops being trivia and becomes something you watch happen.

Which forces one rule: only a total absence signals. One side answering is the ordinary case, reported in the transcript and nowhere else. Two ships, where neither direction resolves, is what opens the debugger — so beat 2 survives intact and the modal never fires on a missile. enact runs once, on whichever direction answered.

Probe order is creation order. Now that both are called it carries no meaning, which is precisely why it can be the boring deterministic choice — a headless frame replays identically.

A call you make enacts nothing

Evaluating (collide a b) yourself returns data and changes the stage not at all. Only the tick's own call is passed to enact. Otherwise inspecting the system would perturb it, and the Workspace would stop being safe to poke with.

Where the positions live

Not in space-object. Adding x/y/vx/vy slots would wreck a class whose entire job is to be a small readable specimen in a class view. The stage keeps a weak :key hash table from instance to a body struct. The objects on screen are the same objects you get from (find-obj "Kestrel") in the Workspace, and they carry no trace of having been on a stage.

4Colour is already decided

The stage introduces no palette. Every mark on it is one of the semantic tokens in poc/widgets.lisp, which is what keeps it legible next to every other pane.

On the stageTokenBecause
every sprite outline *concept* :class A sprite is an instance of a class. Same blue as a class row anywhere else.
the selected sprite *ui-accent* Focus is focus, whether it's a list row or a rock.
the method that fired *concept* :method What you're being shown is a method. Green in the transcript, green in the cell.
a hole / the flash *concept* :condition A missing method is a condition about to be signalled. Red is that promise.
a method added this session *ui-amber* Amber already means "this leads somewhere else" — here, into the change set.
shape, not colour — Class identity is carried by silhouette (dart, chevron, ring, rock) so colour stays free to mean what it means everywhere else in the environment.

5What it costs

An honest inventory before anyone starts. Most of this exists; one item is a genuine change to the input loop.

PieceStateNotes
pane kind :stage new A present method on a subj-stage subject, beside :list :source :matrix :class. Slots into the accordion unchanged.
a tick in the poll loop 1-line change The only real obstacle. fbb-wait hardcodes a -1 timeout at fb-browser.lisp:58, so the browser sleeps until input. It needs a millisecond timeout argument so the loop can wake on a frame deadline. Everything else follows from that.
canvas primitives small fill-rect and draw-rect exist. A stage wants draw-line and a filled convex polygon; both are a dozen lines against the same pixel buffer.
the debugger have it run-debugger-fb already does everything beat 2 needs. The stage only has to wrap its call in restart-case.
inspect a sprite have it Click → the existing Inspector pane on that instance. No new view.
live redefinition have it Workspace C-c C-c, accept-source, the change set — all shipped. Beat 4 is assembly, not construction.
headless frames small poc/render-frame.lisp can render a stage frame for the docs if the tick is seeded and frame-counted, keeping the screenshot discipline intact.

What it deliberately is not

  • No physics beyond constant velocity and a radius test. Momentum, mass and rebound angles would be code with nothing to teach.
  • No score, no goal, no input-driven flying. The moment it becomes playable it stops being a view and starts competing for attention with the thing it illustrates.
  • No thread. It ticks inside the existing single-threaded browser loop, which is the whole reason the timeout change matters.
  • No sprites for anything but this example. If a second subject ever wants a stage, that's the moment to generalise — not before.

6Settled

Decided 2026-09-13. Three of four; the last is still open.

Argument order → call both, show agreement

Not "faster object first", and not creation order as a semantic choice. Both directions fire on every contact and both are printed; only a total absence signals. Worked through in §3, "Both directions, every contact" — it changed more of the design than any other answer here.

Layout → the editable preview pane

The Stage is special-cased as the one subject whose side pane accepts C-c C-c. One tab, no third motion in the accordion, and the form and its consequence stay in one glance — which is the whole reason to build this.

Transcript → its own strip

Automatic collisions scroll in the stage's own strip. The Workspace buffer holds only what you typed, so it stays editable and re-runnable rather than being flooded within seconds.

Naming → still open

No preference recorded, so the mock keeps Kestrel, Anvil, Hornet. They earn their place in the transcript now that every contact prints two lines — (:DESTROYED "Kestrel") reads; (:DESTROYED "ship-2") does not. Nothing depends on it, and it is a rename away whenever the "space"-themed naming idea lands.
