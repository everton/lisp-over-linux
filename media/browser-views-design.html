lisp-over-linux · code browser · view design spec

Two views that have to be Lisp, not Smalltalk

A Smalltalk browser rests on one tree: a method belongs to a class. Common Lisp breaks that in two places on purpose — methods belong to generic functions and dispatch on a tuple, and the condition system is control flow you can't see in the source. Cloning the Smalltalk panes would quietly lie about both. These are the designs that tell the truth instead — mocked in the browser's own chrome so we can argue about them before writing the Lisp.

01

The environment — one tiled screen

Before the individual views, the whole shape: how a single drill-down investigation coexists with the Playground, the Debugger, and the constant "wait — I need to go look at something else." Three nested levels, all tiled, all keyboard-reachable, no floating windows (that's Morphic — much later).

Reading outward: an item you click drills into the next panel of a trail (one investigation — the drill-down accordion); trails are tabs you keep open in parallel — including the persistent ones (Playground, the Debugger, Processes), which are just trails the system pins. No separate rail: the tabs already list every surface, so there is no second place to look. The Spotter jumps to any subject from anywhere; it is the only thing that ever floats.

"I need to look at something else" has three answers, by intent. If it is related to what you're reading (a function it calls, a class it names), open-beside spawns a new trail rooted there and keeps the current one. If it is unrelated, the Spotter finds it and opens a new trail. If you're done here, the Spotter can replace the current trail instead. In every case the thing you were reading is one click away — as a tab, a breadcrumb crumb, or in the Spotter's recents.

The Playground and the other areas are not a second mechanism, and not a second place. A trail's root need not be code: (present workspace) is the Playground notebook, (present condition) is the Debugger, (present any-object) is the Inspector. So the "areas" are just trails the system pins (Playground, always there) or opens for you (the Debugger, when a signal fires) — and they live in the same tab strip as everything else. That is why there's no rail: showing areas both in a rail and as tabs would list them twice. Future areas (a process/thread monitor, the supervisor, meminfo) arrive by the same move — a new subject with a present method — and appear as one more pinned tab.

Why tiled, not floating. Overlapping windows on a World is Morphic, and it is real work — a window manager we've deferred to the last phase. Tiled panes cost none of that, suit a keyboard-first machine, and read better at 1280×800. The present / trail model underneath is identical either way, so when Morphic does arrive a trail simply becomes a draggable window — nothing above is rewritten. The one exception, the Spotter overlay, earns its float by being modal and momentary.

The sections that follow zoom into what fills a trail's panels — the generic-function views and the condition system — and then the present protocol that makes all of it one mechanism.

02

Generic functions & methods

A generic function answers two different questions — where do methods live across the class space (coverage) and what actually runs when I call it (combination) — and you reach the second by drilling into the first. That drill is a general mechanism, not a one-off: it's how you browse packages, files, and objects too.

The problem in one line: a CLOS method is not owned by a class — it is owned by the generic function and specialized on a tuple of classes. A method like (collide ship asteroid) belongs under both ship and asteroid, and under neither exclusively. There is no tree to draw. So we draw the tuple space directly.

An earlier draft put the matrix and the effective method in one flat side-by-side panel. That was wrong — it isn't interactive. A view that shows everything at once, or hides a click's consequence behind a tab, doesn't let you drill. The right model is a drill-down accordion: one panel expanded at a time, each selection opening the next panel while its parent collapses to a breadcrumb bar you can click to re-expand. This is Glamorous Toolkit's Miller-column browser (and Pharo's before it), and underneath it is an old Lisp idea — CLIM presentations: display an object, and clicking it is a typed action on that object.

The crucial part is that this is not specific to generic functions. It is one generic function and one data rule, and everything drillable rides it:

(present subject) → view of itemsthe vieweach item →
(present (p package))its definitions, as a listtarget: a definition
(present (gf generic-function))the dispatch matrixtarget: a dispatch-query
(present (q dispatch-query))the effective-method oniontarget: a method
(present (m method))its source, editabletarget: a called fn…
(present (r restart))its report lineaction: invoke it
(present (d directory))its entries  (future)target: file / subdir
(present (x t))a generic object inspector — the fallbacktarget: any slot value

present dispatches on the subject's type and returns a view: a set of items, each carrying a target (the subject to open in the next panel — a drill) or an action (invoke a restart, accept an edit — a do). To add a new drillable thing you define a subject type and one present method; nothing else changes. Packages, classes, files — and later real directories on disk — are the same mechanism, not seven bespoke browsers. And because (present (x t)) always resolves to the object inspector, nothing is ever a dead end.

Reading it: the three collapsed bars are the breadcrumb — and they are the drill path: LOL.SURFACE ▸ draw ▸ (button · fb-surface) ▸ :before (button T). Each bar remembers what you picked inside it; click any bar and it re-expands while the rest fold away. Note the breadcrumb crosses subject types — a package, a generic function, a dispatch query, a method — yet it is one uniform stack, because each step was just present of whatever the previous item targeted.

This also dissolves the framebuffer-fit question. Only one panel is ever expanded, so the heavy view (matrix, onion, source) always gets the full detail region while its ancestors cost one line each. Nothing has to be crammed side-by-side or measured against 1280×800 — a deep drill on a small screen is a tall view plus a few breadcrumb bars, and it fits by construction, at any resolution.

The matrix itself still degrades honestly as a coverage view: 1 specialized arg is a plain list; 3+ args become a grouped tree; EQL specializers get their own rows. When a cell can't name the tuple (3+ args, an eql value, a live object from the Inspector), the matrix panel carries a small dispatch on: picker strip that sets it — the click is just the fast path.

Buildable from what we have. Axes and cells: sb-mop:generic-function-methods + method-specializers + class-direct-subclasses. The effective onion for the selected cell: compute-applicable-methods-using-classes on the two cell classes, then sort by qualifier and specificity (or read compute-effective-method directly) — cheap enough to recompute on every click. Each layer is a live jump into the definition registry; editing a method and Accept-ing it repaints the matrix and the onion on the spot.
03

The condition system

try/catch unwinds first and asks questions later. Lisp signals without unwinding — the signaller's stack is still standing while a handler decides, and it only collapses when a restart transfers control. That "search up, then jump down" is the whole idea, and it is pure dynamic control flow — invisible in the source. So the view is a picture of the running stack, not of the code.

The shape that makes it click: the live call stack is a spine, and two different things are pinned along it as you descend — handler clusters on one side (from handler-bind/handler-case) and restart clusters on the other (from restart-case/restart-bind). A signal rises up the handler side without disturbing anything; invoking a restart drops down the restart side and unwinds. Two sides, two directions, two meanings.

  1. Signal. + asks for A; it's unbound, so SBCL signals UNBOUND-VARIABLE — and, crucially, establishes use-value / store-value restarts right there before signalling.
  2. The signal rises up the handler side with the stack fully intact — the dashed teal path. It passes frames with no handler, reaches the error handler in run-workspace, and (since this is interactive) lands in the debugger's default handler at the top.
  3. The debugger shows you the restart column — every recovery the descending code established: use-value, abort-to-workspace, abort.
  4. You pick use-value and give it 42. Control jumps down the restart side to that restart's point — the amber path — and now the stack unwinds: everything below it (the dimmed frames) is discarded and + resumes as if A were 42.

The quiet payoff: this view is the debugger. An unhandled condition is just this same picture made interactive — the spine is the backtrace, the restart column is the clickable restart list, and "proceed" is picking one. We don't design a debugger separately; we design this, and the debugger falls out. Which is precisely the plan's "the debugger as a browser."

One honest caveat worth showing in the chrome itself: a handler-bind handler runs before the unwind (that's what makes it more powerful than catch), whereas a handler-case handler runs after. The two-sided arc is exactly what makes that difference visible — a handler-bind acts while still standing on the left rail; a handler-case is a restart in disguise on the right.

That was the dynamic view — the system running. In the browser, not running, the same subject has a static face, and it mirrors Senders / Implementors exactly:

⬦ condition anatomy

  • its place in the condition class DAG (reuses the class view — conditions are CLOS classes)
  • slots & readers: (cell-error-name c)
  • the report string it prints
  • Signallers — who signals / errors this type (who-calls on the constructors): the condition analogue of Senders

↺ handlers & restarts

  • Handlers — every handler-bind/handler-case in the image that catches this type or a supertype: the analogue of Implementors
  • Restarts — named restarts defined near signalling sites, and where
  • found by scanning the definition registry's captured source for the forms — the same source table the browser already keeps
Buildable from what we have. The live spine: sb-di (the same introspection SBCL's own debugger uses). The restart column: compute-restarts — already returns them innermost-first, in stack order. The handler side is the one genuinely internal piece (sb-kernel::*handler-clusters*), but we get its effect for free the moment a condition is unhandled, because that is the debugger. Static side: who-calls + a scan of the registry's source.
